# 信息收集 · "信息够了没、何时该动手"的判断

### 何时停止扫描、转入手工验证
**Q1**: 自动化扫描已经跑了一大堆结果,面板上一片飘红,我该继续扩大扫描面还是收手动手?
**A1**: 判据不是"还有没有没扫的端口",而是"我已经拿到的东西里,有没有一条能形成攻击假设的线索"。只要出现一个可疑版本号、一个报错回显、一个非标准服务,就该暂停横向铺开,转入对这一条的深挖。扫描的边际收益在第一轮之后急剧衰减,继续扫只是心理安慰。
**Q2**: 可我怕漏掉更好的入口,万一手工验证的这个点是死胡同呢?
**A2**: 用"最小验证成本"排序:优先验证那些"只要一个请求就能证真/证伪"的点(如某个已知 CVE 的探测请求)。死胡同要在几分钟内被判死,而不是纠缠。判死的标准是拿到明确的否定回显,而不是"没成功"。
**Q3**: 如果手工验证的三四个点全是死胡同,是不是说明信息还不够?
**A3**: 不一定是"不够",可能是"角度错了"。此时不要盲目回去加扫描线程,而应换正交维度:从"服务漏洞"转向"资产关系"——去看子域、旁站、同 C 段、证书 SAN、favicon hash 关联出的其他资产,攻击面往往在你没扫的那台机器上。
**Q4**: 换资产维度也没新东西呢?
**A4**: 再转一层正交:从"技术面"转"人的面"——目标暴露的邮箱、员工命名规律、GitHub/网盘泄露、历史备份文件(.bak/.swp/.git),这些常常绕过所有漏洞扫描直接给你入口。
**Q5**: 怎么算"信息足够动手"了?给个硬标准。
**A5**: 当你能写出一句完整的攻击假设:"目标 X 的服务 P 存在漏洞 V,我用手法 M 预期得到结果 R"——主谓宾齐全、可证伪,就该动手打了。凑不出这句话,说明还差关键的一环,继续收但要带着这句话的空缺去收。
**Q6**: 攻击假设写出来了但把握只有五成,打还是不打?
**A6**: 看代价。低噪声、可回滚、不触发告警的验证(GET 探测、报错触发),五成把握就该打,打的过程本身就是最好的信息收集。高噪声、可能封 IP 或触发防护的动作(爆破、上传 webshell),把握不到七八成先别动,再补一轮针对性侦察。

### 端口全开还是全闭时的判断
**Q1**: 扫完发现目标只开了 80/443,别的全闭,是不是没戏了?
**A1**: 恰恰相反,端口越少信息密度越高。全部注意力压到这一两个 Web 服务上:指纹、路由、参数、报错、隐藏接口。少端口意味着防御者把攻击面收窄,但也意味着这个 Web 一定承载了业务,业务逻辑漏洞的概率反而上升。
**Q2**: Web 也看了,就是个静态站或登录框,啥都点不动。
**A2**: 别停在肉眼可见的表层。转向"隐藏面":目录爆破找后台/接口/文档、参数 fuzz、看 JS 里硬编码的接口和路径、抓包看 XHR。现代应用真正的攻击面在前端 JS 和后端 API,不在首页。
**Q3**: 那如果反过来,端口开了一大片几十个呢?
**A3**: 端口多不等于机会多,先别兴奋。按"高价值+低防护"两个维度排序:优先非标准端口上的服务(常是内部/测试系统,防护弱)、优先带管理性质的服务(数据库、中间件控制台、CI、监控)。标准 Web 端口排后面。
**Q4**: 一片端口里怎么快速找出那台"软柿子"?
**A4**: 看版本指纹的"陈旧度"和"非常规性"。一个明显过时的中间件版本、一个默认端口上的默认服务、一个自曝 banner 的服务,就是软柿子。用"有没有公开 EXP"作为二次排序。
**Q5**: 所有端口的服务都是最新版、全打了补丁,被墙得死死的,往哪转?
**A5**: 转"配置面"而非"漏洞面":弱口令/默认凭据、未授权访问、目录列表、备份泄露、错误配置的 CORS/权限。补丁修不了配置错误。再不行转"人和供应链":钓鱼、第三方组件、上下游关联资产。
**Q6**: 弱口令也试过一轮无果,是不是该放弃这个目标?
**A6**: 放弃前做最后一次"信息复盘":把已收集的所有 banner、报错、路径、命名拼在一起,找有没有被单点看漏的关联。很多入口是"两条弱信息叠加"才成立的(如某路径+某默认账号)。复盘后仍无假设,才转移目标。

### Web 指纹拿到后往哪个方向深挖
**Q1**: 指纹识别出目标用了某个 CMS/框架,下一步是先找它的 CVE 还是先摸它的结构?
**A1**: 先确认版本精度。指纹只给"是什么"不给"哪个版本",而 CVE 高度依赖版本。花几分钟从静态资源 hash、changelog、README、特定路径回显把版本钉死到小版本号,再去对 CVE,能省掉后面大量无效尝试。
**Q2**: 版本钉死了,对上一个 RCE 的 CVE,但没有现成 EXP。
**A2**: 分两步判断:先看有没有 PoC(证明可达)哪怕不是完整 EXP;再看漏洞前置条件(需要认证?需要特定插件?)。若前置条件你不满足,这个 CVE 就是纸面机会,别在上面耗,回到指纹去找其他组件。
**Q3**: 这个 CMS 装了一堆插件/主题,该怎么定攻击点?
**A3**: 主程序往往被重点审计,插件才是重灾区。枚举插件及其版本,插件的 CVE 密度和更新滞后度通常远高于主程序。优先第三方、小众、明显疏于维护的插件。
**Q4**: 插件也枚举了但打不动,官方组件全绿,怎么办?
**A4**: 转向"这套 CMS 的通用错误配置":上传点、后台默认路径、调试模式开启、安装残留文件、数据库备份可下载。框架本身没洞不代表运维没挖坑。
**Q5**: 连配置层面都很干净,这条框架路彻底走死,转哪?
**A5**: 转正交的"承载层":Web 服务器/中间件/语言运行时/反代/CDN 回源。CMS 干净不代表底下的 Nginx/Tomcat/PHP 版本干净,也不代表 CDN 后面的真实源站没暴露。去挖源站 IP 和中间件。
**Q6**: 怎么知道我在这个框架上"挖够了"可以收手?
**A6**: 当你把"主程序版本、插件清单、上传/认证/调试/备份四类配置"都过了一遍且都证伪,就算挖够了。不要无限 fuzz 参数,那是收益枯竭区,该切资产维度。

### 拿到一个疑似漏洞点,验证到什么程度才动手
**Q1**: 发现一个参数注入报错,看着像 SQLi,我要不要直接上 sqlmap 全参数猛跑?
**A1**: 先手工确认"这个报错到底是不是可控注入"。一个引号触发的 500 可能只是脏输入校验。手工发一对"真/假"payload 看响应差异,确认存在布尔或报错回显,再上自动化。上来就猛跑既慢又吵,还可能把一个逻辑漏洞误判成 SQLi 浪费半天。
**Q2**: 手工确认是布尔盲注了,信息够动手拖库了吗?
**A2**: 够了但要先算成本:盲注拖库慢且噪声大。动手前先判断"有没有更快的路"——报错回显能不能升级成 union、能不能读文件、能不能 stacked query 直接 RCE。信息"够动手"不等于"该用这个动作",选最短路径。
**Q3**: 这个注入被 WAF 拦了,payload 一发就 403。
**A3**: 不要在同一个点上无脑换编码硬刚 WAF。先做正交侦察:换一个"没被 WAF 覆盖"的入口——同一后端的其他接口、API 版本路径、移动端接口、内部回源地址,往往共享同一个漏洞但不过 WAF。绕 WAF 是下策,绕过 WAF 所在的这层路径是上策。
**Q4**: 所有入口都过同一个 WAF,绕不掉,这个漏洞就废了?
**A4**: 降级利用目标:RCE 拿不到就先拿信息。哪怕只能盲注读出几个配置项、几个用户名、一段路径,这些都是喂给下一步的养料。把"拿 shell"的执念转成"拿情报",漏洞就还有价值。
**Q5**: 转成拿情报后,我怎么知道情报够了可以换攻击面了?
**A5**: 当你从这个受限漏洞里榨出的信息,能支撑另一条更短的攻击假设(如读到了某凭据可以直接登另一个服务),就立刻切过去。别把慢速盲注拖到底,情报的价值在于开新路而非榨干旧路。
**Q6**: 拖出来的信息互相矛盾/不可信怎么判断?
**A6**: 交叉验证:同一事实用两个独立途径确认(报错回显 vs 时间盲注,或 A 接口 vs B 接口)。红队最忌基于一个未经复核的"事实"下重注。矛盾时以"可复现、可解释"的那份为准。

### 拿到一台机器后,该马上横向还是先深挖本机
**Q1**: 刚拿下一台主机的普通权限,我是立刻扫内网横向,还是先在本机翻箱倒柜?
**A1**: 先本机。落地第一件事是"信息收集而非扩张":当前权限、进程服务、网络连接、历史命令、配置文件、凭据缓存。横向的弹药(凭据、内网拓扑、信任关系)大多藏在这台机器里,没弹药的横向是盲扫,又慢又响。
**Q2**: 本机翻了一圈,拿到几个凭据和一张内网网段图,现在够横向了吗?
**A2**: 够启动了,但先定"横向的锚点"而非乱扫。用拿到的凭据去撞最高价值目标(域控、文件服务器、跳板),而不是从 .1 扫到 .254。信息足够的标志是:你知道"往哪台打、用什么身份打",而非"内网有哪些机器"。
**Q3**: 本机是普通权限,提权卡住了,该先提权还是先横向带着低权限跑?
**A3**: 不要死磕提权。判据:低权限手里的凭据/网络可达性,能不能直接换来另一台机器的更高权限?内网里"平移到隔壁再纵向提权"常比"死磕本机提权"快。提权和横向是可以互相绕开的两条正交路。
**Q4**: 内网被分段隔离,横向一步就被 ACL/防火墙挡死,往哪转?
**A4**: 转"信任与身份"维度而非"网络可达"维度:被网络隔离,但域凭据、Kerberos 票据、共享账号可能跨段有效。用身份而非用连通性去打。再不行转"数据面":隔离网段里的机器往往回连某个共享的日志/监控/更新服务器,顺着数据流反向摸。
**Q5**: 本机信息收集时,怎么判断"翻够了"不用再翻?
**A5**: 按清单收敛:凭据(内存/配置/浏览器/票据)、网络(连接/路由/hosts/域信息)、权限(用户/组/特权/计划任务)、软件(可提权服务/杀软/EDR)。四类各过一遍就算翻够,别陷入无限翻文件。清单外的深挖留到有明确需求时再回来。
**Q6**: 翻本机时先看杀软/EDR 还是先抓凭据?
**A6**: 先探杀软/EDR。在不知道防护的情况下抓凭据(尤其碰内存)可能直接触发告警把你踢出去。信息收集的顺序原则:先摸清"什么动作是安全的",再做"高价值高风险的动作"。侦察防护本身就是最重要的一条信息。

### 域环境里收集到什么程度才发起攻击
**Q1**: 进了域,枚举出用户、组、机器一大堆,信息海量,反而不知道从哪下手。
**A1**: 海量枚举数据要用"攻击路径"来收敛,而非逐条看。把关系图跑出来(谁能控谁、谁是谁的本地管理员、谁有委派),找从"当前身份"到"目标身份(域管/关键服务器)"的最短路径。信息够不够的标准是:图上有没有一条通向目标的边,而不是枚举了多少对象。
**Q2**: 路径图上有几条通往域管的路,选哪条先走?
**A2**: 按"噪声×前置条件"排序。优先选不触碰高危检测、前置条件已满足的那条(如已有的 Kerberoast 可爆的服务账号 vs 需要额外权限的 ADCS 攻击)。同样通向域管,代价可以差一个数量级。
**Q3**: 图上根本没有直达路径,当前身份被困住了,往哪转?
**A3**: 转"补充枚举维度":当前枚举可能没覆盖 ACL/GPO/证书模板/信任关系。攻击路径断裂往往是因为某类对象没枚举全。针对性补 ACL 滥用点、可滥用的证书模板(ESC 系列)、跨域信任,断路常在这些冷门维度里接上。
**Q4**: 补充维度也没找到路,是不是这个域就打不穿了?
**A4**: 转"凭据面":路径断了但凭据能续。回去在已控机器上收集更多凭据(其他用户的票据、缓存、明文),换一个身份重新跑路径图,新身份可能就有新的边。身份换了,图就变了。
**Q5**: 我怎么知道对域的枚举已经"够充分"可以专注打了?
**A5**: 当"从我到目标的攻击链每一环都有已知手法且前置条件明确"时就够了。链条中只要还有一环是"这里应该有办法但我不知道怎么过",就说明枚举还差那一环的信息,针对性补,而不是泛泛再扫一遍全域。
**Q6**: 枚举动作本身会触发告警吗?怎么权衡收集与暴露?
**A6**: 会。大规模 LDAP/SMB 枚举是经典告警源。权衡原则:先用"已有身份能低调获取"的信息(单点查询、必要属性)拼假设,只在假设需要时做定向的、小范围的深挖枚举,避免一次性全域拉取。信息收集要按需、定向,不要"先囤后用"。

### 外网打点时,广度优先还是深度优先
**Q1**: 目标有一大片资产(几十个域名/IP),我是每个都浅扫一遍,还是挑一个深挖?
**A1**: 先广度做"资产画像"再深度打单点。第一轮只做低成本指纹,目的是找出"最弱那一个"而非全部打穿。资产多时,入口几乎总在最不起眼、最少维护的边缘资产上(测试站、老系统、忘了下线的服务),广度扫描就是为了把它筛出来。
**Q2**: 广度扫完了,怎么从一片资产里选出"最弱那个"深挖?
**A2**: 三个信号排序:陈旧(老版本/老框架)、非常规(测试/临时/内部命名)、边缘(不在主业务线上、易被运维遗忘)。命中越多优先级越高。主站通常最硬,别一头扎进去。
**Q3**: 挑中的弱点深挖了半天没进展,要回去换资产还是继续?
**A3**: 设"时间盒"。单个资产深挖超过预设时间无实质进展(拿不到新假设),就回广度层换下一个候选。红队最大的浪费是"沉没成本效应"——在一个自己选中的点上过度投入。换点不是放弃,是资源再分配。
**Q4**: 所有边缘资产都打了一轮没突破,广度和深度都用尽了,往哪转?
**A4**: 转"资产发现本身没做全"这个可能性:被动测绘(证书、DNS 历史、被动 DNS、代码泄露、云资产)常能挖出主动扫描看不到的影子资产。攻击面比你以为的大。再转供应链/子公司/关联组织的资产。
**Q5**: 怎么判断"资产收集已经够全"可以停止发现、专心打?
**A5**: 当多个独立测绘源(主动扫、证书透明、被动 DNS、搜索引擎语法)给出的资产集合开始高度重叠、几乎不再产出新条目时,就算收敛了。还在不断冒新资产,说明发现没做完,别急着收口。
**Q6**: 边缘资产找到了但都在内网/VPN 后面够不到,怎么办?
**A6**: 转"凭据入口"而非"漏洞入口":够不到就想办法拿到进去的钥匙——VPN/邮箱/SSO 的弱口令、泄露凭据、钓鱼。外网无洞时,合法入口(拿别人的账号进去)往往比找 0day 现实得多。

### 侦察被防护设备(WAF/CDN/蜜罐)干扰时的判断
**Q1**: 扫描结果全是一样的响应,像被 CDN/WAF 统一挡了,拿到的信息真假难辨。
**A1**: 先"证明自己在跟谁说话"。判断响应来自源站还是中间设备:看响应头、错误页特征、TLS 证书、响应时间。信息收集的第一原则是分清"我看到的是防护层还是真实目标",否则后面所有判断都建立在假象上。
**Q2**: 确认前面是 CDN,真实源站藏在后面,怎么摸到源站?
**A2**: 转"绕过前置"的侦察正交维度:历史 DNS 解析记录、证书 SAN 关联、子域直连、邮件头泄露的源 IP、SSRF 回连、favicon/内容 hash 全网关联。拿到源站 IP 后直连,大量防护瞬间失效。
**Q3**: 我怀疑撞进了蜜罐(端口开得太整齐、服务太诱人),该继续吗?
**A3**: 蜜罐的信号:异常"完美"的漏洞、不符合真实业务逻辑的服务组合、响应太快太配合。怀疑时降低交互深度,做只读的被动确认,别投递真实 payload 和真实凭据。宁可放弃一个可疑的点,不给防守方送情报。判据是"这个入口好得不真实"。
**Q4**: 分不清是蜜罐还是真弱点,怎么决策?
**A4**: 用"业务合理性"做裁判:真实系统的漏洞总处在有业务上下文的地方。孤立的、无业务承载的、上下文突兀的高危服务,蜜罐概率高。合理性存疑时,用最低成本、最不暴露自身 TTP 的方式试探,把风险控制在可弃。
**Q5**: 确认全站被强防护包裹,常规侦察全部失效,往哪个维度转?
**A5**: 转"人与流程"维度:技术面被焊死时,社工、钓鱼、供应链、物理/无线、第三方接入,这些不经过 WAF/CDN。防护设备防的是流量,防不住"一个员工点了链接"。
**Q6**: 我怎么知道"绕过防护的侦察"已经够了,可以切回正面攻击?
**A6**: 当你拿到一个"防护覆盖不到的直连通道"(源站 IP、内部接口、合法凭据)时,侦察的目的就达成了,立刻从这条干净通道发起攻击,不要再恋战正面的防护墙。

### 收集到大量数据但形不成攻击假设时
**Q1**: 手头一堆扫描报告、指纹、目录、参数,信息不算少,但就是拼不出"怎么打"。
**A1**: 这是典型的"数据多但情报少"。停止收集,做一次强制的假设生成:把每条信息问一句"它能让我做什么危险的事"。不能回答的信息丢掉。信息的价值只在于能否转化成动作,囤积不产出假设的数据是噪声。
**Q2**: 每条单独看都没用,是不是这些信息本身没价值?
**A2**: 关键在"组合"。红队突破常来自两三条弱信息的叠加(某路径 + 某默认配置 + 某版本特性)。把信息两两配对问"合起来能干嘛"。单点无害不代表组合无害,攻击面在连接处。
**Q3**: 组合也试了,还是没假设,该继续收还是换目标?
**A3**: 先判断缺口类型。缺的是"广度"(没覆盖某类资产/服务)还是"深度"(某个点没挖透)?缺广度就换正交维度补(前面各条提到的资产/人/供应链);缺深度就回到最可疑的单点做定向深挖。盲目泛收既不补广也不补深。
**Q4**: 我发现自己其实是"不知道自己缺什么",怎么破?
**A4**: 用"攻击链倒推":从目标(拿 shell/拿数据/拿域管)反向列出必需的每一环,逐环对照现有信息,第一个对不上的环就是明确的信息缺口。有了具体缺口,收集才有方向,否则就是在黑暗里乱抓。
**Q5**: 倒推出缺口了,但那一环的信息怎么都收不到,被卡死。
**A5**: 换"实现同一环"的替代手法。攻击链的每一环通常有多条实现路(如"获得凭据"可来自内存/配置/钓鱼/爆破/泄露)。此路收不到,换同环的另一条正交路,而不是死磕原来那条。
**Q6**: 什么时候该承认"信息永远凑不够",战略性放弃或转移?
**A6**: 当攻击链的某个必需环,所有已知替代手法都被证伪、且没有新的正交维度可开时,才是真的走死。此前所有"卡住"都只是"这条路卡住",不是"没路"。区分"某路死"和"全盘死",避免过早放弃,也避免无谓死磕。

### 时间/隐蔽有约束时,信息收集的取舍
**Q1**: 有时间/隐蔽约束,不能慢慢全量侦察,怎么定"够用就好"的收集下限?
**A1**: 从目标反推最小信息集:要达成本次目标,最少需要知道哪几件事?只收这几件。有约束时,信息收集从"尽量全"切换到"够用即止",多收一分都是暴露风险和时间成本。判据是"再收这条信息,会改变我下一步动作吗",不会就不收。
**Q2**: 隐蔽优先时,主动扫描风险大,还能收集到足够信息吗?
**A2**: 优先被动收集:被动 DNS、证书、搜索引擎、代码/文档泄露、公开情报,几乎零接触就能拼出可观画像。只在被动信息不足以支撑关键假设时,才做最小范围、最低频率的定向主动探测。
**Q3**: 被动信息不够,必须主动探测,怎么把暴露压到最低?
**A3**: 单点、低频、拟真。只探你假设直接需要的那一两个点,速率贴近正常流量,伪装成常规访问。不要全端口全目录爆破。信息收集的暴露度应与信息的必要性成正比,不必要的广度扫描是纯风险。
**Q4**: 时间快到了信息还不完整,是硬着头皮动手还是收手?
**A4**: 看假设的"可证伪性"和"可回滚性"。哪怕信息不全,只要有一个低风险、失败也不暴露、能快速证真伪的动作,就动手——动作本身会补全信息。高风险不可回滚的动作,信息不全时宁可不做。
**Q5**: 隐蔽收集被对方察觉了(触发了告警),怎么办?
**A5**: 立刻转"改变特征"而非"停手":换源、换 TTP、换时间窗、换目标资产分散动作。被察觉说明当前收集模式的指纹被抓,换一套指纹继续,而不是原地不动等风头(风头不会自己过去)。
**Q6**: 约束下怎么避免"收集不足"和"过度收集"两头翻车?
**A6**: 始终用"下一步动作"当锚:每收一条问"这直接服务于哪个具体动作"。服务不到的不收(防过度),动作缺的必补(防不足)。让信息收集全程被"我马上要干什么"牵引,而不是被"我想知道一切"牵引。

### 捡到一批凭据,先验有效性还是先想打哪
**Q1**: 从内存/配置/泄露里捞到一堆疑似凭据,是逐个去撞服务,还是先规划?
**A1**: 先做低成本"归类"再撞:凭据分明文/hash/票据/API key,分个人/服务/系统。归类决定用法(hash 走 pass-the-hash、票据走 pass-the-ticket、明文走喷洒)。上来乱撞既暴露又低效,归类本身就是最快的信息收集。
**Q2**: 归好类了,先拿哪个凭据去撞哪台机器?
**A2**: 用"权限期望×可达性"排序:优先服务/管理账号(权限高)撞它最可能生效的服务(可达)。别用一个低权用户的凭据去撞域控——先想"这把钥匙最可能开哪扇门",而不是挨个门试。
**Q3**: 撞了一圈全部失效,是凭据过期还是我用错了地方?
**A3**: 别急着丢。转"复用维度"验证:同一凭据在别的服务/协议(SMB/WinRM/RDP/DB/Web)可能有效;明文可能是别处的旧密码但符合密码规律,可用于喷洒变体。凭据失效常是"用错了服务",不是"作废了"。
**Q4**: 确实全作废了,这批凭据完全没价值了吗?
**A4**: 转"情报维度":凭据里的用户名、命名规律、密码构造规律(公司名+年份+符号)本身就是情报,喂给密码喷洒能生成高命中候选。作废的凭据仍泄露了"人怎么设密码"。
**Q5**: 怎么判断"凭据情报够了"可以停止翻找、开始利用?
**A5**: 当你手里有"一把已验证可用的钥匙 + 一个它能打开的高价值目标"时就够了,立刻动手。别为了"再多捞几个凭据"而拖延一个已经成立的攻击。
**Q6**: 撞库动作会触发账号锁定/告警,怎么权衡?
**A6**: 低速、少量、避峰。先用最可能命中的一两个组合定向试,而非全量喷洒。域内尤其注意锁定阈值,宁可慢也别把一批账号打锁引来注意。信息(哪把钥匙开哪门)优先于蛮力。

### 拿到源码/备份泄露,审到什么深度
**Q1**: 摸到一个 .git 泄露或站点备份,是完整审计还是快速扫一遍?
**A1**: 先快速定"高价值文件"再决定深审:配置文件(数据库/密钥/第三方凭据)、部署脚本、路由定义。这些能立刻给你入口或凭据,收益最高。全量代码审计是慢活,先榨快钱。
**Q2**: 配置里的凭据/密钥拿到了,还需要继续审代码吗?
**A2**: 看凭据够不够形成攻击假设。若配置里的数据库/云 key 已能直接连进去,就先动手用,代码审计留作后备。信息足够动手时不要因为"还没审完"而拖延。
**Q3**: 配置里没现成凭据,审代码找逻辑漏洞值不值得?
**A3**: 值,但要定向:直奔认证鉴权、上传、命令拼接、反序列化、SQL 拼接这些高危模式,用关键词/危险函数快速定位,而不是逐行读。白盒审计的优势就是能精准跳到危险点。
**Q4**: 泄露的源码是旧版本,和线上跑的对不上,还有用吗?
**A4**: 有用但要转视角:旧代码里的漏洞可能未修复(线上仍中招),也可能暴露了"隐藏接口/内部路径/历史逻辑"给线上黑盒测试当地图。把旧源码当"结构地图"而非"精确副本"。
**Q5**: 审了半天代码里全是坑但线上都打了防护/补丁,这条路死了往哪转?
**A5**: 转"密钥与信任":源码里常硬编码 JWT 密钥、加密 IV、API 签名秘钥、内部服务凭据,这些即使代码逻辑没洞也能直接伪造身份/解密/横向。代码没洞不代表秘密没泄露。
**Q6**: 怎么知道源码"挖够了"可以停?
**A6**: 当"高价值文件 + 高危代码模式 + 硬编码秘密"三类都过了一遍,就算够。剩下的逐行深审属于收益枯竭区,除非有明确假设指向某段代码,否则转其他攻击面。

### 发现子域接管/DNS 悬挂线索
**Q1**: 枚举子域时发现一个 CNAME 指向已失效的第三方服务,像可接管,值不值得追?
**A1**: 先验"是否真的可注册接管":确认指向的服务确实允许认领且当前无主。可接管才有价值,否则只是死记录。这一步只需一次查询,别脑补。
**Q2**: 确认可接管了,接管后能拿到什么,值得动手吗?
**A2**: 评估这个子域的"信任价值":它是否用于 Cookie 作用域、OAuth 回调、CORS 白名单、内部跳转。高信任子域接管能撬动主站会话/OAuth,价值巨大;孤立营销子域价值有限。按信任度决定投入。
**Q3**: 接管价值不高,是不是白发现了?
**A3**: 转"信息价值":那个失效的第三方服务名本身告诉你目标用过什么技术栈/供应商,是资产画像的一块拼图。低价值漏洞常常是高价值情报。
**Q4**: 一堆子域都试了没有可接管的,这条路走死了往哪转?
**A4**: 转"子域作为攻击面地图"而非"接管漏洞":每个子域背后是一个服务,回到前面的"挑最弱资产"逻辑,子域枚举的真正产出是资产清单,接管只是附带彩蛋。
**Q5**: 怎么算子域侦察"够了"?
**A5**: 当多种枚举手段(证书、被动 DNS、爆破、搜索)产出高度重叠、不再冒新子域,且每个存活子域都做了指纹归类,就够了。转入对最弱子域的深挖。

### 云资产(对象存储/元数据/IAM)侦察
**Q1**: 目标在云上,发现了对象存储桶命名规律,侦察重心该放哪?
**A1**: 先测"桶的可访问性与权限":能否列举、能否读、能否写。云上入口常不是漏洞而是错配权限。一个可列举的桶可能直接泄露备份、凭据、源码,收益极高且几乎零对抗。
**Q2**: 桶是私有的读不到,云侦察还能往哪走?
**A2**: 转"身份与元数据"维度:若已拿到目标某台云主机的 SSRF 或 shell,元数据服务可能吐出临时凭据,进而横穿整个云账号。云的边界是 IAM 不是网络,重心放在拿到一组云凭据。
**Q3**: 拿到一组云临时凭据了,信息够动手扩权了吗?
**A3**: 先枚举这组凭据的权限边界(能做什么、能读哪些资源),再动手。云上盲目调用会触发 CloudTrail 告警。先定向确认权限,再沿权限做最短路径提权/横向。
**Q4**: 云凭据权限极低,几乎啥都干不了,往哪转?
**A4**: 转"配置枚举"找提权路径:可滥用的 IAM 策略、可传递角色(PassRole)、可改的函数/实例。云提权多是策略错配而非漏洞。低权凭据的价值在于"能不能看到一条提权链"。
**Q5**: 怎么判断云侦察"够了"可以收手动手?
**A5**: 当你能画出"当前云身份 → 目标资源"的一条权限路径时就够。画不出来说明还缺权限枚举,定向补;补完仍无路,转回主机/应用层攻击面。

### OSINT 到什么时候停止、转技术侦察
**Q1**: 公开情报(员工、邮箱、泄露库、代码平台)越挖越多,什么时候该收手转技术面?
**A1**: OSINT 的止损点是"边际不再产出可行动线索"。当新挖的信息不再改变任何技术攻击计划(不给新入口、不给新凭据、不给新资产),就该停。OSINT 是为技术攻击铺路,不是终点。
**Q2**: 怎么判断哪条 OSINT 线索值得转成技术动作?
**A2**: 三类高价值直接转:泄露凭据(去撞登录)、暴露资产/接口(去扫)、技术栈情报(去对 CVE)。其余(公司新闻、组织架构)留作社工弹药,不占技术侦察时间。
**Q3**: OSINT 挖出的泄露凭据都过期了,白挖了?
**A3**: 不白挖,转"密码规律"用途:老密码揭示命名/构造习惯,喂喷洒。同时泄露库里的邮箱格式确认了账号命名规则,为枚举有效用户铺路。
**Q4**: OSINT 和技术扫描都做完了还是没入口,回头再深挖 OSINT 值不值?
**A4**: 值,但换维度:从"组织"转"个人"(关键管理员的社交足迹、复用密码),从"公司"转"供应链"(外包、第三方接入、子公司)。入口常在组织边界的模糊地带。
**Q5**: OSINT 阶段怎么避免"信息过载"陷进去出不来?
**A5**: 全程带一个"目标问题清单"(有哪些人?有哪些资产?有哪些技术?有无泄露?),四问答完就收。开放式浏览会无限延伸,清单化能强制收敛。

### 内网存活探测:主动扫 vs 被动听
**Q1**: 刚进内网想摸拓扑,是直接扫存活/端口,还是先被动观察?
**A1**: 优先被动:看本机 ARP 缓存、路由表、hosts、已建连接、DNS 缓存、共享挂载。这些零主动流量就勾勒出"活跃的邻居和它在跟谁通信",往往比全网段扫描更精准且不触警。主动扫是最后手段。
**Q2**: 被动信息不够,必须主动探测,怎么把噪声压最低?
**A2**: 从"目标导向"扫而非"全网段"扫:只探你假设需要的高价值目标(域控、文件服务器、DB),用常见端口而非全端口,低速。内网 IDS/EDR 对全段快速扫描极敏感。
**Q3**: 主动扫一发就触发告警被盯上了,怎么办?
**A3**: 转"借道已有连接":与其自己扫,不如看当前机器/账号"本来就该访问谁",顺着既有的信任关系和会话去够目标,伪装成正常业务流量。在内网,合群比隐身更安全。
**Q4**: 内网被严格分段,存活探测只能看到本段几台,往哪转?
**A4**: 转"枢纽机器":找能跨段通信的机器(跳板、管理机、监控/更新服务器),拿下它就拿到跨段视野。分段网络里,枢纽的价值远高于普通主机。信息重心从"扫更多"转"找枢纽"。
**Q5**: 怎么算内网侦察"够了"可以开始横向?
**A5**: 当你有了"目标是谁、往哪打、用什么身份、走哪条路可达"这四要素,就够了。凑不齐就补对应那一项,而不是继续无差别扫全网。

### 发现多个漏洞时,先打哪个
**Q1**: 一轮侦察下来手里攒了好几个可能的漏洞点,先打哪个?
**A1**: 用"收益×成功率÷噪声"三维排序,而非按发现顺序。优先"直接给 shell/凭据、成功率高、动静小"的点。一个稳的 RCE 优先于三个飘忽的注入。别按情绪先打"最先看到的那个"。
**Q2**: 收益最高的那个漏洞成功率没把握,要不要先拿它当头炮?
**A2**: 不要。头炮选"最稳"的建立据点,拿到立足点后再从内部打高收益高风险的点——内部视角会大幅提高后者的成功率和信息量。顺序上先立足、后扩大。
**Q3**: 排最前的漏洞打了失败,是继续调还是换下一个?
**A3**: 设失败阈值:同一漏洞尝试若干次仍无进展(拿不到新反馈),就切队列里的下一个,把失败的挂起而非死磕。多点并行的价值就是不被单点拖死。
**Q4**: 队列里所有漏洞都打了一遍全失败,往哪转?
**A4**: 转"组合利用"和"信息复盘":单个不成的漏洞串起来可能成(低危信息泄露 + 中危上传 = getshell)。回到已收集信息找能叠加的组合,而非去找第 N 个新漏洞。
**Q5**: 怎么判断"漏洞清单已经够打了"不用再找新漏洞?
**A5**: 只要清单里有一个能形成完整可证伪攻击假设的点,就够了,立刻动手。攒漏洞不是目的,"多攒几个"常是回避动手的拖延。够一个就打一个。

### 目标全部超时/无响应:是死了还是被封
**Q1**: 侦察到一半,目标突然全部超时,是我被封了还是目标挂了?
**A1**: 先做归因区分:换一个干净出口/IP 去访问,若通说明是我被封(IP 级封禁);若仍不通说明目标侧异常(宕机/维护/整体下线)。别在没归因前瞎调 payload,方向都没搞清。
**Q2**: 确认是自己 IP 被封了,怎么恢复侦察?
**A2**: 转"换身份"维度:换出口 IP/代理池、降低频率、更换 User-Agent 和请求特征。被封说明当前行为指纹已被识别,不换指纹换 IP 也会很快再被封。行为特征和 IP 都要换。
**Q3**: 换了 IP 又很快被封,说明防守方在盯我,怎么办?
**A3**: 从"对抗速度"转"对抗隐蔽":大幅降速、拟真化、分散到多源多时段、优先被动情报。被主动盯上时,慢即是快——把节奏降到融入正常流量,而不是继续高频硬冲。
**Q4**: 确认是目标侧下线/维护,不是我的问题,该等还是转?
**A4**: 不干等,转其他资产或转离线分析:利用停机窗口整理已有信息、审已下载的源码、规划下一步。同时监控目标恢复。时间不浪费在盯着一个死掉的服务刷新。
**Q5**: 怎么避免"把被封误判成目标死、或反之"导致方向跑偏?
**A5**: 永远保留一个"对照通道"(干净出口 + 已知稳定的第三方站点)。异常时先用对照通道三方对比,再下判断。归因错误会让你把功夫全用错地方,这一步不能省。

### 版本号对不上已知 CVE(改版/backport)
**Q1**: 指纹拿到的版本号,查 CVE 库对不上,是没洞还是我判断错了?
**A1**: 别轻信版本号。发行版常做安全 backport(版本号老但漏洞已补),厂商也可能魔改。判据从"版本号"转"实际行为":用无害的探测请求验证漏洞是否真实存在,而不是纯靠版本推断有无。
**Q2**: 行为探测显示某 CVE 的特征还在,但没现成 EXP,继续吗?
**A2**: 继续,但先确认前置条件满足。有 PoC 无 EXP 时,评估自己复现的成本;若漏洞机理清晰、前置满足,值得投入手工构造。若机理复杂、前置苛刻,挂起转其他点。
**Q3**: 版本号是厂商魔改的,公开 CVE 全对不上,往哪转?
**A3**: 转"通用弱点"而非"特定 CVE":魔改产品的官方 CVE 可能没有,但配置错误、默认凭据、逻辑漏洞、魔改引入的新漏洞照样存在。冷门/自研系统尤其常有低级配置问题。
**Q4**: 连行为探测都无法确认漏洞,版本这条线彻底模糊,怎么办?
**A4**: 转"获取更精确指纹"的信息动作:找特定静态资源 hash、错误页版本泄露、管理接口 banner、更新日志,把版本钉到能判断的精度。信息模糊时,补精度比瞎猜利用更有价值。
**Q5**: 怎么避免在"版本号误导"上浪费时间?
**A5**: 建立原则:版本号只用于"排序候选",绝不用于"判定有无"。任何基于版本的漏洞结论,动手前都要用一次实际行为探测证实。把版本当线索不当结论。

### SPN 枚举后打不打 Kerberoast
**Q1**: 域里枚举出一批带 SPN 的服务账号,直接全部 Kerberoast 请票吗?
**A1**: 先筛"值不值得爆":看账号所在组和权限(高权限服务账号才有爆破价值)、看密码可能强度(机器账号密码超强不值得爆,人设的服务账号才可能弱)。无差别全请票既噪声大又多是爆不开的强密码。
**Q2**: 筛出几个高价值弱账号,请了票拿到 hash,信息够动手离线爆了吗?
**A2**: 够了,离线爆破不接触目标、零告警,是低风险动作,可以放心跑。但同时并行推进其他路,别把希望全压在"能不能爆开"这个不确定结果上。
**Q3**: 票请下来了但离线爆不开(强密码),这条路死了往哪转?
**A3**: 转其他票据攻击维度:AS-REP Roasting(不需预认证的账号)、委派滥用(约束/非约束/基于资源)、ADCS 证书攻击(ESC 系列)。Kerberos 生态里 Kerberoast 只是一条,票爆不开还有多条正交路。
**Q4**: 大规模请 SPN 票据本身会触发告警,怎么权衡?
**A4**: 定向而非批量:只对筛选出的少数高价值账号请票,加密类型和请求节奏拟真。批量请票是经典检测特征,把动作缩小到"几个目标账号"能大幅降低暴露。
**Q5**: 怎么判断"AD 凭据攻击面已探够"可以专注一条打?
**A5**: 当 SPN、AS-REP、委派、证书模板四类都过一遍并各自标注了可行/不可行,就探够了。挑其中前置条件已满足、噪声最低的一条动手,其余作后备。

### 发现未授权接口,信息到什么程度动手
**Q1**: 发现一个不需认证就能访问的接口,直接开始调用挖数据吗?
**A1**: 先摸接口"能干什么"再动手:是只读查询还是能改能删?参数怎么构造?先用只读、无害的调用摸清语义,再决定利用方式。上来就调危险方法可能改坏数据、触发告警、暴露意图。
**Q2**: 摸清了是个可读的数据接口,信息够动手批量拉取了吗?
**A2**: 够了但要评估价值和噪声:批量拉取前先小样本确认数据含金量(有没有凭据/PII/内部信息),值得再放量。大批量请求是明显异常,别为低价值数据招来注意。
**Q3**: 未授权接口只是个无关紧要的查询,价值不高,白发现了?
**A3**: 转"接口即地图":一个未授权接口暴露了后端 API 的命名/结构/参数风格,顺着推测同系列其他接口(改动词、改资源名、改版本号),真正的高价值未授权点常在旁边。
**Q4**: 顺着推测的接口都要鉴权了,这条路走死往哪转?
**A4**: 转"鉴权绕过"维度:未授权接口的存在说明鉴权实现不统一,试越权(改 ID/越权访问他人资源)、试不同 HTTP 方法、试老版本 API 路径。鉴权不一致本身就是攻击面。
**Q5**: 怎么判断对这组接口"挖够了"?
**A5**: 当你把"可访问的未授权接口 + 可越权的授权接口 + 接口暴露的结构情报"都过一遍,就够了。要么已拿到可利用数据/入口动手,要么确认无果转其他攻击面。

### 上传点发现后,验证到什么程度尝试 getshell
**Q1**: 找到一个文件上传功能,是直接传 webshell 还是先探规则?
**A1**: 先探"过滤与落地"两件事:过滤在前端还是后端?限扩展名/内容/大小?文件落地路径可访问吗、可解析吗?不摸清就传 shell,大概率被拦且暴露意图。先用无害文件探规则。
**Q2**: 探明后端只校验扩展名,信息够动手 getshell 了吗?
**A2**: 还差"落地可解析"这一环。能传上去不等于能执行——要确认文件存到了可被 Web 解析的目录且中间件会解析它。这两环都确认了才动手,否则传上去也是死文件。
**Q3**: 文件能传但落地目录不解析脚本,getshell 卡住往哪转?
**A3**: 转"上传的其他危害"维度:即使不能直接 getshell,上传点还可能配合解析漏洞、条件竞争、路径穿越、覆盖关键文件(配置/.htaccess)达成利用。此路不通转"传什么能造成别的破坏"。
**Q4**: 上传各种绕过全被拦死,彻底走死怎么办?
**A4**: 转正交攻击面:上传功能背后的存储服务(对象存储桶权限)、文件处理组件(图片/文档解析库的漏洞如 ImageMagick 类)、文件名注入。攻击面从"上传本身"转"处理上传的下游组件"。
**Q5**: 怎么判断"上传点研究够了"该收手?
**A5**: 当"过滤规则、落地路径、解析条件、下游处理组件"四点都摸清并各自判过可行性,就够了。能利用就利用,不能就转其他点,别在同一个上传框上无限试后缀。

### 反序列化线索出现后判断可利用性
**Q1**: 抓到疑似序列化数据(特定魔术头/编码特征),怎么判断值不值得深入?
**A1**: 先定"三要素":什么语言/格式的序列化?数据可控吗?服务端会反序列化吗?三者齐了才有利用可能。只是看到个 base64 别脑补成反序列化,先确认它真会被反序列化处理。
**Q2**: 确认是可控的反序列化点了,信息够动手打 RCE 了吗?
**A2**: 还差"利用链(gadget)"这一环。反序列化能否 RCE 取决于目标 classpath/依赖里有没有可用 gadget 链。先探依赖(报错、指纹、已知框架),确认存在可用链再动手,否则可能只能 DoS 或探测。
**Q3**: 反序列化点确认了但打不出 RCE(无可用 gadget),往哪转?
**A3**: 降级利用:反序列化即使不 RCE,也可能实现 SSRF、任意文件读、DoS、探测内网。转"这个点还能干什么",哪怕只拿到内网探测能力也是横向的养料。
**Q4**: 完全利用不了,这条线死了,转哪个正交面?
**A4**: 转"同框架的其他已知漏洞"和"数据流上游":能构造序列化数据说明你控制了某个入口,那个入口可能同时存在注入/SSRF/逻辑漏洞。攻击面从"反序列化"回到"这个可控入口的全部可能"。
**Q5**: 怎么避免在反序列化上过度投入?
**A5**: 反序列化利用链构造是高成本活。设原则:若"可控 + 会反序列化 + 有已知框架 gadget"三者不全,就挂起转性价比更高的点,不为一个理论上可能的链耗掉整场时间。

### SSRF 发现后往哪扩展信息
**Q1**: 确认一个 SSRF,能让服务端发请求,下一步先探什么?
**A1**: 先探"能打到哪":内网可达范围、是否能访问云元数据、支持哪些协议(http/file/gopher/dict)。SSRF 的价值完全取决于它的"射程和弹药",先测边界再谈利用。
**Q2**: 探明能访问云元数据服务,信息够动手了吗?
**A2**: 够了,这通常是 SSRF 的最高收益路——直取云临时凭据。优先走这条,拿到云凭据后攻击面从单机扩展到整个云账号。别在低价值内网探测上耗着不去够元数据。
**Q3**: 元数据打不到(有防护/非云),SSRF 还能怎么用?
**A3**: 转"内网探测和协议利用":用 SSRF 扫内网存活/端口(基于响应差异/时间)、打内网无认证服务(Redis/中间件控制台)、用 gopher 构造复杂协议请求。SSRF 是内网的一只眼和一只手。
**Q4**: SSRF 被限制得只能访问特定白名单域,基本废了怎么办?
**A4**: 转"绕过维度":DNS rebinding、解析器差异、重定向跟随、白名单域上的开放重定向。限制型 SSRF 常能通过这些手法扩大射程。若确实绕不动,转把它当"信息泄露"用(探测存活/报错)。
**Q5**: 怎么判断"SSRF 榨够了"可以收手?
**A5**: 当你从 SSRF 拿到了能开新路的东西(云凭据/内网入口/关键情报),就够了,立刻沿新路推进。SSRF 是跳板不是目的地,拿到跳板价值就该跳,别原地反复探测。

### 拿到 webshell 后先稳权限还是先探内网
**Q1**: 刚 getshell 拿到 web 权限,第一步是加固驻留还是马上探内网?
**A1**: 先做"最小稳固 + 快速摸底"并行,而非二选一到极端。先确认当前权限、有无 EDR、连接是否稳定(避免一刷新就掉),同时快速看本机凭据和网络位置。裸奔深入可能一掉线前功尽弃,但过度加固也会拖慢节奏、增加落地痕迹。
**Q2**: 环境有 EDR,加固动作(落地工具/持久化)风险大,怎么办?
**A2**: 转"无文件/借力"维度:少落地工具,多用目标自带的合法程序(living off the land)收集信息,内存操作优先。有 EDR 时,信息收集要"轻接触",持久化推迟到确有必要且能规避检测时。
**Q3**: web 权限太低,连本机信息都读不全,先提权还是先横向?
**A3**: 参考前述原则:不死磕本机提权。先看低权 shell 能不能读到"通往别处"的凭据/配置/网络可达。web 服务账号常配有连接数据库/中间件/其他服务的凭据,那是横向的直接弹药,比本机提权更快。
**Q4**: webshell 突然掉了/被清了,据点没了怎么办?
**A4**: 转"多据点"思维:单一 webshell 本就脆弱。若之前收集充分,应已握有可重新进入的凭据/其他漏洞;掉线时用后备入口重进,而非慌乱地想恢复同一个 shell。据点要冗余,鸡蛋别放一个篮子。
**Q5**: 怎么判断"本机已站稳、信息够了"可以正式转横向?
**A5**: 当"连接稳定/防护清楚/本机凭据网络已摸/有明确横向锚点"齐备,就该转横向。缺哪补哪,不必等到"本机榨干"——横向本身也会补全信息。

### 目标是纯 API/单页应用时的侦察重心
**Q1**: 目标是个 SPA/纯前端,首页看不到啥,侦察重心放哪?
**A1**: 重心全压在"前端 JS 和后端 API"。SPA 的业务逻辑和接口全在 JS 里,把 JS 拉下来分析:硬编码的接口路径、密钥、内部地址、隐藏功能、鉴权逻辑。传统目录爆破对 SPA 收益低,读代码收益高。
**Q2**: JS 里挖出一批 API 接口,信息够动手测了吗?
**A2**: 够了,直接对 API 做测试(越权、注入、未授权、参数污染)。API 攻击面往往比页面大得多且防护更薄。优先测无鉴权/弱鉴权接口和涉及敏感操作的接口。
**Q3**: JS 被混淆/压缩得很厉害,读不动怎么办?
**A3**: 转"动态观察"而非硬啃静态:直接操作应用,抓所有 XHR/fetch 请求,从流量里逆推接口和参数,比逆混淆代码快得多。动静结合,静态读不动就用动态流量补。
**Q4**: API 全都要 token 鉴权,拿不到 token 就测不了,往哪转?
**A4**: 转"拿 token"这个前置问题:注册/登录流程、OAuth 流程、token 泄露(JS 里/日志里)、弱 token 生成(可预测/可伪造)。同时试无 token 时接口的报错和差异,鉴权可能有绕过。
**Q5**: 怎么判断"SPA 侦察够了"可以专注打?
**A5**: 当你有了"接口清单 + 各接口鉴权要求 + 一个可用身份(token)"时就够。凑齐这三样,把注意力转到接口逻辑漏洞的实际测试,别再无限枚举接口。

### 发现 CI/CD 或 DevOps 组件后的判断
**Q1**: 侦察中撞见 CI/CD、制品库、容器仓库、代码平台一类组件,该重点打吗?
**A1**: 该,优先级往上提。DevOps 组件是"信任和凭据的枢纽":它们持有部署凭据、云 key、源码、可推送到生产。拿下一个 CI 常等于间接拿下它能部署的所有环境。收益远超普通业务系统。
**Q2**: 发现的 CI 组件需要认证进不去,往哪找突破?
**A2**: 转"这类组件的经典弱点":未授权 API、默认凭据、匿名注册、可读的构建日志(常泄露密钥)、公开的流水线配置。DevOps 工具因为"内部用"常疏于加固,配置面比漏洞面更肥。
**Q3**: 进去了但只是低权限视图,信息够动手扩权了吗?
**A3**: 先看能读到什么:构建日志、环境变量、流水线定义里常明文躺着云凭据/部署密钥/内部地址。低权限的"读"权限可能就够榨出高价值凭据。够了就用凭据横向,不必强求这个平台内的提权。
**Q4**: DevOps 组件全部打不动,这条线死了转哪?
**A4**: 转"供应链投毒"的另一面或回主攻击面:若能改代码/依赖/流水线中任一环,可污染下游生产(高危,谨慎);若都不能,那这条线的情报价值(它连着哪些环境、用什么技术)喂回主攻击链。
**Q5**: 怎么判断这类组件"挖够了"?
**A5**: 当你从中拿到了"能通往生产/云/更多系统的凭据或访问",目的就达成,立刻沿凭据推进。DevOps 枢纽的价值在于它连接的下游,拿到通往下游的钥匙就该转场。

### 邮箱/账号枚举后打不打密码喷洒
**Q1**: 枚举出一批有效邮箱/域账号,直接密码喷洒还是再等等?
**A1**: 先降风险准备:确认账号锁定策略(阈值/时间窗)、选高命中候选密码(季节+年份、公司名变体、默认弱密码)。喷洒的铁律是"一轮一个密码打全部账号",绝不"一个账号试多密码",避免锁定。信息足够动手,但动作要精心设计。
**Q2**: 喷洒前怎么知道账号列表是"有效"的,不浪费在死账号上?
**A2**: 先做无害的账号有效性验证(登录接口的用户存在性差异、目录服务查询),把列表收敛到真实存在的活跃账号。对着一堆无效账号喷洒纯属增加噪声和暴露。
**Q3**: 喷洒一轮全没中,继续换密码喷还是转向?
**A3**: 再喷一两轮高质量候选(不同规律)后若仍无果,转向而非无限喷。转"单点弱账号"(可能存在一个用弱密码的倒霉蛋值得多试,但仍受锁定约束)或转"绕过密码"(SSO 漏洞、token、其他认证入口)。
**Q4**: 喷洒触发了锁定/告警,防守方警觉了怎么办?
**A4**: 立刻停喷,转低对抗维度:被动情报、其他非认证攻击面。已经打草惊蛇时继续喷只会加速被封。喷洒是一次性机会,浪费了就换赛道,别硬续。
**Q5**: 怎么判断"账号情报够了"值得发起喷洒?
**A5**: 当你有"经验证的有效账号列表 + 明确的锁定策略 + 一批高命中候选密码"三样齐备,才是发起喷洒的时机。缺锁定策略就贸然喷,是把一手好牌打成大规模锁定告警。

### 移动端/小程序作为侦察入口
**Q1**: 目标 Web 很硬,想到它有 App/小程序,值得转过去侦察吗?
**A1**: 值得,这是经典的正交入口。移动端常调用和 Web 不同或更老的后端接口,且开发者误以为"客户端不可见"而硬编码密钥、内部地址、调试接口。拿 App/小程序包逆向,常挖出 Web 面看不到的攻击面。
**Q2**: 逆向 App 挖到一批接口和硬编码信息,信息够动手了吗?
**A2**: 够了,优先测两类:硬编码的密钥/凭据(直接用)、移动端专属接口(常鉴权更弱)。这些接口的服务端可能和主站共库,一个移动接口的注入能撬动整个后端。
**Q3**: App 有加固/加壳/证书绑定,逆向和抓包都被挡,往哪转?
**A3**: 转"绕过客户端防护"或"降级目标":脱壳、绕过证书绑定拿到明文流量;若成本太高,退而分析静态资源里未加固的部分(配置、字符串常量),或转小程序(通常比 App 更易解包)。
**Q4**: 移动端这条线彻底啃不动,转哪个正交面?
**A4**: 回主攻击面但带着移动端的情报:即使没拿下移动端,逆向过程中瞥见的接口命名、域名、技术栈都是喂给 Web/API 攻击的地图。此外转"移动端的分发和后台"(应用管理平台、推送服务)。
**Q5**: 怎么判断"移动端侦察够了"?
**A5**: 当你从客户端提取出"接口清单 + 硬编码秘密 + 后端结构情报"并判过可用性,就够了。能直接利用就利用,不能就把情报并入主攻击链,别陷进无休止的逆向。

### 第三方/供应链组件作为转向点
**Q1**: 目标自身资产都打不动,什么时候该转向供应链?
**A1**: 当直接攻击面(目标自有资产)全部证伪、且无新正交维度可开时,转供应链。供应链包括:第三方软件/组件、外包开发商、上游服务商、被信任的合作方。目标可能固若金汤,但它信任的某个第三方是软肋。
**Q2**: 供应链范围很大,先从哪个第三方入手?
**A2**: 按"信任深度×防护弱度"排序:优先那些"目标高度信任(有内网接入/共享账号/回连权限)但自身安全薄弱(小厂/外包)"的第三方。信任越深、防护越弱的,越是理想跳板。
**Q3**: 怎么判断某个第三方组件值不值得深挖漏洞?
**A3**: 看它在目标环境里的"位置和权限":一个被目标内嵌、以高权限运行、可联网更新的组件,一旦有洞就是直通车。边缘的、隔离的、低权的第三方,即使有洞收益也有限。
**Q4**: 选中的第三方也打不动,供应链这条大路也走死了怎么办?
**A4**: 转"人的供应链"和"信任滥用":外包/合作方的员工账号、共享的 VPN/协作平台、被信任的接入通道。技术组件之外,"人和流程上的信任关系"是更难修补的供应链弱点。
**Q5**: 转供应链时怎么避免打偏(打到无关方或越界)?
**A5**: 始终用"信任链是否真的连回目标"来校验:只追那些确有信任关系、能实际通往目标的第三方。为打而打、追一个和目标无实质信任关系的第三方,是浪费也是越界风险。

### 数据库直连暴露发现后的判断
**Q1**: 扫到一个数据库端口对外直接开放,先干什么?
**A1**: 先测"未授权/弱口令"而非直接想拖库。很多暴露的数据库存在匿名访问或默认弱口令。用无害的连接尝试确认可达性和认证要求。能直连的库常是运维疏忽,收益极高且几乎无需漏洞。
**Q2**: 成功连进去了,信息够动手了吗,先干嘛?
**A2**: 先枚举而非乱翻:看有哪些库/表、权限多大、能否读文件/写文件/执行命令。数据库价值分三层——数据本身(凭据/PII)、当作横向跳板(读写文件、UDF/命令执行提权到主机)、情报(其他系统的连接信息)。按此规划。
**Q3**: 连进去权限很低,只能读几张无关表,往哪转?
**A3**: 转"库里的凭据情报":哪怕权限低,读到的用户表 hash、配置表里的其他服务凭据,都是横向弹药。低权数据库访问的价值常在"它存了通往别处的钥匙",而非当前这点数据。
**Q4**: 数据库要强认证连不上,这条直连路死了转哪?
**A4**: 转"经应用打数据库":连不上直连端口,就通过前面的 Web 应用(SQLi、注入、应用自身的 DB 凭据)间接操作同一个库。数据库的正门锁了,应用是它敞开的后门。
**Q5**: 怎么判断"数据库这块榨够了"?
**A5**: 当你从库里拿到了"可利用数据 + 横向凭据 + 主机层利用可能"并各自判过,就够了。要么已用它开新路,要么确认它是孤立死水,转其他攻击面,别对着一个库无限翻表。

### 一轮打完没突破,重新收集时看哪里
**Q1**: 一整轮攻击下来一无所获,准备重新收集,该从头再扫一遍吗?
**A1**: 不要从头重扫(会得到同样结果)。先做"失败复盘"再定向补:列出这轮每条假设为何失败,失败原因指向的信息缺口,就是这轮要补的方向。重新收集必须由上一轮的失败驱动,而非机械重复。
**Q2**: 复盘发现假设都"看起来对但打不动",问题出在哪该怎么补?
**A2**: 多半是"精度不足":版本没钉准、防护没摸清、前置条件没验证。转"提高已有信息的精度"而非"收集更多种类"。把模糊的关键信息一个个钉实,常比铺新面更能突破。
**Q3**: 复盘发现是"攻击面根本没覆盖到某类东西",怎么补?
**A3**: 转补"被忽略的正交维度":回看这轮是否只盯了 Web 漏洞而漏了配置面/人面/供应链/移动端/云。一无所获常是因为一整个维度没碰。系统性对照维度清单找空白。
**Q4**: 重新收集又跑了一圈还是没突破,是不是真该放弃了?
**A4**: 放弃前做"降低目标"的转向:拿不到域管就先拿一台机器,拿不到 RCE 就先拿信息泄露,拿不到大目标就先扩一个立足点。把一个宏大目标拆成能达成的小目标,小突破会带来新信息重开局面。
**Q5**: 怎么区分"这轮方法不对(该换)"和"目标真的很硬(该撤)"?
**A5**: 看"正交维度是否穷尽":只要还有一整类攻击面(人/供应链/物理/新资产)没认真碰过,就是方法/覆盖问题,该换维度继续;当所有正交维度都定向打过且证伪,才是目标真硬,考虑战略撤退或升级手段。
**Q6**: 重新收集时怎么避免又掉进"无限收集不动手"的循环?
**A6**: 给每轮重收设"一个明确的待验证假设"作为出口:这轮补信息就是为了验证这一个假设,信息一到位立刻动手验证,验证完再复盘定下一个假设。用"假设—验证"的闭环驱动,而不是开放式地"再多了解一点"。

### 报错/堆栈/调试信息泄露的榨取判断
**Q1**: 触发目标返回了详细报错/堆栈,信息一大片,该怎么从中提取价值?
**A1**: 带着问题读而非通读。报错里找四类高价值:绝对路径(暴露目录结构和系统)、组件版本(对 CVE)、内部 IP/主机名/连接串(拓扑与凭据)、SQL/代码片段(注入证据与逻辑)。逐条问"这能推进哪个假设",无关的报错噪声直接略过。
**Q2**: 报错暴露了框架和版本,信息够动手了吗?
**A2**: 够形成假设了:拿版本去对 CVE、拿路径去构造文件读/写、拿内部地址去规划 SSRF/横向。报错本身不是漏洞,但它常是"把模糊侦察钉成精确假设"的那把尺,拿到就该转向对应的具体利用。
**Q3**: 想要更多报错但目标只在特定输入下才吐,怎么办?
**A3**: 主动"制造报错"作为侦察手段:构造类型错误、超长/特殊字符、破坏预期格式的输入,诱导服务端暴露更多。这是一种定向的信息收集动作——用可控的异常输入换回内部信息,比盲扫高效。
**Q4**: 目标关了调试模式,报错全是统一的通用页面,这条线断了往哪转?
**A4**: 转"侧信道"维度:响应时间差异、响应长度差异、HTTP 状态码差异、不同错误的细微行为区别。显式报错被关时,盲注/盲判据(布尔、时间、带外)就是替代的信息通道。从"读报错"转"读行为差异"。
**Q5**: 怎么判断"从报错榨够信息"可以停止诱导?
**A5**: 当报错已给出足以支撑下一步利用的关键项(版本/路径/内部地址/注入证据之一),就停止诱导、转入利用。继续制造报错只增加噪声和暴露,信息够了就该用,别为收集而收集。

### 带外(OOB/DNS 外带)通道:何时该架、何时该收
**Q1**: 遇到一个"没有回显"的可疑漏洞(盲注/盲 SSRF/盲命令),要不要上带外通道?
**A1**: 先判"是否真无回显"。很多所谓盲点其实有隐蔽回显(时间差异、状态码、二次响应)。只有在确认无任何直接回显、但怀疑服务端有出网能力时,才值得架带外(DNS/HTTP)通道。别一遇盲点就上重装备。
**Q2**: 决定用带外了,架通道前要先确认什么?
**A2**: 先确认"目标能否主动出网"以及"哪种协议能出"。用最简单的探测(触发一次 DNS 查询)验证出网能力——DNS 外带成功率最高、最难被完全封堵。确认能出网,带外通道才有意义,否则白架。
**Q3**: 带外确认了目标能发起 DNS 但 HTTP 出站被防火墙挡,怎么办?
**A3**: 就用 DNS 通道回传数据(把要外带的信息编码进子域名查询)。HTTP 被挡不代表带外失败,降级到 DNS 外带。协议受限时,选择限制最少的那条通道,而不是放弃带外这个思路。
**Q4**: 目标完全不出网(全封),带外这条路死了往哪转?
**A4**: 转"纯盲判据"维度:回到时间盲注、布尔盲注这类不依赖出网的判据,慢但可行。或转"目标内部有无可控回显点"(把结果写到一个自己能访问的位置)。不出网时,把"外带"换成"内部落地+我去读"。
**Q5**: 带外通道跑起来了,怎么判断"验证够了"该转入正式利用?
**A5**: 带外的目的是"证明漏洞可达"这一件事。一旦收到外带请求确认漏洞成立,验证阶段就结束,立刻转入"用这个漏洞拿实际价值"(数据/shell/内网)。别把带外当利用终点,它只是证真的信号枪。
**Q6**: 带外服务器/域名可能被记录暴露自身,怎么权衡?
**A6**: 用一次性、无归属特征的带外基础设施,且只在必要的盲点验证上启用,拿到确认即收。带外通道会在目标日志里留下你的外联域名,属于暴露 TTP 的动作,要按需短用,不长期挂着。
