# Web · 业务逻辑与越权漏洞

### 抓到一个带资源 ID 的请求,先判是不是水平越权(IDOR)
**Q1**: 我在流量里看到 `GET /api/order?id=1024` 这类请求,直觉是 IDOR,该怎么开局?
**A1**: 先别急着改数字。第一步是确认这个 ID 到底"代表谁的资源"——它是我自己账号的订单,还是全局对象。判据:用当前身份读它、看返回体里有没有"归属字段"(userId/tenantId/owner)。如果返回体里根本没有归属绑定,说明服务端很可能只按 ID 取数据、不校验归属,IDOR 概率极高。
**Q2**: 我把 id 改成 1023,返回了别人的订单,是不是就实锤了?
**A2**: 要排除"这本来就是公开数据"和"我恰好也有权限"两种误报。正确做法是双账号对照:用账号 A 拿到 A 的资源 ID,再用账号 B 的会话去访问该 ID。B 能读到 A 的私有数据 = 真越权。单账号改数字看似成功,但可能只是访问了公开资源。
**Q3**: 越权只能读,能不能写?
**A3**: 把同一资源的写操作(PUT/DELETE/PATCH)也拿 B 的会话打一遍。很多系统读接口漏鉴权、写接口却校验,反之亦然。读写要分别验证,别默认"能读就能写"。
**Q4**: ID 是自增的,我想批量拉数据证明危害面。
**A4**: 先小范围枚举(±10)确认规律,再评估是否需要跑量。跑量前想清楚:授权范围是否允许、是否触发风控。证明危害用少量样本 + 说明可枚举即可,不必真的脱库。
**Q5**: 改数字后返回 403 了,这条路是不是死了?
**A5**: 没死,转正交维度。403 可能只拦了这一个参数位置,换传参通道:把 id 从 query 挪到 body、header、cookie、JSON 嵌套、数组形式 `id[]=1023`;或换 HTTP 方法;或试 `id=1023.json`/路径型 `/order/1023`。服务端多入口鉴权不一致是常态。
**Q6**: 全都 403,确实这个对象锁死了。
**A6**: 换对象类型。一个系统里 IDOR 往往不是孤例,订单锁了不代表发票、地址、消息、附件、导出接口都锁了。横向扫遍所有"带 ID 的读写接口",找鉴权最薄弱的那个入口,而不是死磕一个点。

### 普通账号想摸到管理员功能(垂直越权)
**Q1**: 我有一个低权限账号,想验证垂直越权,从哪下手?
**A1**: 先测绘"管理面到底长什么样"。抓低权账号的前端 JS、路由表、菜单接口返回——很多前端会把管理员的路由/按钮也下发,只是靠 CSS 隐藏或 `if(isAdmin)` 不渲染。从 JS 里扒出 `/admin/*`、`/manage/*` 之类端点清单,这是垂直越权的靶点库。
**Q2**: 扒到了 `/admin/userList`,直接用低权 token 请求返回 403。
**A2**: 403 只说明"这一个接口有校验"。垂直越权的核心是找"漏校验的兄弟接口"。同一功能常有多个实现:老版本 `/api/v1/admin/xxx`、内部 `/internal/`、导出 `/export`、移动端 `/m/`。逐个试,鉴权覆盖不全的接口就是缺口。
**Q3**: 有没有更取巧的判据判断哪些接口值得打?
**A3**: 看鉴权是"网关统一做"还是"每接口各做"。若统一网关鉴权,垂直越权难;若发现某些接口返回结构风格迥异(不同框架/不同团队写的),往往是后并进来的、鉴权最容易漏。风格突变 = 鉴权断层信号。
**Q4**: 请求管理接口时返回了数据,但只是空列表,算越权吗?
**A4**: 空列表可能是"通过了鉴权但数据按我身份过滤"。要构造真能证明越权的动作:调一个"改变状态"的管理操作(封禁某用户、改某配置),看是否生效。能执行管理写操作才是硬证据。
**Q5**: 接口有校验,但只校验了 `role` 字段来自我可控的地方?
**A5**: 检查鉴权依据是不是客户端可控。若 role/isAdmin 来自 JWT payload、cookie、请求头且服务端不复核,直接篡改这些字段试。这类"信任客户端声明的身份"是垂直越权高发点。
**Q6**: 所有管理接口都严格校验,垂直越权走不通了。
**A6**: 转向"提权路径"而非"直接访问":找能让低权账号变高权的逻辑——用户组编辑接口是否允许自己给自己加角色、邀请/审批流程是否可自我批准、注册时 role 参数是否可注入。从"访问管理功能"转到"篡改自身权限属性"这个正交维度。

### 越权疑似成立,但怎么排除"这只是我误判"
**Q1**: 我改了个参数拿到疑似别人的数据,但不确定是不是真漏洞,怎么自证?
**A1**: 建立干净的三方对照实验:账号 A(受害者)、账号 B(攻击者)、匿名会话。用 A 创建一个带唯一标记的私有资源(比如备注写随机串),记下其 ID。然后分别用 B 和匿名去访问。只有当"本不该看到 A 私密串的身份看到了"才成立。唯一标记法能一击排除公开数据误报。
**Q2**: B 能看到,但会不会是 B 恰好也被授权了(比如同团队)?
**A2**: 确保 A、B 无任何业务关联:不同租户、不同团队、不互为好友。关系型系统里"同组可见"是设计而非漏洞。隔离性要在建账号时就控制好。
**Q3**: 返回 200 但 body 是加密/编码的,我看不懂是不是真数据。
**A3**: 别只看状态码。对比"越权请求"和"正常请求"的响应长度、字段结构、时间差。若长度与合法响应一致且非固定错误页,大概率是真数据;再用前面埋的唯一标记验证。响应差分比状态码可靠。
**Q4**: 有时能读有时读不到,结果不稳定。
**A4**: 不稳定往往是负载均衡后多个实例鉴权配置不一致,或有缓存。固定 session、固定节点(若有粘性)、加随机参数绕缓存后复测。先消除环境噪声再下结论。
**Q5**: 复现不了了,是不是刚才是偶然?
**A5**: 记录每一步的完整请求(含 header/cookie/时序)。复现失败常因为漏了某个动态 token 或步骤顺序。把成功那次的原始报文存档、逐字节重放,而不是凭记忆重构。可复现是漏洞成立的底线。

### 支付/下单金额可被篡改的业务逻辑
**Q1**: 我在下单流程里看到金额、数量参数在客户端提交,怀疑能改价,怎么系统地测?
**A1**: 先画出这笔交易的"金额从哪来、在哪定稿"。理想系统是:服务端按商品 ID 查价、客户端只传商品和数量。危险信号是客户端直接传 price/amount/total。在支付确认这一步抓包,把价格类字段逐个改小(含 0、负数、小数、超长)。
**Q2**: 改了 price 但服务端二次核验价格,没生效。
**A2**: 转向"价格计算链路里其他可控变量":数量、优惠券、积分抵扣、运费、币种、税率、满减阈值。总价 = f(多变量),服务端可能只校验单价却信任了折扣率或数量。攻击折扣/数量这些间接因子,而非最终总价。
**Q3**: 数量填负数会怎样?
**A3**: 负数量是经典逻辑漏洞:`总价 = 单价 × 数量`,负数量可能让总价为负、甚至给账户"退钱"。同理测超大数量导致整数溢出回绕成负。边界值(0、负、极大、溢出点)是业务逻辑的主战场。
**Q4**: 金额都锁死了,但支付是跳转第三方网关。
**A4**: 攻击"下单金额"与"支付金额"的一致性校验。经典缺陷:下单记 100 元,但发给支付网关的金额或回调里的金额可被改,而系统只信任回调结果不复核订单原价。测支付回调/异步通知的金额、订单号、签名是否被严格绑定校验。
**Q5**: 回调有签名,改不了。
**A5**: 转向状态机维度:能否"未支付却拿到已支付状态"。比如并发调用支付成功回调、重放一次旧的成功回调到新订单、或在"待支付"态直接调"发货/开通"接口跳过支付。绕过支付比伪造金额更常见。
**Q6**: 这些都做了防护,金额逻辑很硬。
**A6**: 换到"薅羊毛/资金增值"正交面:退款流程(退款金额 > 实付、重复退款)、余额/积分互转的舍入误差、货币兑换的四舍五入套利。资金系统的漏洞常在"退和换"这一侧,而非"买"这一侧。

### 优惠券/积分/薅羊毛类逻辑
**Q1**: 目标是电商/营销系统,我想找薅羊毛点,思路是什么?
**A1**: 找"发放"与"核销"两端的失衡。列出所有能凭空产生价值的动作:领券、签到、邀请返利、首单立减、任务奖励。逐个问:能不能重复触发?能不能自己邀请自己?奖励发放有没有幂等/去重?先攻"可重复领取"。
**Q2**: 领券接口有每人一张的限制。
**A2**: 测限制到底"锁在哪个维度"。若锁 userId,能否换设备/新账号绕过?若锁手机号,能否用不同前缀、加空格、大小写、别名邮箱绕唯一性?若靠前端 disable 按钮,直接重放接口。限制维度和唯一性判定是薅羊毛的命门。
**Q3**: 后端有幂等,单账号领不了第二张。
**A3**: 转向并发维度——竞态。在幂等检查和实际发放之间往往有时间窗,同一请求并发发 N 份,可能在"查到未领"后一起写入,突破限领。用并发/单包多请求打这个 TOCTOU 窗口。
**Q4**: 优惠券叠加规则能不能玩?
**A4**: 测规则组合:满减券 + 折扣券 + 免邮是否能非预期叠加、券能否用在被排除的商品、能否先下单用券再改商品、退款时券是否原路退回可再用。业务规则的组合爆炸处最容易有漏网逻辑。
**Q5**: 券系统很严,薅不动了。
**A5**: 换正交目标:分销/邀请返现的资金闭环。A 邀 B、B 邀 A 互刷,或注册返现 > 拉新成本,形成正收益循环。营销系统的钱漏点常在"人拉人"的图结构里,不在单张券。

### 竞态条件(Race Condition)判定与利用
**Q1**: 我怀疑某操作有竞态,但不确定,怎么先判断值不值得打?
**A1**: 找"检查-then-使用"且涉及有限资源/计数器的操作:提现、扣库存、限领、投票、余额扣减。判据:该操作是否"读一个值→判断→写回",且两步非原子。这类 TOCTOU 是竞态温床。反之纯幂等/无状态操作不用打。
**Q2**: 怎么实际打这个窗口?
**A2**: 并发发送多个相同请求,让它们同时落在"检查通过但尚未写回"的瞬间。工具上用单连接多请求(HTTP/2 单包)或多线程同时发。关键是压缩到达时间差,越接近同时命中窗口越大。
**Q3**: 打了几十并发没效果。
**A3**: 时间窗可能极窄。策略:先用大量并发提高命中概率;若仍不中,想办法"拖慢临界区"——制造服务端处理延迟(大 payload、慢查询触发)、或利用网络抖动。也可能这个点根本原子(数据库行锁/唯一约束),那就换点。
**Q4**: 确认这个接口有数据库唯一约束,原子性很强。
**A4**: 转向"跨接口竞态":单接口原子,但两个不同接口操作同一资源时无全局锁。例如"提现"和"转账"分别原子,但并发跑可让余额被花两次。找共享同一状态却各自独立加锁的接口对。
**Q5**: 竞态确实存在但只能多领一两次,危害小。
**A5**: 评估是否值得深挖。竞态的价值在于"能否放大":多领 1 次券危害低,但若命中的是提现/余额,哪怕小窗口重复几十次就是实打实资金损失。按标的价值决定投入,低价值竞态果断放弃转其他逻辑面。

### 密码重置逻辑漏洞
**Q1**: 我要打账号接管,盯上了忘记密码流程,先看什么?
**A1**: 拆解重置令牌的"生成-投递-校验"三段。先问 token 从哪来:发到邮箱/短信(不可见)还是接口返回体里就有(可见)?再问 token 强度:是随机长串,还是可预测的时间戳/自增/短数字验证码。可预测或可见的 token 直接接管。
**Q2**: token 是 6 位数字验证码,发到手机,我看不到。
**A2**: 转爆破可行性:6 位数字仅百万空间。看服务端有没有尝试次数限制、验证码有效期、锁定机制。若限制缺失或能通过换 IP/清 session 重置计数,就爆破。判据是"错误尝试后系统行为是否收敛"。
**Q3**: 有次数限制,5 次锁定。
**A3**: 找"限制作用域"绕过:限制是绑在验证码上还是账号上?能否重新申请新验证码来重置尝试计数(申请无限 + 每码试几次 = 变相无限)?能否并发验证绕过计数器竞态?限制的绑定维度决定能否绕。
**Q4**: 换思路,能不能不猜验证码而是逻辑绕过?
**A4**: 测校验逻辑缺陷:响应里是否泄露 token 或 leak 是否正确的差异(时序/长度);重置请求能否篡改"发给谁"——把手机号/邮箱字段改成受害者但 token 用我自己的;HTTP host 头是否影响重置链接域名(host 注入偷 token)。
**Q5**: 令牌流程很严,爆破和逻辑都不通。
**A5**: 转向重置的"下一步"——设置新密码那一步是否独立可越权。有些系统 token 校验严,但"提交新密码"接口只认 userId 不认 token,或 token 用完不失效可重放。把攻击面从"拿 token"转到"用 token 的接口本身"。
**Q6**: 还是不行,重置链路整体很硬。
**A6**: 彻底换接管路径:换绑手机/邮箱流程、OAuth 绑定劫持、session 相关漏洞、或注册时的账号抢占(用受害者邮箱注册看是否合并账号)。账号接管有多条路,重置只是其一。

### 多步骤流程的跳步/状态机绕过
**Q1**: 目标有个多步向导(如实名认证、开户、结算),我怀疑能跳步,怎么测?
**A1**: 先完整走一遍正常流程,记录每步的接口和它设置的"状态标志"。核心问题:进入第 N 步时,服务端是否校验"第 N-1 步已完成"?测法:直接请求最后一步接口,跳过前面所有步骤,看是否放行。
**Q2**: 直接跳到最后一步,返回"请先完成上一步"。
**A2**: 说明有状态校验,但要看校验依据在哪。若状态存在客户端(cookie/隐藏字段/step 参数),直接把 step 改成已完成态。若存在服务端 session,尝试并发或乱序调用让状态机进入非预期组合。状态存储位置决定攻法。
**Q3**: 状态在服务端,改不了。
**A3**: 找"部分完成"的中间态漏洞:完成步骤 1、2 后拿到中间凭证,但在步骤 3 篡改前面已确认的数据(如实名时改身份证、开户后改绑卡)。系统信任"前面已验证过"而不复核被改的值。攻击已锁定却仍可编辑的字段。
**Q4**: 想验证跳过某关键校验步(如支付、审核)。
**A4**: 找状态机里的"分叉":正常路径要审核,但另有一条"草稿直接发布""导入跳过审核""管理员代操作"的支路,权限校验较松。列出到达终态的所有路径,打防护最弱那条。
**Q5**: 所有路径都严格串行校验。
**A5**: 转向时序/回退维度:完成流程后能否"回退再改"让终态数据与已验证数据脱钩;或已提交订单能否再修改内容;或利用两个流程实例并发,让 A 流程的已验证状态被 B 流程复用。从"跳步"转到"状态错乱/复用"这个正交面。

### JWT/token 相关的越权
**Q1**: 抓包发现认证用 JWT,我想从 token 本身找越权,先看什么?
**A1**: 解开 JWT 看三部分。header 的 alg、payload 的身份声明(sub/role/uid/tenant)。第一批测试点:alg 是否可改 none(去签名)、payload 里 role/uid 改了服务端是否复核。若服务端信任 payload 且验签有缺陷,直接改身份接管。
**Q2**: 试了 alg:none 被拒,签名是 HS256。
**A2**: 测算法混淆:若服务端同时支持 RS256 和 HS256,可能把公钥当 HMAC 密钥用——拿公开的 RSA 公钥作为 HS256 的 secret 重签,服务端用公钥验 HMAC 就通过。前提是能拿到公钥(证书/jwks 端点)。这是 RS/HS 混淆经典打法。
**Q3**: 算法混淆也不行,可能是纯对称密钥。
**A3**: 转弱密钥爆破:HS256 的 secret 若是弱口令(如 secret/字典词),可离线爆破签名。跑 JWT 破解字典。爆到 secret 就能任意伪造身份。判据是密钥熵——常见框架默认密钥、示例密钥要重点试。
**Q4**: 密钥爆不出,很强。
**A4**: 转向 token 生命周期与作用域:token 是否过期后仍可用、注销后是否失效、A 服务的 token 能否用于 B 服务(受众 aud 不校验)、低权 token 刷新后是否可注入更高权限 scope。token 的"用在哪"往往比"能否伪造"更松。
**Q5**: 全都很严,JWT 这条路封死。
**A5**: 换认证以外的越权面。JWT 硬不代表业务接口鉴权硬——token 只证明"你是谁",不保证"你能访问什么"。带着合法 token 去打前面所有的 IDOR/垂直越权。认证强 ≠ 授权强,把火力从"伪造身份"转到"合法身份下的越权"。

### 越权探测触发了 WAF/风控拦截
**Q1**: 我批量测越权时突然被拦,请求返回验证码/封 IP,怎么办?
**A1**: 先分清拦的是"频率"还是"内容"。降速单发几个请求:若恢复正常 = 频率风控;若同样被拦 = 内容特征命中。频率问题就放慢、换 IP 池、加随机延时;内容问题才需要改 payload。别一上来就猛怼特征。
**Q2**: 是频率风控,一快就封。
**A2**: 越权验证本不需要高频——证明一个 IDOR 只要两三个对照请求。放弃"跑量脱库",改为"精准取样 + 逻辑说明可枚举"。把节奏降到人类操作级别,风控多数不会触发。低频精准是绕风控的最优解。
**Q3**: 是内容特征,某些参数值一发就拦。
**A3**: 这更像 SQLi/XSS 特征被 WAF 拦,而非纯逻辑越权(逻辑越权改的是合法数字,一般不带特征)。若确实被内容拦,说明我可能在参数里注入了攻击特征——回到纯业务值(合法格式的 ID)测越权,把注入类 payload 剥离出来单独处理。
**Q4**: 封了 IP,整个测试停摆。
**A4**: 转基础设施维度:换出口 IP(住宅代理/多云节点)、换 UA/指纹、每账号绑不同出口。同时评估——如果风控这么敏感,说明目标有成熟防护,越权面可能也被网关统一收口,考虑把主攻方向转到防护薄弱的子系统/老接口。
**Q5**: 换 IP 也很快被关联封禁。
**A5**: 风控在做行为画像(设备指纹/操作序列)。转向"用真实合法流量夹带":在正常业务操作间隙插入测试请求,模拟真人节奏;或干脆换攻击面到不经过风控的内部/API 直连入口。当外层风控无解时,找绕过风控层的入口比硬刚风控更明智。

### 越权"无回显",不知道打没打成
**Q1**: 我调了个越权写操作,返回 200 但看不到效果,怎么确认成没成?
**A1**: 建立带外验证或二次读取通道。写操作(改别人资料、删别人数据)后,换回受害者账号或用另一读接口去查那条数据是否真被改。不能只信写接口的返回码——它可能"返回成功但被静默过滤"。以状态改变的可观测结果为准。
**Q2**: 我没有受害者账号去验证结果。
**A2**: 用可自观测的资源:让越权操作作用在"我能读到的对象"上。或用带外(OOB)——若操作会触发通知/邮件/webhook,布置一个可控接收端观察回连。无直接回显时,带外信道是判定利器。
**Q3**: 操作是"触发某后台任务",完全黑盒。
**A3**: 用时间/副作用旁证:操作后观察响应时间变化、后续接口返回的计数器/时间戳是否变动、是否产生新的资源 ID。逻辑漏洞的判定常靠"系统状态的可观测扰动",而非直接回显。
**Q4**: 什么旁证都没有,纯静默。
**A4**: 转盲测思路:类比盲 SQLi,构造"若操作生效则系统行为 A,否则 B"的差分实验。比如越权删除后再创建同名资源看是否冲突。用二值化的可观测差异反推操作是否落地。
**Q5**: 盲测也建不起差分,这个点观测不了。
**A5**: 果断转有回显的越权面。黑盒无观测的点性价比极低,把时间投到能立即验证的读型 IDOR、能看到结果的操作上。不可观测 ≈ 不可证明,红队要的是可证明的战果,转向即是止损。

### 多租户系统的租户隔离越权
**Q1**: 目标是 SaaS 多租户,我注册了一个租户,怎么找跨租户越权?
**A1**: 核心是找"租户标识"以及它是否被强制绑定。抓包看请求里的 tenantId/orgId/workspace 参数在哪、是否客户端可控。测法:把我的 tenantId 换成另一个租户的值,看能否访问对方资源。租户 ID 若可枚举/可猜且服务端只按它取数,隔离就破了。
**Q2**: 请求里没有显式租户参数,靠 token 内嵌。
**A2**: 那租户绑在身份上,直接改参数无效。转向"资源 ID 跨租户":直接用对方的资源 ID(订单/文件/用户 ID)去访问,看服务端是否在按 ID 取数时校验"该资源属于当前租户"。很多系统鉴权只到"登录了",漏了"资源归属租户"这一层。
**Q3**: 资源 ID 是 UUID 不可枚举,拿不到别人的 ID。
**A3**: 找 ID 泄露渠道:邀请链接、分享功能、导出文件、日志、错误信息、搜索接口、自动补全。多租户系统常在"协作/分享"功能里泄露跨租户 ID。或注册两个自己的租户互相对照,先证明隔离机制存在缺陷,危害面用逻辑论证。
**Q4**: 数据面隔离得很好。
**A4**: 转控制面:租户的成员管理、角色配置、计费、子域名/自定义域绑定。能否把自己加入别的租户、能否绑定别人的域名、能否越权改对方租户配置。控制面的隔离往往比数据面做得糙。
**Q5**: 全隔离,租户边界很硬。
**A5**: 转向共享基础设施层:多租户常共用缓存、消息队列、文件存储桶、搜索索引。测缓存键是否含租户维度(缓存串号)、上传文件的存储路径是否可跨租户访问、全局搜索是否泄露他租户数据。隔离漏洞常藏在"被忽略的共享底座"里。

### 从"越权读单个"升级到"接管账号"
**Q1**: 我有一个能读任意用户信息的 IDOR,但只是读,怎么升级成账号接管?
**A1**: 盘点这个 IDOR 泄露了什么"接管素材":邮箱/手机(用于重置)、密保问题、API key、session token、绑定的第三方信息。若能读到 token 类凭证,直接拿去用。IDOR 的价值在于它泄露的字段能否接进另一条接管链。
**Q2**: 只能读到基本资料,没有凭证。
**A2**: 把泄露的资料喂给密码重置/身份验证流程:知道了邮箱+生日+手机尾号,可能满足"找回账号"的验证条件。IDOR 提供的信息 + 薄弱的二次验证 = 组合拳接管。单个漏洞不够就找能拼接的第二环。
**Q3**: 有没有直接的写型越权能改凭证?
**A3**: 从读型 IDOR 探对应的写型:同一 userId 参数,试更新资料接口——能否越权改别人的邮箱/手机为我的,再走正常重置流程接管。读写 IDOR 常成对出现,读到 ID 后重点试"改绑定联系方式"。
**Q4**: 写接口有额外校验(改邮箱要验证码)。
**A4**: 转向 session/token 层接管:能否越权重置对方 session、能否读到并复用其活跃 token、OAuth 绑定能否劫持。绕过"改凭证需二次验证"的办法是直接偷用现成的会话凭证。
**Q5**: 凭证层也接管不了。
**A5**: 退一步重新评估战果。若只能越权读大量用户 PII,这本身已是高危数据泄露漏洞,不必强行升级到接管。红队目标是最大影响的可证明漏洞——批量 PII 泄露 + 逻辑说明即可交付,不为"接管"执念浪费时间。

### 前端隐藏的功能/接口(客户端鉴权信任)
**Q1**: 界面上功能很少,但我怀疑后端有更多能力,怎么挖?
**A1**: 把前端当地图而非围墙。下载所有 JS(尤其打包后的 main.js/chunk),提取里面的 API 路径、路由定义、权限判断逻辑。前端为了少发请求,常把完整接口清单和角色枚举硬编码进去。这是隐藏功能的藏宝图。
**Q2**: JS 是压缩混淆的,读不动。
**A2**: 用工具提字符串:正则抓 `/api/`、`http`、路径模式、role 关键字。不必读懂逻辑,只要把端点和参数名捞出来即可。混淆挡逻辑但挡不住字符串常量。抓到端点后直接对着后端发请求测。
**Q3**: 挖到一堆接口,该先打哪个?
**A3**: 优先级:名字带 admin/internal/debug/export/delete/config 的、参数带 id/user/all 的、以及前端有 `if(role===...)` 门控的功能对应的接口。前端用条件语句藏起来的功能 = 后端很可能没做二次鉴权。门控最严的前端功能往往后端最松。
**Q4**: 找到一个前端 disable 的按钮,对应接口直接调通了。
**A4**: 实锤了客户端鉴权信任。立刻横向复制该模式到所有"前端受限"的动作上——禁用的、隐藏的、灰色的按钮全测一遍。一个点通了说明这系统整体依赖前端鉴权,批量收割。
**Q5**: 接口都要求前端传的某个签名/token,单独调用报错。
**A5**: 转向复用前端的合法上下文:在浏览器已登录会话里,通过控制台直接调用前端的 API 封装函数(带上它自己算好的签名),而非从零构造请求。让前端帮我签名,绕过"接口需要复杂前端计算"这道坎。

### GraphQL 接口的越权与信息泄露
**Q1**: 发现目标用 GraphQL,和 REST 越权测法有什么不同,先做什么?
**A1**: 先试 introspection 查询,拿到完整 schema——所有类型、字段、查询、变更。这等于直接拿到 API 全景图。若 introspection 开着,把 mutation 列表全扒出来,里面藏着 REST 界面看不到的管理/内部操作。schema 是 GraphQL 越权的起点。
**Q2**: introspection 被禁用了。
**A2**: 转字段爆破/文档推断:GraphQL 错误信息常提示"did you mean X",可用字段名字典探测存在的字段;或从前端 JS 里的 query 语句反推 schema。introspection 关了不等于 schema 保密。也试常见客户端(Apollo)的持久化查询泄露。
**Q3**: 怎么用 GraphQL 打越权?
**A3**: GraphQL 的鉴权常做在字段级,容易漏。测:能否在一个查询里嵌套访问别人的对象(通过 node(id:) 或关联字段跳转到未授权数据)、mutation 是否校验对象归属。嵌套查询能绕过"入口鉴权但深层字段无鉴权"的缺陷。
**Q4**: 单个查询鉴权都做了。
**A4**: 转 GraphQL 特有攻击面:别名批量(用 alias 在一个请求里发几百个变体,绕过速率限制爆破验证码/枚举);查询嵌套过深导致 DoS;批量查询(batching)绕过每请求的限制。GraphQL 的"一次请求多操作"特性是绕限制的利器。
**Q5**: 都防住了,GraphQL 层很硬。
**A5**: 转向 GraphQL 后面的 resolver 逻辑。GraphQL 只是入口,背后 resolver 常直接拼 SQL/调内部服务。测注入(GraphQL 参数进 SQL)、SSRF(某字段触发内部请求)、以及 resolver 对底层 IDOR 的透传。把攻击面从"GraphQL 协议层"下沉到"它调用的后端逻辑"。

### 验证码/二次验证(短信、图形、OTP)绕过
**Q1**: 某关键操作需要验证码/OTP,我想绕过它,先判断什么?
**A1**: 先定位验证码在流程里"是必经还是可选"。抓包看:不带验证码字段或带空值直接提交,服务端是否放行。大量系统前端强制、后端选校验。判据:去掉/置空验证码参数后的服务端反应。这是最省事的第一测。
**Q2**: 后端确实校验,空值不通过。
**A2**: 测校验的常见缺陷:验证码是否一次性(用过不失效可重放)、是否有效期无限、是否与操作/账号绑定(A 的验证码能否用于 B 的操作)、响应里是否泄露验证码或"是否正确"的旁证。逻辑缺陷比爆破更干净。
**Q3**: 是 4-6 位短信/图形码,想爆破。
**A3**: 判爆破可行性三要素:码空间(4 位数字=万级可爆)、尝试次数限制、验证码更换频率。若无锁定或能刷新计数,直接爆。图形码还可试 OCR 自动识别或已知的固定/弱码。空间小 + 无限制 = 爆破可行。
**Q4**: 有次数限制且验证码强。
**A4**: 转"验证码不刷新"竞态或状态漏洞:同一验证码在服务端未清除前并发提交、或申请后不使用直接进入下一步(有些系统申请即视为通过)。也测"绕过发送"——直接调发送后的验证接口。攻击验证码的状态管理而非其值。
**Q5**: 验证码机制整体很硬。
**A5**: 转向验证码"保护的动作有没有旁路"。验证码保护登录,但记住我 token/OAuth 登录/API key 登录可能免验证码。验证码防的是这一个入口,找到达同一目的的免验证码通道,比正面破验证码高效得多。

### OAuth/SSO 单点登录的逻辑缺陷
**Q1**: 目标用第三方 OAuth/SSO 登录,我想从这里打账号接管,关注哪些点?
**A1**: OAuth 的经典缺陷集中在几个参数:redirect_uri(能否改成我控制的域偷 code/token)、state(缺失则 CSRF 绑定账号)、以及"用 email 关联账号"的信任问题。先抓完整 OAuth 流,标出这些参数是否可篡改。redirect_uri 校验松是重灾区。
**Q2**: redirect_uri 有白名单校验。
**A2**: 测白名单的宽松匹配:是否只校验域名前缀(`evil.com/whitelisted`)、是否允许子路径开放重定向、是否有 path traversal、是否 `whitelisted.evil.com` 能过。白名单常用不严格的字符串匹配,找匹配逻辑的缝。也测同域的 open redirect 中转偷 code。
**Q3**: redirect_uri 锁得很死。
**A3**: 转 email 信任链:若系统用 OAuth 返回的 email 匹配已有账号且不校验邮箱是否已验证,我可在第三方注册一个用受害者 email 的账号(邮箱未验证),用它 OAuth 登录即接管目标账号。攻击"OAuth 身份到本地账号"的映射信任。
**Q4**: state/CSRF 防护也在,email 也校验验证状态。
**A4**: 转 token/code 复用:授权码是否一次性、是否可跨客户端使用、隐式流的 token 是否泄露在 URL/referer/日志里、绑定流程(把第三方账号绑到本地)能否被 CSRF 劫持成"把攻击者的第三方账号绑到受害者本地账号"。绑定方向的 CSRF 常被忽略。
**Q5**: OAuth 流程整体很严谨。
**A5**: 转向 OAuth 之外的登录方式并存问题。系统常同时支持 OAuth 和密码登录——用 OAuth 注册的账号是否有可重置的空密码?能否对 OAuth 账号走"忘记密码"设个密码从而绕过 OAuth 接管?多登录方式的账号往往在方式切换处有缝。

### API 版本/文档泄露带来的越权入口
**Q1**: 我在测新版 API,防护很好,但怀疑有老接口,怎么找?
**A1**: 主动探测版本痕迹:把 `/api/v3/` 改成 v1/v2/v0/beta/internal,把 `/api/` 改 `/api2/`、`/legacy/`。老版本接口常年久失修、鉴权是旧标准。同时找 swagger/openapi/graphql schema/`.well-known` 等自描述文档,直接拿到全量接口。老接口是绕过新防护的后门。
**Q2**: 找到了 swagger 文档,怎么高效利用?
**A2**: 从文档里筛"高危 + 可能漏鉴权"的接口:批量导出、管理操作、内部服务、debug/test 端点。文档会标注参数和是否需认证——挑标注不需认证或认证弱的直接打。文档等于把攻击面明码标价地给你了。
**Q3**: swagger 需要认证才能看。
**A3**: 转其他文档泄露渠道:前端 JS 里的接口调用、移动 App 反编译出的接口清单、Postman 公开集合、代码托管平台上该组织泄露的代码/文档、网页存档里的旧接口。文档一处不通换一处,总有泄露面。
**Q4**: 找到老接口了,但它也要认证。
**A4**: 老接口的价值在于"鉴权实现旧":测它是否用了已废弃的弱鉴权(旧版签名算法、可预测 token、basic auth 弱口令),或它信任新系统不再信任的东西(内网 header、debug 参数)。老接口 + 旧鉴权 = 缝隙。
**Q5**: 老接口全部下线/严格鉴权。
**A5**: 转向版本间的"数据一致性/迁移"漏洞:新老版本共用数据库,老接口写入的数据可能绕过新接口的校验规则。或迁移期的兼容层信任老格式。若版本入口都封了,把注意力转回新接口的业务逻辑本身,版本探测只是补充手段。

### 文件上传/下载的逻辑越权(非 webshell 向)
**Q1**: 有文件上传/下载功能,我先不追 webshell,想找越权,看什么?
**A1**: 下载侧先测:下载 URL 里的文件 ID/路径是否可改,能否下载别人的文件(文件型 IDOR)、能否路径穿越读服务器文件。上传侧测:上传后返回的存储路径是否可预测、别人的文件路径能否枚举。文件的"存储路径 + 访问控制"是越权核心。
**Q2**: 下载要带 token 且文件 ID 是 UUID。
**A2**: 转 token 与 ID 的绑定校验:下载 token 是否只校验"有效"而不校验"这个 token 对应这个文件"——即拿我自己文件的合法 token 去下别人的文件 ID。token 与资源解绑是常见缺陷。也找 UUID 泄露渠道(分享链接、列表接口)。
**Q3**: 绑定得很严。
**A3**: 转向"上传引发的越权后果":上传能否覆盖别人的文件(同名/同路径覆盖)、上传的文件是否进入他人可访问的公共空间、头像/附件上传能否指定任意存储路径(路径穿越写)覆盖关键文件。写侧越权比读侧危害更大。
**Q4**: 想测上传能否影响其他用户。
**A4**: 测"上传内容被谁消费":上传的文件是否被管理员后台预览(打 XSS/SSRF 到管理员)、是否被导入解析(XXE/公式注入到导出的 CSV)、是否作为配置/模板被其他用户加载。上传是"把可控内容送进别人上下文"的通道。
**Q5**: 上传下载都隔离得很好。
**A5**: 转向文件处理的资源/逻辑面:上传大小/数量限制能否绕过打配额、能否上传后无限下载刷流量、图片处理是否可 SSRF(远程 URL 抓取)、文件名是否进入路径/命令。当访问控制无缝时,把攻击面转到"文件被处理的过程"这个正交维度。

### 批量/导出接口的越权与数据放大
**Q1**: 单条数据都做了越权防护,但有批量查询/导出接口,值得单独打吗?
**A1**: 非常值得。批量接口是"防护不一致"的高发区——单查校验了归属,批量查(传 ID 数组、传范围、传 all=true)可能只在应用层过滤或干脆不过滤。测:传入包含他人 ID 的数组、传空过滤条件、传超大分页,看是否返回越界数据。
**Q2**: 批量接口传别人 ID 会被过滤掉。
**A2**: 测过滤是否彻底:传"自己 ID + 别人 ID"混合数组,看是否只过滤部分;传嵌套/编码变形的 ID 绕过过滤器;用范围查询(startId-endId)而非显式列举。过滤逻辑对"混合输入""异常格式"常有疏漏。
**Q3**: 导出接口只导自己的数据。
**A3**: 测导出的过滤条件是否可注入:filter/query/sort 参数能否注入让 WHERE 条件失效(逻辑注入或 SQL 注入),或导出模板/字段选择能否指定越权字段。导出接口背后常是可控的查询构造,是注入 + 越权的复合点。
**Q4**: 导出很安全,但我想放大已有的小越权。
**A4**: 用批量接口放大单点越权:若有一个能越权读单条的 IDOR,找是否有批量版接口能一次拉全量,把"一次读一个"变成"一次脱一库"。批量接口是越权危害的放大器。
**Q5**: 没有可用的批量入口,批量面走不通。
**A5**: 转向"分页/搜索"这个隐性批量面:搜索接口传通配/空关键词是否返回全库、分页 limit 是否可设超大、聚合统计接口是否泄露被隐藏数据的存在(计数泄露)。当显式导出无门,搜索和分页常是变相的批量泄露通道。

### 注册流程的账号抢占与身份冲突
**Q1**: 我想从注册环节找逻辑漏洞,有哪些角度?
**A1**: 核心问 unique 判定的健壮性。测:用受害者的 email/手机号注册,系统是拒绝、覆盖、还是合并?能否用大小写/空格/Unicode 同形/别名(user+x@)绕过唯一性,注册出"视觉相同实则不同"的账号造成混淆。注册的身份唯一性是账号安全地基。
**Q2**: 邮箱唯一性校验很严。
**A2**: 转"预注册抢占":在受害者用 OAuth/SSO 首次登录前,用其 email 手动注册本地账号并设密码。当受害者后来 OAuth 登录若被合并到我的账号,即接管。攻击"账号创建先后顺序"造成的所有权归属。
**Q3**: 想测注册时能否越权设置属性。
**A3**: 抓注册请求,尝试注入额外字段:role=admin、isVerified=true、tenantId=别人的、balance=999、referrer 刷返利。若后端用 mass-assignment 直接把请求体映射到用户对象,注册即提权。多传字段是零成本试探。
**Q4**: 注册字段被严格白名单。
**A4**: 转注册后的"首次状态"漏洞:新账号是否默认继承某些权限、邀请注册是否继承邀请人权限、试用/免费账号与付费账号是否只差一个可篡改的标志位。攻击"账号初始化"时的权限赋予逻辑。
**Q5**: 注册整体很干净。
**A5**: 转向注册的"资源消耗/枚举"副作用:注册接口能否用于枚举已存在的用户(报错差异泄露"该邮箱已注册")、能否被滥用发验证短信/邮件轰炸、能否批量注册刷资源。当注册无法直接越权,它至少是用户枚举和滥用的入口,为后续攻击提供情报。

### 手机号/邮箱换绑与身份联系方式劫持
**Q1**: 系统允许换绑手机/邮箱,我怀疑这里能接管账号,怎么测?
**A1**: 拆换绑流程的验证要求。安全的换绑要"验证旧联系方式 + 验证新联系方式"。测:换绑是否只验新不验旧(那么谁登进去就能换成自己的)、换绑请求里的目标用户 ID 是否可越权改成别人。缺失旧验证 + 可控目标 = 接管。
**Q2**: 换绑要验证新手机的验证码。
**A2**: 那验证码是绑定"新手机"还是"换绑动作"?测:我先给我自己的手机发验证码通过验证,然后在最终提交时把"新手机号"参数改成受害者不知情的号,或把 userId 改成受害者。验证与最终写入的数据是否一致校验,是换绑漏洞关键。
**Q3**: 参数绑定很严,改不了目标。
**A3**: 转竞态/时序:换绑的"验证"和"生效"两步之间,能否并发插入让验证过的旧号与写入的新号脱钩。或"发起换绑"后长期不完成,期间账号状态是否处于可利用的中间态。攻击换绑状态机的原子性。
**Q4**: 想反过来利用换绑做拒绝服务或抢注。
**A4**: 测换绑能否"抢占"别人正在用的联系方式:把我的账号手机换成受害者手机,若成功且系统"一个手机只能绑一个账号",可能踢掉受害者的绑定,造成其无法登录/重置。换绑的"释放旧绑定"逻辑可被武器化。
**Q5**: 换绑机制很硬,接管走不通。
**A5**: 转向换绑触发的下游影响:换绑后是否使旧 session 失效不当(旧 session 仍有效则我改了别人绑定他还在线)、换绑通知是否发给旧联系方式(不发则受害者无感知)。即便不能接管,换绑的"通知与会话处理缺陷"也是可报告的安全问题。把目标从接管转到审计缺陷。

### 权限缓存/响应缓存导致的越权(缓存投毒/串号)
**Q1**: 目标有 CDN/缓存层,我怀疑缓存导致越权,怎么切入?
**A1**: 核心问"用户私有响应会不会被缓存并发给别人"。测:带认证的私有页面响应头里 Cache-Control 是否错误地允许缓存(public/无 no-store)。若私有数据被 CDN 缓存,不同用户命中同一缓存 = 数据串号。先看响应缓存头。
**Q2**: 怎么触发让别人的私有响应被缓存?
**A2**: 缓存键分析:缓存以 URL(+部分 header)为键但响应含用户私有数据。若能让静态化的 URL(如 `/profile.css?x=1`)返回动态私有内容,或利用未纳入缓存键的 header 差异(cache poisoning),就能投毒。找"缓存键"与"响应内容依赖变量"的不匹配。
**Q3**: 缓存键包含了用户标识,串不了号。
**A3**: 转 Web Cache Deception(缓存欺骗):访问 `/account/profile/nonexistent.jpg`,若服务器返回账户页而 CDN 因 `.jpg` 后缀缓存了它,下一个访问该 URL 的攻击者就能读到受害者数据。攻击"URL 后缀决定是否缓存"与"路径实际返回动态内容"的错配。
**Q4**: 缓存欺骗也防住了。
**A4**: 转向缓存投毒打其他影响:通过未键入的 header 污染缓存,注入 XSS/重定向,让所有访问该 URL 的用户中招。此时目标从"越权读数据"转为"缓存放大的客户端攻击"。同一缓存缺陷可打不同影响面。
**Q5**: 缓存层配置很严谨。
**A5**: 转向应用内缓存:很多越权串号不在 CDN 而在应用层缓存(Redis/本地缓存)键漏了用户维度——A 请求后 B 请求命中 A 的缓存。测法:A、B 快速交替请求同一接口,看 B 是否偶发拿到 A 的数据。把缓存攻击面从边缘 CDN 转到后端缓存层。

### 数值边界与符号滥用(负数、溢出、精度)
**Q1**: 面对任何涉及数量/金额/额度的业务,我想系统测边界,有哪些必测值?
**A1**: 建立一套边界字典逐个灌:0、负数、极大值(超 int32/int64)、小数(整数字段传浮点)、超长数字、科学计数法、null/空。每个数值参数都过一遍。逻辑漏洞高度集中在"程序员没考虑到的输入域"。这是逻辑测试的规定动作。
**Q2**: 负数在哪些场景最可能出问题?
**A2**: 凡是"数量 × 单价""余额 ± 变动""配额扣减"的地方:负数量→负总价→退款/加钱;负转账→反向扣对方加自己;负充值。找乘法和减法涉及可控数值的点,负号是撬棍。
**Q3**: 负数被拦了(校验 > 0)。
**A3**: 转整数溢出:传接近类型上限的极大值,让 `a + b` 或 `a × b` 溢出回绕成负或小值,绕过 `> 0` 校验。校验发生在溢出前、使用发生在溢出后时可利用。也试"极大数量"导致后续计算异常。
**Q4**: 想利用浮点精度。
**A4**: 金融/积分系统若用浮点存钱,测舍入套利:反复做会产生 0.5 分舍入的小额交易累积获利、或超多位小数让截断产生偏差。精度问题在"高频小额 + 舍入方向固定"时可放大成实质收益。
**Q5**: 数值校验非常完备。
**A5**: 转向"数值的语义"而非"数值本身":同一操作重复提交(数量为 1 但重放 N 次 = 变相超量)、跨接口累加绕过单接口上限、用不同单位/币种参数造成换算漏洞。当单值边界被封,转到"多次/多维度累积"的正交面。

### 找到一个 IDOR 后,如何判断整个系统的越权模式
**Q1**: 我在一个接口确认了 IDOR,该怎么把它扩展成对全系统的判断?
**A1**: 一个 IDOR 是"鉴权架构缺陷"的信号,不是孤立 bug。立刻假设"该系统对象级鉴权整体缺失",然后系统性验证:把所有带对象 ID 的接口列出来逐一测。判据是漏洞的"根因"——若根因是"按 ID 取数不校验归属",那所有同架构接口都可能中招。
**Q2**: 有的接口中有的不中,规律是什么?
**A2**: 分析中招接口的共性:同一开发团队/同一框架/同一时期/走同一数据访问层的接口往往一起中或一起不中。找出"鉴权断层线"——通常是新老模块交界、微服务边界、或某个绕过了统一鉴权中间件的路由。规律比逐个碰运气高效。
**Q3**: 怎么快速大面积验证而不逐个手测?
**A3**: 用双账号对比法自动化:录制账号 A 的全部合法流量,然后用账号 B 的会话重放这批请求,凡是 B 重放能拿到 A 数据的接口即越权。这种"会话替换重放"能一次性扫出全站 IDOR。
**Q4**: 这么测会不会漏掉需要特定前置状态的接口?
**A4**: 会。有状态依赖的接口(需先创建对象)重放会失败。补充手法:对这类接口,让 A、B 各自创建对象,再交叉访问对方对象 ID。别让"重放失败"误判为"无漏洞",区分"真安全"和"仅状态不满足"。
**Q5**: 大面积测下来只有零星几个点中招。
**A5**: 说明系统有统一鉴权但存在个别遗漏。转向"最近改动/最边缘"的接口:新上线功能、灰度接口、内部/运维接口、第三方集成回调。统一鉴权体系的漏洞总在"来不及纳管"的边缘。把火力从主流程转到系统的边角料。

### 越权测试卡死时的正交转向总纲
**Q1**: 我在一个目标上把能想到的越权都试遍了都失败,如何决定下一步?
**A1**: 先复盘"我是不是只在一个维度反复试"。越权有多个正交轴:身份维度(水平/垂直)、对象维度(不同资源类型)、操作维度(读/写/删)、入口维度(不同接口/版本/协议)、状态维度(不同流程阶段)。检查哪些轴还没覆盖,而非在已试轴上加力。
**Q2**: 感觉每个轴都试了。
**A2**: 换"信任边界"视角:系统在哪里做了"信任假设"?信任前端、信任内网 header、信任第三方回调、信任已验证过的旧数据、信任同租户。把每个信任假设当作攻击点重新审视。逻辑漏洞本质是"错误的信任",找信任比找参数更本质。
**Q3**: 还是没突破。
**A3**: 转情报驱动:去搜目标用的框架/组件/SaaS 产品的已知逻辑缺陷和默认配置问题。很多业务系统基于成熟产品,其固有的越权模式(默认权限、示例配置、已知 CVE)比自己盲试更快命中。从"盲测"转"针对已知面"。
**Q4**: 情报也没有对口的。
**A4**: 彻底换攻击类别。业务逻辑/越权只是 Web 攻击面的一支——若这条线枯竭,横向转注入类(SQLi/SSTI/命令注入)、服务端请求类(SSRF/XXE)、认证类、或基础设施类(组件漏洞/配置错误)。红队不该在一个类别死磕,及时切换类别是核心纪律。
**Q5**: 整个 Web 面都很硬。
**A5**: 转攻击面本身:重新做资产测绘找新入口——子域名、旁站、API 网关外的直连服务、移动端/小程序独有接口、供应链(第三方 JS/依赖)。当已知攻击面全硬,扩大攻击面比深挖单点更有价值。转向"找新门",而不是继续砸旧墙。

### 审批/工作流的自我批准与流程越权
**Q1**: 目标有审批流(报销/发布/权限申请),我想找逻辑漏洞,切入点?
**A1**: 先理清"申请人"与"审批人"的角色隔离。核心测点:申请人能否成为自己的审批人(自我批准)、能否越权调用审批接口批准自己的申请、能否篡改申请单里的"审批人"字段指向可控账号。角色分离失效是工作流第一漏洞。
**Q2**: 审批人是系统按规则自动指定的,改不了。
**A2**: 测审批接口的鉴权:直接用申请人身份调"批准"接口(approve action),看是否只校验登录不校验"你是不是指定审批人"。工作流常把权限做在 UI 层——只给审批人显示批准按钮,但接口谁都能调。攻击接口而非界面。
**Q3**: 审批接口校验了审批人身份。
**A3**: 转"审批后篡改":申请通过后,能否修改申请内容让"已批准的"与"实际执行的"不一致(批的是 A 报销 100,执行时改成 10000)。审批锁定的字段是否真的锁死。攻击审批与执行之间的数据一致性。
**Q4**: 想绕过审批直接到终态。
**A4**: 找"免审批支路":紧急通道、管理员代提交、批量导入、API 直连是否跳过审批。或让申请金额/级别刚好落在"无需审批的阈值"下,拆分大申请为多个小额免审申请。攻击审批触发条件的边界。
**Q5**: 审批流很严密,无支路。
**A5**: 转向审批的"撤回/重开"逻辑:已批准能否撤回重改再自动沿用旧批准、驳回的申请能否被悄悄改回并复用之前的部分审批、多级审批中前级通过后能否让后级基于被篡改的数据审批。从"绕过审批"转到"审批状态的可逆性与数据脱钩"这个正交面。

### 时间/有效期相关的业务逻辑漏洞
**Q1**: 目标涉及有效期(优惠券、会员、token、限时活动),我想找时间维度漏洞,思路?
**A1**: 找"时间由谁判定"。若客户端可传时间参数(下单时间、活动时间戳)或依赖客户端时钟,直接改。若服务端判定,测边界:恰好过期的瞬间、时区差异、有效期计算是否含闰/月末错误。时间的信任来源和边界是切入点。
**Q2**: 时间是服务端判定的。
**A2**: 转"抢跑/延后":限时活动能否在开始前用直连接口提前参与(前端未放开但接口已就绪)、结束后能否用未失效的旧凭证补参与、预约/秒杀能否绕过时间窗。攻击"活动状态"与"接口可用性"的时间差。
**Q3**: 想利用有效期做资源续命。
**A3**: 测有效期能否被非预期延长:操作对象能否刷新其过期时间(每次访问续期→永不过期)、试用期能否通过重置/换绑重新触发、限时权限撤销后 token 是否立即失效。攻击"过期"这个动作是否被可靠执行。
**Q4**: 有效期机制很严。
**A4**: 转竞态与时间窗:过期检查和使用之间的窗口内并发使用(用一张即将过期的券在失效瞬间并发核销多次)。时间边界处的原子性缺陷。也测服务器时间能否被间接影响。
**Q5**: 时间逻辑整体很硬。
**A5**: 转向"时间相关的信息泄露/枚举":基于响应时间差判断资源是否存在(时序侧信道)、token 生成是否用可预测的时间戳作种子(可预测则可伪造)、有效期计算是否泄露了服务器时间用于其他攻击。当时间不能直接利用,把它当作侧信道情报来源。

### 搜索/过滤/排序参数引发的越权与注入
**Q1**: 目标有强大的搜索/筛选功能,我从这里能找到什么问题?
**A1**: 搜索接口危险在于"用户可控的查询条件直接构造后端查询"。先测越权:filter 参数能否被清空/篡改让默认的"仅本人"过滤失效、能否通过搜索匹配到本不该看见的对象(权限过滤在应用层而非查询层)。搜索常绕过对象级鉴权。
**Q2**: 搜索结果做了权限过滤。
**A2**: 测过滤发生在"查询前"还是"结果后"。若查询拉全量再在应用层过滤展示,可能通过:分页/计数不一致(总数泄露隐藏记录数量)、排序参数让隐藏记录的字段值通过排序位置泄露、聚合统计包含无权数据。后过滤模式会泄露"存在性"和"聚合值"。
**Q3**: 想测搜索参数注入。
**A3**: 搜索是注入高发口:关键词进 SQL(SQLi)、进 NoSQL 查询(NoSQL 注入,如传对象 `{"$ne":null}`)、进 Elasticsearch/Lucene 查询(查询语法注入越权检索)、进 ORM 的可控字段名/排序字段(sort=secret_column 泄露字段)。逐一测参数落进了哪种查询引擎。
**Q4**: sort/字段选择参数可控。
**A4**: 重点打可控的"列名/字段名":sort、fields、orderBy、groupBy 参数若直接拼进查询,可指定越权字段排序泄露、或引用不存在字段触发报错泄露表结构。字段名注入比值注入更易绕过 WAF(不带典型攻击特征)。
**Q5**: 搜索接口防护很严。
**A5**: 转向搜索的"资源消耗与联想"面:通配符/正则搜索触发 ReDoS 或慢查询 DoS、自动补全/联想接口泄露他人数据片段、搜索历史/热词是否泄露其他用户输入。当搜索无法直接越权或注入,它的联想和性能特征仍是可利用的正交面。

### 从"合法功能被滥用"角度找逻辑漏洞
**Q1**: 系统防护很好没有明显 bug,但我想从"功能滥用"角度找问题,怎么想?
**A1**: 换思维:不找"程序错误",找"设计被用于非预期目的"。列出所有正常功能,对每个问:如果我以远超设计意图的方式使用它会怎样?分享功能→无限分享绕过付费;导出→反复导出打流量;通知→轰炸;试用→无限续。滥用不是 bug 而是设计缺陷。
**Q2**: 具体怎么把一个功能"武器化"?
**A2**: 找功能的"外部副作用"作为杠杆:任何触发"给第三方发消息/请求"的功能(邀请、通知、webhook、密码重置发信)都可被滥用做轰炸或 SSRF 中继。任何"消耗对方资源"的功能可做 DoS。把功能的副作用指向攻击目标。
**Q3**: 想找"用 A 功能达成 B 功能被禁止的效果"。
**A3**: 找功能间的"权限不一致":直接改资料要审核,但通过"导入/同步/恢复备份"功能改就不审核;直接提权被禁,但通过"复制角色/克隆账号/模板应用"间接提权。当一个操作有多条实现路径且权限校验不一,用弱路径达成强效果。
**Q4**: 功能都很规矩没有明显滥用面。
**A4**: 转"组合滥用":单个功能都正常,但 A 功能的输出喂给 B 功能产生非预期结果。比如用公开的分享功能生成链接,再用另一个功能把该链接的权限提升。逻辑漏洞常在"功能编排"的缝隙里,而非单功能内。
**Q5**: 组合也没找到。
**A5**: 转向"业务规则的经济学漏洞":分析系统的价值流动(钱、积分、配额、信誉),找是否存在"正反馈循环"或"套利路径"——某组合操作的产出 > 投入。这类漏洞不违反任何技术规则却损害业务。当技术面无缝,从业务经济模型找失衡点。

### 微服务/内部接口的信任边界越权
**Q1**: 目标是微服务架构,我怀疑服务间信任可被利用,怎么找?
**A1**: 找"面向内部的信任标志":服务间调用常靠内网 IP、特定 header(X-Internal、X-User-Id、X-Forwarded-For)、或共享密钥来互信,且假设这些不可被外部伪造。测:从外部请求里注入这些内部 header,看边缘服务是否透传、内部服务是否盲信。伪造内部身份是微服务越权核心。
**Q2**: 网关会剥离外部传入的内部 header。
**A2**: 找绕过网关的直连入口:内部服务是否有暴露的端口、管理接口、健康检查/调试端点、或通过 SSRF 从内部发起请求(带上伪造 header)。网关剥离只保护"经过网关的流量",找不经过网关的路径。SSRF + 内部信任是绝配。
**Q3**: 想利用 X-Forwarded-For 等 header 伪造来源。
**A3**: 测系统是否用 XFF/来源 IP 做鉴权决策(内网 IP 免鉴权、特定 IP 获管理权)。伪造 XFF/X-Real-IP 为内网地址或白名单 IP。很多系统"内网即可信",而 header 里的 IP 客户端可控。IP 信任是常见误区。
**Q4**: header 伪造都被过滤。
**A4**: 转服务间认证凭证:服务间若用固定 token/mTLS/JWT 互认,这些凭证是否泄露(配置文件、日志、前端、代码库)、是否可预测、是否过期不轮换。拿到服务间凭证等于获得"内部身份"通行证。
**Q5**: 服务间认证很严。
**A5**: 转向服务网格的"数据面 vs 控制面"和消息队列:服务间通过 MQ/事件总线通信时,能否直接投递伪造消息触发下游操作(绕过入口鉴权)、能否订阅到不该收的事件流泄露数据。当同步调用的信任边界很硬,转向异步消息通道这个常被忽略的正交面。

### 越权到敏感操作:从数据越权升级到系统影响
**Q1**: 我有了稳定的越权读写能力,如何评估并升级到"系统级"影响?
**A1**: 盘点越权能触及的"高价值操作":能否越权触发命令执行类功能(导入脚本、执行任务、配置更新)、能否改系统配置(SMTP、回调 URL、集成密钥)、能否操作其他用户的高权限动作。从"数据 CRUD"找通往"代码执行/配置控制"的功能。逻辑漏洞是入场券,系统影响才是终局。
**Q2**: 越权能改配置,怎么把它变成 RCE 或更深入侵?
**A2**: 找"配置即代码"的点:可控的模板(SSTI)、可控的回调/webhook URL(SSRF→内网)、可控的文件路径(写入危险位置)、可控的脚本/公式字段、集成配置里的连接字符串(改数据库/LDAP 指向)。配置项常是绕过输入校验直达底层的通道。
**Q3**: 越权能设置 webhook/URL,想打进内网。
**A3**: 用可控 URL 做 SSRF:指向内网服务、云元数据端点(取临时凭证)、内部管理接口。越权设置的出站请求功能是从应用层跳进基础设施层的桥。判据是这个 URL 是否真被服务端请求、能否收到内网响应或回连。
**Q4**: 系统对配置类操作校验很严,升级不了。
**A4**: 转横向而非纵深:用越权能力接管更多/更高权限的账号(找管理员账号的数据、改其绑定),用管理员身份再获得系统操作权。当"纵向提权"受阻,先"横向到高权用户"再纵向,往往更顺。
**Q5**: 无法接触高权账号,系统影响到顶了。
**A5**: 重新校准目标与止损。若越权只能停留在数据层,评估已有战果的严重性(大规模 PII/资金/业务数据)是否已达交付标准。红队价值是"可证明的最大影响",不是"一定要拿 shell"。若数据层影响已足够,固化证据交付;若不够,转向完全不同的初始入口重新寻找纵深路径。

### 会话管理缺陷:固定、并发与失效不当
**Q1**: 我想从会话本身找账号安全问题,先看哪些点?
**A1**: 抓登录前后的 session 标识变化。核心测点:登录后 session id 是否重新生成(不变 = 会话固定风险,攻击者预设 sid 诱受害者登录后共享会话)、session 是否绑定 IP/UA、退出登录后旧 session 是否服务端失效(仅前端删 cookie 不算)。会话的"生成-绑定-销毁"三段各有坑。
**Q2**: 登录后 session 确实换了,固定攻击不成立。
**A2**: 转并发会话与失效策略:改密码/换绑后其他设备的旧 session 是否被踢、同一账号能否无限多端在线、被封禁/降权的用户其活跃 session 是否立即生效。很多系统"改了权限但老会话照跑",这是提权撤销失效的漏洞。
**Q3**: 想利用泄露的 session token。
**A3**: 若通过 XSS/日志/referer/前面的 IDOR 拿到他人 session token,直接注入 cookie 复用即接管——前提是 session 不绑定设备指纹。测 token 的作用域:是否 HttpOnly(防 XSS 读取)、是否 Secure、SameSite 设置。会话凭证的保护属性决定能否被盗用。
**Q4**: session 绑定了设备/IP,盗用后被拒。
**A4**: 测绑定的严格度:IP 绑定是否精确到 IP 还是仅 /24 网段(同网段可绕)、UA 绑定能否伪造复制、指纹是否可从受害者环境提取重放。绑定常做得松,复制受害者的环境特征即可绕过。
**Q5**: 会话机制整体很硬。
**A5**: 转向"记住我"/长效凭证:remember-me token、API key、刷新 token 的强度和失效策略往往比主 session 松——可预测、长期有效、注销不失效、泄露后无法吊销。当短会话很硬,长效凭证是更软的替代接管路径。

### CSRF 与状态变更操作的越权触发
**Q1**: 我想测能否让受害者"被动"执行越权操作(CSRF),先判断什么?
**A1**: 找"改变状态且仅靠 cookie 鉴权"的操作:改密码、换绑、转账、加管理员、改配置。判据:该请求是否需要不可预测的 CSRF token/自定义 header,还是仅凭浏览器自动带上的 cookie 就能执行。仅靠 cookie = CSRF 可行。先挑高价值的状态变更操作。
**Q2**: 请求带了 CSRF token,直接伪造不成。
**A2**: 测 token 的健壮性:token 是否真校验(删掉/置空是否放行)、是否与用户绑定(用我的 token 打受害者是否通过)、是否可预测/全局固定、GET 请求是否也接受从而绕过。很多"有 token"的系统校验形同虚设。
**Q3**: token 校验很严。
**A3**: 转 SameSite 与 method 绕过:cookie 的 SameSite 若为 Lax,GET 型跨站请求仍带 cookie——找能用 GET 触发的状态变更;若为 None 则完全可跨站。也测 Content-Type 绕过(用 text/plain 发 JSON 绕过预检)、子域名信任(从可控子域发同站请求)。
**Q4**: 想结合 CSRF 打越权而非仅 CSRF。
**A4**: CSRF + 逻辑漏洞组合:用 CSRF 让受害者(尤其管理员)触发一个"以其权限执行"的操作——诱导管理员点击链接自动把我加为管理员、或触发一个含我可控参数的操作。CSRF 是"借受害者权限"的投递手段,配合越权效果翻倍。
**Q5**: 现代浏览器默认 SameSite=Lax,CSRF 面很窄。
**A5**: 转向 CSRF 的近亲——若前端是 SPA 且用 token 存 localStorage,CSRF 天然失效,那改打 XSS 偷 token。或转 clickjacking(若无 X-Frame-Options,用 iframe 诱骗点击敏感操作)。当经典 CSRF 被 SameSite 封死,把"诱导受害者操作"的思路转到 XSS 或 UI 重定向劫持这些正交手段。
