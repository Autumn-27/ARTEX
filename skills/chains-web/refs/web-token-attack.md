# Web · JWT/OAuth/SSO等认证机制攻击

### 拿到一个 JWT,先决定从哪个维度下手
**Q1**: 抓到一个疑似 JWT 的三段式 base64url 串,我该先做什么判断,而不是盲目乱改?
**A1**: 先 base64url 解前两段看 header 和 payload。重点看 header 的 `alg`、`kid`、`jku`、`x5u`、`typ`,以及 payload 的 `iss`/`aud`/`exp`/`sub`/`role` 类字段。攻击面几乎全在 header 的验签路由上。先建立"这个 token 用什么算法、密钥从哪来"的模型,再决定攻法。
**Q2**: header 里是 HS256,payload 里有明显的权限字段,我第一直觉是什么?
**A2**: HS256 是对称密钥签名,攻击核心变成"能不能拿到/爆破那个 secret"。先假设弱密钥,拿 payload 篡改 role 后用字典离线爆破签名。同时留一手:检查服务端是否存在 alg 混淆(RS→HS)可能。
**Q3**: 如果是 RS256/ES256 非对称呢?
**A3**: 非对称下你没有私钥,直接改签名走不通。转向:alg 混淆(把 RS256 降为 HS256,用公钥当 HMAC secret)、`kid` 注入、`jku`/`x5u` 指向我方 JWKS、`none` 算法。攻击面从"爆破密钥"转到"劫持验签所用的密钥来源"。
**Q4**: 我怎么快速判断改了 token 到底有没有被接受?
**A4**: 找一个"验签通过才会有的差异化响应":越权接口 200 vs 401、返回体里带用户名、或触发一次后端日志/行为。用最小改动(比如只改一个无关紧要字段但重签)先验证"签名校验是否真的在做",再上权限篡改。
**Q5**: 全部 header 攻法都失败、签名铁打不动,往哪转?
**A5**: 转离开"伪造签名"这条线,去打 token 的【逻辑/生命周期】:exp 是否真校验(过期 token 还能用?)、同一 token 是否可跨 session/跨用户重放、注销后是否失效、aud/iss 是否校验(把别的服务签的 token 拿来用)。签名安全 ≠ 逻辑安全,大量靶点在后者。
**Q6**: 还想再挖一层,有没有信息泄露维度?
**A6**: payload 本身是明文,可能泄露内部用户 id 格式、租户 id、内网服务名、权限模型枚举值。即使伪造不成,这些也是横向和越权的情报。把 JWT 当成一份"服务端自曝的结构说明书"来读。

### alg=none 与算法降级的试探顺序
**Q1**: 我想试 alg 篡改,应该先试 `none` 还是先试 RS→HS 混淆?
**A1**: 先试 `none` 系列,因为它零成本零依赖。构造 header `{"alg":"none"}`,payload 改成目标权限,签名段留空(有的实现要保留末尾的点)。同时准备变体:`None`、`NONE`、`nOnE` 绕过大小写黑名单。
**Q2**: none 被拒了,怎么判断是"库根本不支持"还是"被显式拦了"?
**A2**: 看错误信息差异。如果是"unsupported alg"类,库层面禁了;如果是"signature required",说明它期望签名字段。前者转 RS→HS,后者试试空签名的各种编码变体和是否有"允许 none 当配置开关"的历史缺陷版本。
**Q3**: 转 RS→HS 混淆,前提是什么?
**A3**: 前提是我能拿到服务端的 RSA 公钥。公钥常见于:`/.well-known/jwks.json`、OAuth discovery 端点、TLS 证书、前端 JS、文档。拿到公钥 PEM,把它当作 HMAC 的 secret 字符串,用 HS256 对篡改后的 payload 签名。
**Q4**: 公钥格式细节上容易踩什么坑?
**A4**: HMAC key 的字节必须和服务端加载公钥时用的字符串【逐字节一致】——包括 PEM 的换行、有没有尾部换行、是 SPKI 还是 PKCS1。多准备几种 PEM 变体分别签名去试,别只试一种就断言失败。
**Q5**: 混淆也不成,是不是这个库根本区分了算法族?
**A5**: 现代库大多按 `alg` 强绑定 key 类型,混淆失效很正常。转向 `kid`/`jku` 这类"密钥来源劫持",或者干脆退回对称场景:确认它到底用不用 HS,若全程 RS 且验签严格,把精力转到 token 逻辑/OAuth 流程层。
**Q6**: 如何避免在算法层浪费太多时间?
**A6**: 给算法层设一个时间盒(比如 15 分钟跑完 none/降级/kid/jku 四件套)。四件套全绿灯不亮就果断转 OAuth 流程或越权逻辑,不要在签名死磕。红队的转向纪律比单点深度更重要。

### kid 参数的注入攻击面判定
**Q1**: header 里有 `kid` 字段,我该怀疑什么?
**A1**: `kid` 是密钥标识符,服务端拿它去查密钥。若查询实现是拼 SQL、拼文件路径或拼命令,就有注入。先判断 kid 的值形态:是像文件名(`keys/1.pem`)、像数据库 id(数字/uuid)、还是像 URL。
**Q2**: 怀疑它是路径,怎么利用?
**A2**: 试目录穿越指向一个【我知道内容的文件】,让签名 key 变成可控。经典是指向 `/dev/null`(key 为空,再用空 secret 签)或指向静态可预测文件。核心思路:把"密钥值"变成我已知的东西,从而伪造出合法签名。
**Q3**: 怀疑它拼进 SQL 呢?
**A3**: 试 SQL 注入让查询返回我指定的密钥值(UNION 出一个我控制的字符串当 key),然后用这个字符串签名。判据:注入 payload 改变了签名校验结果,或引发数据库报错。
**Q4**: kid 注入怎么和命令执行搭上?
**A4**: 若后端用 kid 拼接系统命令(少见但存在),可试命令注入。但优先级低,先穷尽路径/SQL 两条主线。
**Q5**: kid 各种注入都无效,可能是什么原因,转哪?
**A5**: 可能 kid 只做白名单查表,无拼接。转向 `jku`/`x5u`——同样是"控制密钥来源",但走 URL 而非本地查表。若 header 里没有这些字段,转回 alg 混淆或 token 逻辑层。
**Q6**: 有没有一个信号能提前告诉我 kid 值得深挖?
**A6**: 改 kid 后响应时间/错误类型变化(比如指向不存在文件报 500、注入引号报 SQL 错)就是强信号,说明服务端真的用它做了动态查询,值得继续。若改 kid 毫无反应,基本是查表,别恋战。

### jku / x5u 指向我方 JWKS 的实现
**Q1**: header 出现 `jku`(JWK Set URL),这意味着什么攻法?
**A1**: 服务端会去 `jku` 指定的 URL 拉公钥来验签。如果 URL 可控,我就在自己服务器放一套自己生成的密钥对,用私钥签 token、`jku` 指向我的 JWKS,服务端用我的公钥验签必然通过。核心是"我自带钥匙自证身份"。
**Q2**: 直接把 jku 换成我的域名,通常会遇到什么拦截?
**A2**: 服务端多半有 host 白名单(只允许自己域)。要绕就上 SSRF/URL 解析绕过那套:`@` 混淆(`https://trusted.com@evil.com`)、子域(`trusted.com.evil.com`)、开放重定向(白名单域上找一个跳转到我 JWKS 的接口)、DNS/解析歧义。
**Q3**: 我的 JWKS 里 kid 要怎么配?
**A3**: 让我 JWKS 里的 key 的 `kid` 和 token header 的 `kid` 对上,服务端才会选中我的 key。JWK 里放我的公钥 (n/e),token 用对应私钥签。细节对齐是成败关键。
**Q4**: 服务端根本不出网/拉不到我的 URL 怎么办?
**A4**: 这就是被墙场景。转 `x5u`(证书 URL,同理但走 X.509)、或转回本地密钥来源(kid)。若所有"外部密钥来源"都因不出网失败,彻底转离密钥劫持,去打 OAuth redirect_uri 或 token 逻辑。
**Q5**: 白名单绕过全试遍还是不行,值得继续吗?
**A5**: 给 SSRF 绕过设上限。若白名单是严格的精确匹配且无开放重定向,jku 这条基本死。转向的正交维度:既然它信任自己域的 JWKS,那能不能污染/上传到它自己域下的某个可控路径(文件上传+jku 指向自己域下我传的文件)——把"外部 URL"问题变成"自己域下可控内容"问题。
**Q6**: 拿下 jku 伪造后,怎么最大化战果?
**A6**: 别只 elevate 到 admin 就停。用可控签名去枚举权限模型(逐个试 role/scope 值)、伪造服务间调用的 token(如果同一套密钥体系覆盖内部微服务),把单点 token 伪造扩成对整个信任域的通行证。

### HS256 弱密钥爆破的取舍
**Q1**: 确定是 HS256,我要不要投入爆破?判据是什么?
**A1**: 先低成本快速跑通用弱口令字典(常见 secret、`secret`、公司名、默认值、泄露过的框架示例 key)。跑几分钟不出就要评估:密钥若是高熵随机串,爆破期望收益极低,别把它当主线。
**Q2**: 用什么姿势爆破效率高?
**A2**: 离线爆破,不碰服务端。拿完整 JWT 喂给 hashcat(HS256 对应模式)或 john,字典优先,规则次之,纯掩码最后。字典源:通用弱密钥表、目标相关词(域名/产品名/年份组合)、历史泄露 secret 库。
**Q3**: 字典跑空,要不要上掩码暴力?
**A3**: 看密钥形态线索。若泄露的示例/文档暗示 key 长度或字符集(如 32 位 hex),定向掩码值得一搏;若毫无线索,盲目掩码是浪费,停。
**Q4**: 爆破这条线判死后转哪?
**A4**: 转"密钥获取"而非"密钥猜测":secret 常硬编码在源码/配置/环境变量/git 历史/前端打包文件里。如果能碰到任意文件读、源码泄露、`.env`、备份文件,直接读出 secret 比爆破可靠一万倍。把认证问题转成信息泄露问题。
**Q5**: 万一 secret 是从 KMS 动态取、根本不落地呢?
**A5**: 那 HS 密钥这条彻底放弃,转 token 逻辑层与 OAuth 流程层。同时反思:强密钥管理往往意味着团队安全意识高,应把重心移到业务逻辑越权而非密码学攻击。
**Q6**: 爆到弱 secret 后除了改自己 token 还能干嘛?
**A6**: 能签任意 token 就等于拥有"身份签发权":伪造任意用户、伪造 service account、构造带异常字段的 token 探测后端解析逻辑(如超长 exp、注入 role 数组、多租户 id)。一把 secret 是整条认证链的万能钥匙,要吃干榨净。

### token 不校验过期/重放的逻辑漏洞
**Q1**: 签名攻不动,我怎么系统性验证 token 生命周期有没有漏洞?
**A1**: 逐项打表:1) 拿一个已过期(exp 过去)的旧 token 重放,看是否仍被接受;2) 注销后原 token 是否失效;3) 改密码后旧 token 是否失效;4) 同一 token 是否能被多设备/多 IP 并发使用。每一项都是独立靶点。
**Q2**: 发现过期 token 仍可用,说明什么,怎么放大?
**A2**: 说明服务端没校验 exp 或时钟/校验逻辑有缺陷。放大方向:那么任何一次泄露(日志、Referer、缓存、历史流量)里的旧 token 都长期有效,价值飙升。结合其他泄露点收集历史 token。
**Q3**: 注销后 token 仍有效,红队价值在哪?
**A3**: 无状态 JWT 常见此问题(服务端不维护黑名单)。价值:一旦拿到 token(哪怕受害者已注销),持久访问不受对方"退出登录"影响。这也是判断它是"无状态 JWT"还是"有状态 session"的探针。
**Q4**: 怎么区分它是无状态还是服务端有会话表?
**A4**: 篡改 payload 里非签名保护外的东西不现实,但可观察:服务端重启后 token 是否还有效(有效→无状态)、注销是否即时失效(即时→有状态黑名单)。据此选择后续攻法。
**Q5**: 这些逻辑测试全绿(都正确失效),往哪转?
**A5**: 说明生命周期管理健壮。转向 token 的【获取途径】而非【伪造/重放】:XSS 偷 token、token 存储位置(localStorage vs HttpOnly cookie)、CSRF、以及 OAuth 流程里 token 的泄露点(redirect、Referer、日志)。攻击从"伪造凭据"转为"窃取凭据"。
**Q6**: 有没有容易被忽略的一项?
**A6**: `nbf`(not before)和时钟偏移、以及 refresh token 的轮换/复用检测。很多实现只盯 access token,refresh token 可无限复用或不轮换,是持久化的金矿,常被漏测。

### OAuth redirect_uri 的开放重定向/token 窃取
**Q1**: 进入 OAuth 授权流程,我第一个盯的参数是什么?
**A1**: `redirect_uri`。它决定授权码/token 发回哪里。先测它的校验严格度:能否改成我控制的域、能否改路径、能否加参数、子串匹配还是精确匹配。这是 OAuth 最高频的入口。
**Q2**: 完整替换域名被拒,还有哪些绕法?
**A2**: 分层试:同域下开放重定向(redirect_uri 保持白名单域,但该域有个跳板接口把码转发给我)、路径遍历、追加 `?`/`#`/`@`/反斜杠、子域名通配被过度放宽、大小写与编码变体、以及 `localhost`/私有地址是否被白名单。
**Q3**: 我到底想偷什么——code 还是 token?
**A3**: 看 response_type。`code` 流我偷授权码(还需能换 token,或配合 PKCE 缺失);`token`(隐式流)直接偷 access token 在 fragment 里。隐式流泄露更直接,优先看有没有隐式流可用。
**Q4**: 偷到 code 但换不了 token,卡在哪,怎么破?
**A4**: 通常缺 client_secret 或有 PKCE。破法:检查 PKCE 是否真强制(去掉 code_challenge 还能不能走)、client_secret 是否泄露在前端/文档、code 是否可重复使用或跨 client 使用。若 PKCE 严格且 secret 保密,code 窃取收益受限,转隐式流或别的参数。
**Q5**: redirect_uri 全线严格,整个重定向维度被墙,转哪?
**A5**: 转 OAuth 的其它可控参数与逻辑:`state` 缺失→CSRF/登录混淆;`scope` 提权;授权码绑定不严→code injection/替换攻击;以及 account linking 流程的身份混淆。redirect 不是 OAuth 的唯一软肋。
**Q6**: 拿到别人的 access token 后如何评估影响面?
**A6**: 用 token 去打 resource server 与 userinfo 端点,枚举它的实际 scope、能访问哪些 API、是否可跨应用复用(同一 IdP 多 client 共享)。评估它是"单应用凭据"还是"整个身份平台的通行证",决定战果上报等级。

### OAuth state 缺失导致的登录 CSRF / 账户接管
**Q1**: OAuth 请求里 `state` 参数缺失或不校验,我能干什么?
**A1**: state 是防 CSRF 的绑定值。缺失意味着我可以发起一个授权流程,拿到"把我的账号绑到受害者会话"或"把受害者的第三方账号绑到我账号"的机会,形成登录 CSRF 或账户接管。先想清楚"谁的 code、落到谁的 session"。
**Q2**: 具体怎么构造账户接管?
**A2**: 经典 account linking 场景:诱导受害者点击一个携带【我的】授权 code 的回调链接,使受害者当前登录的账户被链接到我控制的第三方身份,之后我用该第三方身份登入 = 登入受害者账户。判据:绑定操作不校验 state 且不二次确认。
**Q3**: 反过来,pre-account-takeover 怎么玩?
**A3**: 若目标允许"先用邮箱注册,后用同邮箱 OAuth 登录自动合并",我先用受害者邮箱占位注册,受害者后来用 OAuth 首次登录被合并进我已知密码的账户。核心是"邮箱作为身份主键但验证缺失"。
**Q4**: state 其实存在但我怀疑没校验,怎么确认?
**A4**: 把 state 值改掉/删掉/替换成固定值,看流程是否照常完成。若照常 → 未校验。再看 state 是否与会话强绑定(用别的会话的 state 能否通过)。
**Q5**: state 校验严格,登录 CSRF 这条断了,转哪?
**A5**: 转身份混淆的其它面:IdP 返回的邮箱/sub 是否被信任却未验证(邮箱未验证也当已验证)、多 IdP 下相同邮箱不同 provider 是否混用、`nonce` 缺失导致 id_token 重放。从"CSRF 绑定"转到"身份声明可信度"。
**Q6**: 这类逻辑漏洞怎么低风险验证而不误伤真实用户?
**A6**: 用两个我自己控制的账号(攻击者账号 + 模拟受害者账号)在自己浏览器/两套会话间复现,全程不碰真实用户。红队报告要能自证 PoC 可控可重放,而不是靠运气。

### OIDC id_token 的验证盲点
**Q1**: 拿到 OIDC 的 id_token(JWT),它和普通 JWT 的攻击差异在哪?
**A1**: id_token 多了 OIDC 特定 claim:`iss`、`aud`、`nonce`、`azp`、`at_hash`。攻击面除了 JWT 通用那套,还多了"这些 claim 客户端有没有认真校验"。很多客户端只验签名不验 iss/aud/nonce。
**Q2**: iss/aud 不校验能干嘛?
**A2**: 若客户端不校验 `aud`,我可以拿一个由同一 IdP 签发给【别的 client】的 id_token 直接喂给目标 client,冒充身份(token 混淆/audience confusion)。若不校验 `iss`,甚至能用我自己搭的 IdP 签的 token。
**Q3**: nonce 缺失或不校验的后果?
**A3**: id_token 可重放。截获一次的 id_token 能被重复提交完成登录。判据:同一 id_token 提交两次都成功,或改 nonce 不影响结果。
**Q4**: 我怀疑客户端把 id_token 当 access token 用,这有什么问题?
**A4**: 混用意味着 id_token 的宽松验证被用于授权决策,放大了上面所有 claim 校验缺陷的影响。测:能否用 id_token 直接调受保护 API。
**Q5**: 所有 claim 都校验严格,OIDC 层无洞,往哪转?
**A5**: 转 IdP 与 client 之间的【流程】:授权码流的 code 绑定、PKCE、以及 IdP 本身的配置(dynamic client registration 是否开放、redirect_uri 白名单)。也可转 SAML/其它并存的 SSO 协议——同一目标常多协议并存,一个严不代表全严。
**Q6**: 面对多协议 SSO,怎么选突破口?
**A6**: 选实现最"手写"、最少用成熟库的那条。SAML 的 XML 解析、自研 token 交换、老旧 CAS 协议往往比标准 OIDC 库更脆。侦察阶段就要枚举目标支持的所有登录方式,挑最土的打。

### SAML 断言与签名包装攻击(XSW)
**Q1**: 目标走 SAML SSO,我优先测什么?
**A1**: 优先测签名验证的健壮性,尤其 XML Signature Wrapping (XSW)。SAML 断言是 XML,签名保护的节点和应用实际读取的节点可能不是同一个——这个错位就是 XSW 的根。先抓一个合法 SAMLResponse 做基线。
**Q2**: XSW 的核心操作是什么?
**A2**: 在 XML 里塞入一个我伪造的断言(改了 NameID/attribute 为目标用户),同时保留原始被签名的断言,通过调整节点位置/id 引用,让签名校验去验原始那个、而应用去读我伪造那个。有多种 XSW 变体(经典布局有若干种),逐个试。
**Q3**: 我怎么知道应用读的是哪个节点?
**A3**: 观察响应:把伪造断言的 NameID 改成不同值,看最终登录成谁。谁生效说明应用读了哪个节点。用这个反馈定位"签名验证节点"和"数据读取节点"的错位点。
**Q4**: 目标根本不校验签名或可去签名怎么快速发现?
**A4**: 先试最省事的:直接删掉 `<Signature>` 元素、或把断言改了不重签直接发。若还能登录,说明签名压根没验(比 XSW 更严重更简单)。永远先试"有没有验签"再上复杂 XSW。
**Q5**: 库很新、XSW 全变体失败、验签严格,转哪?
**A5**: 转 SAML 的非签名面:断言重放(无 `NotOnOrAfter`/`OneTimeUse` 校验)、`Recipient`/`Audience` 不校验(把发给别处的断言拿来用)、IdP-initiated 流程的接受度、以及 XXE(SAML 是 XML,解析器可能吃外部实体)。SAML 报文本身就是 XXE 的天然载体。
**Q6**: SAML 里还有哪个常被忽略的高价值点?
**A6**: NameID/属性里的注入与身份混淆:comment 截断(`admin<!---->@evil.com` 被解析成 admin)、大小写/规范化差异导致的用户匹配错位。以及 IdP 元数据若可被替换,直接改信任根。这些逻辑面往往比密码学面回报更高。

### session cookie 与 JWT 并存时的选择
**Q1**: 目标同时用 session cookie 和 JWT,我该打哪个?
**A1**: 先摸清"谁是权威"。有的系统 cookie 是主、JWT 是辅(或反之),有的两套并行校验、有的存在降级路径。找出"哪套凭据真正决定授权",以及"能否只带一套绕过另一套的校验"。
**Q2**: 怎么探这个关系?
**A2**: 控制变量:只带 cookie 不带 JWT、只带 JWT 不带 cookie、带矛盾的两者(cookie 是用户A、JWT 是用户B),观察各接口的行为。矛盾态最能暴露"谁说了算"以及是否存在信任混乱。
**Q3**: 发现某些接口只认 cookie、某些只认 JWT,怎么利用?
**A3**: 这种不一致是越权温床。若某高权限接口错误地信任了较弱的那套凭据,针对性伪造较弱凭据即可。把"两套认证的边界缝隙"当作攻击面。
**Q4**: 两套都很严、无缝隙,转哪?
**A4**: 转获取维度:cookie 打 XSS/CSRF/固定/SameSite 配置;JWT 打存储位置与泄露。也转 CSRF——JWT 若放 cookie 自动携带就可能有 CSRF,若放 header 则天然抗 CSRF,据此选路。
**Q5**: session cookie 本身值得测哪些经典点?
**A5**: session fixation(登录前后 session id 是否变)、可预测性、HttpOnly/Secure/SameSite 缺失、跨子域作用范围过宽、以及服务端 session 反序列化(某些框架 session 存序列化对象→反序列化 RCE)。
**Q6**: 如果发现 session 里有序列化对象,这条线怎么升级?
**A6**: 立刻从"认证绕过"升级为"RCE 尝试":判断序列化格式(语言框架特征),找对应 gadget 链。认证攻击有时是通往代码执行的入口,别停在越权层。

### cookie 属性与作用域配置攻击
**Q1**: 我拿到目标的 auth cookie,该逐项检查哪些属性?
**A1**: `HttpOnly`(缺失→XSS 可偷)、`Secure`(缺失→明文可截)、`SameSite`(None/缺失→CSRF)、`Domain`(过宽→子域可读写)、`Path`、以及 `__Host-`/`__Secure-` 前缀是否被伪造利用。每个缺失都对应一种偷/伪造/重放路径。
**Q2**: Domain 设成父域(如 `.example.com`)有什么可打?
**A2**: 任意子域都能读写该 cookie。若我能控制一个子域(子域接管、用户内容子域、测试子域),就能读取或注入 auth cookie,形成跨子域的会话攻击。判据:先枚举子域,找可控/可接管的。
**Q3**: SameSite=Lax 时 CSRF 还有戏吗?
**A3**: 有条件。Lax 对顶层导航的 GET 仍发送 cookie,若敏感操作接受 GET 或存在方法覆盖(`_method`),CSRF 仍可行。还有 Lax 的短暂宽限窗口、以及子域/同站请求不受限。别看到 Lax 就放弃 CSRF。
**Q4**: cookie 属性全都配置完美,转哪?
**A4**: 转 cookie 的解析/注入面:cookie 名冲突(同名多值,前端后端取值不一致)、cookie tossing(子域写一个同名 cookie 顶掉主域的)、以及 `__Host-` 前缀绕过。从"属性防护"转到"cookie 解析歧义"。
**Q5**: cookie tossing 具体威胁模型?
**A5**: 我从可控子域写一个 auth/csrf 相关的同名 cookie,浏览器把它一并发送,服务端若取了"错误的那个"就可能被我固定/污染。常用于打 CSRF token 固定或 session 固定。前提是有可控子域。
**Q6**: 没有可控子域,这些都难,最后退路?
**A6**: 退回最直接的:cookie 是否在 URL/日志/Referer 里泄露、是否可预测、是否登录后不更换。以及彻底转离 cookie,去 JWT/OAuth/SAML 那三条主线。认证攻击是多协议并进,一条堵死换一条。

### JWT 存储位置决定的窃取路径
**Q1**: 我想偷目标的 JWT,先要搞清什么?
**A1**: 先定位 token 存哪:HttpOnly cookie(JS 偷不到,走 CSRF/网络)、localStorage/sessionStorage(XSS 可直接读)、内存/JS 变量、还是 URL/fragment。存储位置直接决定用哪种偷法,别用错工具。
**Q2**: 发现存在 localStorage,攻击链怎么接?
**A2**: 那 token 窃取的前提变成"能不能 XSS"。有 XSS → 一行 JS 读走 token 外带。没 XSS → 找 DOM sink、第三方脚本、依赖投毒等间接 JS 执行路径。把认证问题转成 XSS 问题。
**Q3**: 是 HttpOnly cookie,JS 偷不到,怎么办?
**A3**: 转不依赖 JS 读取的路径:CSRF(带着 cookie 自动发请求代受害者操作)、网络层截获(无 HTTPS/混合内容)、或让服务端把 cookie 反射出来(某些 debug/错误页回显请求头)。HttpOnly 挡读不挡用。
**Q4**: token 出现在 URL 或 fragment 里,风险点?
**A4**: URL 里的 token 会进浏览器历史、服务器日志、Referer 头(跳转到外部时泄露)、以及分享/书签。找一个能让受害者浏览器带着 token 跳到我域的点(外链、开放重定向),从 Referer 收 token。
**Q5**: token 保护得很好、无 XSS、无泄露点,转哪?
**A5**: 转伪造而非窃取(回到签名/逻辑攻击),或转下游:token 交给后端后,后端如何传递给微服务?服务间是否明文传 token、日志是否记录、SSRF 能否读到内部带 token 的请求。窃取战场从浏览器前移到服务端内部。
**Q6**: 偷到 token 后如何延长控制?
**A6**: 立刻找 refresh token。access token 短命,refresh token 才是持久化关键。看能否一并偷到 refresh、refresh 是否轮换、是否可无限续期。持久化访问靠 refresh,不靠一次性的 access。

### 越权:token 里权限字段的篡改探测
**Q1**: token 里有 `role`/`scope`/`is_admin`/`tenant_id` 这类字段,我怎么系统探测越权?
**A1**: 即使签名改不动,也要先"读懂权限模型":枚举这些字段的可能取值(从多个不同权限账号的 token 对比得出)。拿到低权 token 后,目标是让服务端把我当高权,方法有二:伪造(需破签名)或找服务端"不完全依赖 token 字段"的逻辑缝。
**Q2**: 服务端可能不完全信任 token 字段,这怎么利用?
**A2**: 很多系统 token 里带 role,但真正鉴权时又去查数据库或另一个 header。测试:把请求里的 `X-User-Id`/`X-Role` 等辅助头改掉、把 URL 里的资源 id 换成别人的(IDOR),看权限字段和实际鉴权谁生效。缝隙常在这。
**Q3**: 多租户 tenant_id 字段怎么打?
**A3**: 若能伪造或若服务端不严格隔离,改 tenant_id 实现跨租户访问。即使签名锁死,也测 IDOR:URL/body 里的资源 id 是否只受 token tenant 约束,换成别租户 id 是否越界。多租户隔离常在应用层而非 token 层出错。
**Q4**: 我需要两个账号做对比测试,拿不到第二个账号怎么办?
**A4**: 想办法自注册第二个(不同权限级别)。若不能注册,用同一账号的不同状态(升级前后)、或从 token 结构反推权限字段格式,构造推测值。对比测试是发现越权的最高效手段,值得投入拿账号。
**Q5**: token 字段改不动、IDOR 也都做了服务端校验,转哪?
**A5**: 转横向的"功能级越权":不是数据 id 越权,而是能否调用高权限【接口/动作】(admin API 路径、内部端点)。以及转"权限提升链":普通用户能否触碰到修改自己 role 的接口(比如个人资料更新里混入 role 字段——mass assignment)。
**Q6**: mass assignment 这条怎么快速试?
**A6**: 在任意"更新用户资料"类请求 body 里,追加 `role`/`is_admin`/`permissions` 等字段,看服务端是否照单全收。这是绕过 token 签名限制、直接改后端权限记录的经典捷径,成本极低,优先试。

### JWT header 注入与 typ 混淆
**Q1**: 除了 alg,header 里还有什么可玩?
**A1**: `typ`(有的实现区分 `JWT` 与 `at+jwt` 等,混淆可致 token 被错误上下文接受)、`cty`、以及自定义 header 字段。还有 `crit` 参数——若服务端不正确处理 critical header,可能忽略本应强制的校验。逐个塞入异常值观察。
**Q2**: typ 混淆的实际场景?
**A2**: 一个系统里 access token 和 refresh token、或 id_token 和 access token 可能都是 JWT 但 typ 不同。若服务端不校验 typ,我能把 refresh token 当 access token 用、或反之,突破 token 用途隔离。
**Q3**: 怎么发现这种用途隔离缺失?
**A3**: 交叉投喂:把 A 用途的 token 提交到 B 用途的端点。若被接受,隔离失效。这是纯逻辑测试,不需要破密码学,应该在早期就跑一遍全矩阵。
**Q4**: header 里塞未知字段一般什么反应?
**A4**: 多数库忽略未知 header,无收益。但若引发解析异常/不同错误码,说明它在处理 header,值得顺着找解析差异。判据还是"响应是否变化"。
**Q5**: header 层全无斩获,转哪?
**A5**: 转 payload 的解析健壮性:重复 claim(同名两个 `role`,取哪个?)、claim 类型混淆(`role` 期望字符串却给数组/对象)、超大/超长值、Unicode 规范化。JSON 解析歧义可能让签名合法的 token 被错误理解。
**Q6**: 这些解析攻击怎么才算有价值?
**A6**: 当目标存在【多个组件分别解析同一 token】时价值最大:验签的库和读取业务字段的代码若用不同 JSON 解析器,重复 claim 就能造成"验签看到的是安全值、业务读到的是恶意值"。侦察是否存在网关+后端双解析架构,决定这条线深浅。

### 授权码/PKCE 流程的实现缺陷
**Q1**: 目标用授权码 + PKCE,我还有哪些点可打?
**A1**: PKCE 不是万能。测:1) 去掉 `code_challenge` 是否仍放行(PKCE 未强制);2) `code_challenge_method` 能否降级为 `plain`;3) code_verifier 是否真的和 challenge 绑定校验;4) 授权码是否一次性、是否有短过期。逐条戳实现。
**Q2**: PKCE 未强制意味着什么?
**A2**: 意味着可回退到无 PKCE 的授权码窃取(配合 redirect_uri 缺陷偷 code 即可换 token)。这直接让"有 PKCE 所以安全"的假设崩塌。这是高价值发现,优先验证。
**Q3**: method 能降级为 plain 有何用?
**A3**: plain 模式下 challenge 就是 verifier 明文,若 challenge 在流程中泄露(URL/日志),等于 verifier 泄露,PKCE 形同虚设。测服务端是否接受 `plain`。
**Q4**: 授权码可重放/可跨 client 使用怎么打?
**A4**: 授权码本应一次性、绑定单个 client 和 redirect_uri。测:同一 code 换两次 token、用 client A 的 code 到 client B 换 token。任何一个成功都是严重的 code injection 面。
**Q5**: PKCE 与 code 校验全都严格,转哪?
**A5**: 转 token endpoint 本身:client 认证方式(client_secret 是否弱/泄露/可空)、`grant_type` 是否可切换到更宽松的(如允许 password grant / client_credentials 越权)、refresh_token grant 的滥用。从"授权阶段"转到"令牌换取阶段"。
**Q6**: grant_type 切换这条具体怎么探?
**A6**: 在 token 请求里改 `grant_type` 试各种值,看是否有未预期开启的授权模式(如 `password` 直接用用户名密码换 token 绕过前端流程、`client_credentials` 拿到服务级 token)。配置疏忽常留下多余 grant type,是被忽视的后门。

### 无 refresh 轮换的持久化利用
**Q1**: 我拿到一个 refresh token,怎么评估它的持久化价值?
**A1**: 测三点:1) 用它换 access token 后,旧 refresh 是否失效(轮换?);2) 同一 refresh 能连续用几次;3) refresh 的有效期多长、能否无限续期。不轮换 + 长有效期 = 持久后门级资产。
**Q2**: 发现 refresh 不轮换,红队怎么用?
**A2**: 只要偷到一次 refresh,就能长期(数周到数月)自助刷新 access,受害者改密码/注销若不吊销 refresh 则控制不断。这是比 access token 高一个数量级的战果,要重点保全和上报。
**Q3**: refresh 轮换但检测"复用"吗?
**A3**: 安全实现会在检测到旧 refresh 被复用时吊销整条链(reuse detection)。测:换出新 refresh 后再用旧的,若触发全链吊销说明有检测——那我持有的窃取 refresh 一旦真主也用就会暴露/失效。据此决定利用时机。
**Q4**: 如何降低利用被发现的概率?
**A4**: 若有 reuse detection,避免与真实用户并发使用同一链;若无轮换,则可低调长期利用。红队要根据 refresh 机制选择"闪电利用"还是"潜伏利用"。
**Q5**: refresh 机制很严(轮换+检测+短期),持久化这条弱了,转哪?
**A5**: 转其它持久化手段:申请/伪造长期 API key、OAuth 的 offline_access 长期授权、创建新的 OAuth client、或在账户层留后门(备用邮箱/MFA 设备)。凭据持久化不止 refresh 一条路。
**Q6**: refresh 相关攻击里最容易被漏的点?
**A6**: refresh token 与 access token 的作用域是否一致——有的实现允许用 refresh 换取比原始 scope 更大的 token(scope 提升),这是纯逻辑越权,常被漏测。换 token 时故意请求更大 scope 试一下。

### JWT 加密(JWE)与嵌套 token 的攻击面
**Q1**: token 不是三段而是五段(JWE),攻法有何不同?
**A1**: 五段是 JWE(加密),不是 JWS(签名)。header 里 `alg`(密钥管理)和 `enc`(内容加密)是重点。攻击面:密钥管理算法降级、`alg:dir`/RSA 相关的经典 padding oracle(Bleichenbacher 类)、以及 zip bomb via `zip` header。
**Q2**: JWE 里有哪个经典密码学攻击?
**A2**: 若用 RSA1_5(PKCS#1 v1.5)做密钥封装,可能存在 Bleichenbacher padding oracle,可逐步解出 CEK。判据:能否从服务端拿到"解密成功/padding 错误"的可区分响应(oracle)。有 oracle 就能打。
**Q3**: 没有可区分 oracle 或用的是现代算法呢?
**A3**: 那密码学攻击这条基本堵。转 JWE 的实现坑:是否接受 `alg:none` 类的无保护变体、是否有算法混淆(用 signing key 当 encryption key)、以及嵌套 JWT(JWE 里包 JWS)的验证是否两层都做。
**Q4**: 嵌套 token 常见什么疏漏?
**A4**: 解密外层后,内层 JWS 的签名可能没再验(以为加密就够了)。测:构造一个内层签名无效但外层加密正确的 token,看是否被接受。加密 ≠ 认证,这是常见混淆。
**Q5**: JWE 整条太硬(现代算法+严格实现),转哪?
**A5**: 果断转离密码学层。JWE 通常意味着团队安全成熟度高,把资源投到业务逻辑越权、OAuth 流程、SSO 集成的接缝处,回报远高于死磕加密。
**Q6**: 面对 JWE 该有的心态判断?
**A6**: 把 JWE 的出现当成"此处密码学攻击性价比低"的信号,快速跑一遍降级/嵌套验证两个低成本点,不中就撤。红队要会读"防御强度信号"来分配精力。

### 跨服务 token 传递与 SSRF 联动
**Q1**: 前端 token 到了后端,后端如何用它调内部服务?这有什么可打?
**A1**: 微服务架构里,网关校验完外部 token 后,常向内部服务传递身份(转发原 token、或换成内部 service token、或加内部 header 如 `X-Authenticated-User`)。若我能触达内部,这些内部信任头往往【无签名、可伪造】。
**Q2**: 我怎么触达并利用内部信任头?
**A2**: 结合 SSRF:找一个能让服务端代发请求的点,直接打内部服务并附上伪造的 `X-User`/`X-Role` 头。内部服务通常盲信网关来的头。SSRF + 内部认证缺失 = 越权直达。
**Q3**: 如果外部请求里直接塞内部头会怎样?
**A3**: 测试网关是否清洗客户端传入的内部头。很多网关忘了剥离,导致我从外部直接发 `X-Authenticated-User: admin` 就被内部信任。这是零成本高回报,应尽早试。
**Q4**: 网关正确剥离了内部头,SSRF 也没有,转哪?
**A4**: 转回边界:既然内部信任外部拿不到,聚焦攻破外部 token 本身(前述各条),或找 SSRF/RCE 打进内网再回到内部信任面。内部认证缺陷是"进去之后"的提权跳板,需先有立足点。
**Q5**: 拿到内部 service token 后如何扩大战果?
**A5**: 内部 service-to-service token 权限通常很大且校验松。用它横向调用其它内部 API、枚举服务清单、访问它信任的下游。一个内部 token 可能是整个服务网格的通行证,价值极高。
**Q6**: 这条线侦察阶段该收集什么?
**A6**: 收集架构信息:响应头里的网关特征、内部服务名/路径泄露(错误信息、swagger、js 配置)、token 在不同层的形态变化。理解信任拓扑,才能定位"哪一跳的认证最弱"。

### MFA 与 SSO 的绕过接缝
**Q1**: 目标有 MFA,认证攻击还有戏吗,从哪找缝?
**A1**: 有。MFA 常只保护"登录"这一步,而 token/session 一旦签发就绕过了 MFA。找"签发 MFA 后 token 的泄露/伪造点",或"跳过 MFA 步骤直达已认证状态"的流程缺陷。MFA 保护的是入口,不是入口之后的凭据。
**Q2**: 跳过 MFA 步骤具体怎么试?
**A2**: 观察登录多步流程:输密码后进入 MFA 页,此时是否已下发了部分/完整凭据?能否直接请求 MFA 之后的接口跳过验证?MFA 校验是前端强制还是后端强制?后端不强制则可直接跳。
**Q3**: SSO 场景下 MFA 有什么特殊绕法?
**A3**: SSO 里 MFA 常由 IdP 承担,SP 信任 IdP 的断言。若某条登录路径(备用 IdP、遗留协议、IdP-initiated)不触发 MFA,就绕过了。枚举所有登录入口,找不强制 MFA 的那条。
**Q4**: remember-me / trusted-device 机制怎么打?
**A4**: 这类机制发一个长期凭据来跳过后续 MFA。若该凭据可预测、可窃取、绑定不严(换设备/IP 仍有效),就成了 MFA 免除后门。重点测其绑定强度和可伪造性。
**Q5**: MFA 各步都后端强制、SSO 全路径统一 MFA、trusted-device 绑定严,转哪?
**A5**: 转账户恢复流程:密码重置、MFA 重置/恢复码往往是 MFA 的弱侧门。以及转 session 层——绕不过 MFA 就直接偷 MFA 之后的 session/token(XSS/CSRF/网络)。防线最弱处常在"恢复"而非"登录"。
**Q6**: 账户恢复这条为什么值得优先?
**A6**: 恢复流程要在用户失去凭据时仍能验明身份,天然处于"降低验证强度"的矛盾中:恢复码可爆破、重置链接可预测/不过期、重置不吊销现有 session、客服社工面。它是绕过一切前端认证强度的元入口。

### 认证接口的枚举与限速绕过
**Q1**: 我想爆破/枚举认证接口,先判断什么?
**A1**: 先判断有无限速/锁定,以及"用户名枚举"是否可行(登录/注册/找回密码的响应差异能否区分用户是否存在)。枚举出有效用户是后续一切爆破的前提。响应时间、错误文案、HTTP 码都是枚举信号。
**Q2**: 有限速怎么绕?
**A2**: 常见绕法:轮换源 IP(`X-Forwarded-For`/`X-Real-IP` 若被信任)、分布式请求、拉长间隔避开时间窗、切换到不限速的备用端点(移动 API、老版本接口)、以及 password spraying(每个用户只试少数高频弱口令,避开单账户锁定)。
**Q3**: 账户锁定策略下怎么避免锁死真实用户?
**A3**: 用 spraying 而非 brute force:横向一个口令打全部用户,纵向控制单账户尝试次数在锁定阈值以下。既高效又不触发锁定告警。红队要克制,别把目标用户全锁了引发响应。
**Q4**: XFF 类头不被信任、限速严格,转哪?
**A4**: 转离在线爆破。找可离线爆破的资产:泄露的 hash、可离线破的 JWT HS 签名、缓存的凭据。或转认证逻辑绕过(前述各条),一个逻辑洞胜过千万次爆破。在线爆破应是最后手段。
**Q5**: OTP/验证码接口有什么专门的绕法?
**A5**: OTP 常见:无限速可爆(6 位数=百万级,若不限速可破)、OTP 不随请求变化/可复用、响应里泄露 OTP、以及"验证 OTP"和"完成登录"两步解耦可跳过。测 OTP 端点是否独立限速——主登录限速但 OTP 校验没限的情况很常见。
**Q6**: 枚举拿到有效用户和弱口令后如何最大化?
**A6**: 凭据复用(credential stuffing 思路):一处得到的用户/口令组合,在目标的其它系统、VPN、邮箱、云控制台复用。认证攻击的战果往往在于凭据的横向复用价值,而非单点登录本身。

### 逻辑绕过:参数篡改导致的免认证
**Q1**: 除了密码学和流程,有没有更"蠢"但有效的认证绕过?
**A1**: 有,且要优先扫一遍这些低成本高回报点:登录响应里 `{"success":false}` 改成 true 是否被前端信任、`isAuthenticated` 类前端状态可否 JS 篡改、以及"记住登录"cookie 是否只是 base64(`user=guest` 改 `user=admin`)。土办法常一击致命。
**Q2**: 前端信任响应的场景怎么判断?
**A2**: 看鉴权是前端做还是后端做。若拦截登录响应把失败改成功后能进入内部页,且内部接口不再校验,说明鉴权错放前端。这类"胖前端"应用是重灾区。判据:改响应后内部数据 API 是否真返回数据。
**Q3**: cookie/token 是明文可编辑结构怎么打?
**A3**: 若"凭据"只是 base64/JSON/明文键值(非签名),直接改字段提权。先解码看结构。很多自研 remember-me、自研 session 就是无签名的可编辑串。这是最快的胜利,侦察阶段就该解一遍所有 cookie。
**Q4**: 强制浏览(forced browsing)在认证绕过里怎么用?
**A4**: 直接请求受保护 URL 而不登录,测是否只靠"没链接给你看"来保护(security by obscurity)。以及测 admin 面板是否可未授权直达、API 是否可无 token 调用。绕过 UI 直捣后端接口是核心思路。
**Q5**: 这些土办法全被后端严格校验挡住,说明什么,转哪?
**A5**: 说明后端鉴权集中且健壮,土办法无效。转向需要技术深度的面:JWT 密码学、OAuth 流程、越权 IDOR。土办法是"免费侦察",快速跑完就转,不纠缠。
**Q6**: 怎么把这些零散尝试组织成不遗漏的检查?
**A6**: 建一张认证绕过 checklist(前端信任/明文凭据/强制浏览/默认口令/调试后门/备份接口),每接触一个新目标先机械过一遍。红队的稳定输出靠 checklist,灵感靠深挖;两者结合,先广后深。

### JWT 时间声明与时钟偏移利用
**Q1**: payload 里有 `exp`/`iat`/`nbf`,除了"过期还能用"还有什么可玩?
**A1**: 玩时间语义的边界:签名不变的前提下这些改不了,但可观察服务端对它们的处理。若我能拿到签发权(破了 secret),则可签发超长 exp 的永久 token、或 nbf 设未来做定时凭据。无签发权时,重点测服务端校验的松紧。
**Q2**: iat 有什么被忽略的用法?
**A2**: 有的系统用 `iat` 做"密码修改后使早于某时间的 token 全失效"。若它不校验 iat 或 iat 可绕,则改密码/踢出机制形同虚设,窃取的旧 token 长存。测:改密码后一个 iat 更早的 token 是否仍有效。
**Q3**: 时钟偏移(leeway)怎么被滥用?
**A3**: 库常允许几十秒到几分钟的时钟容差。通常影响小,但若容差配置离谱(几小时/几天),过期 token 的可用窗口被大幅延长,提升窃取 token 的利用价值。检查 exp 后多久 token 才真失效。
**Q4**: 拿到签发权后时间声明怎么最大化持久化?
**A4**: 签发一个 exp 极远、涵盖最高权限、绕过一切前端约束的 token。这是比偷 refresh 更彻底的持久化——只要 secret 不换,token 永久有效。务必优先确认 secret 轮换机制。
**Q5**: 服务端时间校验全都严格、又拿不到签发权,这条价值就没了吗?转哪?
**A5**: 时间维度价值确实变低,转 token 的空间维度:同一 token 的作用域(哪些服务/接口接受)、跨环境复用(测试环境 token 能否用于生产,反之)。时间锁死就打空间边界。
**Q6**: 测试/生产 token 混用怎么排查?
**A6**: 收集不同环境的 token,对比 iss/aud/kid。若共用密钥或 IdP,低防护的测试环境签发的 token 可能被生产接受——从软柿子环境拿签发权去打硬目标。跨环境信任是常被忽视的横向路径。

### 自研/魔改认证协议的识别与突破
**Q1**: 目标的 token/认证明显不是标准 JWT/OAuth,是自研的,怎么下手?
**A1**: 自研 = 没有成熟库背书 = 大概率有坑,优先级应【提高】。先逆向其结构:抓多个凭据样本对比,找出哪部分是随机(签名/随机数)、哪部分是编码数据(用户 id/时间/权限)、用了什么编码(base64/hex/自定义)。
**Q2**: 怎么定位它的完整性保护机制?
**A2**: 改动凭据不同部分逐字节测试,看哪些改动被拒(受完整性保护)、哪些被接受(无保护/可控)。据此画出"可篡改区"和"锁定区"。无保护区里的权限字段直接改。
**Q3**: 发现它用了自研签名/校验和怎么打?
**A3**: 分析算法:是简单 CRC/MD5(可自算重签)、还是带密钥的 HMAC(需破密钥)?若是无密钥校验和,任意篡改后重算即可。若是自研加密,找 ECB 模式特征(相同明文块相同密文块)、可控 IV、padding oracle。
**Q4**: 逆不出算法、样本也不够,卡住了怎么办?
**A4**: 转获取源码/实现细节:自研认证的逻辑常藏在前端 JS、反编译的移动 App、泄露的源码、文档。读到实现比黑盒逆向快得多。把密码分析问题转成信息泄露/逆向问题。
**Q5**: 连实现都拿不到、黑盒也打不动,最终转哪?
**A5**: 转认证之外的整体流程:自研认证的系统往往其它地方也自研且脆弱(自研 session、自研权限、自研加密),横向找同一开发团队的其它薄弱环节。一个团队的安全水位是相对一致的。
**Q6**: 面对自研认证的正确心态?
**A6**: 自研认证是红队的机会而非障碍——标准协议有全世界审计,自研只有内部几个人审。投入逆向的性价比通常高于死磕标准协议。看到"非标准"应兴奋而非退缩,但要设逆向时间盒避免无底洞。

### 认证 token 在缓存/日志/CDN 的泄露
**Q1**: 直接攻 token 太难,能不能从"哪里会漏 token"入手?
**A1**: 能,且这是被低估的维度。系统性排查 token 泄露点:URL 里带 token 会进 CDN 缓存/日志/浏览器历史/Referer;错误页/调试页回显请求头;监控/APM 记录完整请求;第三方 JS(分析、广告)可读 token。把"偷 token"变成"找漏点"。
**Q2**: CDN/缓存投毒与 token 泄露怎么联动?
**A2**: 若带认证的响应被错误缓存(cache 配置疏漏),下一个用户可能拿到上一个用户带 token/私有数据的缓存响应。测:带 token 请求某资源,看响应是否被公共缓存(`Cache-Control`/`Age` 头),换个身份/无 token 再请求是否拿到他人数据(web cache deception)。
**Q3**: web cache deception 具体怎么构造?
**A3**: 请求一个"看起来是静态资源"的路径(如 `/account/info.css`)让 CDN 按扩展名缓存,但后端仍返回动态的账户数据。若缓存了,受害者访问该路径后其私有数据被缓存,我再访问同路径即取。前提是缓存按后缀、后端不校验后缀。
**Q4**: 目标缓存配置正确、不带 token 进 URL,转哪?
**A4**: 转下游日志/第三方:SIEM/日志平台若可访问(弱口令/未授权 Kibana 等)可搜历史 token;集成的第三方服务(webhook、分析)可能收到含 token 的数据。泄露战场从目标本体转向其数据流经的第三方。
**Q5**: 怎么判断一个泄露出来的 token 还能不能用?
**A5**: 结合前面"生命周期"判断:先看 exp,再实测重放。日志里的历史 token 若系统无状态且不吊销,可能仍有效。泄露 + 长有效期 = 现成凭据,优先于任何伪造尝试。
**Q6**: 这条线怎么规模化收集?
**A6**: 用侦察思维广撒网:搜 git 泄露、公开缓存/存档、JS source map、公开的 CI 日志、Postman 集合、API 文档托管平台。认证攻击不总是"打",很多时候是"捡"——现成 token/secret 满地都是,先捡后打。

### 同源策略与 CORS 配错导致的凭据泄露
**Q1**: 目标 API 用 token 且前后端分离,CORS 配置里我盯什么?
**A1**: 盯 `Access-Control-Allow-Origin` 是否反射任意 Origin,且 `Access-Control-Allow-Credentials: true`。若两者同时成立,任意站点都能带着受害者凭据跨域读取响应——我建个恶意页就能代受害者读取其数据/token。
**Q2**: 怎么快速验证 CORS 可利用?
**A2**: 发请求带自定义 `Origin: https://evil.com`,看响应 ACAO 是否原样反射我的 Origin 且带 credentials。反射 = 可利用。再看是否 null origin、子域通配、正则错误(`example.com.evil.com` 匹配)等宽松变体。
**Q3**: ACAC 是 false 但 ACAO 反射,还有戏吗?
**A3**: 无 credentials 时读不到需认证的响应,但仍可读公开/无需 cookie 的数据,价值降低。若 token 在 body/localStorage 而非 cookie,CORS+credentials 模型不适用,转 XSS 读取。判断凭据承载方式再定攻法。
**Q4**: CORS 配置严格(白名单精确),这条断了转哪?
**A4**: 转 postMessage:跨窗口通信若不校验 origin,可劫持或注入。以及转 CSRF(CORS 挡读不挡写,若无 CSRF token,跨域写操作仍可行)。同源相关攻击面不止 CORS 一处。
**Q5**: postMessage 相关怎么打认证?
**A5**: OAuth/SSO 常用 postMessage 在弹窗和主窗间传 token/code。若接收方不校验 `event.origin`,恶意页可嵌入并窃取传递中的 token;若发送方 targetOrigin 用 `*`,token 可被任意嵌入者截获。审计 SSO 弹窗流的 postMessage 用法。
**Q6**: 这类客户端侧认证泄露怎么定位?
**A6**: 读前端 JS,搜 `postMessage`、`addEventListener('message'`、`document.domain`、CORS 请求配置。客户端认证逻辑全暴露在 JS 里,静态审计比黑盒试探高效。前端分离架构下,JS 就是攻击地图。

### 多步登录的状态机与 response 篡改
**Q1**: 登录是多步的(账号→密码→MFA→设备确认),这种多步流程有什么结构性弱点?
**A1**: 多步流程靠一个"中间态凭据"(临时 token/session)串起各步。弱点在:中间态是否被过度信任、能否跳步、能否在某步注入另一个身份。核心问:第 N 步用的身份和第 1 步是否被绑死。
**Q2**: "response manipulation"在多步登录里怎么用?
**A2**: 拦截某步的响应(如 MFA 校验返回),把 `verified:false` 改 true 或改状态码,看后端是否据此推进。若中间态推进依赖前端回传的结果,即可篡改绕过。判据:改响应后是否进入下一已认证步骤。
**Q3**: 步骤间身份不绑死怎么被利用?
**A3**: 经典:第 1 步提交受害者账号拿到中间 token,第 3 步(MFA/最终确认)却用【我的】MFA/确认,若后端只认中间 token 不复核身份一致性,可能登入受害者。测各步是否重新核对同一 subject。
**Q4**: 这些多步绕过全被后端严格状态机挡住,转哪?
**A4**: 转横向的登录入口多样性:同一账号是否有多条登录路径(密码/OAuth/魔法链接/API),某条路径的状态机可能没那么严。以及转"登录后"——绕不过登录就偷登录后凭据。
**Q5**: 魔法链接(magic link)/无密码登录有什么专门弱点?
**A5**: 链接 token 的熵(可预测则可爆)、是否一次性、是否过期、是否绑定请求发起的设备/会话、以及能否为任意邮箱请求并从旁路获取。无密码登录把安全全押在链接投递与 token 强度上,重点测这两处。
**Q6**: 怎么判断该在多步流程哪一步下重注?
**A6**: 在每步之间设"探针":观察哪一步真正下发了有权限的凭据。攻击应聚焦"权限凭据实际签发的那一步"及其前后接缝,而非在无关紧要的前置步骤浪费精力。定位关键跃迁点是效率核心。

### 权限模型:scope 与 audience 的错配
**Q1**: token 带 `scope`,我怎么找 scope 相关的越权?
**A1**: 先枚举系统所有 scope 值(文档/discovery/对比不同 token)。然后测三类错配:1) 请求 token 时索要超额 scope 是否被授予;2) 服务端是否真的按 scope 限制接口(有 scope 但不 enforce);3) 低 scope token 能否调高 scope 接口。
**Q2**: scope 不被 enforce 怎么确认?
**A2**: 拿一个明确缺某 scope 的 token 去调需要该 scope 的接口。若成功,说明 scope 只是摆设,鉴权没落地。这是常见的"有 OAuth 但没真授权"问题,纯逻辑测试即可发现。
**Q3**: audience 错配怎么利用?
**A3**: 一个 IdP 给多个服务(audience)签 token。若服务 B 不校验 `aud`,可拿服务 A 的 token 访问 B。测:跨服务投喂 token。这在企业多系统共用 SSO 时极常见,能横向打通多个系统。
**Q4**: scope 与 aud 都被严格校验,转哪?
**A4**: 转 scope 之下的资源级越权:即使 scope 对,具体资源 id 的归属校验(IDOR)可能缺失。scope 管"能不能读订单",但"能不能读【别人的】订单"是另一层校验,常被漏。从粗粒度 scope 转细粒度对象鉴权。
**Q5**: consent(授权同意)环节有什么可打?
**A5**: 测 consent 是否可绕过(直接带 scope 请求跳过同意页)、是否 scope upgrade 时不重新征求同意、是否有"已授权应用"被静默复用。以及恶意 client 诱导用户授予过度 scope(钓鱼式 OAuth,类似"OAuth phishing")。
**Q6**: OAuth 钓鱼这条在红队里怎么定位价值?
**A6**: 若目标允许第三方注册 OAuth client 且 consent 文案模糊,可注册一个看似合法的 client 诱导员工授权,拿到其 token/邮箱/数据的长期 offline 访问。这是社工与技术结合的高价值持久化入口,在企业 SSO 环境尤其致命。

### token 内省(introspection)与撤销端点的滥用
**Q1**: 目标暴露了 OAuth token introspection 或 revocation 端点,这有什么可打?
**A1**: introspection(`/introspect`)返回 token 的有效性与元数据,revocation(`/revoke`)可吊销 token。先看这两个端点的认证要求:是否需要 client 凭据、是否任意人可查。无认证的 introspection 是 token 状态泄露与枚举面。
**Q2**: 无认证 introspection 能干嘛?
**A2**: 可用来验证偷来/猜来的 token 是否有效(离线 oracle),甚至枚举 token 的 scope/sub/exp,辅助后续伪造与越权判断。把它当成"服务端免费提供的 token 校验器"来加速其它攻击。
**Q3**: revocation 端点若认证不足有什么危害?
**A3**: 若能吊销任意 token,是拒绝服务/踢人的手段(把管理员踢下线制造混乱),或在红队后期用于清理痕迹/阻断响应方。判据:提交别人的 token 到 revoke 是否成功。
**Q4**: 这两个端点都要求严格 client 认证,转哪?
**A4**: 转 discovery 端点(`/.well-known/openid-configuration`)——它常无认证且泄露所有端点、支持的算法、jwks_uri、grant types。是侦察金矿,能反推出前述所有攻击的入口配置。端点本身攻不动就用它做情报。
**Q5**: discovery 里最该关注哪些字段来指导攻击?
**A5**: `jwks_uri`(拿公钥做 RS→HS/看 kid)、`token_endpoint_auth_methods`(是否允许 `none`)、`grant_types_supported`(有没有多余的 password/implicit)、`response_types_supported`(有没有隐式流)、`scopes_supported`(枚举提权目标)。一份 discovery 就是攻击计划书。
**Q6**: 如果连 discovery 都不暴露,怎么补情报?
**A6**: 转主动枚举:猜常见端点路径、从前端 JS 里抠出配置常量、抓移动 App 的硬编码端点。情报缺失不等于路径不存在,只是需要更主动地挖。转向信息收集的其它渠道而非放弃。

### 从认证漏洞升级为账户接管的收尾
**Q1**: 我已经能伪造/窃取某用户 token 了,怎么把"访问"升级为"接管"?
**A1**: 访问是临时的,接管是持久的。收尾动作:改绑邮箱/手机、重置密码、添加自己的 MFA 设备、生成长期 API key、创建备用管理员。目标是即使原始漏洞被修、原 token 失效,我仍保有账户控制权。
**Q2**: 改绑邮箱时常遇到"需当前密码"怎么办?
**A2**: 找不需要重认证的改绑路径:某些"更新资料"接口改邮箱不要求密码、OAuth 绑定不要求、或改绑邮箱不发确认到旧邮箱(旧邮箱无从察觉)。测各条改绑路径的重认证强度,挑最松的。
**Q3**: 怎么在不惊动真实用户的前提下接管?
**A3**: 红队要评估隐蔽性:改密码/踢出会话会让用户立即察觉。更隐蔽的是加一个备用凭据(API key、次要邮箱、app-specific password、OAuth 授权),不动用户现有登录。潜伏优于强夺。
**Q4**: 如果接管动作触发了通知/告警怎么办?
**A4**: 这是"被墙"信号,转隐蔽持久化:利用无通知的机制(前述 refresh 不轮换、长期 token、session 不失效)。以及评估是否已达成目标(拿到关键数据即撤),避免为持久化而暴露。红队要权衡战果与暴露。
**Q5**: 单账户接管后如何横向到更多账户/系统?
**A5**: 从被接管账户里挖:它的通讯录/共享/团队权限、它保存的其它系统凭据、它作为 SSO 身份能登入的所有下游应用。一个账户在 SSO 生态里是通往整个组织的节点。列出它的信任辐射面。
**Q6**: 收尾阶段最该记录什么给报告?
**A6**: 完整可复现的攻击链(每步 PoC)、影响范围(能接管多少/什么级别账户)、以及最小修复点(哪一个校验缺失是根因)。红队价值不止于"我进去了",而在于"让防守方精准止血"。清晰的根因定位是交付质量的分水岭。

### JWT header 自带公钥(jwk)伪造
**Q1**: header 里直接内嵌了一个 `jwk`(完整公钥对象),这和 jku 有什么本质区别,怎么打?
**A1**: `jku` 是外链 URL,`jwk` 是把公钥直接塞在 header 里。若服务端错误地【信任 header 里自带的这个 key 来验签】,我就自己生成密钥对,把我的公钥填进 `jwk`、用我的私钥签名——服务端拿我给的钥匙验我给的锁,必过。这是无需出网、无需外部资源的自证身份。
**Q2**: 怎么判断服务端是否吃 header 里的 jwk?
**A2**: 构造一个自签 token(自己的 jwk + 自己私钥签),改个权限字段,直接发。若被接受就是致命的验签逻辑缺陷。判据同前:越权接口从 401 变 200。这是所有"密钥来源劫持"里最直接的一种,应优先于 jku 试(如果 header 支持 jwk)。
**Q3**: 服务端不吃自带 jwk,但可能有别的松处吗?
**A3**: 有的实现"header 有 jwk 就用 jwk,否则查本地"——即便正常流程用本地 key,只要它没禁掉 jwk 分支就中招。也测混合:保留原 kid 但加一个我的 jwk,看优先级。解析优先级歧义是这类漏洞的温床。
**Q4**: jwk 被正确忽略/禁用,转哪个同族维度?
**A4**: 转 jku/x5u(外链密钥)、kid(本地密钥来源)。这几个都是"控制验签所用 key 的来源",jwk 死了试其余三个。全死则说明验签 key 硬编码,转 token 逻辑层或 HS 密钥爆破。
**Q5**: 拿下 jwk 伪造后和 jku 伪造战果有何不同?
**A5**: 本质相同(获得签发权),但 jwk 更隐蔽稳定(不依赖我的服务器在线)。用它批量伪造任意身份、探测后端对异常 claim 的处理。战果最大化思路同 jku:枚举权限、打通信任域内所有服务。
**Q6**: 这条链最该提前收集什么信息?
**A6**: 收集目标 JWT 库及版本(响应头、错误信息、行为指纹)。`jwk`/`jku`/`none` 这类缺陷强相关于特定库的特定版本,识别出库就能查它的已知验签缺陷,把黑盒试探变成定向打击。

### 反向代理/网关路径归一化导致的认证绕过
**Q1**: 目标在网关层做认证(受保护路径需 token),我怀疑能绕过网关直达后端,先想什么?
**A1**: 想"网关和后端对同一 URL 的理解是否一致"。认证在网关按路径匹配,若网关和后端对路径的归一化(大小写、`;`、`//`、`..`、`%2e`、尾斜杠、`.json` 后缀)处理不同,我可以构造一个"网关认为是公开、后端解析成受保护"的路径,绕过认证到达敏感接口。
**Q2**: 具体试哪些变形?
**A2**: 对已知受保护路径 `/admin` 试:`/Admin`、`/admin/`、`/./admin`、`/%61dmin`、`/admin;foo`、`/admin/..;/admin`、`/public/../admin`、加 `.json`/`.css` 后缀等。观察哪种既过了网关(不要求 token)又被后端当成受保护资源执行。
**Q3**: 这和 HTTP 请求走私(request smuggling)怎么结合?
**A3**: 若前端代理和后端对请求边界解析不一致(CL/TE 分歧),可走私一个隐藏请求直达后端受保护接口,完全绕过网关认证层。判据:能否让走私请求得到后端响应。这是绕过前置认证的重武器,适合网关与后端异构时。
**Q4**: 路径变形和走私都试遍没绕过,转哪?
**A4**: 说明网关与后端解析一致或后端有独立鉴权。转回"攻破 token 本身"或"内部信任头伪造"(前述跨服务那条)。绕过边界失败就回到打穿凭据。别在归一化上无限枚举,设时间盒。
**Q5**: 怎么先判断"认证到底在网关还是后端"?
**A5**: 对比:直接访问后端端口(若可达)vs 经网关访问、带畸形 Host/路径看认证是否失效。若某些路径无 token 也能拿数据,认证就是纯网关层的、可绕的。搞清认证边界的位置是这条链的前提侦察。
**Q6**: 绕过后如何确认拿到的是真实敏感功能而非假象?
**A6**: 用一个"只有鉴权后才能做的写操作/数据读取"验证真的越权成功,而不是拿到一个空壳页面。区分"绕过了认证路由"与"真正执行了敏感逻辑",避免误报。红队报告要经得起防守方复现质疑。

### 密码重置流程与 Host 头/token 缺陷
**Q1**: 想通过密码重置接管账户,先审查这个流程的哪几个环节?
**A1**: 审四段:1) 重置 token 的生成(可预测?顺序?时间戳派生?);2) token 的绑定(绑不绑用户/一次性/过期);3) 重置链接的构造(是否用请求里的 Host 头拼 URL);4) 重置是否吊销现有 session。每段都是独立接管入口。
**Q2**: Host 头投毒具体怎么利用?
**A2**: 若服务端用请求的 `Host`/`X-Forwarded-Host` 拼重置链接域名,我为受害者请求重置,同时把 Host 改成我的域。受害者收到的邮件里链接指向我域,他一点,重置 token 就发到我这。判据:邮件里的链接域名是否受我控制的头影响。
**Q3**: token 可预测怎么判断和利用?
**A3**: 连续请求多个重置 token 观察规律:是否是自增、时间戳、弱随机(基于 uid+时间)。若可预测,直接为受害者生成/推算 token 完成重置。对比多个样本找熵不足是关键。
**Q4**: token 强随机、Host 不可控、绑定严格,这条被墙了转哪?
**A4**: 转重置流程的逻辑面:重置请求的响应是否泄露 token(某些 API 直接把 token 回显)、重置接口是否可越权指定 uid、重置后旧 session 不失效则配合其它漏洞、以及"重置不需要旧 token 直接改任意账号密码"的 IDOR。逻辑缺陷常绕过密码学强度。
**Q5**: 怎么低风险验证而不真的改掉别人密码?
**A5**: 用自己控制的两个账号演示:证明能拿到 B 账号的有效重置 token 即可,不必真提交新密码把真实用户锁在门外。PoC 到"可控制 token/可越权指定目标"这一步就足以定性,克制是红队职业素养。
**Q6**: 重置接管和前面 OAuth/JWT 攻击怎么协同?
**A6**: 密码重置是"绕过一切登录态强度"的元入口——不管 MFA、SSO、JWT 多强,只要能重置密码就能接管。当所有认证协议层都很硬时,把重置流程当作最后的软肋优先深挖。它常是防御盲区。

### 静态凭据(API key / Bearer)的识别与滥用
**Q1**: 目标用的不是会话式 token 而是静态 API key/长期 Bearer,攻击思路有何不同?
**A1**: 静态凭据不轮换、长期有效、常被硬编码——攻击重心从"伪造/绕过"转为"翻出来 + 判权限边界"。先确认它是静态的(格式固定、无 exp、多次请求不变),然后主攻它的泄露点与权限范围。
**Q2**: 静态 key 最常泄露在哪?
**A2**: 前端 JS/移动 App 硬编码、git 历史与公开仓库、CI/CD 配置与日志、Postman/API 文档、错误信息回显、以及客户端与服务端通信的可截获处。静态凭据的核心风险就是"到处复制导致到处泄露",广撒网搜集。
**Q3**: 捡到一个 key 后如何判断它的权限和归属?
**A3**: 用它调低风险只读接口探边界(userinfo、账户信息),看它代表哪个用户/服务、有哪些权限、是否有 scope 限制。别一上来就调高危接口暴露自己。先摸清"这把钥匙能开哪些门"再动手。
**Q4**: key 权限很小/是只读的,这条就废了吗?转哪?
**A4**: 不废,转"以小博大":小权限 key 也可能泄露内部信息用于下一步、或存在权限提升接口、或同一泄露源里还有更高权限的 key。以及转 key 的可预测性——若 key 生成有规律,可枚举出其它用户的 key。
**Q5**: key 是强随机、权限严格、无处泄露,认证层很硬,最终转哪?
**A5**: 转回业务逻辑与其它认证机制。静态凭据设计良好通常意味着 API 侧成熟,把精力移到 Web UI 侧的会话认证、OAuth 流程、越权 IDOR。多入口体系里,一个入口硬不代表全硬。
**Q6**: 静态凭据类攻击在红队里最该警惕什么操作风险?
**A6**: 静态 key 一旦被使用可能触发异常检测(新 IP/新 UA 调用),且不像会话 token 那样"本就该到处跑"。使用捡来的 key 要评估其正常调用模式,尽量贴近原用途,避免因凭据滥用画像暴露行动。隐蔽性优先。
