# Web · 反序列化漏洞的判定与链构造

### 识别一个入参到底是不是反序列化入口
**Q1**: 面对目标X一个可控参数,里面塞的是一坨看不懂的二进制/base64,我怎么判断它是不是反序列化入口而不是加密数据?
**A1**: 先做编码剥离与魔数比对,这是判定的第一性动作。base64 解码后看头几个字节:`AC ED 00 05`(base64 前缀 `rO0`)是 Java 原生序列化流;`{` 开头是 JSON(可能 fastjson/jackson);PHP 的 `O:数字:"类名"` 是 PHP 序列化;`\x80\x04`/`\x80\x03` 是 Python pickle;`04 08` 附近是 Ruby Marshal。判据是结构规律而非随机熵,加密数据通常高熵无固定头。
**Q2**: 解出来是 gzip 压缩后再 base64 的多层,剥完还是乱码怎么办?
**A2**: 多重编码是常态,按"外到内"逐层剥:base64→gzip/zlib→可能还有一层 base64。写个循环自动探测每层特征字节。剥到出现类名/魔数就停。若剥到底仍是纯高熵二进制且长度是 16 的倍数,倾向对称加密(如 Shiro rememberMe),此时入口在"解密后"而非当前层。
**Q3**: 判据都不满足,像是自研二进制格式怎么办?
**A3**: 转向副信道判据:改动一个字节看服务端报错。反序列化点在异常里常泄露 `ObjectInputStream`、`unserialize()`、`pickle.loads`、`readObject` 之类栈帧或类名,这比盲猜格式更快。
**Q4**: 如果这条路走死——参数改任何字节都稳定 400 且无栈信息?
**A4**: 转向正交维度:不纠结这个参数,回到全站流量测绘。反序列化点常在 Cookie、rememberMe、ViewState、RPC 端口(Java RMI 1099/T3 7001/Hessian)、消息队列反序列化上,换入口面比死磕单参数高效。
**Q5**: 怎么快速确认"它会被反序列化"而不只是被存储?
**A5**: 发一个结构合法但字段异常的 payload(如 Java 里合法流但类不存在),若返回 `ClassNotFoundException` 类语义错误,说明服务端确实在做对象重建——判定成立。

### 确认语言/框架栈以选对武器库
**Q1**: 确认是反序列化点后,我要不要先花力气判语言?
**A1**: 必须先判,因为 gadget 库是强语言绑定的,判错语言等于零。除魔数外,用旁证:响应头 `X-Powered-By`、`Server`、Set-Cookie 名(`JSESSIONID`=Java,`PHPSESSID`=PHP,`ASP.NET_SessionId`=.NET),报错页风格,URL 后缀(`.jsp/.do/.action` vs `.php` vs `.aspx`)。
**Q2**: Java 确认了,还要不要细分框架?
**A2**: 要。Java 下"原生序列化 / fastjson / jackson / Shiro / WebLogic T3 / Dubbo Hessian"打法完全不同。看反序列化流本身:`rO0`=原生;JSON+`@type`=fastjson;JSON+`$type`=Json.NET(其实是.NET);Cookie 名 `rememberMe`=Shiro。
**Q3**: 判到 PHP 但不确定是原生 unserialize 还是 phar?
**A3**: 看是否有显式反序列化参数。若没有可控 unserialize 入口,但有文件操作类函数(file_exists/fopen/getimagesize),转向 phar 反序列化维度——用 `phar://` 触发。
**Q4**: 语言判据互相矛盾(头说 nginx 但流是 Java)怎么办?
**A4**: 以"数据流的魔数"为最高优先级判据,HTTP 头可被反代/CDN 篡改。nginx 只是前置,后端仍可能是 Java 应用服务器。
**Q5**: 完全判不出语言,黑盒无任何指纹?
**A5**: 转向 DNSLog 盲打:对每种语言各发一条"仅触发 DNS 请求不依赖 gadget"的探测(Java URLDNS、PHP DNS via SoapClient/phar、Python 里 os 触发),哪条回连就锁定哪种语言,用探测反推指纹。

### Java 原生序列化确认后无回显盲区
**Q1**: 确认 Java 原生反序列化,但打过去页面无任何变化,我怎么确认能不能利用?
**A1**: 先用不依赖第三方库的 URLDNS 链验证"流被反序列化且能出网"。它只用 JDK 自带类,触发一次 DNS 解析。收到 DNSLog 即证明:入口活、可控、且目标出网——这是最干净的判定探针,不引入 gadget 变量。
**Q2**: URLDNS 收到了 DNS,但换成 CommonsCollections 命令执行链就没反应?
**A2**: 说明"入口通但缺 gadget 依赖"。URLDNS 成功只证明反序列化本身工作,不代表 classpath 里有 CC/Spring 等可用链。转向探测依赖:用 ysoserial 各链逐个盲发,或先探 classpath(见依赖探测链)。
**Q3**: DNSLog 一直不回,是没漏洞还是不出网?
**A3**: 两种可能要分开判。先确认 DNSLog 平台本身可用(自测),再判目标是否内网隔离。改用带内判据:如果某个 gadget 会因类缺失抛不同异常,用响应差异(错误类型/响应时间)做布尔判据,不依赖出网。
**Q4**: 彻底不出网、无回显、无报错差异,盲区太深怎么办?
**A4**: 转向时间侧信道:构造能造成可测延时的链(如触发大对象/递归/sleep 类行为),用响应时间做 1bit 判据确认执行。确认执行后再转向内存马/反连做实回显。
**Q5**: 时间侧信道也不稳定?
**A5**: 换正交入口。同一目标可能有多个反序列化面(RMI/JMX/T3 端口、其他 HTTP 参数),放弃当前盲点,去打有回显潜力的面。

### ysoserial 全链盲发选择策略
**Q1**: 要盲发 ysoserial,几十条链我按什么顺序打才高效?
**A1**: 按"依赖普及度 × 无害探测优先"排序。先 URLDNS/JRMPClient 验通路,再打最常见依赖链:CommonsCollections 系列(1-7,覆盖不同 CC 版本)、CommonsBeanutils、Spring 系列。每条先用 DNS/延时做无害验证,确认哪条触发,再换该链做命令执行,避免一上来就打 RCE 惊动防护。
**Q2**: CC1 不通但 CC6 通,说明什么?
**A2**: 说明目标 JDK 较高或 CC 版本较新。CC1 依赖的 `AnnotationInvocationHandler` 在高版本 JDK 被改造失效,CC6 用 `TiedMapEntry` 绕开该限制、且不挑 JDK 版本。命中 CC6/CC5 通常指向"高版本 JDK + commons-collections 3.1+"环境,后续都用它。
**Q3**: 所有 CC 链都不通,但确认有反序列化?
**A3**: 转向非 CC 依赖:CommonsBeanutils(常随 Shiro/其他框架进 classpath)、C3P0、Rome、Hibernate、Groovy、Clojure。逐个探。命中面往往取决于业务依赖而非通用库。
**Q4**: ysoserial 生成的流打过去报 `invalid stream header` 或 filter 拦截?
**A4**: 前者多半是编码层没对齐(该 gzip/base64 而没做),对齐外层封装再发。后者是 JEP290/自定义 ObjectInputFilter 拦截,转向"filter 绕过"维度(见相关链)。
**Q5**: 全部链都失败,该放弃 Java 原生这条路吗?
**A5**: 先自查工具与 JDK:ysoserial 需用与目标相近的 JDK 编译生成(高版本 JDK 生成的流可能带目标不认的类)。换低版本 JDK 重生成再试。仍不通再转向该端口的其他协议漏洞(如 T3/IIOP 专用打法)或换入口。

### classpath 依赖盲探——不知道有哪些 gadget
**Q1**: 盲发太费时,能不能先探出 classpath 里到底有哪些库再精准选链?
**A1**: 能,思路是"用类是否存在造成可观测差异"。构造一个反序列化流,其成功与否依赖某个特定 gadget 类在不在。类存在→A 行为,不存在→`ClassNotFoundException`。用报错/延时/DNS 差异逐类探测,拼出依赖指纹再精准打。
**Q2**: 报错都被统一异常页吃掉,看不到 ClassNotFoundException?
**A2**: 转用 DNS 差异探针:设计"仅当目标类存在时才走到触发 DNS 的分支"的构造。收到 DNS=类存在,收不到=不存在。把带内判据换成带外判据。
**Q3**: 出网也被封,带外带内都没差异信号?
**A3**: 转时间判据:让"类存在"路径比"不存在"路径慢一个可测量级。多次采样取中位数抗抖动。
**Q4**: 探测成本太高、库太多探不完怎么办?
**A4**: 改策略:不穷举,先按目标技术栈的高频依赖假设(如 Shiro 必带 CommonsBeanutils,Spring 应用大概率有 spring-core)定向验证 3-5 个高价值假设,命中即用,不追求完整测绘。
**Q5**: 探完发现根本没有任何已知可用 gadget?
**A5**: 转向"无 gadget 也能打"的正交维度:URLDNS 做 SSRF、构造大对象做 DoS、或利用反序列化本身的文件/属性副作用。或换成 JNDI 注入类漏洞(若存在 JNDI lookup 面),绕开对本地 gadget 的依赖。

### JEP290 / ObjectInputFilter 被拦
**Q1**: 高版本 JDK 目标,流发过去被 `filter status: REJECTED` 挡下,还有戏吗?
**A1**: 有,但要看 filter 是黑名单还是白名单。先判类型:换不同 gadget 的顶层类试探,若只有个别类被拒、其他能过,是黑名单,找不在名单里的等价链;若几乎所有非白名单类都被拒,是白名单,难度高得多。
**Q2**: 是黑名单,怎么找绕过链?
**A2**: 换"顶层入口类"不同但效果等价的 gadget。很多 filter 只拦了 `InvokerTransformer`/`TemplatesImpl` 等知名类名,换用 CommonsBeanutils、Rome、或经过不同触发路径的链,顶层类名不同即可绕。
**Q3**: 是白名单,几乎打不动?
**A3**: 转向"协议层/应用层自带的白名单内可利用类"。某些中间件白名单里仍保留了业务必需但可被滥用的类(如特定 RPC 的解析类),或走二次反序列化——外层用白名单允许的容器类,内层再触发一次反序列化绕过外层 filter。
**Q4**: 二次反序列化怎么落地?
**A4**: 找一个白名单允许、但其内部会对某个字节数组再次调用反序列化的类(如某些 Hessian/自定义 readObject 嵌套)。外层过 filter,内层的反序列化可能不受同一 filter 约束。这是绕 filter 的经典正交面。
**Q5**: 全都不行,filter 是严格全局白名单?
**A5**: 放弃这个反序列化点,转向该目标的其他攻击面。严格白名单 filter 是强防御,红队应把时间投入到更软的入口(其他服务、逻辑漏洞),而不是硬啃。

### PHP unserialize + POP 链构造
**Q1**: PHP 目标有可控 `unserialize`,但我不知道有哪些类能用,怎么起手构造 POP 链?
**A1**: 先摸清可用类与魔术方法。反序列化能自动触发的是 `__wakeup`、`__destruct`;后续靠 `__toString`(对象被当字符串)、`__get/__set`、`__call` 串联。判据是:从一个"反序列化即执行"的魔术方法出发,找到能推进到危险 sink(system/eval/file_put_contents/call_user_func)的属性调用路径。
**Q2**: 有源码但类太多,怎么快速定位链头链尾?
**A2**: 双向搜。链尾:grep 危险函数(system/exec/eval/include/file_put_contents/unserialize)反查是谁调用它;链头:grep `__destruct`/`__wakeup`。中间用 `__toString`/`__call` 等把头尾接起来。工具化可用 phpggc 直接生成常见框架(Laravel/Symfony/ThinkPHP 等)的现成 POP 链。
**Q3**: 没有源码,纯黑盒 PHP 反序列化?
**A3**: 转向已知框架链盲打:根据指纹判框架版本,用 phpggc 对应版本链盲发。判据是响应差异。黑盒下自建 POP 几乎不可行,依赖公共链库。
**Q4**: `__wakeup` 拦了我的利用(校验/重置属性)怎么办?
**A4**: 经典绕过:当序列化字符串里对象属性个数标注 **大于** 实际个数时,老版本 PHP(<5.6.25/<7.0.10)会跳过 `__wakeup`。改 `O:4:"Xxxx":N` 里的 N 使其大于真实属性数即可绕。高版本此洞已修,转下条。
**Q5**: 高版本绕不过 __wakeup,或根本没有可用 __destruct?
**A5**: 转 phar 维度或找 `__destruct` 之外的触发点。或利用字符串逃逸/属性注入(见字符逃逸链)。若都无路,转向该参数是否还能做别的(SQLi/文件包含),不困在反序列化。

### PHP phar 反序列化(无显式 unserialize)
**Q1**: PHP 目标没有可控 unserialize,但有文件操作函数,能不能打反序列化?
**A1**: 能,走 phar。`phar://` 伪协议在被文件类函数(file_exists/is_dir/fopen/getimagesize/file_get_contents 等)处理时,会自动反序列化 phar 文件 meta-data 里的对象,触发 POP 链。判据:目标是否有"文件路径可控 + 能上传或写入任意内容文件"。
**Q2**: 怎么把恶意 phar 送进目标?
**A2**: 需要一个文件上传点(哪怕限制了后缀)。phar 可伪装成任意后缀(改成 .jpg/.gif),因为触发靠的是 `phar://` 协议解析而非文件扩展名。上传后用文件函数以 `phar://path/to/file.jpg` 引用它。
**Q3**: 上传有图片格式校验(getimagesize 检查)?
**A3**: 构造 phar 时在文件头前塞合法图片魔数(如 GIF89a),做成"图片+phar"多态文件。getimagesize 认头部为合法图片,phar 解析器仍能读到后面的 phar 结构。
**Q4**: PHP 8+ 目标,phar 还灵吗?
**A4**: PHP 8 对 phar 反序列化触发做了收紧(部分函数不再自动反序列化 meta-data)。判据变严:优先找仍会触发的函数。若全被堵,转向其他反序列化面或放弃 phar。
**Q5**: 没有任何文件函数接收可控路径,phar 完全无触发点?
**A5**: 转正交面:找显式 unserialize、或 SSRF 里能否用 phar,或换整条攻击链(上传本身若能直接落 webshell 就不必绕 phar)。

### PHP 字符逃逸(反序列化字符串注入)
**Q1**: 目标对 unserialize 前的数据做了字符串替换(如过滤后长度变化),这能利用吗?
**A1**: 能,这是反序列化字符逃逸。当替换导致字符串"变长或变短",会打乱序列化格式的长度标注,让攻击者可控地"吃掉"或"注入"后续对象属性。判据:是否存在"反序列化前的 str_replace 等使字节数发生变化"。
**Q2**: 变长逃逸(过滤后字符变多)怎么利用?
**A2**: 每多出 1 字节,就能"顶出"1 字节让我可控注入。用足量可被替换的字符,把多出的空间填成一个伪造的属性/对象序列化片段,从而注入本不该由我控制的属性值。
**Q3**: 变短逃逸(过滤后字符变少)呢?
**A3**: 变短是把后面的合法数据"吸进"某个字符串属性里。构造时把要注入的属性序列化片段放在被吞区域之后,让长度错位后正好让我的片段被当成独立属性解析。
**Q4**: 算不清偏移,构造总是反序列化失败?
**A4**: 转向本地复现:把目标的过滤逻辑在本地 PHP 复刻,逐字节调偏移直到 `unserialize` 返回预期对象。反序列化格式对长度极敏感,必须本地精确对齐,不要在目标上盲试。
**Q5**: 目标过滤不改变长度(等长替换)?
**A5**: 等长替换不产生逃逸,此路不通。转向标准 POP 链/phar,或找其他不经过该过滤的反序列化入口。

### Python pickle 判定与利用
**Q1**: 看到 `\x80\x04`/base64 里像 pickle,怎么确认并利用?
**A1**: pickle 极易利用,因为 `__reduce__` 可直接返回 `(os.system, ('cmd',))` 实现任意执行,几乎不需要 gadget 链。先确认目标确实 `pickle.loads` 可控输入(而非 json),再构造带 `__reduce__` 的类做无害探测(DNS/延时)。
**Q2**: 怎么无害验证再上 RCE?
**A2**: 先让 `__reduce__` 返回一个只触发 DNS 或延时的调用,确认执行后再换命令。pickle 太强,直接打 RCE 风险大,先探活。
**Q3**: 目标用 `pickle` 但加了限制(自定义 `find_class` 白名单/RestrictedUnpickler)?
**A3**: 转向白名单内可滥用的类。若只允许特定模块,寻找该模块内能间接触发执行/文件操作的可调用对象。或找白名单里能二次加载代码的类(如允许了某些能 eval/import 的对象)。
**Q4**: 根本不是 pickle,是 PyYAML/jsonpickle?
**A4**: 换判据与打法。PyYAML `yaml.load`(非 safe_load)可用 `!!python/object/apply:os.system` 执行;jsonpickle 反序列化 `py/object` 可实例化任意类。看数据格式特征切换武器。
**Q5**: 全部是 safe 反序列化(json/safe_load),没有代码执行面?
**A5**: 转正交:safe 反序列化仍可能有类型混淆/DoS/键覆盖逻辑漏洞,但 RCE 无望。放弃反序列化 RCE 思路,回到目标其他攻击面。

### .NET 反序列化判定
**Q1**: .NET 目标,怎么判断有没有反序列化面以及是哪种?
**A1**: .NET 反序列化分几类,判据不同:`BinaryFormatter`(二进制,`AAEAAAD` base64 特征)、`Json.NET` 带 `$type`(TypeNameHandling 不当)、`ViewState`(ASP.NET `__VIEWSTATE` 参数)、`LosFormatter`、`NetDataContractSerializer`。先看数据格式与参数名定位类型。
**Q2**: 定位到 Json.NET 且响应里有 `$type`,怎么利用?
**A2**: 若服务端 `TypeNameHandling` 非 None,可用 `$type` 指定任意类型触发 gadget(如 `ObjectDataProvider` 调用任意方法)。用 ysoserial.net 生成对应 formatter 的 payload。判据是能否注入 `$type` 且被解析。
**Q3**: 是 ViewState,但需要 machineKey?
**A3**: 转 machineKey 维度。ViewState 反序列化利用需要有效 `validationKey/decryptionKey`(除非 `enableViewStateMac=false`)。key 来源:配置文件泄露、已知默认/弱 key、其他漏洞读到 web.config。拿到 key 用 ysoserial.net 的 ViewState 插件生成。
**Q4**: 拿不到 machineKey,ViewState 打不了?
**A4**: 判断 `enableViewStateMac` 是否关闭(老应用/特定配置)。若关闭则无需 key。否则转向其他 .NET 反序列化面或放弃 ViewState,不要在爆破 key 上耗时(现代 key 强度爆破不现实)。
**Q5**: ysoserial.net 各 formatter 链都不通?
**A5**: 转正交:.NET 下 gadget 依赖运行时可用程序集。换 formatter/gadget 组合逐试(TypeConfuseDelegate、ObjectDataProvider、WindowsIdentity 等)。仍不通则换攻击面。

### Node.js 反序列化
**Q1**: Node 目标,怀疑有反序列化,怎么判?
**A1**: Node 常见危险库:`node-serialize`(`unserialize`)、`funcster`、`serialize-to-js`。特征是序列化数据里带 `_$$ND_FUNC$$_` 或函数字符串。利用点是 `node-serialize` 会执行序列化进去的立即执行函数(IIFE)。
**Q2**: 怎么构造 payload?
**A2**: 在对象某属性放 `"_$$ND_FUNC$$_function(){...}()"`,反序列化时该函数被 eval 并因结尾 `()` 立即执行。里面用 `require('child_process').exec` 反连。先做无害 DNS/延时验证。
**Q3**: 目标用的是安全的 JSON.parse,没有函数反序列化?
**A3**: JSON.parse 本身不执行代码,无此面。转向原型链污染(prototype pollution)——若目标对反序列化后的对象做递归 merge,`__proto__` 注入可能间接 RCE。这是 Node 反序列化的正交高价值面。
**Q4**: 原型链污染确认了但找不到从污染到 RCE 的 gadget?
**A4**: 找模板引擎/子进程 spawn 的可污染选项(如 EJS/Pug 的编译选项、child_process 的 shell 参数)。污染到这些"配置属性"才能升级为 RCE。判据是应用后续是否读取被污染的原型属性。
**Q5**: 都不成立?
**A5**: 转回常规:Node 应用的 SSRF/命令注入/路径穿越往往比反序列化更易得手,不困在此。

### fastjson autoType 判定与版本探测
**Q1**: Java JSON 入口带 `@type`,怀疑 fastjson,我先做什么?
**A1**: 先判是否 fastjson 及大致版本,因为不同版本 autoType 开关与绕过手法天差地别。用 DNS 探针:提交一个 `@type` 指向会触发 DNS 的类(如 JdbcRowSetImpl/JNDI 类或探测类),看是否回连,同时用异常回显反推版本区间。
**Q2**: DNS 回连了,说明什么?
**A2**: 说明 autoType 至少对该类放行,存在利用面。接着确认能不能升级到 JNDI RCE:让 `@type` 指向 `JdbcRowSetImpl` 并设 `dataSourceName` 为我方 RMI/LDAP。JNDI 注入是 fastjson 到 RCE 的主路径。
**Q3**: 目标 fastjson 版本较高,autoType 默认关、常见类被 ban?
**A3**: 转向绕过维度:不同版本有不同 bypass(如利用 `Class` 缓存、异常类、`java.lang.` 前缀混淆、`L;` 包裹、双写等历史绕过)。判据是版本号——先精确定位版本再选对应公开 bypass,不要乱试。
**Q4**: JNDI 打过去,目标 JDK 高版本不加载远程 class?
**A4**: 转 JNDI 高版本绕过维度(见 JNDI 链):本地 factory、EL、Groovy、Tomcat/Spring BeanFactory 等不依赖远程 codebase 的利用。
**Q5**: 全被拦,确认不了 fastjson 或打不动?
**A5**: 换 jackson(`@class`/`enableDefaultTyping`)判据,或确认是否为 fastjson2(格式与绕过又不同)。仍无果转其他攻击面。

### Shiro rememberMe 反序列化
**Q1**: 看到 `rememberMe` Cookie,怎么判断是不是 Shiro 反序列化面?
**A1**: 特征极明显:登录相关请求 Set-Cookie 含 `rememberMe=deleteMe`,或 Cookie 里有名为 `rememberMe` 的长 base64。Shiro 把序列化对象 AES-CBC 加密后放 Cookie,反序列化前先解密。判定链:确认存在 rememberMe → 需要 AES key → 才能触发反序列化。
**Q2**: 怎么拿到 AES key?
**A2**: 先爆破已知默认/泄露 key 集合(历史版本硬编码默认 key 广为流传,以及各类泄露 key 字典)。判据:用候选 key 加密一个 payload,若返回 **不含** `rememberMe=deleteMe`(即解密成功未抛异常),说明 key 命中。这是无 gadget 的纯 key 探测。
**Q3**: key 爆破全不中怎么办?
**A3**: 转向 key 泄露渠道:配置文件、源码泄露、其他漏洞读文件。Shiro key 若是随机生成的强 key,离线爆破不现实,必须靠泄露拿到,不要死磕爆破。
**Q4**: key 拿到了,但反序列化 gadget 打不通?
**A4**: 早期 Shiro(1.2.4-)可用 CommonsCollections;但 Shiro 默认依赖是 CommonsBeanutils,所以优先 CB 链。判据:Shiro 环境几乎必带 commons-beanutils,用 ShiroAttack 类工具跑 CB 链命中率最高。
**Q5**: key 对、CB 链也不通,可能是高版本 Shiro?
**A5**: 高版本(1.4.2+)默认改 AES-GCM,老的 CBC padding 绕过失效,且可能有 filter。转向:确认加密模式(GCM 需不同构造),或换该应用其他攻击面。Shiro key 泄露常伴随其他配置泄露,顺藤摸别的。

### JNDI 注入高版本绕过
**Q1**: 反序列化/fastjson/log4j 类漏洞让我能控制 JNDI lookup,但目标 JDK 高版本不加载远程 codebase,怎么办?
**A1**: 高版本 JDK(8u191+/11+)默认 `com.sun.jndi.ldap.object.trustURLCodebase=false`,不再从远程 URL 加载 factory class。转向"本地 gadget"利用:让 LDAP/RMI 返回一个引用本地 classpath 中已存在、且能被滥用的 factory,不依赖远程加载。
**Q2**: 本地 factory 具体找什么?
**A2**: 经典是 `org.apache.naming.factory.BeanFactory`(Tomcat 自带)配合 `javax.el.ELProcessor`,通过 EL 表达式执行命令;或 Groovy/Spring 环境下的对应 bean。判据:目标 classpath 有没有 Tomcat/Spring/Groovy 这类含可滥用 factory 的依赖。
**Q3**: 目标既非 Tomcat 也无 EL/Groovy?
**A3**: 转向反序列化型 JNDI:让 LDAP 返回一个带 `javaSerializedData` 属性的条目,客户端会反序列化它——这又回到"本地 gadget 链"(CC/CB 等)。等于用 JNDI 当反序列化触发器,绕过 codebase 限制。
**Q4**: 反序列化 JNDI 也被 filter 拦?
**A4**: 转 RMI 路径试试(RMI 与 LDAP 的 JEP 限制时间线不同,某些版本 RMI 仍可绕);或结合本地 factory + 反序列化双重尝试。逐一换协议是这里的正交动作。
**Q5**: 全部高版本防护到位,JNDI 彻底打不动?
**A5**: 放弃 JNDI RCE 路径,退回用同一漏洞做低危利用(SSRF 探内网、DNS 出网测绘),或换攻击面。承认 JNDI 在现代 JDK 已大幅收窄,不硬啃。

### 无回显无出网——反序列化打内存马
**Q1**: 确认能反序列化 RCE 但无回显、不出网,命令执行了看不到结果,怎么拿实控制?
**A1**: 转向内存马(无文件 webshell)。既然能执行 Java 代码,就不必反连,而是在当前 JVM 里动态注册一个恶意 Servlet/Filter/Listener/Interceptor,后续用普通 HTTP 请求带特定 header/参数即可触发命令并回显。判据:目标是 Web 中间件(Tomcat/Spring/WebLogic),能拿到其上下文。
**Q2**: 反序列化只能执行一小段,怎么塞进完整内存马?
**A2**: 用 gadget 执行一段 loader:通过反射拿到当前线程的 `StandardContext`/Spring `WebApplicationContext`,动态注册 Filter/Controller。代码长可先反序列化写入一个 defineClass 的 bytes,或分段。核心是"用最小执行权限拿到容器上下文"。
**Q3**: 拿不到容器上下文(非标准 Web 容器)?
**A3**: 转 Agent 型内存马:用 Java Instrumentation/JVMTI,通过 `Runtime` 加载 agent 或用 `ClassLoader` 直接 defineClass 注入。或退一步用最朴素的"写文件 webshell"若有可写目录。
**Q4**: 连内存马都注入失败(高版本安全管理器/RASP 拦截)?
**A4**: 转向 RASP 绕过或降级目标:先用执行能力关掉/致盲 RASP(若可),或改用 RASP 不 hook 的执行原语。若 RASP 太强,转正交——用当前执行能力做内网侦察(读环境变量/配置/凭据)横向,而非硬拿这台的稳定 shell。
**Q5**: 什么都被拦,连命令都执行不了实质动作?
**A5**: 回退到最低价值利用:确认漏洞存在即可作为据点情报,转打同网段其他更软的目标,不在硬目标上无限投入。

### 黑盒模糊测试定位反序列化点
**Q1**: 大站黑盒,不知道哪里有反序列化,怎么高效找?
**A1**: 先枚举高概率位置:所有 base64/十六进制形态的参数、Cookie、隐藏表单字段、RPC/自定义协议端口、消息队列。对每个批量发"通用探测 payload"(各语言的 DNS 触发 payload),用 DNSLog 收哪个位置回连。批量带外探测是黑盒定位的主武器。
**Q2**: DNSLog 收到回连,但不知道是哪个参数触发的?
**A2**: 用唯一子域标记每个 payload(`param1.xxx.dnslog`),回连子域直接指向来源参数。这是黑盒批量测试的必备技巧,一次性打完再看哪个域名回来。
**Q3**: 目标不出网,DNSLog 全无?
**A3**: 转带内差异 fuzz:对疑似反序列化参数发"合法头 + 损坏体",看响应是否出现反序列化特征异常(类名/栈)。用响应差异而非带外信号定位。
**Q4**: 响应被统一错误页吃掉,无差异?
**A4**: 转时间差异 fuzz:某些反序列化在处理特定构造时耗时异常,用响应时间聚类找出"行为不同"的参数。
**Q5**: 全都无信号,fuzz 无产出?
**A5**: 转情报驱动:从指纹/版本/开源代码定位该框架已知反序列化 CVE 的确切入口路径,定点打,而不是继续盲 fuzz。黑盒 fuzz 无果时,已知漏洞的精确复现更划算。

### gadget 类加载了但执行报错——依赖冲突调试
**Q1**: 我的 gadget 顶层类被目标接受(没报 ClassNotFound),但执行时抛别的异常没 RCE,问题在哪?
**A1**: 大概率是链中间某个类的**版本**与本地不一致,导致字段/方法签名对不上。判据:异常是 `NoSuchMethodError`/`NoSuchFieldException`/`InvalidClassException(serialVersionUID mismatch)` 而非 ClassNotFound——说明类在但版本错位。
**Q2**: `InvalidClassException: serialVersionUID mismatch` 具体怎么解?
**A2**: 目标那个类的版本与我生成 payload 用的版本不同,serialVersionUID 不匹配被拒。对策:探出目标的确切依赖版本(报错常泄露版本,或从前端资源/错误页推断),用相同版本库重新生成 gadget。
**Q3**: 探不出精确版本?
**A3**: 转多版本轰炸:用一组常见版本分别生成同一链批量发,命中即成。反序列化对版本敏感,穷举版本比精确探测有时更快。
**Q4**: 换了版本还报中间类方法不存在?
**A4**: 说明该链在目标环境不完整,换一条对版本不敏感的等价链(不同 gadget 对版本容忍度不同)。或换触发路径绕过缺失的中间类。
**Q5**: 所有版本、所有链都卡在执行阶段?
**A5**: 转向"仅需类加载不需完整执行"的利用:如 TemplatesImpl 自带字节码执行,不依赖第三方链的完整性;或退回 URLDNS 做 SSRF/DoS。承认这条 RCE 链在此环境不通,转正交。

### 反序列化点确认但输入不完全可控
**Q1**: 代码里有 readObject,但输入似乎经过了部分校验/包装,不确定我能完全控制字节流,怎么判?
**A1**: 做污点边界测试:改变输入不同区段,观察哪些改动能影响反序列化结果、哪些被校验拦下。判据是"我能否让第一个字节就是我的对象头"。若前面有固定包装(长度头/签名),需先满足包装格式。
**Q2**: 前面有个签名/HMAC,改字节就被拒?
**A2**: 这是"带签名的反序列化"——没有签名密钥就构造不出合法流。转向拿密钥(配置泄露/弱密钥/其他漏洞读文件),或找是否有不校验签名的旁路入口。签名是硬门槛,别硬撞。
**Q3**: 只是长度前缀,不是签名?
**A3**: 那容易:按格式补对长度前缀即可,可控。构造时用本地复现对齐前缀格式再发。
**Q4**: 输入被反序列化成固定类型,`@type`/类不可换?
**A4**: 若类固定但字段可控,转"该固定类自身的字段是否能引出危险行为"(如字段是 URL/文件路径引出 SSRF/文件读)。不能换类时,在允许的类里找副作用。
**Q5**: 完全不可控,纯服务端内部数据?
**A5**: 不是攻击面,别浪费时间。转向真正外部可控的输入点。判定"可控性"是避免在死点耗时的关键。

### 二次/嵌套反序列化(Hessian/Kryo/自定义)
**Q1**: 遇到 Hessian/Kryo 等非原生 Java 序列化,ysoserial 的原生链用不了,怎么办?
**A1**: 换协议专用 gadget。Hessian 有自己的 gadget 生态(利用其在反序列化时调用的 map/comparator 触发链,如 Rome、SpringPartiallyComparableAdvisorHolder 等)。判据:先确认是 Hessian(特征字节)再选 Hessian 专用链,不要套原生链。
**Q2**: Hessian 专用链也被 filter 拦?
**A2**: 转二次反序列化思路:让 Hessian 反序列化触发一次"内层原生反序列化"(某些类在 readResolve 里调 ObjectInputStream),用 Hessian 白名单类做外壳,内层打原生 gadget 绕过外层限制。
**Q3**: Kryo/Protostuff 这类呢?
**A3**: 这些默认不像原生那样通用可利用,判据是目标是否开启了"注册任意类/多态"。若关闭多态,反序列化 RCE 面很小,转向逻辑漏洞。
**Q4**: 中间件用了 Dubbo/RMI 承载这些序列化?
**A4**: 转 RPC 层打法:Dubbo 支持多种序列化(Hessian2 默认),直接打其反序列化端口,用 Dubbo 专用链。判据是端口协议指纹。
**Q5**: 全部非原生序列化都无可用链?
**A5**: 转向该 RPC/中间件自身的已知 CVE(认证绕过、其他 RCE),或换攻击面。非原生序列化 RCE 门槛高,不是每个都能打通,及时转向。

### 反序列化落地写 webshell 的路径决策
**Q1**: 我能通过反序列化写文件,想落个 webshell,但不知道写哪个路径,怎么定?
**A1**: 先确定 web 根目录。判据来源:报错页泄露的绝对路径、默认安装路径(按中间件/OS 组合推断)、其他漏洞读到的配置。写到 web 可访问且可执行脚本的目录才有意义,盲写无用。
**Q2**: 拿不到 web 根路径?
**A2**: 转向"不依赖路径"的利用:内存马(无需落盘)、反连、或写到已知的固定可解析目录(某些中间件有可预测的上传/临时目录)。写文件 webshell 是路径依赖最强的方式,拿不到路径就换无路径方案。
**Q3**: 知道路径但目录不可写?
**A3**: 转其他可写目录:临时目录、日志目录、上传目录。若日志目录可写且日志会被当脚本解析(少见配置),或结合日志包含。否则回到内存马。
**Q4**: 写进去了但脚本不被解析(静态目录/权限)?
**A4**: 说明该目录不在脚本处理器映射内。换到确认能执行脚本的目录(通常是应用主目录)。判据:先写个探测文件用浏览器访问确认能否解析。
**Q5**: 所有可写目录都不解析脚本?
**A5**: 放弃 webshell,转内存马或直接命令执行做横向。落地 webshell 只是手段之一,不是目的,拿到执行能力后按环境选最省事的持久化。

### 从"疑似 XXE/SSRF"误判反序列化
**Q1**: 我以为是反序列化,但打了半天没反应,怎么排查是不是判错了漏洞类型?
**A1**: 回到判定源头复核魔数与语言。XML 数据看着也可能被误判;`<`开头是 XML(XXE/XStream),不是原生序列化。XStream 虽然"反序列化 XML"但打法(用 XML gadget)完全不同。判错类型是最常见的浪费时间原因。
**Q2**: 确认是 XStream(XML 反序列化)?
**A2**: 转 XStream 专用链:利用其可实例化任意类 + 动态代理触发 EventHandler/命令执行链。判据是 XML 里能否注入任意类型标签。与 Java 原生链不通用。
**Q3**: 是 XML 但不是 XStream,是普通解析?
**A3**: 转 XXE 维度:外部实体读文件/SSRF/带外。不是反序列化面。及时切换漏洞类型的心智模型。
**Q4**: 数据是 JSON 但我一直当原生二进制打?
**A4**: 停下,重判。JSON 反序列化(fastjson/jackson/Json.NET)与二进制原生序列化武器完全不同。花 1 分钟重做魔数/格式判定,胜过盲打 1 小时。
**Q5**: 反复判不准类型?
**A5**: 转最笨但可靠的办法:每种类型各发一个该类型专属的无害探针(不同魔数/格式),哪个探针引起服务端行为变化,就是哪种。让目标自己告诉你类型。

### 反序列化触发 SSRF/内网测绘(无 RCE 时的价值)
**Q1**: 反序列化打不出 RCE,但能触发 URLDNS/网络请求,这还有什么用?
**A1**: 转 SSRF 维度榨取价值。URLDNS 类链让服务端发起可控 DNS/HTTP 请求,可用来:探测内网存活主机、探云元数据(169.254.169.254)、打内网未授权服务。RCE 不成不代表这个洞没价值。
**Q2**: 只能触发 DNS 不能发完整 HTTP?
**A2**: DNS-only 仍可做内网主机名解析探测、数据外带(把信息编码进子域名)。判据:能否控制被解析的域名。能就能做带外数据外带。
**Q3**: 能发 HTTP,怎么升级?
**A3**: 转向内网服务利用链:SSRF 打内网 Redis/未授权 RPC/管理接口,可能从 SSRF 二次升级到 RCE。反序列化 SSRF 是内网跳板,不止于探测。
**Q4**: 内网全隔离,SSRF 也够不到有价值目标?
**A4**: 转数据外带/云元数据:即使只够到本机 metadata,也可能拿到云凭据横向。把 SSRF 指向本地/元数据端点而非远端内网。
**Q5**: 连出站都完全封死?
**A5**: 该洞降级为"漏洞存在性情报",记录后转其他面。不是每个反序列化点都能变现,承认并转向。

### log4j 类"表达式/lookup 注入"与反序列化的区分
**Q1**: 我在找反序列化,但发现某输入会被当表达式解析(如 `${...}`),这算反序列化吗?
**A1**: 不算,但同样高危,别混淆。`${jndi:...}`/SpEL/OGNL/EL 是表达式注入,触发 JNDI/直接执行,机制不同但常与反序列化共享 JNDI 利用后端。判据:输入里 `${}`/`#{}`/`%{}` 被求值就是表达式注入。
**Q2**: 确认表达式注入能触发 JNDI?
**A2**: 复用前面的 JNDI 利用链(远程 codebase 或本地 factory,视 JDK 版本)。表达式注入是"触发器",JNDI 利用是"载荷",后半段与 fastjson JNDI 完全相同。
**Q3**: 表达式被 WAF 拦 `jndi`/`${}` 关键字?
**A3**: 转表达式层混淆:各类 lookup 嵌套/大小写/环境变量拼接绕关键字,或换非 JNDI 的表达式利用(直接 SpEL/OGNL 执行,不走 JNDI)。绕过在表达式语法层做。
**Q4**: JDK 高版本 JNDI 打不动?
**A4**: 若是 SpEL/OGNL,本就不必依赖 JNDI,直接用表达式调 `Runtime.exec` 执行,绕开 JDK 的 JNDI 限制。这是表达式注入比 log4j-jndi 更灵活之处。
**Q5**: 表达式被沙箱限制(只读求值)?
**A5**: 转数据泄露:用表达式读环境变量/系统属性/配置(可能含凭据),即使不能 RCE。或转回真正的反序列化面。

### WAF 拦截序列化流的绕过
**Q1**: 我的 Java 序列化 payload 被 WAF 基于特征(如 rO0/类名)拦了,怎么绕?
**A1**: 序列化流有多种等价编码可扰乱特征。先试:去掉不必要的 base64 换 raw、改变 gzip 与 base64 的层序、利用 Java 序列化协议里对同一对象的多种合法表示(TC_ 标记变体)。目标是让静态特征匹配失效而流仍合法。
**Q2**: WAF 拦的是类名字符串(明文类名)?
**A2**: Java 序列化流里类名默认明文。转向"减少明文类名暴露"的链,或用序列化协议的 reference 机制/字符串 block 分片打断连续类名特征。某些工具支持流混淆。
**Q3**: WAF 拦 Content-Type/参数位置?
**A3**: 转投递方式:换请求方法、换参数位置(body↔cookie↔header)、分块传输、charset 混淆。有时同一 payload 换个位置就过了。这是投递层正交动作。
**Q4**: 流混淆后目标反序列化也失败了?
**A4**: 说明混淆破坏了流合法性。回退:反序列化对格式极敏感,混淆必须保持流可解析。本地验证混淆后的流仍能 readObject 再发,不要在目标上盲改。
**Q5**: WAF 太强,任何序列化特征都拦?
**A5**: 转攻击面:去打不经过该 WAF 的入口(内网 RPC 端口、其他子系统),或换非序列化漏洞。硬绕强 WAF 性价比低。

### Ruby 反序列化(Marshal/YAML)
**Q1**: Ruby/Rails 目标,怀疑反序列化,判据是什么?
**A1**: 特征:Marshal 数据以 `\x04\x08` 开头(base64 后 `BAg`);Rails 的 cookie/session 可能是 Marshal。YAML(`yaml.load`)也可反序列化对象。判据是数据头 + 框架(Rails/Sinatra)。
**Q2**: 是 Marshal 且可控,怎么利用?
**A2**: 用公开的 Ruby universal gadget 链(通过 `Gem::Requirement`/`Gem::DependencyList` 等触发)实现 RCE。判据:目标 Ruby/Rails 版本对应的链是否可用。
**Q3**: 是 Rails cookie 但有签名(secret_key_base)?
**A3**: 与 Shiro 类似——需要 `secret_key_base` 才能伪造。转向拿 secret(配置泄露/源码/其他漏洞)。签名有效时无 key 不可伪造,别硬撞。
**Q4**: 是 YAML.load?
**A4**: 转 YAML 特有利用:`!ruby/object:` 标签实例化任意类触发链。若目标用 `safe_load` 则无对象反序列化,转其他面。
**Q5**: 全被安全反序列化/签名挡住?
**A5**: 转 Rails 其他经典面(mass assignment、动态 render、SQLi),Ruby 反序列化不通时框架层往往还有别的路。

### 判定反序列化是否真的"到达 sink"
**Q1**: payload 发出去有异常回显,但我不确定是"反序列化到危险 sink 了"还是"只是解析报错",怎么区分?
**A1**: 看异常发生的深度。若异常栈在 `readObject`/`resolveClass` 早期,是入口层拒绝(filter/类不存在),未到 sink;若异常在 gadget 链中间类的方法里(如 InvokerTransformer/TemplatesImpl 相关),说明已深入到链执行阶段,接近 sink。栈深度是判据。
**Q2**: 看不到栈,只有布尔式成功/失败?
**A2**: 用"分段验证"链:先发只走到链一半就触发 DNS 的构造,再发走到底触发 DNS 的。哪段的 DNS 回连,就知道链推进到哪。把黑盒 sink 判定拆成可观测的分段。
**Q3**: 中间段回连、最后段不回连,卡在链尾?
**A3**: 链尾类在目标缺失或版本不符。转向换等价链尾(不同的最终 sink 类),或换整条链。定位到"卡在哪一段"后针对性换,而非整链盲换。
**Q4**: 连第一段都不回连?
**A4**: 说明入口就没吃进去——回退检查可控性/编码层/filter,而不是继续调链。判定卡点在入口还是链内,决定往哪个方向修。
**Q5**: 分段验证都做不了(无出网无差异)?
**A5**: 转时间分段:让不同链段有不同延时。仍不行则转其他入口,不在盲区里穷调。

### 反序列化配合内存马后的横向决策
**Q1**: 反序列化拿到内存马/命令执行了,下一步该干嘛,直接横向吗?
**A1**: 先做本机情报采集再决定,别急着乱扫惊动 IDS。优先读:应用配置(DB/Redis/中间件凭据)、环境变量、云元数据、`~/.ssh`、history、内网 hosts。反序列化落点常是应用服务器,配置里的凭据是最快的横向燃料。
**Q2**: 拿到 DB/Redis 凭据了,怎么用?
**A2**: 判断是否复用:应用凭据常在内网多处复用。用它连内网 DB/Redis,Redis 未授权/主从复制可再落一个点。凭据复用是内网横向的第一杠杆。
**Q3**: 权限是低权 web 用户,横向受限?
**A3**: 先本机提权(SUID/内核/服务配置/计划任务)拿高权,再横向。或不提权直接用采到的凭据横向到其他机器(横向不一定需要本机 root)。两条路并行评估哪条更近。
**Q4**: 内网被严格分段,这台够不到别的?
**A4**: 转把这台做跳板/隧道(端口转发/socks 代理),让后续工具经它触达内网。分段网络里,落点的价值是"通道"而非"目标"。
**Q5**: 这台是纯 DMZ 死路,啥都够不到?
**A5**: 转向从这台采到的凭据/信息去打其他外部入口(如用泄露的账号打 VPN/邮箱/其他面向公网系统),从另一个方向进内网。承认此点是死胡同,换维度进入。

### 反序列化探测导致目标崩溃/告警后的处置
**Q1**: 我盲发 gadget 时目标应用似乎崩了/大量 500,继续打还是停?
**A1**: 立即降速并评估。反序列化盲打(尤其错误的流)易触发 OOM/线程堆积,把应用打挂既暴露又断了自己的路。判据:若目标进程崩溃,当前会话/token 可能随之失效,应停手观察恢复。
**Q2**: 怎么避免再次打崩?
**A2**: 转精准打法:先用 URLDNS/分段探测最小化盲发,确定链后只发一发有效 payload。减少"广撒网式垃圾流",既隐蔽又不伤目标可用性。
**Q3**: 已经触发了 WAF/IDS 告警,IP 可能被封?
**A3**: 转换出口/节奏:降频、换代理出口、拉长时间窗。反序列化利用不需要高频,慢而准优于快而吵。
**Q4**: 目标恢复后加了防护(之前能打现在不能)?
**A4**: 说明触发了应急响应。转向蓝队盲区:换入口、换时间段、用更隐蔽的利用(内存马替代反连)。假设防守方已在盯这个面,改走正交面。
**Q5**: 目标彻底下线/无法恢复?
**A5**: 这个面暂时报废,转其他目标/其他面,记录已知漏洞待时机。红队要保全长期访问,不为一个点把目标打死。

### 序列化数据在数据库/缓存中的二阶反序列化
**Q1**: 我控制的输入没被立即反序列化,而是先存进了 DB/缓存,怀疑二阶反序列化,怎么确认?
**A1**: 找"读取路径"。数据被存起来,是在另一个功能读取它时才反序列化。判据:提交后去触发"读该数据"的其他接口(如后台展示、定时任务、缓存读取),观察那时是否触发。二阶利用要把"注入点"和"触发点"分开找。
**Q2**: 不知道哪个功能会读它?
**A2**: 用带外探针做"埋雷":存入一个 URLDNS payload,然后广泛点击各功能/等待定时任务,DNSLog 哪一刻回连,就定位到触发功能。让时间和功能自己暴露触发点。
**Q3**: 存进去时被转义/编码,反序列化前格式坏了?
**A3**: 检查存储层是否改动字节(编码转换、转义)。若 DB 字符集导致字节变化,需按存储编码反推构造。这类似字符逃逸,要本地模拟存取链路对齐。
**Q4**: 触发点是异步/延迟的(定时任务),验证慢?
**A4**: 转耐心带外验证:埋雷后挂 DNSLog 长期监听,不阻塞去做别的。二阶反序列化的触发常有延迟,用带外通道异步收割。
**Q5**: 找不到任何读取/反序列化触发点?
**A5**: 可能存的只是数据不被反序列化。转向该存储数据的其他利用(存储型 XSS/SQL 二阶注入),或换面。别假设"存了就一定会被反序列化"。

### 用异常回显做版本与依赖指纹
**Q1**: 目标反序列化会抛异常且回显部分栈,我怎么把它变成情报?
**A1**: 异常栈是免费的依赖测绘。栈里的包名/类名暴露框架(spring/shiro/dubbo)、异常信息可能带库版本、`serialVersionUID` 不匹配错误直接给出目标类的 UID。系统性收集这些,拼出精确的 gadget 选型依据。
**Q2**: 只回显异常类型不显栈?
**A2**: 用"探针类"主动引异常:发已知只在特定库/版本存在的类,存在与否返回不同异常,用异常类型差异反推依赖。把回显的每一 bit 都榨成指纹。
**Q3**: serialVersionUID mismatch 报错怎么直接用?
**A3**: 拿到目标类的 UID 后,本地用相同 UID 重新生成 gadget(或找对应版本的库),消除 mismatch。这是把"报错"直接变成"打通"的最短路径。
**Q4**: 异常全被吞成 500 空页?
**A4**: 回显情报路径断了,转带外(DNS)或时间侧信道做依赖探测。无回显时不要依赖异常,换探测通道。
**Q5**: 连响应状态码都无差异?
**A5**: 转纯时间探测或换入口。当目标完全无信息泄露时,盲打成本极高,优先找有回显的其他面。

### 反序列化点存在但只能 DoS 不能 RCE 的取舍
**Q1**: 我确认反序列化可控,但反复尝试只能造成崩溃/资源耗尽,拿不到执行,这时投入产出怎么权衡?
**A1**: 先判"缺的是 gadget 还是可控性"。若是 classpath 无任何可用链(纯净环境),RCE 面可能天生不存在,继续调链是沉没成本。判据:依赖探测显示无已知链 + filter 严格 → RCE 概率极低。
**Q2**: 确认无 RCE 面,DoS 有没有利用价值?
**A2**: 在红队目标里 DoS 通常不作为主线(伤可用性、暴露)。除非目标就是验证可用性风险,否则记录漏洞、转向能拿访问权的面。
**Q3**: 是不是漏了某类 gadget?
**A3**: 转向"非常规 gadget 源":目标自研类里可能藏着可利用的 readObject/反射逻辑。若有源码,审计业务类的反序列化副作用,而非只盯公共 gadget 库。自研链常被忽略。
**Q4**: 没源码,业务类无从审计?
**A4**: 转其他攻击面。无源、无公共链、有 filter 的反序列化点,黑盒下 RCE 极难,时间应转投更软目标。
**Q5**: 但这是唯一入口,不甘心放弃?
**A5**: 那就把它当 SSRF/情报点最大化利用(内网探测、数据外带),并持续关注目标依赖变更(新上线组件可能引入可用链),而非在当前状态死磕 RCE。

### jackson enableDefaultTyping 判定
**Q1**: JSON 入口没有 fastjson 的 `@type` 但有 jackson 迹象,怎么判有没有多态反序列化风险?
**A1**: jackson 的危险开关是 `enableDefaultTyping()` 或 `@JsonTypeInfo`,启用后 JSON 里可带 `["类名", {...}]` 数组包裹形式或 `@class` 指定类型。判据:尝试注入类型标记看是否被实例化(DNS 探针)。
**Q2**: 确认可注入类型,怎么打?
**A2**: 用 jackson 已知 gadget(通过 JNDI 类如 `com.sun.rowset.JdbcRowSetImpl`、或 C3P0/各类可加载远程的 bean)触发 JNDI/RCE。与 fastjson 打法思路相通,gadget 类清单略有差异。
**Q3**: jackson 版本较高,黑名单更新过?
**A3**: 转向黑名单外的新 gadget 类(jackson 的 CVE 序列不断新增可利用类)。按版本对应公开利用类逐个试,判据是版本区间。
**Q4**: JNDI 后端被高版本 JDK 限制?
**A4**: 同前——转本地 factory/反序列化型 JNDI 绕过 codebase 限制。jackson→JNDI→本地 gadget 是通用降级路径。
**Q5**: 全部被拦或非默认 typing?
**A5**: 若未启用 default typing,jackson 反序列化面基本不存在,转其他面。别假设所有 jackson 都可利用——多数默认配置是安全的。

### WebLogic/中间件 T3-IIOP 协议反序列化
**Q1**: 扫到 Java 应用服务器管理端口(如 T3/IIOP),怀疑协议层反序列化,怎么起手?
**A1**: 这类中间件协议在握手后会反序列化客户端数据,是独立于 HTTP 的攻击面。先做协议探测确认端口与版本,再对应已知的协议反序列化 CVE 选 payload。判据是端口指纹 + 版本。
**Q2**: 打过去被打了补丁(known CVE 被修)?
**A2**: 转同协议的其他 gadget/绕过变体。中间件反序列化补丁常是"加黑名单",历史上被反复用变体绕过。按版本找补丁后的绕过变体。
**Q3**: HTTP 打不动但协议端口能连?
**A3**: 这正是价值——协议端口常疏于防护(WAF 只看 HTTP)。把火力从 HTTP 转到裸协议端口,是绕 Web 层防护的正交维度。
**Q4**: 协议端口被防火墙限制来源 IP?
**A4**: 转向:若已在内网有一个点,从内网打该端口(管理端口常只对内网开放)。外部打不通的中间件端口,拿到内网跳板后往往敞开。
**Q5**: 完全够不到管理端口?
**A5**: 回退 HTTP 面找该中间件的其他洞(路径穿越、SSRF 反打管理端口),或换目标。中间件协议 RCE 威力大但需可达性,不可达时不值当。

### 最终兜底——反序列化整条主线走死时的全局转向
**Q1**: 我把这个反序列化点从判定、依赖、gadget、绕过全试遍了都不通,该怎么系统性决定放弃与转向?
**A1**: 用"卡点归类"决定转向方向,而非情绪化放弃。归类:是入口不可控 / 无可用 gadget / filter 太严 / 不出网无回显 / 版本对不齐。每类对应不同正交出口,先明确卡在哪一层。
**Q2**: 卡在"无可用 gadget"?
**A2**: 转其他漏洞类型(SQLi/SSTI/文件上传/逻辑),它们不依赖 classpath gadget,得手概率可能更高。反序列化不是唯一 RCE 路径。
**Q3**: 卡在"不出网无回显"?
**A3**: 转带内利用(内存马/回显构造)或把它降级为 SSRF/情报点。卡点是"信道"而非"漏洞",在信道维度想办法。
**Q4**: 卡在"filter/WAF 太严"?
**A4**: 转攻击面迁移——找不经过该防护的入口(内网端口、其他子域、API 版本差异)。防护是外层,绕不过就换门。
**Q5**: 所有面都走死,整个目标看似铜墙铁壁?
**A5**: 转人/供应链/信息面:配置泄露、第三方组件、员工凭据、关联资产。技术正面打不动时,红队的价值在于换维度(资产测绘找影子资产、供应链弱点),而不是在最硬的正面无限投入。记录当前进展,战略转移。
