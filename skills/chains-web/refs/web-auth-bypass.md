# Web · 认证与会话绕过的思路

### 面对一个登录框先做什么:摸清认证机制而不是急着爆破
**Q1**: 我打开目标X只有一个登录框,手上没有任何凭据。第一步该干嘛?
**A1**: 不要立刻上字典爆破。先做"认证机制指纹":看登录请求走的是表单POST、JSON API、还是OAuth/SAML跳转;看返回里发的是自签cookie、JWT、还是不透明session id;抓一次成功流程(哪怕用假账号)看有几步、有没有前端加密/加签。判据是——搞清楚"服务端到底靠什么认定你是谁",绕过点永远在这条信任链最薄弱的一环。
**Q2**: 抓包发现密码在前端被JS加密后再发送,我连爆破payload都构造不出来。
**A2**: 别在密文层硬刚。把加密函数从JS里抠出来本地复现(通常是CryptoJS/RSA公钥,公钥就在前端),做成爆破前的预处理器;或者更省事——直接在浏览器控制台hook加密函数,让它对我喂的明文字典逐个吐密文。前端加密只防被动嗅探,挡不住主动攻击者。
**Q3**: 观察到登录成功和失败返回的HTTP状态码一样,但响应体/跳转略有不同。
**A3**: 这就是"预言机"(oracle)。把差异量化:字节长度、响应时间、Set-Cookie有无、Location跳转目标。任何可稳定区分"对与错"的信号,都能拿来做用户名枚举或后续布尔盲注的判据。
**Q4**: 有没有可能这个框根本不是主战场?
**A4**: 要有这个警觉。很多时候登录框固若金汤,但同域下的注册、找回密码、API文档(swagger)、旧版移动端接口才是软肋。先做一遍认证相关端点的横向铺开(/api、/oauth、/reset、/register、/graphql),再决定主攻方向。
**Q5**: 我把常规爆破、SQLi、弱口令全试遍了,这个登录点纹丝不动,彻底卡死。
**A5**: 从"直接绕认证"这个维度撤出来,转正交维度:一是转"不需要登录也能访问的资源"——找未授权接口、目录遍历出的备份/配置,认证信息可能明文躺在里面;二是转"信任外部输入的环节"——找回密码、邮箱验证、第三方登录回调,这些流程往往比登录本身松。认证的墙很高时,翻墙不如找侧门。

### 想试默认/弱口令,但怕触发锁定
**Q1**: 目标像是某款开源系统或设备后台,我想先试默认凭据,但不知道会不会锁账户。
**A1**: 先判系统身份(靠favicon hash、页面版权串、特有路径、报错风格),锁定它的官方默认凭据清单——这是一次成功率远高于盲爆的动作。同时用一个"牺牲账号"探测锁定策略:连续输错几次看是否出现锁定/验证码/延迟,摸清阈值再决定节奏。
**Q2**: 默认口令被改了,但系统类型确认无疑。
**A2**: 转向该系统的历史CVE:很多产品有认证绕过、硬编码后门、未授权API的公开漏洞。用版本指纹去匹配已知漏洞,比继续猜口令高效得多。产品已知+版本确定=优先查漏洞库。
**Q3**: 版本太新,没有可用N-day。
**A3**: 退回弱口令但改策略:用"密码喷洒"而非"账户爆破"——固定一个高频弱口令(季节+年份、公司名+123之类的构造规律),对大量用户名各试一次,天然规避单账户锁定。
**Q4**: 我没有有效用户名列表,喷洒无从下手。
**A4**: 先解决用户名来源这个正交问题:从企业邮箱格式(名.姓@域)推导、从LinkedIn/GitHub/文档元数据收集人名、从登录/找回接口的枚举差异反推。用户名是喷洒的弹药,弹药不足就先去侦察维度补给。
**Q5**: 全站都上了统一的严格锁定+验证码,喷洒也走不通。
**A5**: 转向"绕过计数器本身":锁定往往按用户名或IP计数——换IP池(X-Forwarded-For有时被信任)、换大小写/加空格制造"不同用户名"、找不计入锁定的备用登录端点(移动API、Basic认证接口)。计数器有边界,边界之外就是通路。

### 怀疑登录点有 SQL 注入绕过
**Q1**: 登录处输入特殊字符引发异常或行为变化,我怀疑能SQL注入绕过认证。
**A1**: 先判注入是否发生在认证查询里:在用户名/密码字段试经典的逻辑恒真闭合与注释,观察是否直接登录成功或报错变化。关键判据是"我是否绕过了密码校验而非仅仅报错"——前者才是认证绕过,后者只是普通注入。
**Q2**: 能注入但是登录逻辑是"取出hash再比对",恒真进不去。
**A2**: 换思路:用UNION或子查询构造一行"我可控密码的假记录",让返回的hash等于我已知明文的hash;或注入让查询返回一个已知账号那一行。目标不是让WHERE恒真,而是让返回的凭据行为我所知。
**Q3**: WAF把常见注入关键字全拦了。
**A3**: 先别放弃注入维度,试绕WAF:大小写混淆、内联注释、编码、等价函数、超长payload。但设个止损——如果绕WAF成本过高,记下"此处可能可注入"这个情报,转向别处,回头再啃。
**Q4**: 确认是盲注,没有回显。
**A4**: 上布尔/时间盲注,但认证点的盲注目标要精准:不是慢慢dump整库,而是优先取管理员账号的凭据字段或直接构造绕过。盲注慢,认证场景要"targeted extraction"而非全量。
**Q5**: 数据库层彻底注不动(参数化到位),SQLi这条死了。
**A5**: 转正交维度——认证绕过不止SQLi一条路。转NoSQL注入(如果后端是文档库,操作符注入能让密码校验恒真)、转认证逻辑漏洞(改返回值、跳步骤)、转令牌层(JWT/session伪造)。数据库注不动不代表认证逻辑没洞。

### 拿到 JWT,先拆结构再决定攻法
**Q1**: 登录后服务端发的是JWT,我想在token层做文章。第一步?
**A1**: base64解开header和payload,读三样东西:alg是什么(none/HS*/RS*)、payload里有没有身份/角色/权限字段(role、isAdmin、uid)、有没有kid/jku/x5u这类指向密钥的头。这三者决定后续攻击面。JWT是"自带答案的令牌",先看它把什么信息暴露给了我。
**Q2**: header里alg是HS256,payload有role字段。
**A2**: 两条线并行:一是试alg=none/空签名,看服务端是否接受无签名令牌;二是若签名必须校验,则赌HS256密钥是弱口令,离线爆破密钥,爆出来后就能自由签发任意role的令牌。
**Q3**: alg=none被拒,密钥也爆不出来。
**A3**: 看是不是RS256(非对称)。如果是,试"算法混淆":把alg改成HS256,用服务端公开的RSA公钥当HMAC密钥去签。若后端用同一个verify函数没锁死算法,就会拿公钥来做对称校验而被绕过。公钥是公开的,这就是它的致命处。
**Q4**: header里有kid或jku。
**A4**: 这是密钥注入面。kid若拼进SQL/文件路径,可做注入或路径穿越指向我可控的密钥;jku/x5u指向密钥URL,试改成我控制的服务器托管我自己的密钥对,让它用我的公钥验我的签名。核心是"让服务端用我给的密钥验证我伪造的令牌"。
**Q5**: 所有令牌伪造尝试都被严格拒绝,签名校验无懈可击。
**A5**: 从"伪造令牌"转向"窃取/复用令牌"这个正交维度:找XSS偷token、找日志/URL/referer里泄露的token、看token是否长期不过期可重放、看有没有把token写进localStorage而存在读取路径。签得再严,泄露了一样用。

### 会话 cookie 不是 JWT,判断可预测性与固定
**Q1**: 服务端发的是不透明session id(一串看不懂的字符),不是JWT。怎么下手?
**A1**: 先判它是不是"可预测"或"可伪造"。收集多个session id样本,看是不是顺序递增、时间戳编码、或弱随机(用熵评估工具跑一批)。如果结构里藏着可推导规律,就能预测别人的会话。不透明不等于安全。
**Q2**: session id看起来是高熵随机,预测无门。
**A2**: 转"会话固定"(session fixation):看登录前后session id变不变。如果登录后不重新签发,我就能先拿一个未认证session id想办法种给受害者,等他登录后这个id就升级成已认证会话,我复用即可。
**Q3**: 登录会重新签发id,固定也不成。
**A3**: 转会话生命周期缺陷:登出后旧id是否真失效、改密码后其他会话是否被踢、token有效期是不是无限长。找一个"本该失效却仍有效"的窗口,配合之前泄露的任何旧token做重放。
**Q4**: 想把伪造的cookie种给受害者,但没有注入点。
**A4**: 检查cookie属性:HttpOnly缺失则可用XSS读写,Secure缺失则可在明文信道注入,SameSite宽松则利于跨站携带。属性缺陷决定了我能用哪种投递方式(XSS/中间人/CSRF)去操纵它。
**Q5**: cookie高熵、属性齐全、生命周期严谨,会话层完全打不动。
**A5**: 转正交维度,不打会话打"会话背后的授权":很多系统会话安全但接口鉴权松——直接改请求里的uid/对象id做水平越权(IDOR),或调用只在前端隐藏、后端不校验角色的管理接口。抢不到别人的会话,就用自己的会话去越权。

### 找回密码流程往往比登录松
**Q1**: 登录啃不动,我把注意力转到"忘记密码"。先看什么?
**A1**: 完整走一遍找回流程并记录每一步:输入什么(邮箱/手机/用户名)、服务端发什么(邮件链接/短信OTP)、重置凭证长什么样(token在URL里?可预测?)、重置接口是否二次校验身份。重置流程的目标是"在不知道旧密码的前提下设置新密码",天然是绕过密码的合法通道,逻辑一松就是灾难。
**Q2**: 重置链接里带一个token,我想判断它可不可预测/可不可伪造。
**A2**: 申请多个重置token对比:是否基于时间戳/自增/用户id的弱构造、是否是MD5(邮箱)之类可离线算出的值。若能从公开信息推导token,就能给任意用户重置密码。
**Q3**: token是强随机,推不出来。
**A3**: 转"token投递环节"的信任漏洞:重置邮件里的链接域名是不是取自Host头?若是,我发请求时改Host为我控制的域,受害者收到的链接就指向我服务器,他一点我就拿到token。Host头注入是重置链接的经典软肋。
**Q4**: 链接域名写死了,Host头不生效。
**A4**: 转重置接口本身的逻辑:提交新密码时,请求里是否带了可篡改的用户标识(userid/email)而后端只信任它、不校验token与该用户是否匹配?试用我的合法token配上受害者的id提交,看能否越权改他的密码。
**Q5**: 重置流程各环节都严谨,找回这条路也堵死。
**A5**: 转向2FA/OTP这个正交维度,或转"账户接管的其他入口":邮箱变更流程、绑定第三方登录时的账号合并逻辑、注册时的邮箱抢注。找回密码只是接管账户的一条路,把视野放大到"所有能改变账户归属的操作"。

### OTP / 二次验证的绕过判断
**Q1**: 密码对了但卡在OTP/短信验证码这一步,怎么找绕过?
**A1**: 先分类OTP弱点面:验证码是否可爆破(位数少+无限速)、是否有响应可区分对错、验证请求和"是否已通过2FA"的状态是否解耦。判据是——2FA本质是"第二个门",要么暴力开锁,要么找到不经过这扇门的旁路。
**Q2**: OTP是6位数字,但没看到明显限速。
**A2**: 优先试爆破,但要探测隐藏限速(某些系统N次后静默失效或换新码)。同时试OTP复用/固定:同一个码能否多次用、换新会话旧码是否仍有效、码是否绑定了具体动作。
**Q3**: 有限速,爆破被封。
**A3**: 转"状态解耦"漏洞:验证OTP的接口通过后会给一个"已验证"标记(cookie字段/返回token/跳转到某步)。试跳过OTP直接请求它后面的受保护端点,看后端是不是只信这个标记而不重新确认OTP真的过了。多步流程最爱在"步骤跳跃"上翻车。
**Q4**: 后端每步都校验,跳不过去。
**A4**: 转响应篡改:拦截OTP校验的返回包,把{"success":false}改成true、把状态码400改成200,看前端是否据此放行。对"前端根据返回值决定下一步"的胖客户端尤其有效。
**Q5**: 服务端权威校验,响应篡改也无效,2FA固若金汤。
**A5**: 转正交维度——绕过2FA不如"让账户压根不需要2FA"或"从没有2FA的入口进":检查API/移动端/旧接口是否豁免2FA、备用恢复码流程是否更弱、第三方SSO登录进来是否绕开了本地2FA。第二道门锁死时,去找没装这道门的房间。

### OAuth 登录的 redirect_uri 与 state 面
**Q1**: 目标用OAuth/第三方登录,我想在这个流程里找接管点。先盯哪?
**A1**: 盯授权请求的参数,尤其redirect_uri和state。redirect_uri决定授权码/令牌回传到哪——若校验宽松(允许子域、路径、开放跳转),我就能把凭证劫持到我的地址。state是防CSRF的,缺失或不校验则可做登录CSRF。先摸清这两个参数的校验严格度。
**Q2**: 我改redirect_uri为完全不同的域,被拒了。
**A2**: 别急着放弃,试宽松匹配的边界:同注册域下的开放跳转端点、path追加、@符号构造、子域通配、末尾斜杠/参数差异。校验常只做前缀或包含匹配,构造一个"看起来合法实则回传给我"的URL。
**Q3**: redirect_uri锁得很死,精确匹配。
**A3**: 转授权码/token的其他泄露路径:码是否出现在Referer里泄给第三方、是否可跨client复用(用A应用的码换B应用的token)、隐式流的token是否留在URL片段被后续页面读到。
**Q4**: state参数是不是也值得单独打?
**A4**: 是。若state缺失或服务端不校验,可发起"登录CSRF"——诱导受害者用我的授权码完成绑定,使他的会话登入我的账号,或把我的第三方身份绑到他账户上,后续用我的第三方登录直接进他账户。方向是"把身份绑定关系搅乱"。
**Q5**: OAuth各参数校验都规范,这条链打不穿。
**A5**: 转正交维度:攻击OAuth背后的"账号合并/绑定逻辑"——同邮箱在第三方已验证vs本地未验证时如何合并、能否抢先用受害者邮箱注册本地账号再等他用第三方登录合并进来。也可整体转回本地认证面。OAuth协议本身很成熟,洞多在实现方的账号映射逻辑里。

### SAML / SSO 断言的签名处理
**Q1**: 企业目标走SAML SSO,我想在断言层伪造身份。切入点?
**A1**: 拿到一份SAMLResponse样本,看三件事:断言是否签名、签名覆盖范围(整个response还是仅assertion)、解析器是否存在XML签名包装(XSW)空间。SAML的命门在"签名校验的XML节点"和"实际取用身份的XML节点"能否被错位。
**Q2**: 断言有签名,直接改NameID会破坏签名。
**A2**: 试XML签名包装(XSW):保留原始已签名的节点让校验通过,同时插入一个我伪造的未签名断言让业务逻辑去取用。利用"验哪个节点"与"用哪个节点"的不一致。这是SAML最经典的绕过范式。
**Q3**: 解析器对XSW有防护。
**A3**: 转XML层的其他老问题:XXE(SAML是XML,解析器若不安全可读文件/SSRF)、注释截断(在NameID里插XML注释改变解析器读到的值)、以及签名剥离(有的实现签名缺失时竟默认放行)。
**Q4**: 我想直接伪造整份断言自己签。
**A4**: 那就需要IdP私钥——转情报维度找它:元数据端点、配置泄露、证书是否用了弱密钥或公开测试密钥。拿不到私钥,伪造签名就是空谈,把力气花在"找密钥"或"绕签名"而非"硬算签名"。
**Q5**: SAML实现很硬,签名与解析都无懈可击。
**A5**: 转正交维度:攻击SSO的信任链末端——SP和IdP之间的会话建立后,SP本地会话管理是否有前述那些普通漏洞;或转向该SSO保护之外的应用入口(遗留的本地登录、服务账号、API token)。协议算牢固,但接入它的应用群里总有掉队的。

### 认证是多步流程,找"步骤跳跃"
**Q1**: 认证不是一步到位,而是"输账号→输密码→选设备→进主页"这种多步。怎么利用?
**A1**: 把每一步的请求和它携带的"进度凭证"记下来(隐藏字段、step参数、临时token、cookie里的state)。多步流程的漏洞几乎都在"能否伪造进度、直接请求靠后的步骤而跳过前面的校验"。先画出这条状态机。
**Q2**: 我直接请求最后一步,被打回第一步了。
**A2**: 说明有进度校验。看进度凭证从哪来:如果它在第一步(输账号、还没验密码)就发下来了,那我用它去请求后续步骤就可能跳过密码。找"过早签发的凭证"。
**Q3**: 进度凭证在密码验证后才发。
**A3**: 转参数篡改:多步里常有形如step=2、stage=verify的参数,试直接改成完成态;或把"是否需要2FA"这类布尔判定参数从true翻成false。前端主导的流程尤其脆弱。
**Q4**: 服务端权威维护状态,参数改不动。
**A4**: 转竞态:在两步之间存在检查与使用的时间窗时,并发请求可能让状态机进入非预期组合(如同时提交导致跳过校验)。多步认证+并发是被忽视的角落。
**Q5**: 状态机严密、无竞态窗口,跳步彻底失败。
**A5**: 转正交维度:既然流程走不通,就攻流程依赖的"数据"——每步信任的用户标识是否可越权替换(用我的进度凭证配受害者id)。把"绕过流程"转成"在合法流程里替换成别人的身份"。

### 前端 vs 后端鉴权不一致
**Q1**: 我用低权账号登进去了,想提权。先怀疑什么?
**A1**: 先怀疑"前端隐藏、后端不校验"。前端根据角色隐藏了菜单/按钮,但对应API可能没做服务端权限检查。抓一份高权限功能的请求样例(从JS里挖端点、从文档挖),用我的低权会话直接打,看后端认不认。
**Q2**: 我不知道高权限接口长什么样。
**A2**: 从前端JS里静态挖:所有路由、API路径、被角色判断包起来的调用都在代码里。把JS里出现但当前角色调不到的端点列出来,逐个用我的会话试。前端代码是后端接口的地图。
**Q3**: 直接调高权接口返回403。
**A3**: 转参数级越权:接口本身开放,但靠请求里的字段区分能操作谁/什么。改uid、objectId、role、tenantId这些字段(水平越权IDOR/垂直越权),看能否操作别人的数据或以更高角色行事。
**Q4**: 关键操作还需要一个我没有的token/签名字段。
**A4**: 看这个字段是否可从别处获取或本身可预测,或者是否在某个低权接口的返回里泄露了。很多"额外校验字段"其实在别的响应里明文给过。
**Q5**: 后端鉴权到处都严,提权彻底卡住。
**A5**: 转正交维度:横向找"同权限但更信任的入口"——内部/管理子系统、运维接口、消息队列/回调这类默认内网可信的通道;或转回拿更高权限凭据(打管理员的会话/密码)。当前应用鉴权严,就换攻击面而非在同一堵墙上撞。

### 注册流程的 Mass Assignment 提权
**Q1**: 系统开放注册,我想在注册时就把自己变成管理员。思路?
**A1**: 抓注册请求的JSON/表单,看它提交了哪些字段。核心猜测是后端是否把整个对象直接绑定入库(mass assignment)。试往请求里加role、isAdmin、isVerified、accountType这类字段,看能否越权设置本不该由用户控制的属性。
**Q2**: 我不知道后端模型里有哪些可控字段。
**A2**: 从别处推断字段名:用户信息接口的返回JSON、API文档、前端表单的隐藏项、报错信息。返回体里出现的字段名往往就是可尝试注入的属性名。
**Q3**: 加了isAdmin没生效,可能字段名不对。
**A3**: 试命名变体(is_admin、admin、userType=1、level=99)和嵌套结构(role:{name:"admin"})。ORM的绑定粒度和命名规范决定了正确的键,多做几组组合。
**Q4**: 注册接口过滤了敏感字段。
**A4**: 转其他"接受对象更新"的端点:个人资料修改、偏好设置、批量导入接口往往过滤不如注册严。同一个mass assignment漏洞常在更新接口上没堵。
**Q5**: 所有写入接口都做了字段白名单,提权字段进不去。
**A5**: 转正交维度:从"提升自己权限"转向"降低验证门槛"——注册时能否跳过邮箱验证直接激活、能否抢注特权邮箱域(如@内部域名被后端当员工)、能否触发默认赋予高权限的边缘逻辑。写入被白名单挡住时,去找逻辑赋权的旁门。

### 篡改 cookie 里的角色/身份字段
**Q1**: cookie不是纯随机,而是能看懂一部分(如base64里有用户名或role)。怎么办?
**A1**: 解码所有可解的部分,识别其中的身份/权限字段和完整性保护方式(是纯明文?带一段签名?还是加密?)。判据是"我改了字段后,服务端有没有办法发现"。先确定它靠什么保证cookie不被篡改。
**Q2**: cookie是"数据+一段签名"的结构。
**A2**: 攻签名:若是HMAC且密钥弱可离线爆破;若签名算法从数据里可推(如某框架的已知签名格式);若服务端存在签名缺失时放行的降级。爆出/绕过签名后即可任意改role。
**Q3**: cookie整体是加密的,看不懂内部。
**A3**: 转密码学攻击面:若是ECB模式可做块重排、若是CBC可试位翻转(padding oracle)改出想要的明文、若加密无完整性保护则篡改密文可能改出有利明文。加密不等于防篡改。
**Q4**: 加密带完整性(AEAD),动不了。
**A4**: 转"合法获取一个高权cookie"而非伪造:能否注册/诱骗一个高权角色、能否让系统给我发一个含更高role的cookie(通过前述mass assignment等)。改不了就想办法让它合法地发给我一个好的。
**Q5**: cookie从密码学到签发逻辑都严密,篡改路线全死。
**A5**: 转正交维度:放弃"改自己的身份凭证",转"用自己的合法凭证去越权访问"——cookie里的身份没法改,但接口对数据对象的鉴权可能没做(IDOR)。身份是真的,访问的对象却可以是别人的。

### 逻辑漏洞:响应值决定登录成败
**Q1**: 我怀疑这是个胖客户端/SPA,登录成败由前端读后端返回值决定。怎么验证?
**A1**: 用错误密码登录,拦截响应包。观察返回结构里有没有形如authenticated、success、role、code这类字段。假设:前端可能只看这些值就放行。判据是——把false改true、把普通用户改admin后重放,前端会不会误以为登录成功。
**Q2**: 改了返回值后前端确实进去了,但一操作就报未授权。
**A2**: 说明这是"前端假登录",后端并不认。这种进去多半只能看前端渲染的静态内容,价值有限。但别浪费:进去的界面会暴露真实的API端点和数据结构,拿它当侦察成果,去打真正的后端鉴权。
**Q3**: 前端进去后确实调出了一些真实数据接口。
**A3**: 那说明后端某些接口没做鉴权(前端登录门形同虚设)。立刻把这些接口清点出来,直接用未认证请求打,看哪些真能拿数据/执行操作。假登录的价值就在于它帮你找到了裸奔的后端。
**Q4**: 后端接口都要真token,假登录拿不到。
**A4**: 转"返回值篡改"到别的环节:2FA校验、权限判定、支付/审批这类同样依赖返回布尔值的流程。哪里有"前端根据后端返回决定放行",哪里就复用这招。
**Q5**: 全站都是权威后端校验,响应篡改毫无作用。
**A5**: 转正交维度:承认这是个厚后端应用,把注意力从"骗前端"转到"真实凭据获取与注入漏洞"(SQLi、SSTI、反序列化、令牌伪造)。响应篡改只对信任客户端的架构有效,遇到厚后端要换整套打法。

### GraphQL 端点的认证绕过
**Q1**: 发现目标有GraphQL端点,认证方面能挖什么?
**A1**: 先introspection摸清schema(若开放),重点找:哪些query/mutation没被鉴权指令保护、有没有直接暴露用户/凭据的字段、有没有绕过REST层鉴权的"后门"操作。GraphQL常把REST上藏好的能力平铺暴露。
**Q2**: introspection被关了,看不到schema。
**A2**: 转字段爆破/推断:用常见命名字典猜query名,借助报错信息("did you mean...")反推字段,或从前端JS里的GraphQL文档挖出真实查询。schema藏起来不等于接口没了。
**Q3**: 找到一个敏感mutation但需要认证。
**A3**: 试鉴权不一致:同一个schema里,有的字段有@auth指令有的漏了;批量查询(aliases)里是否只校验第一个;嵌套查询能否借一个已授权的父对象拿到未授权的子字段。GraphQL的鉴权漏点多在"粒度不齐"。
**Q4**: 想爆破登录,但GraphQL怎么放大攻击?
**A4**: 用别名(aliases)在单个请求里塞成百上千次login调用,一个HTTP请求完成大批量爆破,天然绕过基于请求数的限速。这是GraphQL特有的爆破放大。
**Q5**: 鉴权齐整、限速也按操作数算,GraphQL这条没突破。
**A5**: 转正交维度:GraphQL背后仍是同一套数据层,转去打它可能引入的注入(参数拼进SQL/NoSQL)、IDOR(node(id:)直接按id取任意对象)、或批量查询导致的DoS辅助其他攻击。协议绕不过就打它暴露的数据访问逻辑。

### Basic/Digest 与 API Key 这类"简单认证"
**Q1**: 目标某接口用HTTP Basic或一个API Key做认证,怎么下手?
**A1**: 先定位凭据可能泄露的地方——Basic/API Key是"静态共享秘密",最大弱点是泄露而非破解。翻前端JS、移动端反编译、Git历史、公开代码仓库、Swagger示例、Wayback存档。判据是"这个静态秘密有没有在什么地方被明文写死过"。
**Q2**: 没找到泄露,想爆破Basic认证。
**A2**: Basic就是base64(user:pass),可离线构造字典爆破,但先探限速与锁定。同时注意:Basic常用于机器对机器,账号可能是service/admin这类固定名,配弱口令喷洒。
**Q3**: API Key爆不出、也没泄露。
**A3**: 转"Key的授权边界":一个低权API Key能否调用高权端点(后端只验key有效性不验权限)、key是否可跨环境复用(测试key能打生产)、key在URL里是否被日志/referer记录。key有效但边界松,一样能越权。
**Q4**: 接口对每个key都做了严格权限绑定。
**A4**: 转"获取一个更高权的key":管理面板、CI/CD配置、容器环境变量、内部服务间调用里流转的key。很多高权key躺在配置与日志里,不需要破解。
**Q5**: 静态凭据到处都严,拿不到也爆不出。
**A5**: 转正交维度:放弃凭据本身,转协议/传输层——Basic若走明文HTTP可中间人截获、若有SSRF可从内网视角访问只信任内网的免认证接口。静态秘密拿不到时,想办法站到"被信任的位置"上去。

### 会话登出/失效逻辑的缺陷
**Q1**: 我搞到一个疑似过期或被登出的token,还想利用它。值得吗?
**A1**: 值得先验证"失效是否真失效"。很多系统登出只删了客户端cookie,服务端session并未销毁;或改密码后旧token仍有效。拿这个token重放一个受保护请求,看还通不通。判据是——服务端有没有真正维护token的吊销状态。
**Q2**: token确实还能用,但我不确定权限范围。
**A2**: 逐步探测这个token能访问的端点边界,确认它对应的角色和有效期。一个"本该失效却仍活着"的高权token是黄金,优先固化访问(尽快用它拿更持久的立足点)。
**Q3**: token是JWT,服务端根本无法主动吊销。
**A3**: 这是无状态JWT的固有弱点:一旦签发,在过期前无法作废。若过期时间设得很长,任何一次泄露的token都是长期有效的钥匙。把攻击重心放到"获取任一泄露JWT"上,因为拿到即长期可用。
**Q4**: token有效期很短,窗口太小。
**A4**: 转刷新令牌(refresh token):它生命周期长、是续期的关键。若refresh token泄露、可预测、或换发逻辑有缺陷(旋转不彻底、可重复使用),就能持续换取新的访问令牌。短窗口下,refresh token才是真正的目标。
**Q5**: 会话失效、吊销、刷新逻辑都很严谨。
**A5**: 转正交维度:不打"会话持久性",转"重新获取会话的便利性"——是否有"记住我"长期cookie、是否可通过前述接管流程随时重新登入、是否有免登录的API凭据。会话管得严,就找一条能反复进门的稳定通道。

### 验证码/人机挑战挡住了自动化
**Q1**: 爆破/枚举的路子被验证码挡了,怎么继续?
**A1**: 先判验证码是否"真的生效":有时验证码只在前端渲染,后端不校验或校验可绕(空值、复用上次通过的值、固定万能码)。先试提交时把captcha字段置空/乱填,看后端认不认。判据是——这个人机挑战是不是只是摆设。
**Q2**: 后端确实校验验证码。
**A2**: 试"验证码复用":一次通过的captcha token能否在多次请求里重复使用、刷新页面不刷新码。若码不与单次请求绑定,拿一个通过的码连打即可绕过限速。
**Q3**: 码每次都变、单次绑定。
**A3**: 转触发条件:验证码是否只在失败N次后才出现?若是,把节奏放慢到阈值以下做"低频喷洒",完全不触发验证码。绕验证码有时不如"不惊动它"。
**Q4**: 想直接识别验证码。
**A4**: 简单图形/数字码可OCR或过打码服务,但要评估投入产出比——为一个不确定有没有弱口令的登录点搭识别管线可能不划算。设止损:先确认背后真有可爆的东西再投入。
**Q5**: 验证码强、限速严,自动化路线全堵。
**A5**: 转正交维度:放弃"大批量猜",转"精准单点"——用OSINT拿到的真实凭据/泄露库做一次性的凭据填充(credential stuffing,量小不触发防护)、或转攻根本没有验证码保护的接口(API、移动端、找回流程)。人机挑战防的是海量自动化,防不住精准的少量尝试。

### 凭据填充:手里有一批泄露账号密码
**Q1**: 我从公开泄露数据里拿到一批"邮箱:密码",想打这个目标。怎么用最有效?
**A1**: 做凭据填充(credential stuffing)而非爆破——用真实存在的账密组合,一对一试,成功率远高且不触发单账户锁定。先小批量、低速试,验证目标是否复用了这些泄露凭据。判据是命中率,一旦有命中说明用户在此复用密码。
**Q2**: 直接打生产登录点怕触发风控。
**A2**: 先探风控形态:设备指纹、IP信誉、行为分析都可能拦截。用少量样本、分散IP、模拟正常节奏试探边界,或优先打风控较弱的入口(旧版API、移动端、合作方接口)。
**Q3**: 命中了但账户开了2FA。
**A3**: 密码正确+2FA挡路,转前面的2FA绕过维度;若绕不过,这个凭据仍有价值——它证明密码正确,可用于其他复用了同密码的系统(横向到目标的其他资产)。
**Q4**: 泄露库里的密码都过期了/命中率为零。
**A4**: 转"密码变体推测":用户改密常有规律(旧密码+递增数字/年份)。基于泄露的旧密码构造变体小字典,做targeted喷洒。人对密码的记忆惯性是可利用的。
**Q5**: 凭据填充完全打不中,风控还封了IP。
**A5**: 转正交维度:从"猜用户的密码"转"绕过密码机制本身"——回到SQLi/逻辑绕过/令牌伪造这些不依赖正确密码的路;或转"钓鱼/社工"获取实时凭据(在授权范围内)。凭据填充是概率游戏,打不中就换成确定性的技术绕过。

### 竞态条件打认证/授权
**Q1**: 常规认证攻击都试过了,我想看看有没有竞态条件可利用。哪些点值得试?
**A1**: 找"检查与使用之间有时间窗"的操作:限速计数、优惠/额度的一次性校验、账户激活、2FA尝试次数、令牌一次性使用。用高并发同时发多个请求,看能否让状态判断在更新前被多次通过。判据是"同一资源的校验是否原子"。
**Q2**: 我怀疑OTP/爆破的限速有竞态。
**A2**: 在限速计数器递增前并发打一批请求(单包多请求/并行连接),可能在计数器反应过来前多试很多次,变相突破限速。限速若非原子递增,就有超发窗口。
**Q3**: 并发没打出效果,可能窗口太窄。
**A3**: 用同步发包技术把请求压到同一瞬间(如HTTP/2单连接多流、或先发头留最后一字节再同时释放),最大化落在同一时间窗内的请求数。竞态成功率对同步精度极敏感。
**Q4**: 竞态确实存在但难以稳定复现。
**A4**: 提高样本量+多轮尝试,记录成功率而非要求次次成功——对认证绕过,偶尔一次成功(如多创建一个高权账户、多通过一次校验)可能就够立足。不稳定的竞态也有价值。
**Q5**: 目标各处校验都做了原子/锁,竞态无窗口。
**A5**: 转正交维度:竞态是"时序"维度的攻击,打不动就回到"逻辑/注入/令牌"这些"内容"维度。或者把竞态思路平移到业务逻辑而非纯认证(如认证后的一次性操作),换战场而非换技术。

### CSRF 拿下认证态操作
**Q1**: 我打不进账户,但想让已登录的受害者替我执行操作。切入点?
**A1**: 找"改变账户归属/凭据"的状态变更请求:改邮箱、改密码、绑定第三方、加信任设备。判断它们有没有CSRF防护(token/SameSite/自定义头)。若没有,诱导受害者触发即可代其改掉关键属性,间接接管。判据是"这个高危操作能否被跨站发起"。
**Q2**: 关键操作带了CSRF token。
**A2**: 看token是否真校验:是否可省略、可留空、可用别人的token、是否不绑定用户。很多CSRF token只是形式,后端并不严格校验其归属。
**Q3**: token校验严格,但登录本身没防护。
**A3**: 转"登录CSRF":诱导受害者登入我的账户(用我的凭据发起),之后他在"我的账户"里输入的敏感信息(卡号、上传的文档)就落进我手里。方向反过来——不是拿他的会话,是把他塞进我的会话。
**Q4**: 想配合其他漏洞放大CSRF。
**A4**: CSRF+自身:用CSRF改掉受害者邮箱,再走找回密码完成完整接管;或CSRF触发一个存储型XSS的写入。单独的CSRF价值有限,串起来才是接管链。
**Q5**: SameSite严格、所有状态操作都防了CSRF。
**A5**: 转正交维度:从"跨站诱导"转"同站执行"——若目标有XSS,则同源脚本可读token、可带凭据直接发请求,彻底绕过CSRF防护。CSRF打不动时,一个XSS就让所有CSRF防护失效。

### 密码策略与账户激活的逻辑洞
**Q1**: 注册/改密流程,除了mass assignment,还有哪些逻辑洞值得看?
**A1**: 看"状态转换"的完整性:注册后账户是待激活还是直接可用、激活token怎么校验、改密是否验证旧密码、密码策略是否可绕(空密码、超短、与用户名相同)。判据是——有没有一个能让我"跳过某个本该必需的验证"的路径。
**Q2**: 账户需邮箱激活才能用,我没收到激活邮件。
**A2**: 看激活是否真的必需:直接用未激活账户登录看是否被拦、激活token是否可预测/可自造、是否有接口能自助激活。有的系统激活只是形式,登录并不强制校验激活态。
**Q3**: 改密码接口需要旧密码,我没有。
**A3**: 看旧密码校验能否绕:字段留空是否被当作"跳过"、旧密码字段是否根本没被后端读取、是否可通过找回流程绕开旧密码校验直接设新密码。"需要旧密码"常只是前端要求。
**Q4**: 想批量注册/滥用,但有邮箱唯一性限制。
**A4**: 转邮箱规范化漏洞:大小写、加号别名(user+x@)、点号、Unicode同形字可能被当作"不同邮箱"注册但投递到同一真实邮箱,或反之绕过唯一性/抢注特权邮箱。规范化不一致=身份边界模糊。
**Q5**: 所有状态转换都严格校验,逻辑洞挖不出。
**A5**: 转正交维度:从"注册/改密逻辑"转到"这些逻辑依赖的底层能力"——发邮件处若可控收件人可做SSRF/钓鱼、模板处若可注入可SSTI。逻辑严丝合缝时,盯它调用的危险功能。

### 判断某个接口是否"根本不需要认证"
**Q1**: 我在梳理攻击面,想快速找出压根没鉴权的接口。方法?
**A1**: 拿一个已知需鉴权的功能对应的请求,把认证凭据(cookie/token/header)整个去掉再发,看返回。系统化地对每类端点做这个"去凭据重放"。判据很直接——去掉认证还能拿到数据/执行操作的,就是未授权接口。这类洞回报最高、最该先扫。
**Q2**: 大部分接口去凭据后返回401,但有少数返回了数据。
**A2**: 立刻深挖那几个:它们可能是开发遗漏的内部接口、调试端点、或"前端从不直接调所以没人加鉴权"的后台接口。顺着它们能访问的数据面扩展,常能拿到用户列表/凭据/配置。
**Q3**: 需鉴权接口都拦得很好,但我怀疑有隐藏端点。
**A3**: 转端点发现:从JS/移动端/文档/历史存档挖未公开路径,试不同版本前缀(/v1 /v2 /internal /admin)、不同HTTP方法(GET锁了试POST/PUT)、试尾缀绕过(.json、路径大小写、双写斜杠)。隐藏的往往就是没鉴权的。
**Q4**: 有个接口对已知路径鉴权,但换个方法/大小写就绕过了。
**A4**: 这是鉴权中间件的路径匹配缺陷:匹配规则与实际路由解析不一致(大小写、编码、尾斜杠、HTTP方法白名单)。系统化fuzz这些变体,专找"鉴权层和业务层对同一URL理解不一致"的缝。
**Q5**: 全站接口鉴权都严丝合缝、无遗漏端点。
**A5**: 转正交维度:承认"未授权访问"这条走不通,转回"获取合法凭据"或"越权"——用最低权限的合法账户去逐个接口探边界(IDOR/垂直越权)。没有裸奔接口时,就用一个真身份去越权,而不是找无身份的入口。

### 令牌泄露的被动搜集(不打登录先捡钥匙)
**Q1**: 与其猛攻登录,我想先看看有没有token是"捡现成的"。去哪捡?
**A1**: 系统性搜集泄露面:前端JS里硬编码的key/token、Git仓库历史、CI日志、错误页栈信息、Wayback/公开缓存、公开的S3/存储桶、移动端APK反编译。判据是"任何一处把长期凭据写进了可被外部读取的地方"。捡钥匙永远比撬锁快。
**Q2**: JS里发现一个疑似token/key,但不知道有没有权限。
**A2**: 先判类型和范围:是前端公开key(如某些SDK的可公开key)还是本不该暴露的服务端密钥。用它去调对应服务的接口探边界,确认它能读/写什么。分清"设计上就公开的"与"误暴露的"。
**Q3**: 找到的token似乎已过期或无效。
**A3**: 转旁证价值:即便失效,它揭示了token格式、签发方、字段结构、密钥id(kid)等信息,为伪造/理解认证体系提供情报。失效的样本也是分析令牌机制的素材。
**Q4**: 想把泄露搜集自动化但噪声太大。
**A4**: 聚焦高信号来源:优先前端主JS bundle、配置类文件(.env、config.js)、和已知会存密钥的路径。设正则匹配常见token形态(JWT三段式、常见key前缀)。精准比广撒网更有效。
**Q5**: 翻遍所有泄露面,一个可用凭据都没捡到。
**A5**: 转正交维度:被动搜集空手时,转主动技术绕过(前述SQLi/令牌伪造/逻辑漏洞)。或转扩大资产范围——同组织的其他子域/系统可能泄露了能横向复用的凭据。这个目标干净,不代表它的兄弟系统也干净。

### 多租户系统里的租户越界
**Q1**: 目标是多租户SaaS,我有A租户的账号,想越到B租户。切入点?
**A1**: 先搞清租户隔离靠什么实现:请求里的tenantId/orgId字段、子域、还是token里的租户claim。判据是"服务端做数据查询时,租户边界是取自我可控的输入,还是取自不可篡改的会话上下文"。前者就是越界的口子。
**Q2**: 请求里带了明显的tenantId参数。
**A2**: 直接改成B租户的id重放,看能否读到B的数据。若成功即水平越权跨租户。若tenantId在URL、body、header多处出现,注意是否只需改其中一处(后端可能信任了不该信任的那一处)。
**Q3**: tenantId取自token,改不了。
**A3**: 转对象id越界:即便租户claim固定,若按objectId直查资源时未校验"该对象是否属于我的租户",改objectId为B租户的资源id仍可越界(IDOR跨租户)。隔离常在"列表接口"做了、"详情接口"漏了。
**Q4**: 想枚举其他租户的资源id。
**A4**: 看id是否可预测(自增/短随机),或从公开处(分享链接、邮件、导出文件)搜集真实id。可预测的对象id让跨租户越界从"能不能"变成"批量收割"。
**Q5**: 租户隔离在每层都严格校验,越界不成。
**A5**: 转正交维度:从"数据越界"转"控制面越界"——共享的管理接口、跨租户的搜索/报表、平台级super-admin功能、以及租户间共用的缓存/队列。也可转攻租户自身的用户(在我这个租户内部提权)。租户墙很硬时,找墙上的公共门或退回自己院子里提权。

### 认证背后依赖的第三方/内部服务信任
**Q1**: 应用把认证委托给了某个内部/第三方服务,我想利用这层信任。怎么看?
**A1**: 画出信任链:前端→网关→认证服务→业务服务。找"某一跳假设上一跳已经认证过所以自己不再校验"的环节。判据是——业务服务是否直接信任某个header(如X-User-Id、X-Authenticated-User)而这个header可被我从外部注入。
**Q2**: 我怀疑业务服务信任某个身份header。
**A2**: 试从外部请求里直接加上这类header(X-User-Id、X-Forwarded-User、X-Auth-Request-User等常见形态)。若网关本该剥离/覆盖它却没有,业务层就会拿我伪造的身份当真。这是网关鉴权架构的经典裂缝。
**Q3**: 网关会剥离这些header,注入无效。
**A3**: 转"绕过网关直连后端":业务服务是否有未经网关的直接可达地址(内网端口、调试端口、旁路域名)?直连后端时,网关的剥离和鉴权都被跳过,伪造header重新生效。找那条不经过前门的路。
**Q4**: 后端不可直连。
**A4**: 转SSRF借力:若应用内有SSRF,可从"被信任的服务器视角"去请求这些内网免认证/信任内网的接口,等效于站到了信任边界内部。SSRF是把外部攻击者搬进内网信任区的桥。
**Q5**: 信任链每一跳都独立校验、无旁路、无SSRF。
**A5**: 转正交维度:架构层的信任绕过走不通,退回应用层的常规认证/授权漏洞(令牌、逻辑、注入)。或转向链条里最弱的那个服务本身(某个内部服务可能有独立的N-day)。信任链严密时,打组成它的某个薄弱节点。

### 密码找回的答案/安全问题这类弱二次验证
**Q1**: 找回流程用"安全问题"或个人信息做二次验证,怎么打?
**A1**: 先评估这些验证项的"可获取性":安全问题(母亲姓氏、出生地、宠物名)、身份证/工号片段等大多是OSINT可查或可枚举的弱秘密。判据是——这个"只有本人知道"的信息,是不是其实公开可查或答案空间很小。
**Q2**: 安全问题的答案我不知道。
**A2**: 分两路:一是OSINT(社交平台、公开资料常直接泄露这些答案);二是枚举——很多安全问题答案空间极小(是非、有限选项、常见姓氏),可直接爆破,且这类验证常没上限速。
**Q3**: 安全问题有尝试次数限制。
**A3**: 转验证流程的逻辑绕过:答案校验的返回值能否篡改、能否跳过这一步直接到设置新密码、多个验证因子是否可只满足其中最弱的一个。弱二次验证常伴随不严谨的流程实现。
**Q4**: 需要同时验证多项信息。
**A4**: 找"或"逻辑漏洞:本应"全部满足"却实现成"满足其一即可",或某一项校验为空时被当作通过。多因子的实现里,组合逻辑最容易写错。
**Q5**: 二次验证严格、信息也查不到。
**A5**: 转正交维度:放弃"回答验证问题",转前述的token可预测、Host头注入、越权改密等不依赖回答问题的找回漏洞;或彻底换赛道到登录/令牌层。基于知识的验证防不住技术性绕过。

### 无密码/魔法链接/OTP-only 登录的攻法
**Q1**: 目标用"魔法链接"或纯OTP的无密码登录,没有密码可打,怎么办?
**A1**: 重新定位攻击面:无密码把"秘密"从密码转移到了"链接/验证码的投递与校验"。判据是——那个一次性凭证(magic link token / OTP)是否可预测、可拦截、可重放、可枚举。秘密换了载体,弱点也跟着换了地方。
**Q2**: 魔法链接的token看起来随机。
**A2**: 转投递与绑定:链接域名是否取自Host头(可劫持)、token是否绑定发起设备/会话(不绑定则我发起、诱受害者点击后我用)、token是否一次性(可重放则窗口更大)。无密码系统的命门常在token的绑定关系上。
**Q3**: OTP-only登录,验证码6位。
**A3**: 回到OTP爆破/限速探测维度:无密码时OTP就是唯一门槛,若限速不足则直接爆破登入,风险等级比"密码+OTP"高得多。优先验证它有没有严格的尝试限制。
**Q4**: token/OTP的生成和校验都严谨。
**A4**: 转"账户标识"环节:无密码登录通常只需邮箱/手机就发凭证。若能让系统把凭证发到我控制的地址(改变绑定的邮箱/手机、利用规范化让两个标识指向我),就绕过了整个校验。攻投递目标而非投递内容。
**Q5**: 从生成、校验到投递绑定都无懈可击。
**A5**: 转正交维度:无密码登录的会话建立后,后续会话管理/授权仍是常规面,回去打session/IDOR/越权。或转攻它依赖的邮件/短信通道本身(接管邮箱=接管所有无密码账户)。前门无密码且严密时,去打"收凭证的信箱"。

### 判断该继续深挖认证还是换攻击面(元决策)
**Q1**: 我在认证绕过上已经花了很久,该继续还是转向?怎么做这个元决策?
**A1**: 做投入产出评估:列出还没试的正交维度(注入/逻辑/令牌/会话/找回/OAuth/越权),估算每个的信号强度(是否已有异常迹象)。判据是——是否还有"有迹象但没试透"的方向。若所有维度都试过且无信号,继续死磕就是沉没成本。
**Q2**: 认证点看起来就是很硬,但我还没摸别的功能。
**A2**: 立刻转向"认证不是唯一入口"这个认知:很多目标真正的突破口在业务功能(文件上传、导出、SSRF、注入)而非登录。先用现有的最低权限访问把整个应用功能面铺一遍,再回来决定认证值不值得继续。
**Q3**: 我担心一转向就错过了认证这里的洞。
**A3**: 用"记录并搁置"策略:把认证点所有观察到的异常、可疑点、半成品payload记成清单,标注"待回访",然后放心转向。有结构的搁置不等于放弃,后续拿到新情报(如泄露的密钥)可精准回来。
**Q4**: 转向后在别处拿到了低权立足点。
**A4**: 用新立足点反哺认证:内网视角能看到认证服务的配置/日志/密钥、能读数据库里的hash、能直连绕过网关。很多从外部啃不动的认证,从内部一个低权点回看是敞开的。立足点是重新审视认证的新镜头。
**Q5**: 所有维度都试遍,整个目标都打不动,彻底卡死。
**A5**: 做最后的正交转向:扩大范围(同组织其他资产/子域,横向找更弱的兄弟系统)、转时间维度(等新N-day或重新做资产/情报收集)、或转人的维度(在授权范围内的社工/钓鱼)。单个目标的技术面穷尽后,战场要在"资产广度、时间、人"这三个更大的正交轴上重开。

### WebSocket 握手时的认证薄弱点
**Q1**: 目标应用重度使用WebSocket,我想看它的实时通道认证有没有洞。先看什么?
**A1**: 抓WebSocket握手(HTTP Upgrade)那一步:认证凭据是随握手带的(cookie/token)、还是连上之后靠一条应用层消息鉴权。判据是——通道建立与身份校验是否解耦。若先建连后鉴权,建连到鉴权之间的消息可能不受保护。
**Q2**: 握手时带了cookie做认证。
**A2**: 注意WebSocket握手默认不受同源策略和CSRF token约束(经典CSWSH,跨站WebSocket劫持):若服务端只靠cookie而不校验Origin,我可从任意站点发起带受害者cookie的握手,建立以受害者身份通信的通道。先测Origin是否被校验。
**Q3**: 服务端校验了Origin。
**A3**: 转连内消息的授权粒度:建连后每条消息(订阅频道、调用方法)是否重新校验权限?很多实现"连上=全放行",可越权订阅别人的频道或调用管理方法。把攻击面从握手转到消息级鉴权。
**Q4**: 消息级也校验了。
**A4**: 转token在WS场景的处理:因浏览器WS无法自定义header,token常被塞进URL查询串,从而进日志、referer、代理缓存。找这些泄露点拿到token再复用。
**Q5**: WS通道从握手到消息都严密。
**A5**: 转正交维度:回退到承载它的HTTP认证面,或攻WS背后的消息处理逻辑(消息内容注入、反序列化)。实时通道的认证严密时,打它传输的数据本身。

### 认证响应被缓存导致的会话串号
**Q1**: 目标前面有CDN/缓存层,我怀疑认证相关响应可能被错误缓存。怎么判断?
**A1**: 看包含个性化/认证信息的响应(带用户名的页面、Set-Cookie、私有API返回)有没有被缓存的迹象:响应头里的Cache-Control、Age、X-Cache命中标记。判据是——"本该私有、随用户不同的响应"是否被公共缓存存了下来。若是,一个用户的会话/数据可能被缓存后发给其他人。
**Q2**: 发现带Set-Cookie的响应似乎被缓存了。
**A2**: 这可能导致会话串号:A登录时的Set-Cookie被缓存,B请求同一URL时拿到了A的会话cookie。构造/等待这种缓存命中,即可"捡"到别人的已认证会话。先稳定复现缓存键与命中条件。
**Q3**: 想主动投毒而非被动等命中。
**A3**: 转Web缓存投毒:找不进入缓存键但影响响应的输入(某些header),污染一个公共缓存条目,让所有后续用户拿到我构造的内容(如注入的脚本偷token)。从"捡缓存"升级为"投毒缓存"。
**Q4**: 缓存键设计严谨,投毒不进去。
**A4**: 转缓存欺骗(cache deception):诱导受害者访问一个"看起来是静态资源"(加.css/.js后缀)但实际返回其私有数据的URL,使缓存把他的私有响应当静态文件存下,我再去读同一URL。方向是骗缓存去存本不该存的私有页。
**Q5**: 缓存层对认证内容处理得当,无投毒/欺骗空间。
**A5**: 转正交维度:缓存层干净就回到源站的认证/会话漏洞本身。缓存问题是"基础设施配置"维度,打不动就退回"应用逻辑"维度。

### 反序列化型会话令牌的攻法
**Q1**: session cookie解码后像是某语言的序列化对象(Java/PHP/.NET/Python结构),意味着什么?
**A1**: 意味着服务端可能在反序列化我可控的数据——这既是认证绕过面也是RCE面。先确认格式(Java的rO0/aced开头、PHP的a:/O:结构、.NET的ViewState等)。判据是:这个令牌是被反序列化成对象后使用的吗?若是,篡改它就同时威胁"身份"和"代码执行"。
**Q2**: 确认是序列化对象,我想先做认证绕过。
**A2**: 改对象里的身份/角色字段重新序列化(若无完整性保护)。很多框架把用户信息序列化进cookie却不签名,直接改role=admin即可。先试最轻的篡改,能改身份就先拿权限。
**Q3**: 序列化数据带了签名/MAC(如某些框架的签名cookie)。
**A3**: 攻MAC密钥:框架默认密钥、弱密钥、泄露的密钥(配置/源码泄露)。拿到密钥后既能伪造身份也能构造恶意序列化payload。签名令牌的强度完全取决于那个密钥的保密性。
**Q4**: 既然能反序列化,认证绕过之外还该做什么?
**A4**: 升级到反序列化RCE:用对应语言的gadget链构造payload,让反序列化过程触发命令执行。认证绕过只拿到应用内身份,RCE直接拿服务器——同一个洞,后者价值高得多,值得优先尝试。
**Q5**: 对象带完整性保护、密钥拿不到,篡改与gadget都打不出。
**A5**: 转正交维度:密钥是死结时,转"获取密钥"的情报维度(源码/配置泄露),或退回不依赖此令牌的其他认证漏洞。反序列化的门锁死时,门的钥匙(密钥)藏在别处等你去别的维度找。

### 基于来源 IP / 转发头的信任绕过
**Q1**: 某些接口/后台似乎"内网免认证、外网要认证",怀疑靠来源IP判断信任。怎么打?
**A1**: 判断它信任的"来源"是TCP真实IP还是某个可伪造的header。判据是——应用是否读取X-Forwarded-For、X-Real-IP、X-Client-IP等转发头来判定"你是不是内网/可信来源"。若读这些头且不校验,我就能伪造成内网IP骗过它。
**Q2**: 我加了X-Forwarded-For: 内网段地址,没生效。
**A2**: 试头的各种变体和多值构造(XFF可为逗号分隔列表,应用可能取第一个或最后一个)、试其他等价头、试不同大小写。不同框架/代理对"哪个头、取哪一段"理解不一,穷举这些差异找它信任的那一个。
**Q3**: 应用取的是可信代理设置的真实IP,伪造头无效。
**A3**: 转"从被信任的位置发起":若存在SSRF,可让内部服务器代我请求那个只信内网的接口,天然带上可信来源。SSRF把"我在外网"变成"请求来自内网"。IP信任绕不过,就借一个内网的嘴替我说话。
**Q4**: 没有SSRF,也进不了内网。
**A4**: 转找"暴露在外的本应内网"的接口:运维/调试/监控端点常配了IP白名单却又意外可从外部访问,或白名单配置有缺口(如某个中间节点未生效)。找白名单没盖严的那一角。
**Q5**: IP信任严格、无SSRF、白名单无缺口。
**A5**: 转正交维度:基于网络位置的信任打不穿,回到基于凭据的认证面(令牌/口令/逻辑)。位置信任是"你在哪"的维度,穷尽后转回"你是谁"的维度。

### 令牌比较的时序侧信道与短随机
**Q1**: 有个API key / token / 重置码,我怀疑校验方式或长度有弱点。怎么评估?
**A1**: 先评熵和长度:token有多少位、字符集多大、是否有可预测前缀(时间戳/自增段)。判据是——它的有效空间是否小到可爆破,或结构里是否泄露了可推导的部分。短或半结构化的令牌,是可以在合理时间内穷举或推算的。
**Q2**: token够长够随机,爆破不现实。
**A2**: 转比较方式的时序侧信道:若服务端用逐字节短路比较(==而非恒定时间比较),正确前缀越长响应越慢。理论上可逐字节测出正确值。判据是响应时间是否随前缀正确度稳定变化。
**Q3**: 网络抖动太大,时序信号淹没在噪声里。
**A3**: 提高信噪比:大量重复取统计中位数、就近发包、用HTTP/2减少连接开销。但要现实评估——远程时序攻击极难,若抖动始终盖过信号,果断判定此路不通,记为"理论存在但不可行"而非死磕。
**Q4**: 时序打不出,还有别的角度看这个令牌吗?
**A4**: 看令牌生成的随机源:是否用了弱PRNG(基于时间/pid播种)、是否可通过多次索取样本反推种子从而预测后续令牌。弱随机让"高熵"只是表象,能从生成侧预测就不必从比较侧爆破。
**Q5**: 令牌长、随机强、比较恒定时间,侧信道全无。
**A5**: 转正交维度:令牌本身密码学无懈可击时,不打令牌的"值",打令牌的"流转"——它在哪里被传输/存储/日志记录而可能泄露(前述令牌泄露搜集)。算不出、测不出的秘密,总可能在某处被明文写下过。
