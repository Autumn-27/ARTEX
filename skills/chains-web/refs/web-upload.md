# Web · 文件上传绕过决策

### 上传点刚发现:先摸清"回显契约"再动手
**Q1**: 找到一个文件上传功能,还不知道服务端怎么处理。第一步该干什么?
**A1**: 不要急着打 webshell。先传一个"最良性"的合法文件(如 1x1 的 gif/png),观察三件事:响应里有没有回显【存储路径/文件名/URL】、文件名是否被【重命名/加随机前缀/加时间戳】、能不能直接访问到刚传的文件。这三点决定了后续所有策略——路径不可知就没法访问 shell,文件名被完全随机化就要靠别的落地方式。
**Q2**: 回显里根本没有路径,访问也 404,怎么建立"落地可访问"这个前提?
**A2**: 找间接线索:图片类上传常有缩略图/头像展示,查看页面 img src 反推目录规律;下载/导出功能可能暴露真实路径;报错信息(故意传超大或畸形文件)常泄露绝对路径。实在无路径,转向"上传+另一个漏洞组合"思路(如上传配合本地文件包含 LFI)。
**Q3**: 服务端把文件重命名成纯随机 hash 且无回显,单靠上传打不动,往哪转?
**A3**: 这条路(直接 RCE)先搁置。转向【上传作为原语】的其它利用:①上传覆盖已知路径的配置/静态文件(条件竞争或路径穿越);②XXE/SSRF 类文件解析漏洞(传恶意 svg/xlsx/xml);③存储型 XSS(上传 html/svg)。上传能落地本身就是资产,RCE 不是唯一目标。
**Q4**: 怎么快速判断该上传点值不值得深挖?
**A4**: 判据:是否可控落地路径 + 是否可控文件名后缀 + 服务端是否解析文件内容。三者全否则价值低,优先转其它攻击面;有其一即有戏,继续。
**Q5**: 先试后缀还是先试内容?
**A5**: 先做一次"基线探测":传一个正常后缀+webshell内容,再传一个坏后缀+正常内容,分别看拦截点在哪。这能定位过滤是在【前端/后缀黑白名单/内容检测/服务端解析】哪一层,避免盲目穷举。

### 前端 JS 校验:天生纸糊,别浪费时间在浏览器里斗
**Q1**: 选文件时页面弹"仅支持jpg/png",这是哪层校验,怎么处置?
**A1**: 极大概率是前端 JS 校验。判据:拦截发生在【点上传瞬间、没有网络请求发出】。这种校验对代理毫无意义。直接开 Burp,先传一个合法文件让请求发出去,再在 repeater 里改 filename 和 content,或直接禁用 JS/删掉校验函数。
**Q2**: 怎么确认拦截确实只在前端?
**A2**: 抓包看:若被拦时 Burp 里【根本没有对应 POST 请求】,就是纯前端;若请求发出去了、服务端返回拒绝,那才是服务端校验,前端绕过无效。
**Q3**: 绕过前端后服务端又拦了,说明什么?
**A3**: 说明存在多层校验,前端只是第一道。此时把注意力全部转到服务端,前端不用再管。开始逐层拆:后缀?content-type?文件头?内容特征?

### 后缀黑名单:逐个试等价可执行扩展名
**Q1**: 服务端拒绝 .php,判断是黑名单,怎么绕?
**A1**: 黑名单意味着"列举了坏后缀但列不全"。系统性尝试同引擎的等价可执行后缀:PHP 系有 php3/php4/php5/phtml/pht/phps/php7;ASP 系有 asp/aspx/asa/asax/cer/cdx;JSP 系有 jsp/jspx/jspf。逐个试,哪个能落地且被解析就用哪个。
**Q2**: 所有等价后缀都被拦,黑名单挺全,下一步?
**A2**: 转向【解析层欺骗】而非【后缀本身】:①大小写混淆(.pHp,若服务端后缀比较大小写敏感而解析不敏感);②后缀加特殊字符(.php空格、.php.、.php::$DATA[Windows]、.php/[某些环境]);③双写(.pphphp,若做了一次性替换)。
**Q3**: 这些花招也全废,是不是后缀这条路死了?
**A3**: 基本死了。转正交维度:【中间件解析漏洞】(Nginx/Apache 配置缺陷让图片当脚本跑)或【内容型攻击】(不追求脚本落地,改打文件解析)。别在后缀上继续磨。
**Q4**: 怎么知道某个绕过后缀是否真被当脚本执行,而不只是落地?
**A4**: 落地≠执行。落地后访问它,若返回的是【源码文本或原样内容】就是没解析;若返回【执行结果/空白/预期输出】才是被解析。用带明显输出的探针(如打印固定字符串)判定,别用纯 webshell 盲连。

### 白名单后缀:把战场从"后缀"移到"解析"
**Q1**: 服务端只允许 jpg/png/gif,白名单很死,后缀绕不了怎么办?
**A1**: 白名单下别再纠结后缀本身。核心思路转为:让一个【合法后缀的文件】被当脚本执行。三条主路:①中间件解析漏洞;②服务端把文件名拼进包含/解析逻辑(配合 LFI);③文件内容本身触发解析(如上传的是被 include 的配置/模板)。
**Q2**: 有没有可能白名单是"取最后一个点后缀",能不能用多后缀骗?
**A2**: 值得试:shell.jpg.php(骗取后缀检查看到.jpg?通常不行,取最后一个点)、shell.php.jpg(反过来,骗中间件按 .php 解析——这依赖 Apache 多后缀从右往左找可识别后缀的特性)。判据是搞清服务端【取后缀的算法】和中间件【解析后缀的算法】是否不一致,不一致就有缝。
**Q3**: 中间件解析漏洞也不存在(补丁全),白名单铁桶,往哪转?
**A3**: 放弃"上传即RCE"。转【上传+二次漏洞】链:上传合法图片但内容含 phar/序列化 payload,配合 phar://反序列化;或上传 svg/xml 打 XXE;或上传能被其它组件消费的文件(头像被后台管理页渲染 → 存储XSS打管理员)。上传只是入口,利用点在别处。

### Content-Type 校验:改 MIME 头是最廉价的一击
**Q1**: 上传被拒且怀疑查 Content-Type,怎么绕?
**A1**: 这是最容易绕的一层。Burp 里把 multipart 里那段 `Content-Type: application/x-php` 改成 `image/jpeg` 或 `image/png`,内容后缀不动。因为 Content-Type 是客户端可控字段,服务端信它就是设计缺陷。
**Q2**: 改了 MIME 还是拒,说明校验不止 MIME,如何定位真正拦截点?
**A2**: 做控制变量:固定坏内容只改 MIME(拦→不是纯MIME问题);固定好MIME只改后缀(变化→查后缀);固定后缀改文件头(变化→查magic bytes)。逐维度隔离,锁定真实校验维度再针对性打。

### 文件头/magic bytes 检测:给 shell 戴图片帽子
**Q1**: 怀疑服务端读文件头判类型(getimagesize 类),怎么过?
**A1**: 在文件最前面加合法图片的 magic bytes:GIF 用 `GIF89a`,JPG 用 `FFD8FFE0`,PNG 用 `89504E47`。后面再跟脚本代码。让 getimagesize/file 命令误判为图片,而脚本引擎仍会执行其中代码(条件是该文件最终被当脚本解析)。
**Q2**: getimagesize 过了但还是不执行,问题出在哪?
**A2**: 分清两件事:通过图片校验(内容层)和被当脚本执行(解析层)是独立的。图片帽子只解决前者。后者需要后缀/解析漏洞配合。若解析这关过不了,回到"白名单/中间件解析"那条支线;若服务端做了图片二次渲染把附加数据洗掉了,转下面"二次渲染对抗"专节。

### 00 截断:老环境的一次性钥匙
**Q1**: 什么条件下考虑 %00/0x00 截断?
**A1**: 前提苛刻:PHP < 5.3.4 或特定 C 函数处理路径、且【路径/文件名可控并进入文件系统调用】。场景是 `upload/shell.php%00.jpg`,系统在 00 处截断,实际写成 shell.php。判据:目标是老旧环境。现代环境基本无效。
**Q2**: 现代环境 00 截断没戏,等价的"截断类"思路还有吗?
**A2**: 转向其它路径处理缺陷:路径穿越(../ 控制落地目录)、Windows 的 ::$DATA 与结尾点/空格被去除、以及文件名里的换行/特殊字符导致的解析歧义。本质都是"文件名可控 + 系统对文件名的规范化不一致"。

### 中间件解析漏洞:让服务器配置替你执行 shell
**Q1**: 白名单铁桶但目标跑 Nginx/Apache/IIS,该怎么用中间件?
**A1**: 目标是利用【Web服务器把非脚本文件交给脚本解释器】的配置缺陷。Nginx 经典是 `shell.jpg/x.php`(路径信息 + cgi.fix_pathinfo=1,把 jpg 当 php 跑);Apache 从右往左解析多后缀 `shell.php.jpg`;IIS6 有 `x.asp;.jpg` 分号截断和 `x.asp/` 目录解析。先探中间件类型和版本,再选对应技法。
**Q2**: 怎么确认目标存在这类解析缺陷而不是盲试?
**A2**: 先精确指纹中间件+版本+PHP运行方式(fpm/cgi/module)。cgi.fix_pathinfo 相关缺陷只在特定配置成立。传一个无害探针文件用对应路径访问,看是否触发解析。别在明显不适用的架构上耗时间。
**Q3**: 中间件全是新版、配置安全,这条彻底断了往哪转?
**A3**: 回到应用层逻辑:找【应用自己把上传文件路径拼进 include/require/模板渲染】的地方(LFI/模板注入),或【上传文件被其它功能二次处理】的链。中间件不给机会就让应用给。

### .htaccess/web.config:改写解析规则的元武器
**Q1**: 能上传但后缀全被限,能不能改服务器"怎么解析"这件事本身?
**A1**: 若允许上传 .htaccess(Apache)或 web.config(IIS)且目录生效,这是降维打击:上传一个 .htaccess 让 .jpg 被当 php 解析(AddType/SetHandler),再传图片马即可。前提是 AllowOverride 开启、上传目录能放 .htaccess。
**Q2**: .htaccess 传上去了但不生效,可能什么原因,怎么排查?
**A2**: 原因通常是 AllowOverride None、或上传目录不在解析范围、或文件被重命名。排查:确认 .htaccess 是否原名落地(改名就废)、目录是否被 Apache 接管。若 IIS 环境则改用 web.config 同理路线。
**Q3**: 不允许自定义配置文件上传,这招用不了,替代?
**A3**: 转向"利用已有解析规则"而非"新增规则":即中间件既有解析漏洞,或应用层包含逻辑。元武器不可用就退回常规上传绕过矩阵,别卡死。

### 条件竞争:趁"落地到删除"的时间窗打
**Q1**: 上传后文件被立即检测并删除(先落地再校验),还有机会吗?
**A1**: 有——条件竞争。文件从"写入磁盘"到"被删除"之间有微小时间窗。用高并发同时【疯狂上传 shell】和【疯狂访问该 shell URL】,只要某次访问命中未删除的瞬间且触发了写更持久的落地(如 shell 自身再写一个新文件到别处),就赢了。
**Q2**: 竞争一直抢不到,窗口太小,怎么提高成功率?
**A2**: 提高并发+让 payload"自我固化":上传的脚本内容第一件事就是把一个新 webshell 写到另一个目录(脱离被删范围)。这样只要执行一次就永久落地。同时多线程访问,单机不够上分布式。
**Q3**: 服务端改成"校验通过才落地"(内存里校验),竞争窗口消失,转哪?
**A3**: 竞争这条死了。转回内容/后缀绕过让它"校验就通过",或转其它攻击面。条件竞争只对"先落地后校验"架构有效,识别架构再决定用不用。

### 二次渲染对抗:在压缩幸存区藏代码
**Q1**: 图片被 GD 库重新渲染,常规图片马全被洗掉,怎么让代码幸存?
**A1**: 需要理解渲染=解码再编码,某些字节区在这个过程中不变。做法:先上传一张正常图,把渲染后的输出下载回来,对比找出【渲染前后未改变的字节块】,把 payload 塞进那些幸存区,再上传。这样二次渲染后代码仍在。
**Q2**: 找幸存区太费劲,有没有更省力的判断?
**A2**: 先判断值不值得:若该图片仅做展示、不会被当脚本解析,做出图片马也无 RCE 意义,不如转存储型 XSS 或 XXE。只有当"落地文件能被解析执行"时,二次渲染对抗才有终值。先确认解析可行再投入。
**Q3**: 渲染库是 Imagick 不是 GD,对抗策略要变吗?
**A3**: 变——Imagick 攻击面更大,优先打它的解析漏洞(MVG/MSL/svg 触发命令执行、SSRF),而不是费力做幸存区图片马。库越强,越该"打库"而非"绕库"。

### 压缩包上传:解压落地与穿越
**Q1**: 上传的是 zip/tar 且服务端会自动解压,这带来什么机会?
**A1**: 两类:①【解压路径穿越】(Zip Slip):压缩包内文件名带 `../../`,解压时逃出目标目录,覆盖任意位置文件(如写入 web 根目录的脚本、覆盖 crontab/authorized_keys)。②压缩包内藏可执行后缀文件,借解压绕过上传时的后缀检查(检查的是 .zip,解压出的是 .php)。
**Q2**: Zip Slip 写文件但不知道写哪里能 RCE,怎么定目标?
**A2**: 优先覆盖:web 目录脚本(直接 RCE)、计划任务文件、SSH authorized_keys、应用配置/自动加载文件。判据是"哪个文件被系统或应用主动执行/加载"。不确定 web 根路径时,先用报错/信息泄露定位绝对路径。
**Q3**: 解压有安全校验(拒绝 ../ 和绝对路径),穿越封死,还能利用解压吗?
**A3**: 转向【符号链接】(tar 保留 symlink:先让包内含指向 /etc/passwd 的软链,再触发读取)、或【解压炸弹/资源耗尽】做 DoS 试探,或退回"包内藏坏后缀"这条独立支线。穿越封了不代表解压这一功能没别的缝。

### SVG 上传:XSS 与 XXE 的双开口
**Q1**: 允许上传 svg,这算不算"没用的图片"?
**A1**: 恰恰相反,svg 是 XML,天生两个开口:①内嵌 `<script>` → 存储型 XSS(当 svg 被浏览器直接渲染时);②svg 支持外部实体 → XXE(读文件/SSRF/内网探测),尤其当后端用 XML 解析器处理它时。别把 svg 当普通图片放过。
**Q2**: svg 里的 script 不执行(被当 img src 引用),XSS 落空,转哪?
**A2**: img 引用确实不执行脚本。转 XXE:构造带 DOCTYPE 外部实体的 svg,看后端解析(生成缩略图/提取尺寸)时是否发起外连或回显文件内容。用 OOB(打自己的 DNS/HTTP)确认盲 XXE。
**Q3**: 后端解析器禁用了外部实体,XXE 也没了,svg 还剩什么?
**A3**: 转向渲染链下游:若 svg 被转 png(Imagick/rsvg),打转换器的解析漏洞;若 svg 存起来后在【某个真正会执行脚本的页面】被 include,回到脚本执行思路。svg 死了就顺着"它后续被谁消费"继续找。

### 上传+LFI 组合:落地不能执行就找人包含它
**Q1**: 文件能上传但服务端不解析(纯静态目录),同时站点有 LFI,怎么串?
**A1**: 经典组合:上传一个【内容是脚本、后缀随意】的文件(甚至 .jpg 图片马),再用 LFI 去 include 它。LFI 的 include 会执行文件内容,不管后缀。这样绕开了"上传目录不解析"的限制。
**Q2**: LFI 有路径限制(只能包含特定目录),包含不到上传目录?
**A2**: 转向 PHP 伪协议与包装器:`php://filter` 读源码定位、`data://`/`php://input` 直接执行(若 allow_url_include)、或 phar:// 结合上传的图片马触发反序列化。上传文件包含不到就让协议帮忙。
**Q3**: 站点没有 LFI,这条组合成立不了,替代包含点?
**A3**: 找其它"会加载文件内容"的功能:模板引擎渲染用户文件(→SSTI)、反序列化消费上传文件、日志包含(先上传污染日志再包含日志)。核心是"谁会把我落地的字节当代码/数据消费"。

### Phar 反序列化:图片是伪装,phar 是弹头
**Q1**: 上传只收图片、无法执行脚本,但代码里有 phar:// 可达的文件操作,怎么打?
**A1**: 用 phar 反序列化:构造一个 phar 文件,其 meta-data 是恶意序列化对象,把整个 phar 伪装成 jpg(加图片头骗校验)上传。再想办法让某个文件函数(file_exists/fopen/getimagesize 等)以 `phar://上传路径` 触发,反序列化就执行 POP 链。
**Q2**: 上传能过但找不到能被 phar:// 触发的 sink,链断了怎么办?
**A2**: 回到代码审计视角找 sink:任何接受文件路径且路径部分可控的函数都是候选。若目标是黑盒无源码,先靠功能推测(文件预览、图片处理、附件校验)哪里会二次读取上传文件。找不到 sink 就说明这条链不成立,转其它。
**Q3**: PHP 版本已默认不解析 phar 元数据(8.0+),phar 链废了,转哪?
**A3**: 转其它反序列化入口(框架的 unserialize 点、session 反序列化)或放弃反序列化,回到常规 RCE 绕过矩阵。phar 有版本窗口,过期就换弹药。

### 路径穿越控制落地位置
**Q1**: 上传目录固定且不解析,但 filename 字段似乎可控,能不能改落地目录?
**A1**: 试路径穿越:在 filename 里塞 `../../` 把文件写到 web 可解析目录或系统敏感位置。判据:服务端是否对 filename 做了规范化/basename 处理。没处理就能逃出隔离目录,把不可解析变可解析。
**Q2**: 直接 ../ 被过滤,穿越被拦,变形怎么试?
**A2**: 试编码与变体:`..%2f`、`..%252f`(双编码)、`....//`(过滤一次 ../ 后残留)、Windows 下 `..\`、绝对路径注入。本质是找过滤逻辑与文件系统规范化的不一致。
**Q3**: filename 被服务端强制 basename+重命名,穿越彻底无效,转哪?
**A3**: 落地位置不可控就放弃"移动 shell 到解析目录"。转回中间件解析、LFI 包含、或让当前目录变可解析(.htaccess)。路径不可控时,改变"解析规则"比改变"文件位置"更现实。

### 文件名注入:落地路径进入命令/SQL
**Q1**: 除了当脚本执行,文件名本身还能怎么利用?
**A1**: 若服务端把 filename 拼进【shell 命令】(如调用 convert/ffmpeg 处理)或【SQL 语句】或【日志】,filename 就是注入点。构造 filename 含命令分隔符 `;$(...)` 或 SQL 语法或 XSS payload,不追求文件执行,追求"文件名被消费时触发"。
**Q2**: 怎么判断 filename 是否流入了命令执行?
**A2**: 传一个 filename 含 OOB 探针(如 `` `curl 我的服务器` `` 或 `$(nslookup 我的域名)`),看是否有外连回来。盲注思路,用带外通道确认,不依赖回显。
**Q3**: filename 被严格过滤特殊字符,注入不了,还有类似面吗?
**A3**: 转其它可控元数据:图片 EXIF/文档元信息可能被后台提取展示(→存储XSS/注入)、上传时的其它表单字段。凡是"用户可控且被服务端二次处理"的字段都是候选,不止 filename。

### 大小写与后缀规范化不一致
**Q1**: 后缀黑名单看着挺全,有没有"大小写/规范化"级别的缝?
**A1**: 试:①纯大小写 `.PHP/.pHp`(服务端小写比较但文件系统/解析大小写不敏感时可绕,尤其 Windows);②后缀带尾随点/空格 `.php.` `.php `(Windows 自动去除后落地为 .php);③`.php::$DATA`(NTFS 数据流,落地去掉 ::$DATA)。这些都是利用"检查时的字符串"与"落地后的真实名"不一致。
**Q2**: 这些技巧在 Linux 上大多无效,平台不对怎么办?
**A2**: 先确认目标 OS:Windows 特性(尾点、空格、::$DATA、大小写不敏感)在 Linux 上基本失效。判据是指纹 OS。Linux 环境就把精力转到后缀等价名、中间件解析、内容层,别在 Windows 专属技巧上耗。

### 双扩展名与解析算法博弈
**Q1**: 服务端"取最后一个点后的后缀"做白名单,能不能用双扩展骗?
**A1**: 关键是让【上传校验的取后缀算法】和【中间件的解析取后缀算法】不一致。若上传校验取最后一段(看到 .jpg 放行),而 Apache 从右往左找到第一个可识别后缀(遇到 .php 就解析),`shell.php.jpg` 就同时过校验和被解析。这是两套算法打架的产物。
**Q2**: 中间件也取最后一个后缀(不打架),双扩展没用,转哪?
**A2**: 引入分隔符制造第三方歧义:`.php%00.jpg`(截断类)、`.php;.jpg`(IIS分号)、`.php#.jpg`。或退回让中间件规则本身出错(解析漏洞)。算法一致就制造"字符层歧义"让某一方误判。

### 空字节/特殊字符污染文件名解析
**Q1**: 想在文件名里用不可见/特殊字符制造解析歧义,有哪些方向?
**A1**: 方向:null 字节(截断)、换行/回车(污染 multipart 头解析,可能拆分出额外字段)、分号(IIS)、斜杠(制造目录)、Unicode 同形/规范化(overlong UTF-8、全角点)。每一种都是赌"解析器与校验器对同一串字节理解不同"。
**Q2**: 这类字符大多被 WAF/框架规范化掉了,污染失效,还试吗?
**A2**: 现代框架多已规范化,收益递减。判据:先发一两个探针看是否被清洗,清洗了就别穷举。转向逻辑层缺陷(算法不一致、二次处理)比字符级污染更值得投入。

### multipart 协议层畸形绕 WAF
**Q1**: WAF 拦上传请求,但我怀疑它对 multipart 解析不完整,怎么绕?
**A1**: 攻击 WAF 与后端对 multipart 的解析差异:①filename 用引号/编码变体、多个 filename 参数、大小写 `Content-Disposition`;②Content-Type 后加多余参数或换行;③boundary 玩花样(超长、特殊字符、大小写)。目标是让 WAF 解析不到恶意字段而后端能解析到。
**Q2**: 具体从哪个变形先试,有优先级吗?
**A2**: 优先"WAF 少见但后端宽容"的:filename 双写/编码、charset 混淆、multipart 里塞垃圾字段扰乱 WAF 状态机。判据是找到"WAF 看到 A、后端看到 B"的解析裂缝。用响应差异(拦/不拦、落地/不落地)二分定位有效变形。
**Q3**: WAF 解析很健壮,协议层绕不动,转哪?
**A3**: 转"内容层免杀"而非"协议层欺骗":WAF 拦的可能是 payload 特征(如 `eval/system`),那就混淆 webshell 内容(变量函数、编码、无回显)让特征匹配失效。协议绕不了就绕特征。

### webshell 内容免杀:过静态查杀
**Q1**: 文件成功落地并被解析,但一句话木马内容被查杀/WAF 拦,怎么办?
**A1**: 这是内容对抗层。放弃 `eval($_POST)` 这种高特征写法,转:①函数名动态拼接/回调(call_user_func、可变函数);②payload 编码(base64/异或/gzip)运行时解;③利用非常规执行函数(反引号、assert 替代、pcntl、preg_replace /e 老版);④无明显关键字的一句话。目标是消除静态特征。
**Q2**: 免杀 shell 能连但流量被检测(行为层),怎么进一步?
**A2**: 转流量层对抗:用加密流量马(冰蝎/哥斯拉类思路——AES加密通信)、把 C2 藏进正常参数、降低交互频率。静态过了还有流量这关,分层过。
**Q3**: 环境查杀极严,落地即被删,内容免杀也扛不住,转哪?
**A3**: 转"不落地"利用:内存马(通过反序列化/表达式注入注册一个内存中的恶意 filter/servlet/中间件,不写磁盘)。查杀盯磁盘就打内存。这是从"上传落地"彻底转向的正交维度。

### 内存马:当磁盘落地这条路被杀绝
**Q1**: 所有落地文件都被秒删/秒杀,上传落地这条路彻底死,怎么维持执行?
**A1**: 转内存马。前提是已有一次代码执行能力(哪怕是通过上传触发的短暂 RCE、或反序列化、或表达式注入)。用这次执行动态注册一个驻留内存的恶意组件(Java 的 Filter/Servlet/Listener,PHP 的常驻进程/扩展,.NET 的 module),之后靠特定请求触发,磁盘上无文件。
**Q2**: 有短暂 RCE 但重启就没了,内存马也会丢,怎么权衡?
**A2**: 内存马换持久性:牺牲"重启存活"换"磁盘无痕"。判据看目标:若是高对抗环境(EDR杀磁盘)优先内存马;若要长期驻留则想办法落地到监控盲区(非 web 目录、伪装系统文件)或加计划任务。按对抗强度选。
**Q3**: 连一次代码执行都没拿到,只有上传落地,内存马前提不成立?
**A3**: 对,内存马需要先有 RCE 入口。若只有上传,回到"让上传变 RCE"的所有支线(解析/包含/反序列化)。内存马是"已有执行后的驻留手段",不是获得执行的手段,别本末倒置。

### 云存储/OSS 直传:攻击面整个换了
**Q1**: 上传直接走对象存储(S3/OSS)预签名 URL,传统 webshell 思路全不适用,怎么办?
**A1**: 攻击面变了。对象存储桶通常不执行脚本,别想 RCE。转:①预签名 URL/policy 参数是否可篡改(改 key 覆盖他人文件、改 content-type、上传到非预期路径);②桶是否配了 CDN 回源到执行环境;③是否有 SSRF 通过上传回调打内网;④存储型 XSS(桶托管的 html/svg 被同源加载)。
**Q2**: 预签名策略很严、桶隔离得好,直传本身没缝,转哪?
**A2**: 转上传的"前后逻辑":申请预签名 URL 的接口是否越权(替别人生成、遍历 key)、上传完成回调是否可伪造(直接调回调让系统以为传好了、注入回调参数)、以及元数据被后端消费的地方。云上传的缝常在"业务逻辑"而非"文件本身"。

### 上传+SSRF:让服务器替你去取文件
**Q1**: 上传功能支持"从 URL 导入文件",这意味着什么?
**A1**: 天然 SSRF。服务端会去请求我给的 URL。利用:①探内网(给内网地址看响应差异)、②打云元数据(169.254.169.254 取临时凭证)、③协议走私(file:// gopher:// 读文件或打内网服务)。上传功能变成 SSRF 入口。
**Q2**: URL 有协议/域名白名单,SSRF 被限,怎么绕?
**A2**: 转 SSRF 常规绕过:DNS rebinding、302 跳转到内网、IP 编码变体(十进制/八进制/短地址)、@ 混淆、可信域下的开放重定向。目标是让白名单校验的 URL 和实际请求的 URL 不一致。
**Q3**: SSRF 绕不动,但导入功能会把远程内容存下来并解析,还能怎么用?
**A3**: 回到内容层:让远程返回恶意 svg/xml(XXE)、图片(触发处理库漏洞)、或超大文件(DoS)。SSRF 打不动就利用"它取回来之后如何处理这份内容"。

### 文档类上传:office/pdf 的宏与解析
**Q1**: 目标只收 docx/xlsx/pdf 这类办公文档,能怎么打?
**A1**: 这些是复合/结构化文件,攻击面在"解析与后续消费":①docx/xlsx 本质是 zip+xml → 塞外部实体打 XXE、或 Zip Slip;②若文档被转换/预览(LibreOffice/wkhtmltopdf)→ 打转换器(如 wkhtmltopdf 的 file:// SSRF/LFI、宏执行);③若给人下载打开 → 宏钓鱼(社工向)。
**Q2**: 文档只是存档不解析、也不给人开,静态躺着,还有价值吗?
**A2**: 价值低,转其它上传点或攻击面。文档类的杀伤全在"被解析/被打开"这个二次动作上,纯存档等于没有触发条件。判据:追踪这份文档后续会被谁、以什么方式消费。
**Q3**: 文档会被服务端转 PDF 预览,转换器是打点重心,先试什么?
**A3**: 先探转换器类型(响应特征/元数据),再针对性:LibreOffice 的宏/公式、wkhtmltopdf/Chrome-headless 的 SSRF+本地文件读取(html 里放 file:// 或 iframe 内网)、ImageMagick 委托命令注入。转换链是文档上传最肥的面。

### 头像/资源被后台渲染:打管理员的存储型XSS
**Q1**: 上传的图片/资料会显示在后台管理界面,普通用户视角没 RCE,怎么升级?
**A1**: 转存储型 XSS 打管理员。若能上传 svg/html 或让文件名/EXIF 含 XSS payload,且后台管理页原样渲染,管理员一打开就中招——偷 cookie/CSRF token、代其操作、甚至借管理后台功能进一步 RCE。低权限上传变横向打高权限。
**Q2**: 后台对显示内容做了转义,XSS 不弹,替代?
**A2**: 转其它"被后台消费"的注入:文件名/元数据流入后台 SQL、后台调用命令处理文件(命令注入)、后台的文件预览触发 SSRF/XXE。转义挡的是 XSS,挡不住其它 sink。换 sink 继续。
**Q3**: 完全不确定文件会不会被后台看,盲区怎么处理?
**A3**: 埋盲打探针:上传带 OOB 回连的 payload(如 svg 里加外链、EXIF 里放 XSS beacon),等待管理员触发时的外连回调。用带外通道探测"不可见的消费者",有回连说明这条链活。

### 无回显盲传:靠 OOB 与差异建立反馈
**Q1**: 上传后完全无回显、访问不到、不知落地与否,像打进黑洞,怎么判断成效?
**A1**: 建立带外反馈。让 payload 自带回连(webshell 内容里第一行就 curl/dns 我的服务器;svg/xml 用外部实体外连;文件名注入用 OOB 探针)。有回连=被解析/消费了。无回显不等于无反馈,用 OOB 造反馈。
**Q2**: 连 OOB 都不回,是真没打中还是出网被限?
**A2**: 区分二者:换 DNS 外连(比 HTTP 更容易出网)测试是否出网受限;若 DNS 都不回,可能纯内网无出网。转 OAST 的多协议尝试,或改用"时间/响应差异"这种无需出网的盲判据(如触发 sleep 看响应变慢)。
**Q3**: 目标完全不出网、也无差异可测,盲传彻底没反馈,转哪?
**A3**: 放弃盲打这个点,转有回显的攻击面积累信息,或先解决出网(找代理/隧道)再回头。无反馈的点性价比极低,别死磕,记录后转移。

### 文件覆盖:改写已知关键文件而非新增shell
**Q1**: 不能新增可执行文件,但能上传并控制目标路径,还有别的赢法吗?
**A1**: 有——覆盖已存在的关键文件。目标:配置文件(改成恶意配置/开调试)、自动加载/包含的文件、静态资源(打前端供应链)、依赖/模板文件、甚至覆盖认证相关文件。不新增,而是篡改系统已经会执行/信任的文件。
**Q2**: 怎么找到"值得覆盖且能被覆盖"的文件?
**A2**: 判据两条:该文件会被系统/应用主动加载或执行(有触发价值)+ 上传能写到它的路径(可达)。优先框架的自动加载文件、定时任务、可写的模板缓存。先靠信息泄露/报错定位真实路径,再评估可写性。
**Q3**: 目标文件权限只读、覆盖失败,转哪?
**A3**: 转其它可写且有价值的位置(临时目录、缓存目录、日志),或回到"新增+让它被解析"的主线。覆盖受权限约束,写不动就换目标或换手法,不必执着于某个特定文件。

### 上传大小/类型限制引出的边界攻击
**Q1**: 上传有严格大小/数量限制,除了绕它,这些限制本身能否成为攻击点?
**A1**: 能:①上传超大文件/大量文件试资源耗尽 DoS;②大小校验若在前端或可绕,后端无兜底则可传超预期文件破坏存储;③分片上传/断点续传接口常有逻辑漏洞(分片序号越界、合并时路径穿越、未校验总大小)。限制机制本身可能实现有缺陷。
**Q2**: 分片上传接口,重点看什么?
**A2**: 看合并逻辑:分片文件名/路径是否可控(穿越)、能否用分片机制绕过对最终文件的后缀/内容检查(检查在合并前还是后)、并发上传同名分片的竞争。分片把"一个上传"拆成多步,每步交接处都可能有缝。

### 多个上传点:横向比对找最弱的那个
**Q1**: 站点有好几个上传功能(头像、附件、导入、富文本贴图),该怎么选打哪个?
**A1**: 别只盯一个。横向比对:不同上传点常由不同代码/不同人写,校验强度不一。富文本编辑器贴图、后台导入、老功能模块往往校验最松。先快速对每个点做基线探测,挑"校验最弱 + 落地最可能被解析"的下手。
**Q2**: 主上传点铁桶,但另有个隐蔽上传接口没做防护,如何发现这类点?
**A2**: 主动挖:抓全站流量看所有 multipart 请求、目录爆破找 upload/import/api 接口、翻 JS 找隐藏上传端点、看编辑器/插件自带的上传路由。防护往往只加在"显眼"的点,隐蔽点是突破口。
**Q3**: 所有上传点都同样严格(统一网关校验),分不出强弱,转哪?
**A3**: 说明有统一校验层,那就打这一层的通用绕过(协议畸形、解析差异),一处绕过处处通。或彻底转离上传攻击面。统一防护意味着"绕一个=绕全部",集中火力找那层的裂缝。

### 全线受阻:退一步重估上传点的真正价值
**Q1**: 后缀、内容、解析、竞争、组合都试遍了,这个上传点就是打不动,该继续磕吗?
**A1**: 停下重估。红队要控制时间成本。判据:这个点是不是唯一路径?若非唯一,记录已试过的维度,转其它攻击面(其它功能、其它主机、其它协议)。执着于单点是新手病,资深会做"机会成本"评估。
**Q2**: 怎么系统性确认"上传维度确实穷尽了"再撤?
**A2**: 过一遍矩阵清单:前端/MIME/后缀黑白名单/文件头/二次渲染/中间件解析/htaccess/竞争/穿越/双扩展/协议畸形/内容免杀/组合利用(LFI/phar/XXE/SSRF)/云直传/文档解析/存储XSS。每维打勾。全打勾且无缝,才算穷尽,可撤。
**Q3**: 撤了之后怎么不浪费这段侦察?
**A3**: 上传过程积累的情报(绝对路径、OS/中间件版本、后端框架、出网情况、内部接口)对其它攻击面同样有用。把它们喂进整体决策,让这个"失败点"成为其它路径的铺垫。红队没有白打的点,只有没利用好的情报。
