# App客户端 · 通信协议与加密还原

### 拿到一个陌生 App，先流量还是先静态
**Q1**: 目标给了个 apk/ipa,要还原它的通信协议,第一步该抓包看流量还是先反编译?
**A1**: 先抓包定性、再静态定位。流量是"事实",能立刻告诉你:走不走 HTTP、有没有 TLS、body 是明文/base64/密文、有没有 sign/ts/nonce 这类风控字段。不要一上来扎进反编译海里,那样容易在几万个类里迷路。判据:抓 5~10 个典型请求(登录、列表、下单),看请求体形态,先形成"这是什么形态的协议"的假设,再带着问题去逆向。
**Q2**: 流量抓到了,body 是一坨看不懂的字符串,怎么快速定性?
**A2**: 三看:看长度是否 16 字节整数倍(对称分组密码嫌疑)、看字符集(纯 base64/hex/还是二进制)、看是否有固定头部魔数。base64 先 decode 一层看是否出结构;定长且高熵→AES/SM4;开头有 30 82 之类→ASN.1/RSA/证书。
**Q3**: 静态反编译从哪个函数切入最省时间?
**A3**: 不要通读,做"关键字驱动搜索":搜 sign/encrypt/AES/doFinal/getBytes/Cipher、搜请求 URL 里的路径字符串、搜 Content-Type。字符串常量是逆向界的路标,顺着字符串交叉引用往上找到组装请求的那一层。
**Q4**: 这条"先抓包"的路失败了——根本抓不到任何包,代理里一片空白怎么办?
**A4**: 转向"这不是标准 HTTP 代理流量"的假设维度。可能它走了非 HTTP 的自定义 TCP、走了 QUIC/UDP、或做了代理逃逸(不读系统代理)。改用透明网关抓(iptables 重定向 / VPN 模式抓包工具)在链路层截,而不是应用层代理层截。
**Q5**: 透明抓包能看到 TCP 流但都是二进制,不是 HTTP?
**A5**: 说明是自定义二进制协议,转到"协议结构还原"子任务:先按 TCP 流分帧,找长度字段(分包粘包边界),再猜 TLV 结构,同时静态里搜 socket/OutputStream/ByteBuffer 定位打包函数。
**Q6**: 时间紧,怎么判断该继续深挖静态还是切动态 hook?
**A6**: 判据是"关键逻辑是否可读"。如果反编译出来是清晰 Java、关键函数一眼能读→继续静态,成本最低。如果混淆严重/在 so 里/白盒→别硬啃,切动态 hook 直接在运行时抓明文与密钥,用时间换可读性。

### HTTPS 抓包被证书固定(SSL Pinning)挡住
**Q1**: 装了系统证书,浏览器能抓,但 App 一联网就报错断连,典型 Pinning,怎么破?
**A1**: 先确认是不是 Pinning(报 SSL handshake / cert 校验失败,而非业务错误)。破法按成本排序:先试通用绕过脚本(Frida 的 universal unpinning)覆盖 OkHttp/TrustManager/常见框架;不行再定位具体校验点单点 hook。
**Q2**: 通用脚本跑了还是断,说明校验不在标准位置?
**A2**: 说明 Pinning 在非常规层:可能在 native so 里做证书比对、用了 BoringSSL 自校验、或校验响应而非握手。转到 so 层,hook SSL_CTX_set_custom_verify / SSL_get_verify_result 这类底层函数,或直接 patch 校验返回值。
**Q3**: so 层也 hook 了还是不行,怀疑是双向认证(mTLS)?
**A3**: 这是关键转向:如果服务端要求客户端证书,单纯绕过服务端证书校验没用,你缺客户端证书。转到"提取客户端证书/私钥"维度——从 apk 资源、assets、加密的 p12/bks 里找,或运行时 hook KeyStore/PrivateKey 拿到密钥材料。
**Q4**: 客户端证书是加密存储的 p12,密码不知道?
**A4**: 别去爆破密码,去 hook 加载点。App 自己一定要用明文密码去 load,hook KeyStore.load(InputStream, char[]) 直接读第二个参数,或 hook 生成 SSLContext 的地方拿到已初始化好的对象。
**Q5**: 目标是 iOS,Frida 环境搞不定?
**A5**: 转向平台正交维度:iOS 上优先用越狱 + SSL Kill Switch 类工具,或用 objection 的 pinning bypass;实在不越狱就上 MITM + 描述文件信任 + 二进制层 hook。iOS 的 pinning 常在 NSURLSession delegate 的 didReceiveChallenge 里,定位这个回调。
**Q6**: 所有绕过都失败,时间不够了,还有什么退路?
**A6**: 退到"不解密链路、只在端点取明文"这个正交思路:放弃在传输层看明文,改为 hook App 内部的加密函数入口(参数就是明文),或 hook 响应解密函数出口。你要的是明文语义,不一定非要在网络层拿。

### 抓到流量但 body 整体加密,找不到加密入口
**Q1**: 请求体是一整段密文,我想改参数重放,先得找到组装+加密那段代码,从哪下手?
**A1**: 用"明文关键字反查"。你知道某个明文参数值(比如你输入的手机号/用户名),在运行时 hook 常见编码/加密入口(getBytes、String→byte、Cipher.doFinal、Base64.encode),在栈里搜这个明文出现的调用,顺着调用栈就能定位到打包函数。
**Q2**: hook 了 doFinal 但触发太多,噪音大分不清哪个是目标?
**A2**: 加过滤:按数据长度、按调用前后的 URL、按线程、按是否包含你的标记明文过滤。或者反向从网络发送点 hook(OkHttp Interceptor / write(byte[]))拿到密文,再用密文反查是哪次 doFinal 产出的。
**Q3**: 定位到加密函数了,但它调了一堆自定义变换,懒得逐行逆,怎么快?
**A3**: 别逆算法,做"函数级 RPC":直接 hook 这个函数暴露成主动调用接口,输入明文得密文、输入密文得明文。你把 App 当加解密黑盒 oracle 用,绕开算法细节。
**Q4**: 这条"找加密入口"完全卡死,怎么都定位不到?
**A4**: 转向"响应端"这个正交入口。请求加密函数难找时,响应解密函数往往更好抓——因为解密后马上要被 JSON 解析、要 setText 显示。hook JSON 解析入口(fromJson/JSONObject 构造)或 UI 渲染点,反查解密函数,再顺着对称性推请求加密。
**Q5**: 换响应端也不行,怀疑加密在 native?
**A5**: 转 so 层:用 hook 记录 JNI 边界(RegisterNatives 拿到 native 函数地址),对进出 native 的 byte[] 做打印,先不管 so 内部怎么算,先确认明密文在 JNI 边界的形态,把黑盒边界缩到 native 入口。
**Q6**: 只想快速验证漏洞,不想完整还原加密,有没有捷径?
**A6**: 有——如果目标只是"发一个特定加密请求打某接口",用 App 自己当加密器:通过 hook 让 App 用你控制的明文走一遍正常发包流程,截获它产出的合法密文报文,直接拿去重放/改造,完全不还原算法。

### 判断用了什么加密算法
**Q1**: 拿到加密函数但没注释,怎么判断是 AES 还是 DES 还是国密还是自研?
**A1**: 看特征常量。AES 有 S-box / Rijndael 常量表、SHA-256 有 K 常量、MD5 有魔数 0x67452301、SM4 有固定 CK/FK。反编译里搜这些常量表能秒判算法。分组长度 16→AES/SM4,8→DES/3DES。
**Q2**: 看到调用的是标准 Cipher.getInstance,怎么确认模式和填充?
**A2**: 直接读 getInstance 的字符串参数,"AES/CBC/PKCS5Padding"这类一目了然。重点抓 IV 来源:是固定的、随机每次拼在密文头、还是由 key 派生。IV 处理错了重放/构造都会失败。
**Q3**: getInstance 的算法名是运行时拼出来的字符串,静态看不到?
**A3**: 转动态:hook Cipher.getInstance 打印实际 transformation 字符串、hook init 打印 key 和 IV 的 byte[]。运行时一切都是明的,别跟静态里的字符串拼接较劲。
**Q4**: 判出来是"标准算法"但自己实现复现死活对不上,哪里错了?
**A4**: 常见坑排查:字符编码(UTF-8 vs GBK)、key 是直接用还是先 hash/截断、IV 是否前置、有没有先 gzip 再加密、base64 是标准还是 URL-safe、末尾有没有换行。逐个变量固定,拿 App 实测的一组明密文当"金标准"对齐。
**Q5**: 复现始终对不上,怀疑不是标准算法而是魔改?
**A5**: 转"魔改验证"维度:很多 App 会魔改 S-box、改轮数、在标准算法前后加异或/字节置换。别再假设标准库,回到反编译逐个比对轮函数常量,或干脆放弃复现改用前面说的 RPC 黑盒调用。
**Q6**: 判断是国密 SM2/SM4 但工具链不熟?
**A6**: 转到国密专用工具/库(gmssl / bouncycastle 国密扩展)。SM4 用法类比 AES,SM2 是非对称类比 ECC(注意 C1C2C3 vs C1C3C2 密文排列顺序,这是最常踩的坑)。

### 硬编码密钥定位
**Q1**: 确认是 AES,现在要找 key,怀疑硬编码,去哪找?
**A1**: 顺着 Cipher.init 的第二个参数往回追。key 常见藏身:字符串常量、strings.xml/资源文件、assets、拼接出来的、从 native getKey() 拿的。先在反编译里对 SecretKeySpec 的构造做交叉引用,90% 能追到源头。
**Q2**: key 是几段字符串拼接 + 变换出来的,静态追很累?
**A2**: 别手算,动态 hook SecretKeySpec 构造函数直接打印最终 key 的 byte[]。不管它怎么拼、怎么变换,到构造密钥对象那一刻一定是完整明文 key。
**Q3**: 打印出来 key 每次运行都不一样?
**A3**: 说明是动态密钥,不是硬编码。转向"密钥来源"分析:可能是设备指纹派生、服务端下发、或一次一密的密钥协商。这时找单一硬编码 key 是错的方向,得去还原密钥生成/协商逻辑(见密钥协商专条)。
**Q4**: key 在 so 里,native getKey 返回,静态 IDA 也被混淆?
**A4**: 转动态:hook 那个 native 函数的返回值,或 hook JNI 边界拿返回的 jbyteArray。so 混淆再狠,它总要把 key 交给上层 Java 的 Cipher,在 JNI 交接处拦最省事。
**Q5**: 这条"找硬编码 key"彻底走不通(白盒密码学,根本没有独立 key)?
**A5**: 关键转向:遇到白盒(WBC),key 被融进查表运算里,不存在可提取的 key。停止找 key,改为把整个白盒加解密函数当黑盒 RPC 调用,或提取白盒表 + 逆向查表逻辑(成本高,优先 RPC)。
**Q6**: 找到 key 了但只是"其中一层",解出来还是乱码?
**A6**: 说明是多层加密/编码嵌套。转"分层剥洋葱"策略:每解一层就重新判形态(是不是又一层 base64、是不是 gzip 魔数 1f8b、是不是又一段密文),一层层剥,别指望一步到位。

### Frida attach 不上 / 被反调试
**Q1**: 想动态 hook,Frida 一 attach 目标就闪退或检测到,怎么办?
**A1**: 先定位它检测的是什么。常见:检测 frida-server 端口/进程名、检测 /proc/self/maps 里的 frida、检测 TracerPid、ptrace 自附加。对症下药:改 frida-server 名字和端口、用 gadget 注入方式、hook 掉检测函数的返回。
**Q2**: 换了非标准端口还被杀,怀疑是 maps 扫描?
**A2**: 上 hook maps 读取/字符串比对,把含 "frida"/"gum" 的行过滤掉;或者用无端口的注入方式(把 gadget 打进 apk 重打包)避开网络特征扫描。
**Q3**: 反调试太顽固,一直闪退,hook 检测点像打地鼠?
**A3**: 转向"更底层的运行时"维度:用魔改内核/LSPosed/Zygisk 类框架从系统层隐藏,或用模拟器/unidbg 把目标 so 拉出来在受控环境跑,彻底脱离 App 的反调试自检环境。
**Q4**: 是 root 检测导致 App 直接不启动,连 hook 机会都没有?
**A4**: 先过 root 检测再谈 hook:hook File.exists 屏蔽 su/magisk 路径、hook 常见 RootBeer 类库返回 false、用 Zygisk-denylist/隐藏面具。启动都进不去时,root 隐藏优先级高于一切。
**Q5**: 干脆连不上设备/环境天天崩,时间全耗在环境上?
**A5**: 战略转向"静态优先":如果动态环境成本失控,退回纯静态逆向 + unidbg 补环境模拟执行关键函数。别在环境泥潭里无限投入,把能静态解决的先解决。
**Q6**: 目标做了完整性校验,重打包注入 gadget 就启动报错?
**A6**: 转注入方式:放弃重打包,改用运行时注入(ptrace 注入 gadget / LSPosed 模块),不修改 apk 本体就绕过签名和完整性校验。校验的是文件,你不动文件。

### 抓不到包——不是 HTTP 协议
**Q1**: 代理、透明网关都配好了,就是抓不到业务流量,但 App 明明在联网,咋回事?
**A1**: 假设它用了非 HTTP 传输。先在设备上看连接:netstat/ss 看 App 建了哪些 TCP/UDP 连接、连的什么端口。443 以外的怪端口、UDP 连接都提示自定义协议或 QUIC。
**Q2**: 看到它连了个非 443 的 TCP 端口,持续长连接?
**A2**: 长连接 + 自定义端口 → 很可能是自建长连(IM/推送/RPC)。转"二进制协议还原":抓这条流的原始字节,分析分帧,同时静态搜 Socket/Netty/mars/自研网络库定位编解码器。
**Q3**: 是 UDP,怀疑 QUIC 或自研 UDP 协议?
**A3**: QUIC 本身加密抓了也是密文,别在链路层死磕。转到端点 hook:hook App 的网络发送函数(sendto / 网络库的 write)在加密前/解密后取明文,QUIC 的加密对你透明。
**Q4**: 静态里网络库是自研的,找不到标准 send?
**A4**: 转"数据溯源"法:从你知道的明文字段(用户名)出发 hook 编码入口,顺调用栈往下走到最终的字节写出点,不管中间叫什么名字,终点一定是某个 write(byte[])。
**Q5**: 这条完全无解,连它建的连接都定位不到(可能多进程/native 直连)?
**A5**: 转向系统调用层:用 strace/ltrace 或 eBPF 在 syscall 层抓 connect/sendto/write,绕过应用层一切封装。系统调用是最后一道能观测的边界,App 逃不掉。
**Q6**: 抓到二进制流但完全无结构,怎么起步?
**A6**: 做差分分析:发多次相同操作对比字节差异(哪些字节变、哪些不变),变化的往往是序号/时间戳/随机数,不变的是协议头/魔数/命令字。用行为差分反推字段语义。

### protobuf 无 .proto 文件还原
**Q1**: 抓到的 body 是 protobuf 二进制,但没有 .proto 定义,怎么读懂字段?
**A1**: 先用 protobuf 的自描述性硬解:protoc --decode_raw 或在线 raw decoder,能解出 field number + wire type + value 的骨架。这一步不需要 .proto,先拿到结构轮廓。
**Q2**: raw decode 出来只有编号和类型,不知道字段含义?
**A2**: 结合已知语义对齐:你知道请求里有手机号/金额,在 raw 结果里按值匹配(手机号会是 string,金额是 int),给每个 field number 起名,逐步重建语义化的 .proto。
**Q3**: 想批量、可靠地还原,而不是一个个猜?
**A3**: 从 App 里提取现成的 descriptor。很多 App 打包时带了 protobuf 的 FileDescriptor(反射注册用),在反编译里搜生成的 protobuf 类或 .proto 的 descriptor 字节,直接还原出完整定义。
**Q4**: 字段嵌套了 message,还嵌了一层加密的 bytes?
**A4**: protobuf 里的 bytes 字段很可能又是一段密文或嵌套 message。转"分层判形态":对每个 bytes 字段单独判(是嵌套 pb、是密文、还是原始二进制),嵌套 pb 就继续 decode_raw 递归。
**Q5**: decode_raw 直接失败,报不是合法 protobuf?
**A5**: 转向假设修正:可能外面还包了一层(加密/压缩/自定义头)。先剥掉头部/解密/gunzip 再 decode;或者它根本不是 protobuf 而是 thrift/flatbuffers/自定义 TLV,回到形态判断重新定性。
**Q6**: 要改字段重放,手工构造 protobuf 太痛苦?
**A6**: 用还原出的 .proto 生成编解码代码,或直接改 App:hook 序列化前的 message 对象改字段,让 App 自己序列化+加密+签名,你只改语义不碰字节。

### 请求签名 sign 校验绕过 / 复现
**Q1**: 改了请求参数重放,服务端报签名错误,有 sign 字段,怎么复现签名?
**A1**: 先还原签名算法:sign 通常是 参数排序拼接 + 盐/key + hash(MD5/HMAC/SM3)。hook 计算 sign 的函数,打印它的输入串和输出,你就知道"拼接规则 + 盐"这两个关键。
**Q2**: 找到 sign 函数,输入串规则搞清了,但盐从哪来?
**A2**: 盐(salt/appsecret)常和 key 一样藏在常量/native/资源里,方法同密钥定位。hook 到最终喂给 hash 的完整字符串是最快的——盐一定在那个串里明文出现。
**Q3**: 参数排序规则复杂(有的字段不参与签名、有嵌套),复现总对不上?
**A3**: 精确对齐:打印 App 真实计算时的原文串,和你自己拼的逐字符 diff,立刻看出哪个字段没算进去、顺序哪不对、有没有 URL 编码差异。以 App 的原文串为唯一真相。
**Q4**: 干脆不想复现,能不能不算 sign?
**A4**: 转"借刀"思路:hook sign 函数暴露成签名 oracle,你传参数它返回 sign;或让 App 帮你签——用 hook 把你的参数注入到正常请求流程,App 自己签好发出去。省掉复现整个算法。
**Q5**: 这条路失败——sign 在服务端也校验 body 的完整加密,单改参数无论如何过不了?
**A5**: 说明签名覆盖了整个加密 body,转向"从加密前动手":不要在密文/签名层挣扎,回到明文层——在 App 加密+签名之前用 hook 修改明文参数对象,后续加密和签名都是 App 自动做,天然合法。这是攻加密+签名双保险接口的通用打法。
**Q6**: 还想进一步做未授权/越权测试,但每个请求都要合法签名太慢?
**A6**: 把 App 做成"签名代理服务":常驻 hook + 一个本地 HTTP 接口,你的 fuzz/越权脚本发明文,App 侧自动加密签名后转发。这样就能用常规 Web 测试工具打这个加密接口了。

### 时间戳 + nonce 防重放
**Q1**: 复现了加密和签名,单个请求能过,但过一会儿再发就失效,怎么回事?
**A1**: 大概率是 ts(时间戳)超窗口 + nonce 防重放。先确认:请求里有没有 timestamp、随机 nonce 字段,且它们参与签名。服务端校验 ts 在几分钟窗口内、nonce 不复用。
**Q2**: 确认有 ts,怎么让重放持续有效?
**A2**: 不要重放旧包,要"实时重签":每次发请求前用当前时间生成 ts、生成新 nonce,重新计算签名。也就是把静态重放升级成动态构造。
**Q3**: nonce 有服务端下发的挑战值(challenge),不是客户端随机的?
**A3**: 转"先取 challenge 再应答"两步流程:先请求拿到服务端 nonce/challenge,再用它构造应答。逆向要还原的是"challenge→response"的计算关系,而不是找固定值。
**Q4**: 时间戳还带客户端时钟同步/服务端时间偏移校正?
**A4**: hook 取时间的地方看它用的是本地时间还是服务端下发的基准时间;若是服务端基准,先抓一次时间同步接口拿 offset,构造请求时用"服务端时间"而非本地时间。
**Q5**: 全都对了还是失败,防重放机制根本绕不过?
**A5**: 转向"不重放、走活体"这个正交维度:放弃离线构造,直接把 App 变成实时代理(hook 明文注入),让每个请求都是 App 现场生成的合法请求,ts/nonce/签名全部由 App 实时产生,防重放对你无效。
**Q6**: 想批量跑接口但 nonce 有频率限制/一次一用?
**A6**: 评估这是防护而非可绕点时,调整测试策略:降低并发、串行取 nonce、或聚焦逻辑漏洞(用少量合法请求验证越权/参数篡改),而不是高频 fuzz。识别"这是设计限制"避免在此空耗。

### 加壳 App 脱壳
**Q1**: 反编译打开发现没几个类,或者类名全是壳的 loader,加壳了,怎么脱?
**A1**: 先识别壳类型(看包名/特征 so:常见几家商业壳有指纹)。脱壳按代次:一代壳整体 dex 在内存,用内存 dump 类工具在运行时把 dex 拉出来;高代次抽取壳(方法级抽取)要用主动调用/补 dex 的脱壳机。
**Q2**: dump 出来的 dex 方法体是空的(CodeItem 被抽取)?
**A2**: 这是函数抽取壳。转"主动调用脱壳":用 FART/北斗 类框架遍历所有方法触发解密还原,在方法执行前 dump CodeItem 再回填,重组出完整 dex。
**Q3**: 只关心某几个关键加密函数,不想脱整个 App?
**A3**: 精准打击:定位到目标类/方法,用 hook 在它被调用、代码已还原到内存那一刻单点 dump,或者干脆不脱壳直接 hook 它的入参出参拿明文。脱壳是手段不是目的。
**Q4**: 脱壳后的 dex 反编译还是报错/结构破损?
**A4**: 修复 dex 头和引用(用脱壳机自带修复或专用工具),或换个反编译器交叉验证。破损常因 dump 时机不对,换个更晚的 dump 点重来。
**Q5**: 关键逻辑根本不在 dex 里,全被搬进 so 了?
**A5**: 转 so 层:壳把核心逻辑 native 化了,脱 dex 白费。改逆向 so(IDA/Ghidra)或 hook JNI 边界 / unidbg 模拟执行,战场从 Java 层转到 native 层。
**Q6**: 脱壳环境总崩(壳有强反调试)?
**A6**: 转向"环境隔离"维度:用定制 ROM / 特定安卓版本 / 模拟器规避壳的环境自检,或用云真机。壳的反调试常绑定特定检测面,换环境比硬刚检测点快。

### so 层 native 加密逆向
**Q1**: 加密全在 libxxx.so 里,IDA 打开一堆汇编,从哪切入?
**A1**: 先定位入口:看 JNI_OnLoad 里的 RegisterNatives 拿到 native 方法与 so 内地址的映射,直接跳到目标 native 函数,不用在整个 so 里瞎逛。
**Q2**: 函数找到了但太长,不想逐条读汇编?
**A2**: 先动态观察再决定要不要细读:hook 这个 native 函数的入参(明文 byte[])和返回(密文),如果输入输出关系稳定,直接当黑盒 RPC 用,根本不用读 so 内部。
**Q3**: 必须还原算法(比如要离线批量算),so 又被 OLLVM 混淆(控制流平坦化)?
**A3**: 转反混淆:用符号执行/去平坦化脚本(基于 IDA/Miasm/Triton)还原原始控制流,或用 unicorn/unidbg 直接模拟执行这段代码,黑盒喂输入取输出,绕开静态读混淆的痛苦。
**Q4**: so 里还有 native 反调试(ptrace 自附加、检测)?
**A4**: hook/patch 掉 native 反调试:hook ptrace 让它返回成功、patch 检测分支。或者用 unidbg 在纯模拟环境跑,根本没有真实 ptrace 环境,反调试逻辑自然失效。
**Q5**: unidbg 补环境补到一半,缺一堆 JNI/系统调用补不动?
**A5**: 权衡转向:如果补环境成本超过收益,退回"真机 hook 黑盒调用"——不追求脱离 App 的独立复现,接受"必须有 App 在场"的 RPC 方案。unidbg 适合函数纯净、依赖少的场景,依赖爆炸时及时止损。
**Q6**: so 是加壳的(so 也被保护/加密段)?
**A6**: 转 so 脱壳:很多 so 保护是运行时解密代码段,在 so 加载后、函数执行时从内存 dump 出解密后的 so,再拿去静态分析;或直接在解密后的内存里 hook。

### 白盒密码学(WBC)识别与应对
**Q1**: 找加密函数发现没有独立 key,一堆巨大的查表和位运算,怀疑白盒,怎么确认?
**A1**: 白盒特征:超大静态表(几十 KB~MB 的查找表)、密集的字节代换+异或、没有可辨识的独立 key 变量、算法结构像 AES 但塞进了表里。看到"大表 + 查表流水线"基本可判白盒。
**Q2**: 确认白盒后,还想不想提 key?
**A2**: 通常别提。白盒的设计目的就是让 key 不以明文存在,提取需要 DFA/BGE 等专门的白盒攻击,成本极高。红队实战优先级:先把白盒函数当黑盒 RPC 用,满足"能加解密"即可。
**Q3**: 但我需要离线、脱离设备批量加解密?
**A3**: 提取整个白盒实现搬走:把查表数据 + 运算逻辑完整 dump 下来,用 unidbg/unicorn 模拟执行或移植成独立程序。你搬走的是"带表的加密机器",不是 key。
**Q4**: 白盒在 so 里且和反调试/完整性校验绑死,一动就崩?
**A4**: 转"就地取用"策略:不搬走,在真机上把白盒函数暴露成本地服务(hook + 本地接口),让它待在原生环境里正常跑,你远程调用。绕开搬迁引发的一切环境依赖。
**Q5**: 想真破白盒拿 key(比如要伪造大量凭据),值不值?
**A5**: 做 ROI 判断:白盒差分故障分析确实能出 key,但需要专业密码分析投入。除非目标价值极高且必须离线大规模伪造,否则这条路对红队时间线通常不划算,回到 RPC/黑盒方案。
**Q6**: 白盒 + 动态密钥协商叠加(表也是下发的)?
**A6**: 转"协商流程还原"维度:表/参数是服务端下发的,说明有一层密钥/参数分发协议,先还原分发协议拿到当前会话的表,再谈用表。战场从"破表"变成"抓分发"。

### 密钥协商 / 一次一密(DH/ECDH/下发)
**Q1**: hook 到 key 每次都变,确认是动态密钥,怎么还原?
**A1**: 先分清是"协商"还是"下发"。看有没有握手请求:客户端发公钥/随机数、服务端回公钥/加密的会话密钥→协商(DH/ECDH/RSA 封装)。有个接口直接下发密文 key→服务端下发。抓握手报文定性。
**Q2**: 是 ECDH 协商,想还原会话密钥?
**A2**: 你既然在客户端有完全控制权,不用破 DH——hook 协商完成后生成的会话 key(在 KDF 输出/SecretKeySpec 构造处),直接拿到本次会话的对称 key,后续用它解密整段会话流量。
**Q3**: 想离线解密之前抓的一段流量(事后取证式)?
**A3**: 需要当时的会话密钥或私钥。若客户端私钥是固定的(RSA 封装场景),提取私钥可解历史流量;若是 ECDH 临时密钥,没当时的中间值就解不了,必须实时 hook。判断清楚再决定能不能"事后解"。
**Q4**: 服务端下发的 key 本身又被一个上层密钥加密(密钥链)?
**A4**: 顺密钥链往上剥:找解开"下发 key 密文"的那个上层 key(常是硬编码根密钥或设备派生),解出会话 key。层层套娃时,每层都用"hook 解密函数出口"取下一层明文最省事。
**Q5**: 协商里掺了服务端随机数,想中间人篡改却过不去?
**A5**: 转向:如果目标是解密/构造而非 MITM,别做中间人。你在客户端是"合法一端",直接用客户端 hook 到的会话密钥操作即可,不需要在协商里插手。MITM 是解决"我不是通信方"时才用的手段。
**Q6**: 整个协商在 native 里、又是白盒,实时 hook 也拿不到干净的对称 key?
**A6**: 退到最终使用点:不管协商多复杂,业务数据总要用某个 key 过一次 Cipher.doFinal/native 加密函数。在"实际加解密业务数据的那一次调用"处 hook 参数,是密钥协商所有复杂度的最终收敛点。

### 混合应用 / 小程序 / H5 抓包
**Q1**: 目标是小程序或 App 里的 H5 页面,常规抓包看到的是 WebView 流量,还有加密,怎么搞?
**A1**: 分清层次:H5/小程序的加密逻辑在 JS 里,不在 native。先抓包看请求形态,再去拿 JS 源码——小程序有 wxapkg 包可解包拿到源码,H5 直接看远程 js。战场从二进制逆向变成 JS 逆向。
**Q2**: 小程序包解出来的 JS 被压缩/混淆?
**A2**: 用 JS 反混淆(AST 还原、变量重命名)+ 格式化,再搜 encrypt/sign/CryptoJS 关键字。JS 逆向比 native 友好得多,且能直接在浏览器/node 里调试执行验证。
**Q3**: 加密函数在 JS 里但依赖小程序运行时环境(wx.xxx),抠不出来单独跑?
**A3**: 补环境或就地调:补齐 wx 等全局对象的 mock 在 node 里跑,或直接在小程序开发者工具/调试环境里断点 hook,让它在原生环境算,你取值。类比 native 的 RPC 思路。
**Q4**: 是 WebView 里的 H5,JS 又调了 native 的 JSBridge 做加密?
**A4**: 转 JSBridge 边界:hook WebView 的 addJavascriptInterface / JS 调 native 的桥接方法,在桥这一层取明密文。JSBridge 是 H5 和 native 的交接点,加密常发生在跨越它的时候。
**Q5**: WebView 流量根本抓不到(自定义 WebView/内核)?
**A5**: 转 JS 层 hook:直接 hook JS 引擎里的 XMLHttpRequest/fetch/发请求函数,或注入 JS 打印请求前的明文。绕开链路层,在 JS 运行时取数据。
**Q6**: 加密 key 在 JS 里但也是服务端下发/动态?
**A6**: 同 native 思路收敛到使用点:hook JS 的加密调用(CryptoJS.AES.encrypt 之类)打印 key 和明文,不管 key 怎么来,在调用那一刻是明的。JS 里连断点都不用编译,更方便。

### 设备指纹 / 风控拦截
**Q1**: 加密签名全复现对了,请求却被风控拦(返回风控码/滑块),怎么办?
**A1**: 先定性拦截原因:缺设备指纹字段、环境被识别(root/frida/模拟器)、行为异常(频率/无正常前置请求)。看被拦请求缺了哪些正常请求有的 header/字段,风控往往靠一堆环境采集字段。
**Q2**: 发现请求头里有个 device-id / 风控 token 字段,是加密的设备指纹?
**A2**: 转"指纹生成还原":hook 生成这个字段的函数,它采集了 IMEI/mac/传感器/系统属性等拼成指纹再加密。你需要的是让它生成一个"看起来正常"的指纹,直接用 App 现生成的即可(hook 取值),别自己造。
**Q3**: 环境本身被判风险(检测到 hook/root)导致指纹带风险标记?
**A3**: 回到环境隐藏维度:先把 root/frida 藏干净(Zygisk 隐藏、去特征),让 App 采集到"干净环境"再生成指纹。指纹是环境的快照,环境脏了指纹就脏了,顺序是先净环境后取指纹。
**Q4**: 风控要求真人行为序列(先浏览再下单),纯打接口触发风控?
**A4**: 转"行为链补全":别只发目标接口,补齐正常业务前置请求(初始化、埋点、列表),模拟合理时序。风控看的是行为图,不是单点请求。
**Q5**: 死活过不了风控,这条协议复现路线还值得继续吗?
**A5**: 做正交转向判断:如果风控是硬骨头,评估是否改用"活体 App 代理"——让真机上的正常 App 帮你发请求(hook 注入 payload),你的攻击藏在合法环境和合法行为里,风控几乎无从识别。这是对抗强风控最稳的通用退路。
**Q6**: 目标其实是找漏洞不是刷量,风控只是挡路?
**A6**: 摆正目标:风控主要防批量/自动化,做逻辑漏洞验证只需要少量合法请求。用"App 代理 + 手工/低频"方式发几个精心构造的请求验证越权/参数漏洞,完全避开触发风控的高频行为。

### 请求能过但服务端二次校验参数
**Q1**: 我改了金额/ID 重放,签名加密都合法,服务端却报错或不生效,为什么?
**A1**: 服务端做了业务侧二次校验(金额和商品对不上、ID 不属于当前用户、状态机不允许)。别怀疑加密复现,这是逻辑层。先看错误码语义,区分"技术性拒绝(签名/格式)"和"业务性拒绝(逻辑校验)"。
**Q2**: 怎么确认加密复现没问题、问题在业务逻辑?
**A2**: 控制变量:先原样重放不改任何参数,若成功→加密链路 OK,失败原因在你改的那个参数触发的业务校验。这一步把"我加密错了"和"服务端不让我改这个"分开。
**Q3**: 确认是越权类业务校验,怎么找可改的点?
**A3**: 转 Web 逻辑漏洞思路:枚举哪些参数服务端没校验归属(改别人的 order_id、改数量、改状态),做水平/垂直越权测试。加密只是外壳,里面是标准的 Web 越权/逻辑漏洞战场。
**Q4**: 每改一个参数都要重新加密签名,测试效率极低?
**A4**: 上"加密代理":把 App 做成本地加解密/签名代理服务,让 Burp/脚本发明文,代理层自动加密签名转发、并把响应解密回明文。这样就能用成熟 Web 测试工具流畅 fuzz 加密接口。
**Q5**: 二次校验里有个字段是服务端算的哈希/token,改了主参数它对不上?
**A5**: 追这个关联字段的来源:是客户端算的(那就一起重算)还是上一步接口返回的(那就先走上一步拿到匹配的值)。转"多步业务流"还原,把有依赖的字段按调用链顺序凑齐。
**Q6**: 折腾半天发现服务端确实校验严密,单接口打不动?
**A6**: 转攻击面:换别的接口。同一 App 几十上百个接口,防护强度不均,老接口/内部接口/新上线接口常有薄弱点。用还原好的加密能力去广度扫接口,而不是死磕一个硬点。

### 混淆严重(OLLVM / 控制流平坦化)读不懂
**Q1**: 反编译或 IDA 出来控制流平坦化、假分支满天飞,人根本读不下去,怎么办?
**A1**: 先别硬读。评估是否需要"读懂算法"——如果只要输入输出,直接动态 hook/模拟执行黑盒取值,混淆再狠都不影响黑盒行为。读源码是成本最高的路,能不读就不读。
**Q2**: 确实必须还原逻辑(离线批量/无法带 App),怎么对付平坦化?
**A2**: 用去混淆工具链:符号执行(Triton/Miasm/angr)恢复真实控制流、去除分发器(dispatcher),或用 IDA 插件去平坦化。把混淆后的 CFG 还原成可读的原始逻辑再分析。
**Q3**: 字符串还被加密了(动态解密),交叉引用找不到路标?
**A3**: 转动态取字符串:hook 字符串解密函数批量 dump 所有解密后的字符串,或运行时 dump 内存里已解密的字符串表。有了明文字符串,交叉引用的路标就回来了。
**Q4**: OLLVM 还叠加了虚拟化(VMP 类)保护?
**A4**: 虚拟化是最硬的,逆 VM 解释器成本极高。战略转向:坚决走黑盒——unidbg/真机 hook 让被虚拟化的函数正常执行,你只取输入输出。逆 VM 只在万不得已(必须完全还原且无法执行)时做。
**Q5**: angr/符号执行路径爆炸跑不出来?
**A5**: 缩小范围 + 换执行式模拟:只对关键小函数做符号执行,大范围用 unicorn 具体值模拟(concrete execution)喂真实输入跑一遍拿结果,避免路径爆炸。混合具体+符号比纯符号实用。
**Q6**: 时间预算快耗尽,还没读懂?
**A6**: 及时止损转黑盒:承认"读懂"这条路不划算,回到 hook 黑盒 RPC 满足实战需求。红队目标是打通攻击链,不是发表逆向论文,能用即可。

### hook 到明文但只在特定时机 / 不稳定
**Q1**: hook 上了,偶尔能打印出明文,但大多数时候打不到或漏,咋回事?
**A1**: 排查触发条件:是不是多进程(hook 错了进程)、是不是多个重载函数只 hook 了一个、是不是时机太早函数还没加载。先确认 hook 到的是不是真正跑业务的那个进程和那个方法。
**Q2**: 确认是多进程,业务在子进程/native 进程?
**A2**: 转多进程注入:让 hook 框架 spawn 时注入所有进程或指定目标进程,用进程名过滤。App 常把网络/加密放独立进程,hook 主进程当然打不到。
**Q3**: 函数有多个重载 / 泛型擦除导致 hook 不全?
**A3**: 枚举所有重载都 hook,或 hook 更底层的收敛点(所有重载最后都会调的那个基础函数)。往调用链下游找唯一必经之路,比在上游追多个分叉稳。
**Q4**: 时机问题——函数在 hook 脚本加载前就执行了?
**A4**: 改用 spawn 模式(挂起启动、注入完成再放行)而不是 attach 模式,确保 hook 先于目标代码执行。attach 慢一步就漏早期调用。
**Q5**: hook 本身导致 App 行为变了/崩了(观察者效应)?
**A5**: 减少侵入:hook 里别做重操作(避免大量日志/阻塞),只读不改;或换更轻的观测方式(内存断点/采样)。若 App 检测到 hook 副作用,回到反调试隐藏维度。
**Q6**: 折腾很久 hook 始终不稳,还有别的取数据方式吗?
**A6**: 转正交观测手段:改用内存扫描(在密文发送前扫内存找明文残留)、或 core dump 后离线分析、或 eBPF 在 syscall 层观测。hook 不是唯一的运行时观测方式,换一种观测面。

### 请求和响应都加密都要还原
**Q1**: 请求 body 加密、响应 body 也加密,两边都要还原,先搞哪个?
**A1**: 先搞响应解密——因为解密后的数据马上要被 JSON 解析/展示,更好定位(hook UI 或 JSON 入口反查)。而且请求加密和响应解密常用同一套 key/算法,搞定一边另一边基本白送。
**Q2**: 搞定响应发现和请求算法不同(非对称)?
**A2**: 分别处理:很多 App 请求用一套(可能含非对称封装 key)、响应用对称。分别 hook 两个方向的 Cipher 调用,记录各自的算法/key/IV。别假设两边一定对称。
**Q3**: 想做完整的中间层还原(既能读响应又能改请求)?
**A3**: 搭双向加解密代理:请求方向明文→加密→发,响应方向密文→解密→给你。用 App 的 hook 能力或复现的算法实现这个代理,你就得到一个"明文视角"的目标 App。
**Q4**: 响应解密卡住(响应先解密再验签,验签不过它自己丢弃)?
**A4**: 转 hook 更下游:在它验签通过后、真正解析业务数据的地方 hook;或 hook 验签函数让它恒真,让流程往下走到解密后的明文。跟着数据流找"已是明文"的那一刻。
**Q5**: 两边都还原了但只想快速验漏洞,不想搭完整代理?
**A5**: 按需简化:验单个漏洞时,手工解一次响应看结果、手工加密一次请求发出去即可,不必工程化。工程化代理是为大量测试准备的,小规模验证别过度投入。
**Q6**: 响应里还嵌套加密字段(整体解密后某字段又是密文)?
**A6**: 分层剥:整体解密拿到 JSON 后,对可疑字段单独判形态再解。多层加密常见于敏感字段(密码/支付),外层会话加密 + 内层字段加密,逐层处理。

### 决策:纯静态逆 vs 动态 hook vs RPC/unidbg
**Q1**: 面对一个加密还原任务,三条路(静态逆算法 / 动态 hook 取值 / unidbg 模拟)该选哪条?
**A1**: 按"目标 + 可读性 + 是否需要离线"三维决策。只要输入输出且能带 App→动态 hook RPC(最快)。必须离线批量且函数纯净→unidbg。必须完全理解算法(写报告/无法执行)→静态逆。默认从 hook 起步,成本最低。
**Q2**: 一开始怎么快速判断该走哪条,不至于选错浪费时间?
**A2**: 先花 10 分钟侦察:反编译看关键函数可读性(清晰 Java?混淆?native?)、看是否有反调试(能不能 hook)、看需求(要不要脱离设备)。侦察结果直接映射到三条路之一,别盲选。
**Q3**: 选了 hook,但需求其实要离线大批量,hook 带 App 太慢?
**A3**: 及时切 unidbg:把关键 so 函数拉进 unidbg 模拟,补最小环境,得到脱离设备的高速加解密。判据是"是否需要脱离 App 且高吞吐",满足就值得付补环境的成本。
**Q4**: 选了 unidbg 但环境依赖爆炸补不动?
**A4**: 回切 hook RPC:承认这个函数依赖太重不适合模拟,退回真机 hook 黑盒调用,接受"带 App"的代价。三条路要能来回切,发现此路成本失控就换,不要沉没成本绑架。
**Q5**: 三条路都试了都很痛苦,是不是方向错了?
**A5**: 反思攻击目标本身:也许根本不需要还原这个加密。重新看目标——如果只是要打某个接口,前面说的"App 当加密器/代理"可能几分钟搞定,比还原算法优雅。先问"我到底要什么",避免为逆向而逆向。
**Q6**: 团队协作,怎么让还原成果可复用?
**A6**: 产出接口化的加解密能力(本地服务/库),而不是一次性脚本。无论走哪条路,最终封装成"明文进密文出"的稳定接口,后续所有攻击(fuzz/越权/重放)都复用它。

### 代理逃逸——部分流量不走系统代理
**Q1**: 配了系统代理,登录能抓到,但关键接口抓不到,像是绕过了代理?
**A1**: 这是代理逃逸(App 主动不读系统代理,直连 socket)。先确认:抓到的和抓不到的是不是不同域名/不同网络库。关键接口自己 new Socket 直连就绕过了系统代理设置。
**Q2**: 确认它直连,怎么把这部分流量拉回来?
**A2**: 用透明代理/VPN 模式在网络层强制重定向(iptables REDIRECT / tun 抓包),不依赖 App 主动走代理。链路层劫持对代理逃逸免疫,因为它劫的是数据包不是代理配置。
**Q3**: 透明代理也抓不到(它还做了 TLS Pinning 或直接 TCP)?
**A3**: 分两种:若是 HTTPS+Pinning,叠加前面的 unpinning;若是自定义 TCP,回到二进制协议 + 端点 hook。代理逃逸常和 Pinning/自定义协议叠加出现,分层解决。
**Q4**: 它甚至用了 DNS-over-HTTPS / 自定义 DNS 绕过我的解析劫持?
**A4**: 转端点 hook:DoH/自定义 DNS 让链路劫持失效时,直接在 App 里 hook 网络发送函数取明文,或 hook 它的 DNS 解析/连接函数。App 内部一切绕过对"在 App 里 hook"都无效。
**Q5**: 链路和 hook 都试过还是漏,怎么系统性排查漏了哪些流量?
**A5**: 转 syscall/eBPF 全量观测:在系统调用层记录所有 connect/write,和你抓到的对比,精确定位哪些连接漏了、连到哪。用最底层的观测面做流量审计,不留死角。
**Q6**: 就是想彻底看清 App 所有出站流量,有没有兜底方案?
**A6**: 终极兜底是"在 App 与内核之间"截:tun 模式全量接管 + hook 加密前明文,两者叠加。链路层保证抓到所有包(哪怕密文),hook 层保证拿到明文语义,组合起来无遗漏。

### iOS App 逆向的差异化决策
**Q1**: 目标从安卓换成 iOS 版,同样要还原加密,思路要怎么调整?
**A1**: 核心方法论一样(抓包定性→定位加密→hook 取值),但工具链和环境不同:iOS 是 Mach-O/Objective-C/Swift、有沙盒和签名限制。先决定越狱还是不越狱,这决定了后续所有手段。
**Q2**: 有越狱设备,怎么快速上手?
**A2**: 越狱下和安卓类似:Frida/objection 做 hook,class-dump/Hopper/IDA 看 OC 方法,SSL Kill Switch 破 pinning。OC 的方法名通常没混淆,比安卓还好读,顺着方法名找 encrypt/sign。
**Q3**: 拿不到越狱设备,只有普通设备?
**A3**: 转免越狱路线:重签名注入 Frida gadget(用 objection patchipa / 手动 dylib 注入),或用非越狱的抓包 + 描述文件。能力受限但能覆盖大部分 hook 需求。
**Q4**: 加密在 Swift 里,符号被 strip、名字重整(mangling)难读?
**A4**: Swift 比 OC 难逆:先 demangle 符号,重点还是转动态 hook(hook 到方法就行,不必读懂 Swift 实现)。Swift 静态逆成本高,更依赖运行时取值。
**Q5**: iOS 特有的保护(越狱检测、加固)让 hook 环境起不来?
**A5**: 转越狱隐藏 + 环境处理:用越狱隐藏工具过检测,或换更干净的越狱方案。若加固太狠,退回"只抓包 + 端点 hook 关键函数",不追求全量控制。
**Q6**: 关键逻辑还是被搬进了 native(C/C++ 静态库)?
**A6**: 和安卓 so 一样处理:逆 Mach-O 里的 native 函数或 hook 它,战场从 OC/Swift 层转到 native 层,方法论完全复用安卓 so 那一套。

### JSON 字段 base64 解出来还是乱码
**Q1**: 响应是 JSON,某字段 base64 decode 后期望是明文,结果一堆乱码,哪出错了?
**A1**: 说明 base64 里面还有一层。乱码判形态:高熵→还是密文(还得解密)、开头 1f8b→gzip、开头 78 9c→zlib、又像 base64→再 decode 一层。base64 只是编码,不等于终点。
**Q2**: 判断里面是 gzip,解压后就明文了吗?
**A2**: 试着 gunzip,若出结构化数据(JSON/文本)就到底了;若还是高熵,那是"先加密再压缩"或"先压缩再加密",继续按形态剥。记住剥的顺序要和加密时相反。
**Q3**: 里面是密文,但我不知道用哪个 key/算法解这层?
**A3**: 回到 hook:与其猜这层怎么解,不如 hook 处理这个字段的解密函数直接看它怎么解、用什么 key。字段级嵌套加密最快的破法是运行时观察那段处理代码。
**Q4**: base64 decode 就直接报错(不是合法 base64)?
**A4**: 检查变体:URL-safe base64(- _ 替换 + /)、无填充、或根本不是 base64 是 base62/base58/hex/自定义字母表。换对应解码器,或看 App 里的编码函数确认字母表。
**Q5**: 剥了好几层还是乱,怀疑判断链某步错了?
**A5**: 转"以 hook 为准"校验:别再盲猜层次,在 App 里 hook 这个字段从密文到明文的完整处理链,把每一层的中间值打印出来,看清真实的编码/加密顺序,再照着实现。
**Q6**: 想批量处理这类嵌套字段?
**A6**: 还原出稳定的剥离流水线(decode→decrypt→decompress 固定顺序)封装成函数,或直接复用 App 的解密函数做 RPC。一次搞清结构,后续批量套用。

### WebSocket / 长连接协议逆向
**Q1**: App 用 WebSocket 长连接推消息,帧内容加密,怎么还原?
**A1**: 先抓 WS 握手和帧:确认是标准 WS(有 Upgrade 握手)还是自研长连。标准 WS 抓包工具能拆帧,看每帧 payload 形态(文本/二进制/加密)。定性后再定位加密。
**Q2**: WS 帧是加密的二进制,里面可能还有子协议(命令字+body)?
**A2**: 拆两层:WS 是传输层,里面的加密 payload 才是业务协议。先解密单帧,再分析业务协议结构(命令字、序号、body 常是 protobuf/JSON)。别把 WS 帧结构和业务协议混为一谈。
**Q3**: WS 走 wss(TLS)且有 pinning,抓不到帧?
**A3**: 叠加 unpinning,或转端点 hook:hook WebSocket 的 send/onMessage 回调,在加密前/解密后取明文帧。长连接框架的收发回调是最好的 hook 点。
**Q4**: 是自研长连(非标准 WS),抓包工具拆不了帧?
**A4**: 转自定义二进制协议还原:按 TCP 流找长度字段做分帧,处理粘包/分包,再逐帧判结构。同时 hook 长连库的编解码器定位打包函数。
**Q5**: 长连接里有心跳/加密握手,重放单帧没意义?
**A5**: 转"在连接内注入"思路:长连接有状态(序号、会话密钥),离线重放单帧没用。改为 hook 已建立的连接,在它的发送函数里注入你的帧,复用它的会话状态和加密。
**Q6**: 想主动构造消息打服务端(比如伪造推送/越权指令)?
**A6**: 用活体连接:让 App 建好连接后,通过 hook 在这条已认证的连接上发你构造的业务帧。你借的是 App 已经完成的握手+认证+加密上下文,自己从零建连几乎不可能。

### 二进制自定义协议:分包粘包与 TLV
**Q1**: 抓到一条 TCP 流全是二进制,要拆成一条条消息,怎么找消息边界?
**A1**: 找长度字段。多数自定义协议是"长度前缀":开头 2/4 字节是本消息长度。对比多条消息,看开头哪几个字节的值恰好等于后续内容长度,那就是长度域。定位长度域=解决分包粘包。
**Q2**: 找到长度域后,消息内部结构怎么拆?
**A2**: 常见是 TLV(Type-Length-Value)或固定头+body。做差分:多发几个不同操作,看哪些字节固定(魔数/版本/命令字)、哪些变化(序号/时间戳/payload)。固定的是协议骨架,变化的按语义猜。
**Q3**: 命令字(cmd)对应什么操作对不上号?
**A3**: 关联行为:每种操作抓一次,记录它的 cmd 值,建 cmd→功能映射表。同时静态里搜 switch/case 或 cmd 常量定义,反编译里的 cmd 分发逻辑直接给你完整命令表。
**Q4**: body 是加密的,分完帧也读不懂内容?
**A4**: 分层:先解决协议框架(分帧+头部),body 解密是另一子任务,转到加密还原流程(hook 加解密函数)。框架层和加密层分开攻,别一锅炖。
**Q5**: 长度字段找不到(定长消息?或有转义/分隔符?)?
**A5**: 换分帧假设:可能是定长消息(每 N 字节一条)、或用分隔符(特定字节序列分隔)、或有转义机制。逐个假设验证,或直接静态看编解码器怎么切帧,别在字节里瞎猜。
**Q6**: 大小端 / 对齐搞错导致解析全乱?
**A6**: 校准字节序:长度和数值字段试大端和小端,哪个解出来合理(长度等于实际内容长)就是对的。自定义协议大小端两种都常见,拿"长度域自洽"当校验锚点。

### 账号接管:定位登录 / token 刷新逻辑
**Q1**: 想做账号接管或会话操纵,需要理解登录和 token 机制,从哪切入?
**A1**: 抓登录全流程:账号密码怎么加密传、服务端返回什么(token/refresh_token/session)、后续请求怎么带 token。先画出"登录→拿 token→带 token 访问→token 过期→刷新"这条链。
**Q2**: 密码是加密传的,想看它怎么处理密码?
**A2**: hook 密码输入到发送之间的处理:常是 RSA 加密密码 + 传输层再加密。定位密码加密函数,理解是可重放(固定加密)还是带随机(每次不同)。这决定能否离线构造登录包。
**Q3**: token 刷新机制想利用(比如 refresh_token 不失效)?
**A3**: 分析刷新接口:refresh_token 的有效期、是否一次性、刷新时校验什么。红队关注点:token 泄露后能续多久、能否绕过二次验证刷新。转到 token 生命周期的逻辑漏洞分析。
**Q4**: 登录有短信/图形验证码,构造不了完整登录?
**A4**: 转向:账号接管未必要走登录。看有没有免密逻辑(token 直接注入、设备信任、越权改绑手机)、或者利用已有 token 做操作。验证码挡的是登录入口,不一定挡业务接口。
**Q5**: 加密登录包复现不了(带设备指纹/风控),这条路断了?
**A5**: 转"活体+逻辑"维度:用 App 代理发合法登录后拿 token,再研究拿到 token 后的越权/改绑/信息泄露。把攻击重心从"伪造登录"移到"合法登录后的逻辑漏洞",避开登录处的强加密强风控。
**Q6**: 想批量验证账号(撞库类),但每个请求加密开销大?
**A6**: 评估必要性与手段:若确需批量,用还原好的加密能力做加密代理批量发;但更要意识到批量登录必触发风控,红队价值通常在"单账号深度接管"而非"批量",按目标调整。

### 环境搭建卡死(设备/root/版本不匹配)
**Q1**: 逆向还没开始,环境就崩——root 不干净、frida 版本对不上、设备架构不符,怎么破局?
**A1**: 先止血,别边搭边试。列出环境依赖清单:安卓版本、架构(arm64/arm)、frida-server 版本要匹配 client、root 方案(magisk)、目标 App 的最低版本要求。一次对齐,别东试一下西试一下。
**Q2**: frida attach 报版本不匹配 / 协议错?
**A2**: 严格对齐 frida-server 和主机 frida 工具版本号(必须一致),架构要和设备 CPU 一致。这是最常见坑,版本号差一点就连不上,先把这个基础打稳。
**Q3**: 没有合适的物理设备 / root 不了真机?
**A3**: 转模拟器/云真机:用支持 root 和 arm 转译的模拟器,或云真机服务。注意 App 可能检测模拟器,需配套过模拟器检测。设备不是唯一解,虚拟环境+反检测常够用。
**Q4**: App 检测模拟器直接不启动?
**A4**: 转反模拟器检测:hook 检测点(getprop 里的模拟器特征、传感器缺失、特定文件),或用更真实的模拟器/真机。若模拟器成本太高,回到物理设备路线。两条腿走路,哪条通用哪条。
**Q5**: 环境问题反复消耗大量时间,严重拖进度?
**A5**: 战略转向静态/离线:如果动态环境是无底洞,把能静态做的(拉 so 用 unidbg、纯反编译读逻辑)先做掉,减少对脆弱动态环境的依赖。环境是手段,别让搭环境变成主线任务。
**Q6**: 多个目标 App 要测,每个都重搭环境?
**A6**: 沉淀标准化环境:固化一套可复用的 root+frida+抓包镜像/脚本,新目标直接套用。把环境搭建从"每次踩坑"变成"一键就绪",这是红队工程化的基础投资。

### 差分分析法逆向未知协议
**Q1**: 面对一个完全未知的加密协议,没头绪,有没有不靠读代码的通用起步法?
**A1**: 差分分析(黑盒)。对同一操作发多次,对比报文:找出不变部分(协议头/固定字段)和变化部分(序号/时间/随机数/业务值)。再改单个输入(改用户名一个字),看报文哪里变,建立"输入字段↔报文位置"映射。
**Q2**: 加密的报文差分,改一个字节明文密文全变(雪崩),差分看不出对应?
**A2**: 雪崩说明是分组/流密码整体加密,字段级差分在密文上失效。转到"加密前"差分:hook 拿到明文再差分,或直接放弃密文层差分,转攻加密还原(拿到明文后一切好办)。
**Q3**: 想确认某字段是不是时间戳/随机数?
**A3**: 时间维度差分:间隔不同时间发相同请求,看哪个字段随时间单调变→时间戳;每次都变但无规律→随机数/nonce;完全不变→固定配置。用"控制时间"这个变量做判定。
**Q4**: 差分能标出字段位置但不知道字段的编码(int?变长?)?
**A4**: 改已知数值观察:把某数值参数从 1 改到 255 再改到 256,看报文对应字节怎么变,推出是定长 int(第 256 时进位到下一字节)还是 varint。用边界值探编码方式。
**Q5**: 纯黑盒差分到瓶颈,再也推不出更多语义?
**A5**: 转白盒补充:差分给你结构假设,拿这些假设回反编译/hook 里验证和补全。黑盒差分和白盒逆向是互补的——差分快速起步定位,白盒精确确认语义。两者结合。
**Q6**: 想把差分自动化?
**A6**: 脚本化采集+对比:自动发变体请求、自动 diff 报文、自动标注变化位。对字段多的复杂协议,自动化差分比手工肉眼快得多,也更不容易漏掉细微变化字段。

### 完整性校验 / 防篡改(重打包被拒)
**Q1**: 我重打包注入代码后,App 启动就报错或闪退,是完整性校验,怎么办?
**A1**: 先定位校验类型:签名校验(比对 APK 签名)、文件哈希校验(校验 dex/so 完整性)、还是 CRC。看报错时机和内容。对策:能不改文件就不改——优先用运行时注入(免重打包)绕过一切文件校验。
**Q2**: 必须改文件(比如 patch 某逻辑),怎么过签名校验?
**A2**: hook 签名校验点:hook PackageManager.getPackageInfo / getPackageInfo 返回的签名,让它返回原始签名值。或找到自校验函数直接 patch 成通过。把"读到的签名"伪造成合法值。
**Q3**: 校验在 native 里,而且校验的是 so 自身?
**A3**: 转 native patch/hook:hook native 校验函数返回值,或在校验前把内存里的比对基准改成实际值。so 自校验通常是读自己文件算哈希比对,hook 掉哈希比对结果即可。
**Q4**: 有服务端参与的完整性校验(把校验结果上报服务端)?
**A4**: 这是硬骨头,转向"不篡改客户端"路线:放弃改 App,改用纯 hook(运行时注入不改文件)+ 抓包分析。服务端校验完整性时,任何本地篡改都会暴露,那就别篡改,只观测和用现成能力。
**Q5**: 连运行时注入都被检测(检测 hook 框架)?
**A5**: 回到反调试/反 hook 隐藏维度:先把注入框架藏干净(隐藏 frida/xposed 特征)再谈注入。检测 hook 和检测调试是同一类对抗,用同一套隐藏手段应对。
**Q6**: 所有本地手段都被防死,还能怎么推进?
**A6**: 转纯网络侧 + 活体:完全不碰客户端二进制,靠抓包 + 用干净 App 当加密代理发请求,把攻击面收缩到服务端接口的逻辑漏洞。客户端防得再死,服务端接口还是要处理请求的,那才是最终战场。

### 国密算法(SM2/SM3/SM4)专项
**Q1**: 识别出目标用国密(SM 系列),和常规 AES/RSA 处理有什么不同要注意?
**A1**: 方法论一样,坑在细节。SM4 类比 AES(分组 16 字节,注意 ECB/CBC 和 IV)。SM3 类比 SHA-256 做哈希/HMAC。SM2 类比 ECC 做非对称。先确认具体用了哪几个,别笼统当"国密"。
**Q2**: SM2 加密复现,密文格式老是对不上?
**A2**: 最大的坑是密文排列顺序:SM2 密文有 C1(椭圆曲线点)、C2(密文)、C3(哈希),标准是 C1C3C2 但很多实现用 C1C2C3,还有带不带 04 前缀的区别。逐一试排列组合,拿 App 实测密文对齐。
**Q3**: SM4 复现对不上?
**A3**: 排查同 AES:模式(ECB/CBC)、IV、填充(PKCS7)、key 长度(16 字节)。国密库之间实现差异也会导致细节不同,以 App 一组真实明密文为金标准逐项对齐。
**Q4**: 工具/库对国密支持不好,复现困难?
**A4**: 转成熟国密库(gmssl、bouncycastle 国密扩展、各语言的 sm-crypto),别用不支持国密的标准库硬套。选对库能省掉大量密文格式的坑。
**Q5**: 国密算法在 native 且魔改,复现无望?
**A5**: 回到通用退路——黑盒 RPC:不管它是不是国密、有没有魔改,hook 那个加解密函数当黑盒用。算法是什么对黑盒调用无所谓,这是所有"复现困难"场景的统一出口。
**Q6**: SM2 签名想伪造(拿私钥)?
**A6**: 同私钥定位思路:客户端签名必然要用私钥,hook 到私钥或签名函数当签名 oracle。想真正破 SM2 拿私钥靠密码分析不现实,靠"客户端持有私钥"这个事实去 hook 才是实战路径。

### 目标是打漏洞:构造合法加密报文才能触达
**Q1**: 发现一个疑似漏洞接口(如未授权/注入),但它要求加密报文,不构造对就到不了漏洞点,怎么办?
**A1**: 先把"加密外壳"和"漏洞载荷"分开。你需要的是:能对任意明文载荷加密成合法报文的能力。优先用 App 当加密器(hook 注入你的 payload 让 App 加密发出),而不是从零复现算法。
**Q2**: 漏洞是注入类(SQLi/命令注入),payload 有特殊字符,加密后能正常触达吗?
**A2**: 能——加密是透明通道,你的 payload 明文里带什么特殊字符,解密后服务端拿到的就是什么。关键是确保 payload 进了被加密的那个字段。用加密代理让你能像打明文接口一样打这个字段。
**Q3**: 想用自动化工具(sqlmap/burp)打这个加密接口?
**A3**: 搭加密代理中间层:工具发明文→代理加密签名→转发→响应解密→回给工具。这样把加密接口"降维"成普通明文接口,所有 Web 自动化工具都能直接用。这是攻加密接口漏洞的核心工程手段。
**Q4**: 加密里带签名,payload 一变签名就得重算,代理里怎么处理?
**A4**: 代理里集成签名逻辑:每次转发前用 hook 到的签名能力对当前(含 payload 的)明文重新签名。也就是代理不只加密,还要复现完整的"加密+签名"组装流程,保证每个变异 payload 都是合法报文。
**Q5**: 加密报文能触达了,但漏洞利用失败,是漏洞不存在还是构造有问题?
**A5**: 控制变量确认:先发一个已知合法的正常请求确认通道通、再发一个明显的探测 payload(如报错注入探测)。若正常请求通、探测无反应,可能是漏洞不存在或被过滤;若正常请求都不通,是加密构造问题。分层排除。
**Q6**: 加密接口打不动,是不是该换思路?
**A6**: 转攻击面 + 信息维度:这个接口硬,换其他接口;或先做信息收集(还原出的协议里可能暴露内部接口路径、参数、版本),用协议还原的成果指导找更软的单点。协议还原本身就是一次深度信息收集,别只盯着一个洞。
