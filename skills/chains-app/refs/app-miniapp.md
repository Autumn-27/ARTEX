# App客户端 · 小程序/H5/移动API攻击面

### 拿到一个APK/IPA/小程序包，第一步做静态盘点还是直接抓包
**Q1**: 目标X刚交到手上，只有一个安装包（或商店链接），我该先动态抓包还是先静态拆包？
**A1**: 先静态盘点，成本最低且不惊动风控。解包看三样东西定方向：①网络域名/接口清单（在字符串、资源、配置里搜 http、api、host、Base_URL）；②鉴权与加密线索（sign、token、secret、AES、RSA、appKey 关键字）；③加固/壳与SDK清单。静态先画出"后端长什么样"，再带着问题去动态抓包，效率比盲抓高一个量级。
**Q2**: 静态里域名和接口都很少，几乎没字符串，怎么判断是被藏了还是真没有？
**A2**: 大概率是加固/字符串加密。判据：DEX 异常小、有明显 native so 承载逻辑、字符串大量是密文或反射调用。此时静态收益递减，转动态。
**Q3**: 那静态阶段最该优先提取的"高价值单点"是什么？
**A3**: 硬编码凭据（第三方云AK/SK、推送/短信/地图key）、测试/debug 开关、以及接口的整体命名规律（RESTful 路径前缀、版本号 /v1/ /api/）。命名规律能让你后续枚举未公开接口。
**Q4**: 如果这条静态路彻底走死（全加固、无可读信息）怎么办？
**A4**: 转正交维度——放弃"读客户端"，改"看客户端说的话"。直接上动态抓包/插桩，把注意力从"逆向文件"切到"逆向流量与运行时"。客户端再怎么加固，最终都要发网络请求，流量是绕不过去的暴露面。
**Q5**: 动态抓包也需要方向，静态该给动态留什么"钩子"？
**A5**: 留下：核心业务接口的域名、疑似鉴权参数名、加密算法类型（对称/非对称）。这样动态抓到密文时你能立刻对上号，而不是从零猜。

### HTTPS 抓不到包，先怀疑什么
**Q1**: 装了代理证书，浏览器能抓，但目标App的流量在抓包工具里完全不出现或报错，怎么定位？
**A1**: 按概率排查：①App 用了系统代理不感知（很多用 OkHttp 自定义，不走系统代理）→ 需要透明代理/VPN模式抓；②证书固定 SSL Pinning → 握手直接失败；③App 内置了自己的 CA 校验或双向认证。先看现象：完全无流量往往是"不走代理"，握手 alert/断开往往是 Pinning。
**Q2**: 切到透明代理/VPN 抓包模式后，出现了 TLS 握手就断，说明什么？
**A2**: 基本确认 SSL Pinning。此时不要在代理层硬刚，转到运行时——用插桩框架 hook 掉证书校验函数。
**Q3**: 如果连非HTTPS的流量也一点没有，App 像"离线"？
**A3**: 怀疑三点：强制走 native 层网络栈、检测到代理直接罢工、或用了非HTTP协议（自定义TCP/QUIC/WebSocket over 443）。抓一份全端口 pcap 看它到底往哪连、用什么协议，别只盯 HTTP。
**Q4**: 这条"网络层抓包"整体被封死（检测代理+Pinning+反调试三件套齐全）怎么办？
**A4**: 转正交维度：从"中间人"转到"端点旁路"。既然中间截不到，就在客户端进程内部截——hook 加密函数的明文入口/出口（在 encrypt 前、decrypt 后拿明文），或直接读发送前的 buffer。绕开TLS本身，在应用逻辑层拿数据。
**Q5**: 端点旁路也需要落地，具体 hook 哪一层最稳？
**A5**: 优先 hook 语言运行时里的高层 API（如 OkHttp 的 Request/Response、系统 HTTP 客户端），比 hook 底层 socket 拿到的数据更结构化、可读性更好。拿不到再往下沉到加解密函数。

### SSL Pinning 绕过选哪种打法
**Q1**: 确认了证书固定，绕过手段有通杀脚本、手改smali重打包、hook三条路，先选哪条？
**A1**: 先试通用 hook 脚本（覆盖常见网络库和系统校验点），成本最低、五分钟见效。判据：脚本注入后握手是否恢复。它能过掉绝大多数"标准写法"的 Pinning。
**Q2**: 通杀脚本无效，握手还是断，说明 Pinning 写在哪？
**A2**: 说明是非标准实现：可能在 native so 里做证书比对，或用了自研校验、或校验点被混淆。通杀脚本只覆盖高层 Java/系统 API，覆盖不到 native。转向：定位 so 里的校验函数。
**Q3**: 怎么快速定位 native 层的校验点？
**A3**: 动态 trace 网络握手前后被调用的 so 函数，或在 so 里搜证书/公钥指纹的常量（Pinning 必然内置一份期望指纹）。找到比对函数，hook 其返回值恒真即可。
**Q4**: 如果连 native hook 都被反调试拦住（一插桩就崩）怎么办？
**A4**: 转正交维度：放弃"让App相信我的证书"，改"用App自己的证书通道"。既然它信自己内置的公钥，就不做中间人了——回到端点旁路，直接 hook 明文，让 Pinning 形同虚设。绕过认证 ≠ 必须做MITM。
**Q5**: 重打包改 smali 这条路什么时候才值得用？
**A5**: 当目标没有 App 级签名校验、且你需要长期稳定复现（给队友/自动化用）时才做。它一劳永逸但重，且遇到签名校验会连锁触发另一个绕过任务，短期打点不划算。

### 客户端逆向太硬，转攻API本身
**Q1**: 加固脱不了、Pinning绕不动、时间在流逝，是不是该放弃客户端？
**A1**: 是，重新评估：客户端只是"接口的调用者"，真正的攻击面是后端API。只要你抓到过哪怕一个接口的完整请求（域名+路径+一次合法签名），就有了 API fuzz 的支点。把精力从"打穿客户端"转到"直接和API对话"。
**Q2**: 我只有一个能抓到的接口样本，怎么扩展到整个API面？
**A2**: 三个方向：①按路径规律枚举同类接口（/user/info → /user/list、/order/detail）；②翻小程序/H5版本（往往加固更弱、接口一致）拿到更全的接口清单；③找接口文档泄露（swagger、api-docs、测试环境）。
**Q3**: 签名参数怎么办，没有客户端算不出 sign？
**A3**: 先判断签名覆盖范围：很多 sign 只签了部分参数或只防篡改不防重放。测试：改一个未被签名覆盖的参数看是否仍成功；或直接重放原请求改越权目标（id 换成别人）——重放合法签名往往能打越权，根本不需要重算 sign。
**Q4**: 如果所有接口都强签名、强时间戳、必须客户端参与怎么办？
**A4**: 转正交维度：把"离线算签名"变成"在线借签名"。让真客户端跑起来，通过 hook 暴露一个本地签名服务（把待签数据喂进去、拿签名出来），你的 fuzz 工具调用它。用它自己的算法给你打工，不必逆向出算法。
**Q5**: 连一个合法样本都抓不到（全条件都失败）时最后一招？
**A5**: 退到最外层——找同一后端的其他入口：官网/PC端/合作方开放API/历史APP版本，它们常共享后端但鉴权更松。攻击面是"后端"，不是"这一个App"。

### 识别加固壳并决定要不要脱
**Q1**: 拿到APK，DEX里全是壳的加载器，怎么先判断脱壳的必要性？
**A1**: 先问自己：我脱壳是为了拿字符串/接口，还是为了改逻辑？如果只想拿接口和加密算法，动态 hook 往往比脱壳快得多——脱壳是重活，只有需要完整静态审计时才值得。先识别壳厂商（特征目录、so命名、加载流程），判断成熟脱壳方案是否现成。
**Q2**: 是主流商业壳，有现成脱壳机，直接上？
**A2**: 上，但注意版本对抗——新版壳常有反脱壳。判据：脱出的 DEX 是否完整（方法体是否被抽空、CodeItem 是否 nop）。抽取型壳脱出来可能只有空壳方法，需要主动调用/内存dump补全。
**Q3**: 脱出来发现关键方法体是空的（函数抽取/VMP），怎么办？
**A3**: 说明是高强度保护，静态还原成本极高。别硬啃单个函数。转向：只在运行时观察这个函数的输入输出（hook 边界），把它当黑盒——你要的是行为，不是源码。
**Q4**: 如果脱壳整条路被反脱壳彻底挡死怎么办？
**A4**: 转正交维度：从"还原代码"转到"观测运行时状态"。壳保护的是静态形态，保护不了运行时内存——它终究要在内存里把明文DEX/密钥还原出来才能执行。切到内存 dump / 运行时 trace，在它最脆弱的"执行瞬间"取物。
**Q5**: 怎么避免在脱壳上无限投入时间？
**A5**: 设时间盒（如1小时）。脱壳是手段不是目的，超时就切hook或切API面。红队要的是突破口，不是把这个壳研究透。

### 小程序包怎么拿、怎么还原
**Q1**: 目标是微信小程序，我怎么拿到它的代码来审计？
**A1**: 小程序包在设备本地有缓存（加密的 wxapkg）。路径：用已 root 的安卓/模拟器打开一次小程序触发下载，从微信数据目录取包，再用现成解包工具还原成 wxml/wxss/js。小程序比 App 好打——代码几乎是明文 JS，加固很弱。
**Q2**: 解出来的包是加密的（.wxapkg 打不开）怎么办？
**A2**: 新版包做了简单加密，但算法公开、有现成解密脚本（需要设备相关的解密参数）。拿到解密key后一键还原。这一步基本是流程化的，卡住多半是包路径或版本对不上。
**Q3**: 还原后海量 JS，先看什么？
**A3**: 直奔三处：①request/接口调用（小程序网络请求域名在后台配置里是白名单，反查能拿到全部后端域名）；②硬编码的 appid/key/云环境ID；③业务逻辑判断（前端做的鉴权/金额校验，几乎必然可绕）。小程序大量把逻辑放前端，是越权和逻辑漏洞的富矿。
**Q4**: 如果小程序用了云开发（serverless），接口不是传统HTTP怎么办？
**A4**: 转向云开发攻击面：云函数调用、云数据库直连。前端代码里能翻到云环境ID和数据库集合名；小程序云数据库常有过松的安全规则（前端直接读写），直接构造云调用尝试越权读写整张表。这是和"打HTTP接口"完全正交的一条线。
**Q5**: 小程序真机调试/抓包被限制怎么办？
**A5**: 转向——小程序本质是H5+JS，用开发者工具加载还原后的源码本地跑，或直接以拿到的域名清单去打后端API，绕开小程序客户端本身。

### 挖硬编码密钥后怎么判断价值
**Q1**: 静态里搜到一串疑似 AccessKey/Secret，怎么判断它有没有用？
**A1**: 先分类型再验活。看它属于哪个云/服务（对象存储、短信、推送、地图、IM），不同服务危害天差地别。验活方式：用对应云的 CLI/SDK 拿这对密钥做一次最小权限探测（列举资源）。判据：能否成功调用。死key一文不值，活的对象存储key可能直接接管整个存储桶。
**Q2**: key 能用但报权限不足，还有戏吗？
**A2**: 有。枚举它到底能干什么——很多 App 图省事给了过大权限。逐个服务/动作探测边界。即便只读，也可能读到全量用户上传文件/备份。别因为一个动作被拒就丢掉。
**Q3**: 搜到的是 RSA/AES 密钥而不是云凭据，怎么用？
**A3**: 它的价值在"解密流量/伪造签名"。对称key能解请求体密文、伪造合法请求；RSA私钥若在客户端（危险的错误设计）能伪造服务端签名或解密。先确认它在通信中扮演的角色，再决定是拿来解包还是拿来伪造。
**Q4**: 如果硬编码key全是死的/占位/测试值，这条路断了怎么办？
**A4**: 转正交维度：从"静态捡现成的key"转到"动态从内存抓活的key"。很多真正的密钥是运行时由服务端下发或本地生成的，静态里根本没有。切到运行时——在加解密函数被调用时 dump 参数，活体取密钥。
**Q5**: 怎么避免把大量时间浪费在验证一堆无效字符串上？
**A5**: 建立优先级：云对象存储/短信/支付类key优先验；地图/统计类key低优先。按"泄露后危害"排序，而不是按发现顺序。

### 移动API的签名机制怎么拆
**Q1**: 每个请求都有 sign 参数，改任何参数就 403，怎么系统性拆掉它？
**A1**: 目标是搞清"sign = f(哪些数据, 什么算法, 什么key)"。方法：抓多组请求做差分——对比只改一个参数时 sign 的变化，推断哪些字段参与签名、是否含时间戳/nonce。同时静态/hook 定位签名函数。先把"签名覆盖哪些字段"搞清楚，往往发现它没签全。
**Q2**: 差分发现 sign 只覆盖了部分关键参数，意味着什么？
**A2**: 意味着未被覆盖的参数可以随便改而签名依然有效——这就是突破口。比如 sign 签了业务参数但没签 userId/orderId，那越权直接成立。先攻"签名盲区"，比逆向算法性价比高得多。
**Q3**: 签名覆盖了全部参数，只能逆算法了，怎么高效逆？
**A3**: 别死磕反编译。hook 签名函数入口，打印它拿到的原始待签串和输出——一眼就能看出拼接规则和算法（MD5/HMAC 的长度特征很明显）。key 也在入参里。运行时观测 >> 静态逆向。
**Q4**: 算法在 native/VMP 里逆不出来怎么办？
**A4**: 转正交维度：不逆算法，做"签名预言机"。让客户端持续运行，hook 出一个可被外部调用的签名接口，你的工具把任意 payload 发给它、拿回合法 sign。把不可逆的黑盒变成你的签名服务。
**Q5**: 如果签名还带了服务端下发的动态盐/一次性token怎么办？
**A5**: 说明签名有会话依赖。转向：先走正常登录流程拿到当前会话的盐，再在会话有效期内批量重放/构造。或直接用签名预言机方案——它自带会话状态，不用你手动管理盐。

### 越权(IDOR)测试的推进与判据
**Q1**: 接口里带 userId/id 参数，想测水平越权，怎么开局？
**A1**: 准备两个账号A、B（或一个账号+一个已知他人id）。用A的会话去请求B的资源id，看是否返回B的数据。判据很硬：返回了不属于A的数据即越权成立。没有第二账号时，先改id探测返回差异（404 vs 403 vs 200带数据）。
**Q2**: 直接改明文id被拦（返回无权限），是不是就没越权了？
**A2**: 不一定。检查id是否被间接引用/加密：改成加密id、改成用户名、改成手机号等其他标识试试。很多系统只在主id上做了校验，旁路标识没校验。也测批量接口、导出接口、老版本接口——校验强度常常不一致。
**Q3**: id是加密的（比如密文串），怎么测越权？
**A3**: 先看能否拿到别人的密文id（列表接口、分享链接、消息推送里常泄露他人加密id），拿到就能直接替换。加密只是遮挡，不等于授权校验。或者结合签名/加密算法自己造密文。
**Q4**: 全站越权都被严格校验，这条路走死了怎么办？
**A4**: 转正交维度：从"水平越权"转到"垂直越权/功能越权"。普通用户去调管理接口（admin路径、后台API）、去调本不该出现在他角色下的功能。前端隐藏≠后端鉴权，很多管理接口只靠前端不显示按钮来"保护"。
**Q5**: 垂直越权也没有，还能往哪转？
**A5**: 转"越权的读写不对称"——很多接口读校验严但写/删校验松，或反之。分别测GET和POST/DELETE。再转"越权的时序"——状态流转接口（订单待支付→已支付）常缺校验，可跳过步骤。

### 短信/验证码类逻辑漏洞的决策
**Q1**: 登录/注册走短信验证码，想找逻辑漏洞，从哪几个方向切？
**A1**: 五个经典方向并行排查：①验证码可爆破（4位无锁定/无频率限制）；②验证码在响应里回显（返回包直接带code）；③验证码不绑手机号（A手机的码能验证B）；④短信轰炸（无频率限制）；⑤万能码/测试码（000000、123456）。先看响应包——回显是最快的一击必杀。
**Q2**: 验证码是6位且有失败次数锁定，爆破无望，怎么办？
**A2**: 转攻"绑定关系"和"复用"：同一个码是否多次可用、验证成功后是否失效、A的验证态能否用于B的操作。逻辑漏洞常不在"猜对码"，而在"码和身份的绑定/生命周期"没做好。
**Q3**: 发现验证接口和业务接口是分离的（先验码换token，再拿token做业务），有什么可打的？
**A3**: 攻"换token"这一步：验一次码拿到的token能否复用于多次/多人操作、能否越权换成别人的token、token是否可预测。分离设计常在"码→凭证"的转换处漏校验。
**Q4**: 所有短信逻辑都很严，这条业务线打不动怎么办？
**A4**: 转正交维度：从"验证码本身"转到"验证码保护的功能"。找那些本该验码却漏了的入口——改密、改绑手机、支付确认，看是否存在无需验码的旁路接口（老接口、H5接口、内部接口）。同一敏感操作往往有多个入口，校验强度不一。
**Q5**: 还想深入，验证码之外的凭证有没有戏？
**A5**: 有，转向图形验证码/滑块的绕过（识别、打码平台、参数复用）作为爆破前置，以及登录/注册接口的用户枚举（不同错误提示区分账号是否存在），为后续密码喷洒铺路。

### H5/WebView 混合应用怎么找洞
**Q1**: App里内嵌了大量H5页面（WebView），这块攻击面怎么切入？
**A1**: 先定位WebView加载的URL和它开放的能力。关键看：①是否加载可控URL（外部链接、参数可控的url）→ 可能XSS/钓鱼；②是否 addJavascriptInterface 暴露原生方法给JS（JSBridge）→ JS可调原生能力，风险巨大；③是否开启 file:// 访问和 setAllowUniversalAccessFromFileURLs。
**Q2**: 发现WebView加载的URL可以通过参数或deeplink控制，能干什么？
**A2**: 尝试加载我方页面到它的WebView里，从而调用它注入的JSBridge。判据：能否让WebView跳到任意域。如果能，你的JS就跑在有原生桥的上下文里，可调用暴露的native方法（读文件、拿token、调支付）。
**Q3**: JSBridge有域名白名单，只允许自家域调用怎么办？
**A3**: 找白名单绕过：自家域下的XSS（有反射/存储XSS就能在白名单内执行JS）、子域接管、或白名单校验用了弱匹配（域名后缀/包含判断可被 evil.com/self.com 或 self.com.evil.com 绕过）。桥的安全强依赖"谁能在白名单域执行JS"。
**Q4**: WebView做得很严（不加载外链、无桥、白名单严格），这块死了怎么办？
**A4**: 转正交维度：从"客户端WebView"转到"H5页面本身对应的后端"。H5页面调的接口和App共用后端或独立后端，直接以浏览器打开H5、抓它的API打——H5的鉴权和加密通常比原生App弱得多，是同一后端的软肋入口。
**Q5**: 还有别的WebView相关面吗？
**A5**: 有：本地HTML/资源的路径穿越、WebView缓存里的敏感数据、以及 intent scheme / 自定义scheme 唤起WebView时的参数注入。把WebView当成"App内的浏览器"，浏览器的洞它基本都可能有。

### deeplink/URL Scheme 劫持与滥用
**Q1**: App注册了自定义scheme和deeplink，我怎么判断它是不是攻击面？
**A1**: 先枚举它注册了哪些scheme/host/path（清单文件里都有），再看这些入口把参数传给了谁。关键问题：外部可调起的组件是否处理了不可信参数——跳转URL、加载WebView、执行动作。可被任意应用/网页唤起 + 参数流入敏感操作 = 攻击面。
**Q2**: 发现某个deeplink能带一个跳转url参数，怎么利用？
**A2**: 测开放重定向和WebView注入：让它跳到我方页面。若目标WebView带JSBridge或带登录态，就能钓token、调原生能力。判据：外部构造的链接能否让App加载/跳转到任意地址。
**Q3**: deeplink 触发的是敏感动作（如打开支付、绑定、授权）而非跳转，怎么打？
**A3**: 测"一键动作劫持"——诱导用户点一个链接就完成敏感操作（CSRF式）。看动作是否二次确认、是否校验来源。移动端的组件调用常缺来源校验，外部可静默触发。
**Q4**: scheme都做了来源/签名校验，唤不动怎么办？
**A4**: 转正交维度：从"外部唤起"转到"组件导出"本身。同一App里被导出的Activity/Service/Provider（exported=true）可被同设备其他应用直接调用，绕过scheme层。ContentProvider 越权读写、导出Activity的参数注入，是和deeplink正交的一条本地攻击线。
**Q5**: 本地无其他恶意应用配合（远程场景），deeplink还剩什么价值？
**A5**: 剩"网页→App"的跨界攻击：一个网页里的链接就能触发App行为，配合WebView信任链可做远程钓鱼/token窃取。这是移动端少见的"远程可达"面，值得深挖。

### 客户端本地存储的敏感数据
**Q1**: 想看App在设备本地存了什么敏感东西，从哪找？
**A1**: 系统性翻本地存储：SharedPreferences/plist、SQLite数据库、缓存文件、SD卡目录、keystore/keychain。搜关键字 token、password、secret、id。判据：是否明文存储凭据。很多App把token、甚至账号密码明文写在本地。
**Q2**: 存储是加密的（数据库/文件是密文），怎么办？
**A2**: 找解密key的位置——十有八九也在客户端（硬编码、或从设备id派生、或在keystore）。客户端存储加密的悖论是"密钥也得在客户端"，所以几乎总能本地解。定位加密函数，hook 或提取key。
**Q3**: 拿到本地token/凭据后，价值怎么最大化？
**A3**: 验证它的权限和有效期：是长期token还是短期？能否直接用于API调用（拿它去打接口）？能否跨设备复用（说明服务端没绑设备）？长期token+无设备绑定=账号可被持久接管。
**Q4**: 如果本地啥敏感数据都没存（都在内存、用完即焚）怎么办？
**A4**: 转正交维度：从"落盘存储"转到"运行时内存"。数据不落盘不代表不存在，它一定在内存里出现过。切到内存dump/运行时hook，在token被使用的那一刻截获。存储扫描扑空就转内存取证。
**Q5**: 需要设备物理/root权限才能读存储，但没有怎么办？
**A5**: 转向"备份"和"日志"两条软路：App是否允许调试备份（backup=true 可无root导出数据）、是否往系统日志/崩溃上报里打印了敏感信息。这两条常不需要root就能拿数据。

### Root/越狱检测挡住了动态分析
**Q1**: 在root设备上App一启动就退出/提示环境风险，怎么继续？
**A1**: 先确认是root检测。绕过分层次：先试通用root隐藏方案（隐藏su、denylist、常见检测点hook）。判据：App能否正常进入。多数App用的是标准检测（检查su文件、包名、属性），通杀方案能过。
**Q2**: 通用隐藏无效，App还是检测到，说明检测在哪？
**A2**: 说明有自定义/native检测点。转向：trace App启动时读了哪些文件、调了哪些系统属性、fork了什么进程，逐个定位它的检测逻辑，针对性hook使其返回"干净"。检测点再多也是有限集，逐个敲掉。
**Q3**: 检测在native且和反调试联动（一hook就崩）怎么办？
**A3**: 别在有root的环境硬碰。转正交维度：换到"不需要root的分析路径"——非root抓包（VPN模式）、非root的frida gadget注入（重打包内置）、或直接在模拟器/云真机上跑（有些检测对模拟器反而更弱或你能改底层）。改变战场而非在原战场硬刚。
**Q4**: 连非root抓包都被Pinning挡、模拟器也被检测怎么办？
**A4**: 回到最正交的一招：放弃动态分析客户端环境，全力转API面。root检测保护的是"客户端运行环境"，它保护不了后端接口。你已经从静态或一次抓包拿到接口，就绕开客户端直接打API。
**Q5**: 怎么判断该花多少力气绕root检测？
**A5**: 看你的目标：若只为抓接口，绕检测常常得不偿失，直接VPN抓包或打API更快。只有当核心逻辑必须在真机运行时才值得投入绕检测。手段服务目标。

### Frida/插桩被反检测怎么破
**Q1**: 一注入frida，App就崩溃或检测到，动态hook做不下去，怎么办？
**A1**: 先确认是anti-frida。特征：注入即崩、检测到frida端口/进程/内存特征后退出。先试对抗方案：改frida默认端口、改进程名、用gadget方式而非server方式、隐藏内存特征。判据：能否稳定注入不崩。
**Q2**: 改端口改名后还是被检测，它在检测什么？
**A2**: 常见检测点：扫描内存中的frida字符串、检查maps里的可疑库、检测特定线程/文件描述符、TracerPid。转向：定位它的检测函数（trace 崩溃前调用栈），hook 掉检测本身，或用更隐蔽的注入方式（先注入再抹痕迹）。
**Q3**: 反调试+反frida+完整性校验三合一，插桩这条路极难怎么办？
**A3**: 转正交维度：换插桩载体。从frida换到其他机制——ptrace based调试器、内核层hook、或干脆用静态patch（把检测跳转nop掉后重打包，但要处理签名校验）。不同插桩技术的检测覆盖不同，换武器换掉它的检测面。
**Q4**: 所有运行时插桩都被封死怎么办？
**A4**: 退回纯静态+网络两条不需要进程内插桩的路：静态还原算法（虽慢但不触发运行时检测）、纯被动流量分析（如果能突破Pinning就在网络层看）。以及回到API直打——不进它的进程，它的反插桩就打不到你。
**Q5**: 怎么避免和反检测无限拉锯？
**A5**: 设边界：反检测是军备竞赛，投入产出比会骤降。核心资产（密钥、算法）一旦拿到就撤，转向用成果打后端，而不是把这个App的所有保护都研究穿。红队是拿结果，不是做逆向教科书。

### 登录态/Token 机制的分析路径
**Q1**: 想搞清App的会话机制以便伪造/劫持身份，先看什么？
**A1**: 抓登录流程，看它发的是什么凭证：JWT、opaque token、cookie、还是自研签名。关键判据：token是自包含的（JWT可解）还是服务端存储的。JWT先解开看payload（角色、userId、过期），常有可篡改点。
**Q2**: 是JWT，怎么找攻击点？
**A2**: 经典四查：①alg=none 是否被接受；②弱密钥可爆破HMAC；③kid注入/jku指向可控；④payload里角色/id可改后服务端是否校验。改一个字段重放看是否生效。JWT的信任常常放错地方。
**Q3**: token是服务端存储的opaque串，改不了内容，怎么打？
**A3**: 转攻token的"生命周期和绑定"：是否长期不失效、登出后是否真失效、是否绑定设备/IP、是否可预测/枚举。拿到一个token能用多久、能在哪用，比它内容是什么更重要。
**Q4**: 会话机制做得很严（短期token+刷新+设备绑定），劫持无门怎么办？
**A4**: 转正交维度：从"伪造/篡改token"转到"合法获取他人token"。通过越权接口、日志泄露、WebView钓取、本地存储读取等方式直接拿到别人的合法token——你不需要破解会话机制，只需要偷一把有效钥匙。分析机制无果就转窃取实物。
**Q5**: 刷新token机制本身有没有可打的？
**A5**: 有。refresh token常被忽视：是否长期有效、泄露后能否无限续命、刷新接口是否有越权（用A的refresh拿B的access）。刷新链路的鉴权往往比主接口松。

### API 被限流/风控封了怎么继续
**Q1**: fuzz/爆破打到一半，接口开始返回429或直接封IP，怎么办？
**A1**: 先判断封禁维度：是封IP、封账号、封设备指纹、还是封token？分别测试才知道。判据：换IP恢复=封IP；换IP不恢复但换账号恢复=封账号/设备。对症下药，别盲目换IP。
**Q2**: 确认是封IP，怎么持续作业？
**A2**: 上IP池/代理轮换，并把请求频率降到风控阈值以下（慢就是快）。同时看是否有豁免路径——某些接口（H5、老版本、内部）可能不在同一风控策略下。
**Q3**: 封的是设备指纹/风控参数（换IP无效）怎么办？
**A3**: 定位风控参数：请求里带的deviceId、指纹串、风控SDK生成的token。这些常是客户端生成的。转向hook风控参数的生成函数，做到"一机一指纹"批量伪造，让每个请求看起来来自不同设备。
**Q4**: 风控极强（行为分析、机器学习拦截），常规绕不动怎么办？
**A4**: 转正交维度：从"对抗风控做高频攻击"转到"低频精准打击"。很多高价值漏洞（越权、逻辑漏洞、硬编码泄露）根本不需要高频请求——一次正确的越权请求就够了。放弃爆破思路，转向单点逻辑漏洞，风控就失去了打击对象。
**Q5**: 怎么在触发风控前就规划好？
**A5**: 先侦察风控边界（小规模试探阈值、封禁维度、恢复时间），再设计攻击节奏。把风控当成一个需要先摸清规则的对手，而不是撞上去才反应。

### 请求体整体加密，看不懂在传什么
**Q1**: 抓到的请求body是一整坨密文，参数完全不可见，怎么下手？
**A1**: 目标是拿到加解密的明文和算法。别在密文上瞎猜。直接hook：在App进程里，加密函数调用前的入参就是明文、解密函数返回的就是明文。定位这两个函数（搜encrypt/decrypt、AES/RSA调用、或在网络发送函数往上回溯），拿到明文一切迎刃而解。
**Q2**: 怎么快速定位加密函数？
**A2**: 两条路：①静态搜加密API调用点（系统crypto库的调用一定存在）；②动态在网络发送函数下断，看密文是谁传进来的、往上回溯到加密点。动态回溯通常比静态搜快，因为发送点很明确。
**Q3**: 拿到算法和key后，怎么用于攻击而不只是解密看看？
**A3**: 构建自己的加解密工具链：解密看请求(找参数)→篡改明文→用同样算法重新加密→发出。这样你就能对加密接口做完整的参数篡改/越权/注入测试，加密对你透明了。或做成加解密预言机（hook暴露服务）避免自己实现。
**Q4**: 加密在native/VMP，key动态生成，逆不出来怎么办？
**A4**: 转正交维度：不逆算法，用"加解密预言机"。hook 出encrypt/decrypt两个函数供外部调用，你的fuzz工具：明文→调encrypt得密文→发送；收到密文→调decrypt看结果。让客户端做你的加解密引擎，完全不碰算法本身。
**Q5**: 如果加密的目的只是防抓包，参数改了签名会挂怎么办？
**A5**: 注意加密和签名是两回事：加密解决"看不见"，签名解决"改不了"。解密看到参数后若还有独立签名，回到签名机制处理。两个机制常独立，逐个拆。

### 业务逻辑漏洞（支付/优惠/积分）怎么系统找
**Q1**: 想找充值/支付/优惠券这类"能薅到钱"的逻辑漏洞，从哪切？
**A1**: 盯住"金额/数量/状态"这三类参数在客户端和服务端的信任边界。经典打法：①金额篡改（改支付金额、单价为负/为0/小数溢出）；②数量篡改（负数、超大数、越界）；③订单状态跳变（跳过支付直接置为已付）；④优惠叠加/重复使用。判据：服务端是否二次校验，还是信了客户端传的值。
**Q2**: 直接改金额被服务端拒了，是不是没戏？
**A2**: 不是。转攻"计算过程"而非"最终结果"：改单价而非总价、改折扣率、改积分抵扣比例、改数量让服务端自己算错。服务端常只校验总金额但信任了参与计算的中间参数。攻击计算链的输入，而非输出。
**Q3**: 优惠券/积分类，怎么找？
**A3**: 攻"并发"和"时序"：同一张券并发提交多次（竞态，条件竞争绕过一次性校验）、先下单锁券再取消订单但券已消耗回退异常、退款后积分不回收。并发和状态回退是逻辑漏洞的重灾区，单线程测不出来，要并发压。
**Q4**: 支付逻辑很严（服务端全校验、有幂等、有并发锁），这条打不动怎么办？
**A4**: 转正交维度：从"篡改交易参数"转到"篡改支付回调/凭证"。第三方支付的异步通知回调是否验签、支付结果凭证能否伪造/重放、订单和支付单的绑定是否可错配（用一笔小额支付的成功回调去核销一笔大额订单）。回调链路常比下单链路校验松。
**Q5**: 还想深入，有没有更隐蔽的逻辑面？
**A5**: 有：退款逻辑（多退、重复退、退到他人账户）、跨业务的额度共享（一个额度多处消费的竞态）、以及测试商品/内部价接口泄露。逻辑漏洞的本质是"业务规则的边界没在服务端兜住"，顺着钱和状态流走一遍必有缝。

### 从客户端反推隐藏/内部API
**Q1**: 已知的接口都打完了没洞，怀疑有没暴露的内部接口，怎么挖？
**A1**: 三个来源：①客户端代码里出现但正常流程不会走的接口（debug、admin、内测功能）；②接口路径规律外推（/api/v1/user → 试 /api/v1/admin、/internal/、/api/v2/）；③接口文档泄露（swagger、api-docs、js里的接口map）。客户端里"提到但没用"的接口最值得试。
**Q2**: 外推路径大多404，怎么提高命中率？
**A2**: 用真实的命名习惯而非乱猜：从已知接口提取命名风格（下划线还是驼峰、版本号格式、动词习惯），按同样风格构造。同时区分404（不存在）和403/401（存在但没权限）——后者是金矿，说明接口在但你没权限，转越权。
**Q3**: 发现一批403的接口（存在但拒绝），怎么办？
**A3**: 这正是内部接口的信号。转攻鉴权：换更高权限的token、加内部标识头（X-Internal、来源IP伪造头）、试无鉴权的兄弟接口。内部接口常假设"只有内网/内部客户端会调"从而鉴权很弱。
**Q4**: 路径外推和文档泄露都没结果怎么办？
**A4**: 转正交维度：从"猜接口"转到"让服务端告诉你接口"。找信息泄露入口——报错栈、GraphQL的introspection（若用GraphQL，一次自省拿到全部schema和接口）、健康检查/actuator类端点、以及不同端（PC、H5、合作方SDK）暴露的接口差集。换个客户端可能暴露App里没有的接口。
**Q5**: 怎么优先级排序这些疑似内部接口？
**A5**: 按危害预期排：带admin/manage/internal/export/config字样的优先；数据导出、用户管理、配置修改类优先。这些一旦无鉴权就是重大突破。

### 接口版本回退/老接口攻击
**Q1**: 当前版本接口鉴权/加密都很严，怀疑老版本更松，怎么验证？
**A1**: 老接口是移动端的经典软肋——为了兼容老App，后端常保留旧版接口且不敢下线，安全加固却没跟上。方法：把请求路径里的版本号往下降（/v3/ → /v2/ → /v1/），或去掉版本号，看老接口是否仍活、鉴权是否更松。
**Q2**: 怎么知道有哪些老版本？
**A2**: 从多个来源拼：历史APK版本（下载旧版包，逆出它当年的接口）、web archive里的旧文档、以及直接枚举版本号。旧版客户端往往用明文、弱签名、无某些新校验——用旧客户端的调用方式打新后端。
**Q3**: 老接口还活着但也做了鉴权，怎么办？
**A3**: 找新老接口的"能力差集和校验差集"：同一功能新接口加了越权校验、老接口没加；新接口加了参数签名、老接口只要token。用老接口做新接口做不了的越权/篡改。差异本身就是漏洞。
**Q4**: 所有老接口都已下线或同样严格怎么办？
**A4**: 转正交维度：从"版本回退"转到"端差异"。同一后端服务的不同客户端（安卓/iOS/H5/小程序/PC/开放平台）对接口的鉴权实现可能不一致。找"某个端能调而这个端被拦"的接口，用弱端的调用方式打。版本是一个维度，客户端类型是另一个正交维度。
**Q5**: 这类攻击怎么固化成方法论？
**A5**: 建立"接口版本×客户端类型"矩阵，对同一功能在所有版本、所有端上各测一遍鉴权强度。安全性取决于最弱的那个组合，而防守方几乎不可能把所有组合都加固到位。

### debug/测试环境/内测开关泄露
**Q1**: 想找测试环境和debug入口，从客户端能挖到什么？
**A1**: 静态搜debug/test/dev/beta/staging关键字、搜被注释或条件关闭的测试域名、搜隐藏的调试菜单开关。很多App把测试环境地址、调试开关、mock数据留在了发布包里。判据：是否存在非生产的域名或可开启的调试功能。
**Q2**: 找到了测试环境域名，直接打？
**A2**: 打，但先评估：测试环境常常①无WAF/无风控；②用弱口令/默认账号；③数据是脱敏不彻底的真实数据；④开着各种调试接口。它是同一套代码的"裸奔版"。但注意测试环境的数据真实性和授权边界，别打到无关系统。
**Q3**: 客户端里有隐藏调试开关（比如连点logo进调试模式），能干什么？
**A3**: 开启后常暴露：环境切换、接口日志、mock登录、跳过校验的后门。这些是开发留的便利后门，可能让你直接切到测试后端、看到明文请求、甚至免鉴权登录。想办法触发这个开关（改配置、hook开关判断为真）。
**Q4**: 没有测试环境泄露、也没有调试开关怎么办？
**A4**: 转正交维度：从"找非生产环境"转到"找生产环境的调试残留"。生产接口是否开着详细报错（stacktrace泄露）、是否有actuator/监控端点、是否有未关闭的接口文档、日志里是否打了敏感信息。生产环境的"调试没关干净"和"存在测试环境"是两条正交的信息泄露线。
**Q5**: 测试环境打进去了，怎么利用到生产？
**A5**: 看两者的关联：是否共用数据库/缓存/账号体系、测试环境拿到的密钥/token是否在生产也有效、测试环境的漏洞（如SSRF、命令执行）能否横向到生产网络。测试环境常是打进生产内网的跳板。

### App级签名校验挡住重打包
**Q1**: 我改了smali重打包想插桩，但App一装就检测到签名不对退出，怎么办？
**A1**: 确认是签名校验（App校验自己的签名指纹）。绕过分两层：①找到校验函数patch掉（但校验可能在native、可能多点）；②用不改包的注入方式避开重打包（如系统层注入、frida server而非gadget）。先判断你是否非重打包不可——很多时候用运行时注入就不用改包，也就不触发签名校验。
**Q2**: 必须改包（比如内置gadget做免root注入），签名校验怎么绕？
**A2**: 定位校验点：搜getPackageInfo、signatures、证书指纹常量的比对。校验逻辑本质是"实际签名==内置期望值"，hook/patch让它恒真。注意可能有多个校验点和native校验，要trace全。
**Q3**: 签名校验在native且和完整性校验联动（改任何字节都崩）怎么办？
**A3**: 转正交维度：从"改包后骗过校验"转到"不改包"。用不修改APK文件的技术达成同样目的——磁盘上文件原封不动，只在运行时内存里注入/hook。签名和完整性校验查的是磁盘文件，运行时内存注入它查不到。
**Q4**: 如果连运行时注入也被反调试挡，重打包又过不了签名校验，两头堵怎么办？
**A4**: 退到不进程内的路线：纯静态还原关键算法（不运行App）+ 直接打API面。签名校验、完整性校验、反调试都是"客户端自我保护"，全部作用于"运行这个客户端"这件事上。你只要拿到算法和接口就绕开客户端，这些防护对你归零。
**Q5**: 怎么判断重打包这条路值不值得走？
**A5**: 重打包会连锁触发签名校验+完整性校验两个绕过任务，是重投入。只有当你需要"分发一个改造版给自动化/队友长期用"时才值得。临时打点，优先选不改包的运行时方案。

### 运行时从内存提取密钥/明文
**Q1**: 静态找不到key、算法在native逆不动，我知道key在内存里，怎么取？
**A1**: 核心思路：在key"必然以明文出现"的瞬间截获它。密钥无论怎么保护，加解密执行时必须还原成明文喂给crypto运算。方法：hook系统crypto API（几乎所有加密最终调系统库），在它被调用时dump传入的key和data。系统库是所有加密的收口，防不住。
**Q2**: 它没调系统crypto库，用了自研算法在内存里跑怎么办？
**A2**: 转向内存搜索/dump：在加密操作前后dump进程内存，用已知的密文/明文对做差比对定位key所在内存区域；或对疑似key的内存区下访问断点，看谁在用它。自研算法逃不过"数据要进内存被读写"。
**Q3**: 反调试导致无法attach、下断即崩怎么办？
**A3**: 转向"离线内存快照"：想办法拿到进程的内存转储（core dump、模拟器内存快照），在离线快照里静态搜索密钥特征（高熵字符串、已知格式的key）。离线分析不触发运行时反调试。改变"何时取内存"。
**Q4**: 如果内存里key也做了混淆/分片存储（用时才拼）怎么办？
**A4**: 转正交维度：不找"key这个静态对象"，而找"key被使用的那个函数"。在crypto运算函数（而非key变量）处hook，此刻key必然已被拼好还原为可用形态。从"找存储的密钥"转到"截使用中的密钥"。
**Q5**: 拿到内存中的key后要注意什么？
**A5**: 确认它是长期key还是会话临时key。会话key只对当前会话有效，你需要的可能是那个能派生所有会话key的主密钥或算法。若是临时key，回头hook它的生成函数才是根。

### WebSocket/长连接/私有协议怎么分析
**Q1**: App用WebSocket或自定义TCP长连接传核心数据，HTTP抓包工具看不了，怎么办？
**A1**: 先确认协议类型：抓全流量pcap看端口和握手特征（WebSocket有升级握手，私有TCP没有）。WebSocket over TLS 可用支持WS的抓包工具或hook上层frame。私有二进制协议则必须hook客户端的收发函数拿明文。判据：是文本帧还是二进制、是否再套一层加密。
**Q2**: WebSocket帧内容还是密文/protobuf，看不懂结构怎么办？
**A2**: 是protobuf就找proto定义（客户端里常带.proto或可从代码还原字段结构），或用protobuf解码工具盲解出字段。是再套加密就回到hook加解密函数。私有协议的关键是拿到"编解码"这一层，通常在客户端有明确的序列化/反序列化函数。
**Q3**: 想对长连接做篡改测试，不只是看，怎么做？
**A3**: 在收发函数处hook实现"运行时中间人"：拦截outgoing frame改内容再发、拦截incoming frame改内容再交给App。这比网络层MITM更强，因为你在加密之内、协议之内操作。用它测越权、注入、逻辑绕过。
**Q4**: 长连接协议逆向成本太高、时间不够怎么办？
**A4**: 转正交维度：从"啃长连接"转到"找它的HTTP兄弟接口"。核心业务除了长连接推送，登录/下单/查询等关键操作往往仍走HTTP接口（长连接多用于消息/实时推送）。先把HTTP面打透，长连接留到最后。别被最难的协议绊住整个评估。
**Q5**: 长连接本身有没有独特的攻击面？
**A5**: 有：连接建立时的鉴权是否只在握手做一次（之后不再校验，劫持连接即劫持身份）、消息是否可越权投递给他人、服务端推送是否可被伪造。长连接的"一次鉴权长期信任"模型是它特有的弱点。

### 没有账号/未登录态怎么打开局面
**Q1**: 目标App需要注册登录，我手上没有有效账号，怎么开局?
**A1**: 先枚举未登录可达的攻击面：注册接口、登录接口、找回密码、游客/未登录可访问的接口、以及静态资源和公开API。很多接口在未登录态就能打（信息泄露、越权、注入），根本不需要账号。先把"匿名可达面"摸清。
**Q2**: 想要个账号做已登录测试，注册被限制（需邀请码/实名/手机号）怎么办？
**A2**: 找注册的旁路：H5端/小程序端注册是否更宽松、老版本注册接口是否无需某些校验、第三方登录（微信/apple登录）是否能绕过手机号注册。同一账号体系常有多个注册入口，门槛不一。
**Q3**: 完全注册不了，一个账号都搞不到怎么办？
**A3**: 转正交维度：从"需要认证的攻击面"转到"认证机制本身"。把登录/注册/找回流程当作攻击目标而非门槛——短信验证码逻辑漏洞、密码找回逻辑漏洞、用户枚举、OAuth逻辑漏洞。攻破认证流程既能拿账号，本身也是高危漏洞。从"用账号打业务"转到"打认证拿账号"。
**Q4**: 认证流程也很严怎么办？
**A4**: 转向"横向借身份"：第三方登录的逻辑漏洞（token混用、绑定劫持）、或从其他合法渠道拿到测试凭据。以及看是否有开放注册的测试环境。始终在授权范围内操作。
**Q5**: 拿到一个低权限账号后，下一步的决策是什么？
**A5**: 立刻转越权——用这个账号试水平越权(看别人数据)和垂直越权(调管理接口)。一个普通账号是撬动整个系统的支点，它让你能带鉴权访问几乎所有接口，从而系统性测越权和逻辑漏洞。

### 攻击面优先级：客户端 vs API vs 服务端组件
**Q1**: 面对一个移动App目标，客户端逆向、API测试、服务端组件三块都能打，先投哪？
**A1**: 按"投入产出比"排，通常：API面 > 服务端组件 > 深度客户端逆向。因为高危漏洞（越权、逻辑漏洞、注入、未授权）大多在API/服务端，而深度逆向（脱壳、绕VMP）投入大、产出常只是"拿到算法"这个中间品。策略：轻量逆向拿到接口和签名 → 主力打API → 逆向只在API需要时按需深入。
**Q2**: 什么时候必须优先深度客户端逆向？
**A2**: 当①核心资产就在客户端（硬编码高价值密钥、本地敏感数据）；②不逆出算法就完全无法和API对话（全加密全签名且无预言机可用）；③目标本身就是评估客户端安全性。否则逆向是手段不是目的。
**Q3**: API打了一圈都很严，该往服务端组件转吗？
**A3**: 该。从"应用层API逻辑"转到"服务端基础设施"：接口背后的中间件、上传功能导致的文件解析/SSRF、接口触发的服务端组件（如导出用了某解析库、图片处理用了某组件）。App的接口是打到服务端组件的入口，逻辑打不动就打技术漏洞。
**Q4**: 三块都投了都不顺，整体卡住怎么办？
**A4**: 转正交维度：跳出"这一个App"，转到"这个后端的其他暴露面"。同一后端服务通常还被web端、开放平台、合作方对接、内部系统调用。攻击面的边界是"这套后端系统"，不是"这个移动App"。资产测绘找出关联域名/系统，从最薄弱的入口进。
**Q5**: 怎么动态调整这个优先级？
**A5**: 每突破一个信息点就重排。拿到硬编码云key→云资产优先；拿到一个越权→深挖越权面；发现测试环境→转打测试环境。红队的优先级是随情报滚动更新的，不是开局定死。始终把资源压在"当前已知信息里最可能一击致命的那条线"。

### 第三方SDK成为突破口
**Q1**: App集成了一堆第三方SDK（推送、统计、支付、客服、地图），这算攻击面吗？
**A1**: 算，而且常是"防守方管不到"的软肋。先清点SDK清单和版本（静态可提取包名/类名/版本）。判据：是否有已知漏洞版本、是否暴露组件、是否有自己的鉴权和接口。SDK是别人写的代码跑在目标里，主程序再安全也兜不住SDK的洞。
**Q2**: 发现某SDK有已知CVE，怎么利用？
**A2**: 确认版本命中后，看该漏洞的触发路径在目标App里是否可达（是否用了漏洞功能、入口是否可控）。常见SDK漏洞：反序列化、任意文件读写、暴露的service/provider、WebView相关。可达即可打。
**Q3**: SDK自己也调后端（如客服SDK、IM SDK有独立服务），怎么打？
**A3**: 把SDK的后端当独立目标：它有自己的鉴权、自己的API、常和主业务共享用户身份。SDK后端的安全水平参差不齐，可能存在越权读消息、越权发消息、信息泄露。抓SDK的独立流量单独分析。
**Q4**: SDK都是最新版、无已知洞怎么办？
**A4**: 转正交维度：从"SDK漏洞"转到"SDK配置错误"。开发者集成SDK时的错配才是重灾区——把应密的SDK secret硬编码、给SDK过大权限、SDK的回调/白名单配错、推送SDK可被任意推送。漏洞不在SDK代码而在集成方式。
**Q5**: SDK这块还能怎么延伸？
**A5**: 延伸到"供应链视角"：同一SDK被大量App使用，一个SDK的通用错配模式可批量复用。以及SDK上报的数据流（统计SDK可能把敏感信息带出去、可被劫持）。第三方SDK是攻击面里最容易被防守方忽视的一环。

### 客户端做的校验，服务端信不信
**Q1**: 我发现App在客户端做了大量校验（金额、格式、权限判断），这些是不是都可绕？
**A1**: 默认全部可绕，直到证明服务端也校验了。核心原则：客户端校验只是UX，不是安全边界。方法：绕过客户端（直接构造请求，不经过App的校验代码），把客户端拦下来的非法值直接发给服务端，看服务端是否接受。判据：服务端是否独立校验。
**Q2**: 怎么高效地"绕过客户端只测服务端"？
**A2**: 直接在API层构造请求（用抓到的合法请求做模板），完全不经过App界面。客户端的所有前端校验(禁用按钮、格式限制、金额锁定)在直接发包时统统失效。这是移动/前端安全测试的基本功：永远在流量层测，不在UI层测。
**Q3**: 哪些客户端校验最值得优先绕过测试？
**A3**: 优先级：①涉及金额/权限/身份的校验（绕过=越权或薅钱）；②格式/长度校验（绕过=注入的前置）；③业务状态校验（绕过=逻辑漏洞）。凡是"客户端说你不能这么做"的地方，都值得在服务端验一遍它是不是真不能。
**Q4**: 绕过后发现服务端确实也都校验了，客户端校验这条思路断了怎么办？
**A4**: 转正交维度：从"客户端做了服务端没做"转到"客户端和服务端理解不一致"。两端对同一数据的解析/校验规则若有差异（如客户端按A规则、服务端按B规则），中间的差集就是漏洞——参数污染、类型混淆、编码差异、截断差异。不是"谁没校验"，而是"两边校验得不一样"。
**Q5**: 怎么把这个原则内化成检查动作？
**A5**: 对每一个客户端限制，都问一句"如果我不通过客户端、直接发这个非法值，服务端会怎样"。把这变成条件反射。移动端和H5的绝大多数漏洞，根源都是"信任了不该信任的客户端"。

### OAuth/第三方登录的逻辑漏洞
**Q1**: App支持微信/Apple/第三方账号登录，这块怎么找洞？
**A1**: 盯授权码/token的流转和绑定环节。经典点：①第三方返回的code/token在服务端换取用户信息时，绑定关系是否可被劫持；②redirect_uri是否校验严格（可控则劫持授权码）；③第三方的openid/unionid是否被信任为身份而缺乏二次校验。判据：能否用一个第三方身份登录/绑定到另一个业务账号。
**Q2**: 具体怎么测账号劫持？
**A2**: 测绑定流程：登录态下绑定第三方账号时，绑定的目标账号id是否可篡改（把攻击者的第三方号绑到受害者账号，或反之）。以及登录时若第三方号未注册是否自动创建/自动关联到已有账号，关联逻辑常有缺陷。
**Q3**: redirect_uri和授权码都校验很严怎么办？
**A3**: 转向"token混用/跨端"：一个第三方的access token能否被用到其他不该用的地方、不同App共用第三方appid时token能否跨App使用、id_token的签名和受众(aud)是否被校验。OAuth的信任错配常在"token被用在了非预期的接收方"。
**Q4**: 整个OAuth流程都很严怎么办？
**A4**: 转正交维度：从"OAuth协议逻辑"转到"OAuth之后的会话"。第三方登录成功后，业务系统自己签发的会话token/绑定逻辑才是薄弱点——第三方把身份认证做对了，但业务系统接住这个身份时可能出错（越权绑定、会话固定、身份混淆）。攻击点从协议本身转到"业务系统如何消费认证结果"。
**Q5**: 这类漏洞的危害怎么评估?
**A5**: 看它能否"零交互接管账号"或"批量接管"。授权码/绑定劫持类若能诱导一次点击就接管，是高危；若能通过openid可预测/可枚举批量登录他人账号，是极危。第三方登录漏洞往往一击就是完整账号接管。

### 移动接口的注入类漏洞
**Q1**: API的鉴权逻辑都打不动，想找传统注入(SQLi/命令注入等)，怎么切入移动接口？
**A1**: 移动API的注入面和web一样，但常被忽视因为参数藏在加密body里。前提：先解密看到明文参数。然后对每个参数常规测：SQLi(报错/布尔/时间盲注)、NoSQL注入、命令注入、SSTI。移动后端也是普通后端，参数进了SQL/命令/模板照样能注。判据：注入特征payload是否引发异常/延时/数据变化。
**Q2**: 参数经过加密和签名，改了就签名失败，怎么测注入？
**A2**: 用加解密/签名预言机的能力：解密→改参数注入payload→重新加密→重算签名(或用预言机)→发送。加密签名只是让注入测试多一道手续，不改变注入本身的存在性。很多人因为"改不了参数"就放弃注入测试，恰恰漏了这块——防守方也常以为加密了就没注入。
**Q3**: 哪些移动接口参数最可能有注入？
**A3**: 优先测：搜索/筛选/排序参数(直接进SQL的orderby/where)、导出/报表接口、老接口(常无参数化)、以及拼接进后端命令的参数(文件名、路径)。移动端的搜索和列表接口是SQLi高发区。
**Q4**: 常规注入都被参数化/WAF挡住怎么办？
**A4**: 转正交维度：从"注入用户输入的参数"转到"注入被信任的header/元数据"。移动接口常把设备信息、版本号、来源等放在header里且服务端不设防地记录/查询它们(如把User-Agent、deviceId拼进日志SQL或用于查询)。防守的注意力都在业务参数上，元数据字段是盲区。
**Q5**: 找到一个注入点后怎么扩大战果?
**A5**: 评估注入位置能触达什么：数据库注入→拖库/写文件/提权；命令注入→直接RCE到服务端；SSTI→常也是RCE。移动接口的注入一旦成立，就从"App漏洞"升级成了"服务端沦陷"的入口，全力往深处打。

### 文件上传接口的攻击
**Q1**: App有头像/图片/附件上传功能，这个接口怎么打？
**A1**: 上传是移动端常见的高危面。先摸清：上传到哪(自建存储还是云OSS)、服务端如何校验(类型、后缀、内容)、上传后文件如何被访问和处理。判据：能否上传非预期类型、能否控制存储路径、上传的文件是否会被服务端解析。分"传上去"和"能利用"两步。
**Q2**: 想传webshell但有类型校验怎么办？
**A2**: 常规绕过组合拳：改后缀/大小写、改Content-Type、加图片头做多语言文件、利用解析漏洞(某些中间件的解析特性)、双扩展名、路径穿越改存储位置。判据：先看校验在客户端还是服务端(客户端校验直接绕)，服务端校验再逐个试绕过点。
**Q3**: 上传成功但文件存在OSS且不可执行，传shell没用怎么办?
**A3**: 转攻其他上传危害：①路径穿越覆盖已有文件(覆盖配置/他人文件)；②XSS(上传html/svg被浏览器解析)；③服务端处理时的漏洞(图片处理组件的解析漏洞、SSRF via 远程图片url)；④越权访问他人上传的文件。上传的危害不止webshell。
**Q4**: 上传校验极严、存储也隔离得很好，这条路断了怎么办？
**A4**: 转正交维度：从"上传文件内容"转到"上传引发的服务端行为"。比如上传时传的是一个url让服务端去拉取(SSRF)、上传后触发的转码/预览/病毒扫描(可能有组件漏洞)、或上传接口本身的越权(传到别人的空间)。攻击点从"文件本身"转到"服务端处理文件的过程"。
**Q5**: 怎么判断上传漏洞的最终价值?
**A5**: 排序：可执行目录传shell=RCE(最高)；路径穿越覆盖关键文件≈RCE或权限提升；触发服务端组件漏洞=RCE；存储型XSS/越权读文件=中危。先判断能否落到代码执行，不能再退而求其次拿信息泄露/XSS。

### GraphQL/新式API的攻击面
**Q1**: 抓包发现接口是GraphQL(或类似的聚合查询接口)，和REST打法有什么不同?
**A1**: GraphQL的最大礼物是introspection(自省)。先试自省查询能否拿到完整schema——一次请求就得到所有类型、字段、query、mutation，等于拿到全部接口文档。判据：自省是否开启。开着就等于目标把接口地图送给你了，重点找敏感query/mutation。
**Q2**: 自省被关了怎么办?
**A2**: 转向字段爆破和错误信息利用：GraphQL的报错常提示"你是不是想要字段X"(did you mean)，可据此逐步猜出schema；或从客户端代码里提取它实际用的query。自省关了不代表接口没了，只是地图要自己拼。
**Q3**: GraphQL特有的漏洞有哪些要重点测?
**A3**: ①越权：GraphQL常在字段级鉴权上出错，某个字段忘了加权限就能查到敏感数据；②嵌套查询DoS(深度嵌套耗尽资源)；③批量查询绕过限流(一个请求打包多个操作绕过频率限制，可用于爆破验证码/枚举);④mutation的越权(改别人数据)。字段级越权是GraphQL的头号问题。
**Q4**: GraphQL鉴权做得很严怎么办?
**A4**: 转正交维度：利用GraphQL的"聚合"特性做别的API做不到的事——用别名/批量在一个请求里发起大量操作绕过基于请求数的限流，把GraphQL当成绕过速率限制的工具去打其他漏洞(爆破、枚举)。从"打GraphQL本身"转到"用GraphQL特性打别的面"。
**Q5**: 怎么快速判断GraphQL目标的优先动作?
**A5**: 开局三连：试自省(拿schema)→翻schema找敏感mutation(改密码/改角色/转账类)和敏感query(查用户/查配置)→挑一个测字段级越权。GraphQL把攻击面结构化地暴露了，比REST更容易系统性梳理,善用这个特点。
