# 逆向PWN · 动态调试与断点策略

### 上手一个二进制:先静态还是先动态跑起来
**Q1**: 拿到一个陌生 ELF/PE,时间有限,该先 IDA 静态通读还是直接扔进调试器跑?
**A1**: 先做 30 秒的"廉价侦察":`file` 看架构/是否 strip/是否 PIE,`checksec` 看 NX/Canary/RELRO/PIE,`strings` 抓关键字符串。这决定后面所有断点策略——有符号就能按名字下断,strip 就得靠字符串/导入表定位。别急着通读汇编。
**Q2**: 侦察完了,先动还是先静?
**A2**: 判据是"输入到危险点的路径长短"。若程序交互简单(读一次输入就处理),直接动态跑一遍观察 I/O 行为最快;若控制流复杂(状态机、多层菜单),先静态画出关键函数调用图,再带着假设去动态验证,避免在调试器里瞎点。
**Q3**: 动态跑第一遍应该看什么?
**A3**: 不下断点,先 `ltrace`/`strace` 或 procmon 看它调了哪些库函数/系统调用——read/recv 在哪读输入、有没有 malloc/free(暗示堆题)、有没有 open 配置文件。行为轮廓比逐行读汇编信息密度高得多。
**Q4**: 动态静态都摸了还是理不清核心逻辑怎么办?
**A4**: 转向"数据驱动"——不追控制流,追数据。在输入缓冲区下 watchpoint/硬件读写断点,让程序自己告诉你"谁碰了我的输入",顺着访问点反推处理函数,比顺着 main 往下 trace 高效。
**Q5**: 如果这条静态+动态的常规路彻底卡死(混淆严重、反调试拦截)?
**A5**: 正交转向——放弃"理解代码",改为"黑盒差分"。用不同输入跑,diff 输出/covered basic block(用 QEMU/DynamoRIO/Pin 插桩记录覆盖),观察哪些分支被哪类输入触发,把逆向问题降级成 fuzzing+覆盖率反馈问题。

### 断点该下在哪:入口点还是关键函数
**Q1**: 程序太大,不可能全程单步,断点下在哪最省事?
**A1**: 不要盲下入口断点然后单步到天荒地老。优先下在"数据边界":输入函数返回处(read/recv/scanf 之后)、输出函数调用处(printf/send 之前)、以及可疑危险函数(strcpy/memcpy/sprintf/system)。这些是信息浓度最高的点。
**Q2**: 有符号的话按名字下,strip 了怎么定位这些点?
**A2**: 靠 PLT/IAT——库函数调用即使 strip 也在导入表里。gdb `b read`、`b system` 直接断 libc 符号;Windows 用 `bp kernel32!ReadFile`。程序自身函数 strip 了,就用字符串交叉引用:找到关键提示串地址,search/xref 定位引用它的代码再下断。
**Q3**: 想断在"处理输入的核心函数"但不知道是哪个?
**A3**: 用"倒推法":在输出/判定点(如打印"Wrong"/"Correct"的地方)下断,断下后看调用栈(`bt`),沿栈帧往上就是判定逻辑的调用链,核心校验函数通常就在栈的中上层。
**Q4**: 断在库函数结果断点命中太频繁(malloc 被调几千次)?
**A4**: 上条件断点。gdb `b malloc if $rdi > 0x400`(按 size 过滤),或断在特定调用者返回地址。频繁命中说明选点太底层,往上挪一层到业务函数。
**Q5**: 关键函数就是找不到、断点全落空怎么办?
**A5**: 转向"内存改动追踪"这个正交维度。既然找不到"谁处理",就监视"什么被改"——对目标全局变量/flag 缓冲区下硬件写断点,或用 rr 录制后反向执行(reverse-continue)从结果倒查到起因。

### 反调试触发了:程序检测到调试器就退出
**Q1**: 一进调试器程序就自杀或行为异常,判定是反调试,先怎么定位检测点?
**A1**: 先分类别。Linux 最常见 `ptrace(PTRACE_TRACEME)`——`catch syscall ptrace` 或 `b ptrace`,断下后直接改返回值为 0。Windows 最常见 `IsDebuggerPresent`/`CheckRemoteDebuggerPresent`/PEB.BeingDebugged,断这些 API 或直接 patch PEB 标志位。
**Q2**: patch 掉一个检测后又在别处崩,像有多重检测?
**A2**: 多层反调试是常态。别一个个手改,直接上通用绕过:Linux 用 `LD_PRELOAD` hook ptrace 返回 0;Windows 用 ScyllaHide/TitanHide 插件一键隐藏 PEB/时间差/异常等一堆检测。把精力留给逻辑,不要陷入反调试消耗战。
**Q3**: 怀疑有基于时间的反调试(单步慢就退出)?
**A3**: 找 `rdtsc`/`QueryPerformanceCounter`/`GetTickCount` 的调用,它测量两点间耗时,断点单步会让差值暴涨触发检测。对策:不在被测区间内单步,改用硬件断点直接跳到区间末尾;或 patch 掉时间比较分支。
**Q4**: 检测点用 int3 扫描自身代码(检测软件断点)怎么办?
**A4**: 这正是软件断点(0xCC)会被自校验发现的场景。改用硬件断点(gdb `hbreak`,x64dbg 硬件断点),它不修改内存字节,躲过 CRC 自校验。
**Q5**: 所有静态 patch/hook 都被更隐蔽的检测识破,反调试太顽固?
**A5**: 正交转向——完全脱离进程内调试。改用"外部观察":QEMU/Unicorn 模拟执行关键片段(反调试大多依赖真实 OS 行为,模拟器里失效),或用硬件辅助的 Intel PT/基于 eBPF 的追踪,从 CPU/内核层拿到执行轨迹而不进它的进程。

### PIE 开启:每次运行地址都变,断点地址算不准
**Q1**: 程序是 PIE,IDA 里看到的是偏移地址,gdb 里下 `b 0x1234` 命中不了,怎么办?
**A1**: PIE 下静态地址是相对 0 的偏移,运行时要加载基址。别硬编码。先 `starti` 停在入口,`vmmap`/`info proc mappings` 拿到映像基址,`b *(base+offset)`;或干脆用符号名/函数名下断,让 gdb 自己处理重定位。
**Q2**: 每次调试都手算基址太烦?
**A2**: pwndbg/gef 里直接 `b *$rebase(0x1234)` 自动加基址;写 exp 时在 gdbscript 里用 `$rebase`。要泄露运行时基址做 exploit,则需要一个地址泄露原语(格式化字符串/越界读),把某个已知代码/数据地址泄出来减去其静态偏移。
**Q3**: 断点下对了但 exploit 里算 libc/PIE base 老是错?
**A3**: 核对"泄露的是哪个地址"。泄露值必须减去它自己在对应模块里的静态偏移,不能减别的符号偏移。用 `vmmap` 确认段起始,`泄露地址 - 该符号静态偏移 = base`,再核对 base 低三位是否为 0(页对齐),不对齐就是算错了对象。
**Q4**: 本地能算对,远程环境基址规律不同?
**A4**: 远程 ASLR 熵/加载顺序可能不同,但"模块内偏移固定"这条不变。确保 exploit 全程用"泄露 base + 偏移",绝不写死任何绝对地址。libc 版本不一致也会让偏移全错——先确认远程 libc 版本(见后续 libc 识别条)。
**Q5**: 就是拿不到任何泄露、PIE base 无从算起,路走死了?
**A5**: 正交转向——绕开对绝对地址的需求。改用不依赖 PIE base 的技术:partial overwrite(只改地址低字节,页内偏移固定不受 ASLR 影响)、ret2csu/ret2dlresolve(无需 libc 地址)、或 stack pivot 到已知可控区域。把"需要精确地址"的问题转成"只需页内相对"。

### 定位崩溃点:程序 crash 了但不知道哪行挂的
**Q1**: 喂了畸形输入程序段错误,如何快速定位崩溃指令?
**A1**: 直接在调试器里跑到 crash,gdb 会停在故障指令,`info registers` 看 rip/pc 和出错地址。若 rip 已经是 0x41414141 之类的可控值,恭喜——控制流已劫持,直接进入偏移计算阶段。
**Q2**: rip 不可控,是在某条 mov/访问指令挂的,怎么判性质?
**A2**: 看 crash 类型:读非法地址(SEGV on read)多半是指针被污染/UAF;写非法地址是缓冲区溢出写越界;执行非法地址是控制流已被劫持但地址算错。结合 `bt` 看栈是否已被踩烂(bt 打不出正常帧=栈溢出典型特征)。
**Q3**: 想更精确地知道"哪个字节导致的崩溃"?
**A3**: 上 sanitizer——用 ASAN 重编(有源码)或 QASAN/Valgrind(无源码),它直接报出越界读写的精确地址、大小、以及分配/释放栈。比裸 gdb 逐步定位快一个数量级。
**Q4**: crash 偶发,不是每次都挂?
**A4**: 偶发崩溃常是堆布局/未初始化数据/竞态导致。用 `rr` 录制一次崩溃的执行,再反向调试稳定复现;或固定堆环境(关 ASLR、tcache 状态清零)让崩溃确定化。
**Q5**: 能崩但完全无法控制、看不出可利用性,这条 crash 路是不是废了?
**A5**: 不一定废,但先转向找"更好的原语"。一个不可控的 crash 说明当前输入点原语弱。转去审计其它输入面(其它菜单项、其它字段),或换 bug 类型:这个溢出不可控,看看有没有 UAF/double free/整数溢出等能提供更强控制的漏洞。别死磕一个弱原语。

### 求溢出偏移:知道能覆盖返回地址但不知道偏移量
**Q1**: 栈溢出能控 rip,怎么快速求出从输入到返回地址的精确偏移?
**A1**: 用 cyclic pattern。pwntools `cyclic(200)` 生成不重复序列灌进去,crash 后取 rip/pc 里的值 `cyclic_find(value)` 直接算出偏移。别手动二分数 A 的个数。
**Q2**: 64 位下 rip 值被截断(canary/地址不可打印导致只覆盖到一半)?
**A2**: 64 位地址高位常为 0,crash 时 rip 可能只拿到 pattern 的前几字节。用 `cyclic_find` 时按实际拿到的字节数匹配;或看 rsp 指向的 pattern(`x/gx $rsp`)反推,栈上的 pattern 比寄存器里的更完整。
**Q3**: 偏移求出来了但覆盖后没到预期返回地址?
**A3**: 检查中间是否有 canary。如果偏移处正好是 canary 位置,覆盖它会触发 __stack_chk_fail 而非返回劫持。gdb 里 `b __stack_chk_fail` 验证,若命中说明需要先泄露/绕过 canary,偏移要算到 canary 之后的返回地址。
**Q4**: 缓冲区里有长度检查/字符过滤,pattern 灌不满?
**A4**: 换策略——不靠一次性溢出。看是否有循环写入(逐字节)、或能多次写的场景;若有坏字符(\x00\n 等),cyclic 会被截断,改用 `cyclic(n, alphabet=...)` 避开坏字符集。
**Q5**: 反复调不出稳定偏移,栈布局老变?
**A5**: 正交转向——放弃固定偏移思路。栈布局随环境变量/argv 长度浮动时,改用相对定位:leak 一个栈地址后按相对偏移写,或用 stack pivot 把栈迁移到你完全掌控的堆/bss 区,消除对不稳定栈偏移的依赖。

### 堆题起手:该在哪些点下断观察堆布局
**Q1**: 判定是堆利用题(大量 malloc/free),动态调试第一步断在哪?
**A1**: 断在堆操作原语的封装函数上,而不是裸 malloc/free——业务代码通常有 add/delete/edit/show 菜单包了一层。在每个菜单处理函数入口下断,每步操作后用 pwndbg `heap`/`bins`/`vis_heap_chunks` 看 chunk 布局变化,建立"操作→堆状态"的映射。
**Q2**: 想盯住某个特定 chunk 的生命周期?
**A2**: 拿到它的地址后下硬件写断点(`watch *addr` / `hbreak`),任何对它的写入(包括 free 后写入 fd 指针)都会停下,这是抓 UAF/double free 触发点的利器。
**Q3**: 怎么确认 free 后的 chunk 进了哪个 bin(tcache/fastbin/unsorted)?
**A3**: free 前后各 `bins` 一次对比。看 size 落在哪个范围决定去向——tcache(默认 <0x410 且对应 tcache 未满)、fastbin、unsorted。这直接决定利用手法:tcache poisoning 还是 fastbin dup 还是 unsorted bin leak。
**Q4**: 需要泄露 libc,断点怎么配合?
**A4**: unsorted bin 里的 chunk 的 fd/bk 指向 main_arena(libc 内)。构造一个 chunk 进 unsorted bin,不清空就 show,泄露出的值减去 main_arena 相关偏移即得 libc base。断在 show 的读取处验证泄露的正是 arena 指针。
**Q5**: 堆手法在本地调通,但换个 libc 版本利用就失效?
**A5**: glibc 版本强相关(tcache key/安全链接 safe-linking/指针加密从 2.32 引入)。先精确识别目标 libc 版本,在对应版本下重新调试。若手法被新版缓解(如 safe-linking 让 fd 加密),正交转向:改用不依赖裸 fd 覆盖的手法——House of 系列里适配该版本的变种、或 largebin attack、tcache stashing 等。

### 断在比较函数:想看明文/绕过校验
**Q1**: 程序对输入做校验(密码/序列号/flag 比对),想动态拿到正确值,断哪?
**A1**: 断在比较原语。`b strcmp`/`b memcmp`/`b strncmp`,命中时看两个参数(rdi/rsi 指向的内存),其中一个是你的输入,另一个往往就是期望值——直接 `x/s` 读出来。这是最省事的"动态取答案"。
**Q2**: 它不用标准库比较,而是自写循环逐字节比?
**A2**: 那就找那个循环。特征是:一个索引递增、逐字节取输入与某常量/数组比较、不等就跳走。在循环体的比较指令下断,单步观察每轮拿你的字节和谁比,把"谁"逐字节记下来就是目标串。
**Q3**: 校验是把输入变换后再比(哈希/加密/异或),断比较点只看到密文?
**A3**: 断点要往前挪到"变换发生前"或抓变换的逆。若是对称变换(异或、简单加),读出常量和算法反推;若是哈希则无法反推,转为在变换函数上分析算法,或直接爆破(若空间小)。关键:比较点看到的是变换后的值,别在这里浪费时间试图逆哈希。
**Q4**: 逐字节比较但有"整体校验后才判对错",没法一字节字节试?
**A4**: 若是"全对才过"的整体比较,动态直接读期望值即可(上面 A1/A2)。若是"逐字符即时反馈"(对一个字符走一条路),可以用侧信道:计时/覆盖率反馈逐字符爆破,或 angr 约束求解各个字符。
**Q5**: 校验逻辑被 VM 保护/混淆,断点看不到明文比较?
**A5**: 正交转向——放弃"读比较",改"符号执行求解"。用 angr/Triton 把"输出=正确"设为约束,让求解器反解输入,绕过对混淆比较逻辑的人工理解。或黑盒 fuzz+覆盖率,让工具找到通过校验的输入。

### 就地 patch:跳过校验/反调试直接放行
**Q1**: 有个校验分支挡路,想直接改指令让它永远通过,怎么操作最稳?
**A1**: 定位那条条件跳转(je/jne/jz),动态里 `set $eflags` 临时翻转标志位验证"改了能过";确认后决定持久化方式:调试期改 EIP/eflags 是临时的,要长期就 patch 字节(je→jmp 或 nop 掉跳转,或改 test 结果)。先临时验证再持久化,别一上来乱改。
**Q2**: patch 后程序在别处崩,像有完整性自校验?
**A2**: 代码段被 CRC/hash 自校验时,改字节会被发现。对策:改用调试期动态 patch(不落盘,自校验读到的是原字节但执行时被你改)、硬件断点+改寄存器绕过、或先把自校验函数本身 patch 成永远返回"完好"。
**Q3**: 想 patch 但不确定改哪个跳转才对?
**A3**: 别猜。在两个分支的目标处各下断点,正常输入走一次看命中哪边、错误输入走一次看命中哪边,确定"通过"对应的分支后,反推需要让哪个跳转怎么走。用行为区分,不靠读汇编猜。
**Q4**: patch 是为了调试推进,但最终 exploit 是打远程,远程改不了字节?
**A4**: 关键提醒——patch 只是本地理解/调试的手段,远程拿不到二进制修改权。远程要靠合法输入让它自己走到目标分支,或靠内存写原语在运行时改远程进程内存。别把"本地 patch 通了"当成"题解了"。
**Q5**: 保护太强,任何 patch 都被自校验/反篡改击破?
**A5**: 正交转向——不改代码,改数据/环境。让校验读到的"数据"满足条件而非改"代码":构造满足条件的输入、hook 它依赖的外部数据源、或用 LD_PRELOAD 替换它调用的库函数(改行为不改它自己的字节),避开针对代码段的完整性检查。

### 多线程/子进程:断点断下来但停错了线程
**Q1**: 目标 fork 出子进程处理请求,我下的断点在父进程,子进程逻辑追不到,怎么办?
**A1**: gdb 默认跟父进程。`set follow-fork-mode child` 让它跟子进程,或 `set detach-on-fork off` 同时保留父子。网络服务型 PWN(fork per connection)必须先设对 follow 模式,否则断点永远在 accept 循环的父进程里空转。
**Q2**: 多线程程序,断点一命中所有线程都乱了,变量值时对时错?
**A2**: 先确认调度模式。`set scheduler-locking on` 让单步时只跑当前线程,避免别的线程在你单步间隙改了共享状态。分析竞态时再关掉。用 `info threads`/`thread N` 明确自己在看哪个线程。
**Q3**: 想断在"处理我这个连接的那个子进程/线程",但有很多并发?
**A3**: 用条件缩小。断点加条件匹配你的连接特征(如某 fd、某请求 id、某源端口对应的 buffer 内容);或干脆让服务单进程/单线程跑(很多服务有 -d/debug/单 worker 参数)以简化调试环境,调通逻辑再回到并发。
**Q4**: fork 后子进程立刻 exec 了新程序,断点全丢?
**A4**: exec 会替换镜像,旧断点失效。`catch exec` 停在 exec 后,再对新镜像下断;或用 `set follow-exec-mode new`。若是 setuid 提权链,关注 exec 前后的权限/环境变化点。
**Q5**: 并发调试实在理不清,竞态难复现?
**A5**: 正交转向——从"在线调试"转"离线录制回放"。rr 支持记录多线程/子进程执行后确定性回放,把不可复现的并发 bug 变成可反复研究的固定轨迹;或用 strace -f 全量记录父子进程系统调用,离线分析交互序列。

### 远程调试:目标在别的机器/架构上
**Q1**: 目标跑在 ARM/MIPS 路由器或另一台机器,本地没法直接 gdb,怎么调?
**A1**: 上 gdbserver 远程调试。目标端 `gdbserver :port ./prog`(或 attach `--attach pid`),本地对应架构的 gdb-multiarch `target remote ip:port`。先确认目标架构(`file` 输出),配对的交叉 gdb,否则符号/寄存器全乱。
**Q2**: 目标是嵌入式设备,塞不进 gdbserver 或没权限?
**A2**: 换 QEMU 用户态模拟:`qemu-arm -g port ./prog` 直接起 gdbstub,本地远程连。不用真机、不用 gdbserver,还顺带绕过一部分依赖真实硬件的反调试。系统级则用 `qemu-system-*` 全系统模拟+gdb 接内核。
**Q3**: 远程连上了但断点行为诡异、地址对不上?
**A3**: 检查两端二进制是否完全一致(同一份文件、同样的加载基址)。库路径不同会导致 libc 符号/偏移错位——本地要 `set sysroot`/`set solib-search-path` 指向目标的库副本,保证 gdb 解析的符号和目标运行时一致。
**Q4**: 远程调试网络延迟大、单步极慢?
**A4**: 少单步、多用断点直达。设好条件断点一步跳到关键点,减少往返;或用 QEMU 本地模拟替代真机远程,消除网络往返。timing 敏感的反调试在慢速远程下更容易误触发,能模拟就模拟。
**Q5**: 目标设备完全封闭,gdbserver/QEMU 都上不去?
**A5**: 正交转向——从动态调试转纯静态+模拟片段执行。用 Ghidra/IDA 静态逆核心算法,用 Unicorn 单独模拟执行你关心的函数片段(喂寄存器/内存初值,拿输出),不需要跑整个真实设备。把"调试整个系统"降级为"模拟一个函数"。

### strip 无符号:下断点无从下手
**Q1**: 二进制被 strip,没有函数名,想下断点却不知道函数地址,怎么破?
**A1**: 库函数不受影响——PLT/动态符号还在,`b malloc`/`b system` 照样能断。自身函数则靠三招:字符串交叉引用(找提示串→xref)、导入函数调用点(在 printf/read 处断再看调用栈)、以及入口 main 定位(_start 里传给 __libc_start_main 的第一个参数就是 main)。
**Q2**: 想批量恢复符号让后续断点好下?
**A2**: 用签名匹配。IDA 的 FLIRT/Lumina、Ghidra 的 Function ID,能识别出静态链接进来的 libc 函数(memcpy/strlen 等)并自动命名。识别出 libc 版本后加载对应符号,一大批库函数名就回来了,断点直接按名下。
**Q3**: 静态链接且 strip,连 PLT 都没有,库函数也没名?
**A3**: 静态链接的库函数得靠签名(FLIRT)识别,或行为特征认(如 memcpy 的循环 rep movs、malloc 的 arena 操作)。实在认不出就按行为下断:反正 read/write 最终走 syscall,用 `catch syscall read/write` 从系统调用层拦,不依赖任何符号。
**Q4**: 只想断"处理输入的那个函数",符号全无?
**A4**: syscall 层兜底。`catch syscall read`(或 recvfrom)命中后 `finish` 返回到调用者,那里就是读输入的业务函数,记下地址下断。用系统调用作为"锚点"反推业务函数,strip 也拦不住。
**Q5**: 函数太多、字符串也被混淆,常规定位全失效?
**A5**: 正交转向——覆盖率引导定位。用 Pin/DynamoRIO/QEMU 记录不同输入下执行到的地址集合,diff 出"只有特定输入才触发的代码块",那就是处理该输入的关键函数。用运行时行为差分代替静态符号定位。

### watchpoint:想知道某变量/内存何时被改
**Q1**: 某全局变量/标志位莫名其妙变了,想抓改它的元凶,怎么做?
**A1**: 硬件写断点。gdb `watch *0xADDR`(或 `watch varname`),内存被写就停,`bt` 直接给出修改者的调用栈。这是定位"谁污染了我的数据"最直接的手段,比逐函数下断高效得多。
**Q2**: `watch` 下了但报"software watchpoint"跑得极慢?
**A2**: 软件 watchpoint 靠单步检查,慢到不可用。确保用硬件 watchpoint——大多平台 gdb 会自动选,若没有,检查是否超过硬件调试寄存器数量(x86 只有 4 个 DR),或地址未对齐。ARM/嵌入式要确认目标支持硬件断点。
**Q3**: 想监视一整块缓冲区被读或被写,不止一个字节?
**A3**: 硬件断点有长度限制(通常 1/2/4/8 字节)。监视大区域时挑"哨兵字节"(区域首尾或关键字段)watch;或用 `rwatch`(读)/`awatch`(读写)按需。要监控整段用页级保护(mprotect 设不可写,写触发 SIGSEGV 再看栈)更灵活。
**Q4**: watch 命中太多次,变量被合法写很多次,找不到"异常"那次?
**A4**: 加条件。`watch var if var == 0xdeadbeef`(只在写成特定值时停),或 `if $rip == 某段` 只关心某代码区的写入。用异常值/异常写入者作为过滤条件,跳过海量正常写。
**Q5**: watchpoint 硬件资源不够、或目标不支持,监视不了?
**A5**: 正交转向——用页保护或录制回放替代。mprotect/VirtualProtect 把目标页设为不可写,用 SEGV handler 捕获写入者(可监控大范围);或 rr 录制后对内存地址做反向 watch(reverse execution 里查最后一次写),不消耗硬件调试寄存器。

### 验证 ROP 链:构造好了但打不通
**Q1**: ROP 链写好了本地打不通,怎么用调试器定位是哪个 gadget 出问题?
**A1**: 在 ret 到第一个 gadget 前的那次返回处下断(即栈溢出返回点),然后单步 `si` 走 ROP 链,每 ret 一次对照你的预期地址,看第几跳偏离。核对 rsp 是否指向你链的下一项、rdi/rsi 等寄存器是否被正确设置。
**Q2**: 链在中途某 gadget 崩了?
**A2**: 看崩的那条指令。常见坑:gadget 里除了你要的 pop 还有别的副作用指令(pop 了多余的值导致栈错位)、或 gadget 地址算错(PIE/libc base 没加对)。核对该 gadget 反汇编,确认栈上为它准备的填充项数量和它实际 pop 的数量一致。
**Q3**: 栈对齐问题(movaps 崩在 system 调用)?
**A3**: 64 位下调用 system/libc 函数前 rsp 需 16 字节对齐,否则 movaps 触发 SIGSEGV。在进入 system 前查 `p $rsp & 0xf`,不为 0 就在链里加一个 ret gadget 做对齐补偿。这是本地能打通远程/特定环境打不通的经典原因。
**Q4**: 单步验证时对了,连续跑(continue)就崩?
**A4**: 说明问题在"没断点时的真实执行环境"——可能是缓冲/坏字符导致链在传输中被截断/改写。检查坏字符(\x00\x0a 等)是否出现在链的地址里,读入函数是否按预期长度收全了整条链。
**Q5**: 链逻辑全对但就是打不通,反复验证无解?
**A5**: 正交转向——换利用技术降低对长链的依赖。ROP 链越长越脆弱,改用更短更稳的路径:ret2libc 单次调 system、ret2dlresolve(免 leak)、SROP(一个 sigreturn 一次性设全寄存器)、或劫持到 one_gadget(一条约束满足即 getshell)。用"短链/单点"替代脆弱长链。

### one_gadget:约束不满足打不了
**Q1**: 有了 libc base,想用 one_gadget 一步 getshell,但跳过去没起 shell,怎么查?
**A1**: one_gadget 每个候选都带约束(如 `[rsp+0x40]==NULL` 或 rdx/rsi 需为 0)。`one_gadget libc.so` 列出所有候选及约束,在跳转到 gadget 的瞬间下断,逐个检查当前寄存器/栈是否满足某个候选的约束,挑满足的那个用。
**Q2**: 所有 one_gadget 约束当前都不满足?
**A2**: 别放弃,先看差多少。如果只差某个寄存器为 0,能不能在跳 gadget 前先用一个 gadget 把它清零?或换一个劫持点——不同的触发点(malloc hook/free hook/exit handler/返回地址)执行到 gadget 时的寄存器上下文不同,换个点约束可能就满足了。
**Q3**: 高版本 glibc 里 __malloc_hook/__free_hook 都没了,劫持点少了?
**A3**: 2.34+ 移除了这些 hook。转向新劫持点:__exit_funcs(exit 时的析构链,配合 pointer guard 需泄露/绕过)、_IO_FILE 结构的 vtable(FSOP/House of 系列)、或 tls_dtor_list。跳 one_gadget 的载体变了,但思路一样——找一个"你能改+程序会调用的函数指针"。
**Q4**: 约束满足了但 execve("/bin/sh") 起来的 shell 立刻退出?
**A4**: 常是 stdin/stdout 环境问题(远程尤其)。exp 里 `p.interactive()` 前确认没关流;若 execve 的第三参数(envp)非法可能导致异常,换一个 rdx 更干净的 gadget,或改用 ret2system 显式控参数。
**Q5**: one_gadget 这条路彻底走不通(约束死活不满足、版本无 hook)?
**A5**: 正交转向——放弃"一步到位",回到可控的多步。用 ROP 显式 setup 参数调 execve/system(自己控 rdi/rsi/rdx 就不受 one_gadget 约束限制),或走 orw(open-read-write)直接读 flag 文件(适用于沙箱禁 execve 的场景)。约束打不过就自己造上下文。

### libc 版本识别:偏移全错的根源
**Q1**: 泄露了 libc 里的地址想算 base,但不知道远程用的哪个 libc 版本,偏移没法定,怎么办?
**A1**: 用泄露值的低 12 位(页内偏移,ASLR 不变)去 libc-database/blukat.me 查匹配版本。泄露一两个已知符号(如 puts/read 的 GOT 值)的低三位,数据库反查出候选 libc,下载对应 .so 拿到全部偏移。
**Q2**: 查出多个候选 libc?
**A2**: 多泄露一个符号缩小范围——两个符号的低位组合几乎唯一确定版本。或看题目环境线索(Ubuntu 版本对应特定 glibc)。拿到候选后,本地用该 libc 打一遍,通了就是它。
**Q3**: 题目直接给了 libc.so.6 文件,还要不要识别版本?
**A3**: 给了就直接用它算偏移,但仍要确认"给的就是远程实际用的"。用 `strings libc.so.6 | grep "GNU C Library"` 看版本号,配对 loader(`ld.so`)以正确版本运行本地测试(`patchelf --set-interpreter`/LD_PRELOAD),避免本地 loader 与题目 libc 不匹配导致假失败。
**Q4**: 版本对了但堆手法还是失效?
**A4**: 小版本差异也致命——tcache(2.26+)、safe-linking(2.32+)、去除 hook(2.34+)、House of 各种缓解都卡在特定版本。精确到小版本号,按该版本的缓解状态选手法,不能只对大版本。
**Q5**: 死活找不到匹配 libc、或是魔改 libc?
**A5**: 正交转向——不依赖 libc 偏移的利用。用 ret2dlresolve(不需要 libc 地址,滥用动态链接器自己解析 system)、或纯 ROP 在程序自身 .text 里找 gadget 完成 orw 读 flag。魔改/未知 libc 时,把攻击面收缩到程序自身和 loader 这些你有确定信息的部分。

### 单步太慢:大循环/初始化耗时间
**Q1**: 关键逻辑前有个跑几百万次的循环或大初始化,单步到那要一辈子,怎么快速越过?
**A1**: 别单步。在循环之后的第一条指令下断点直接 `continue` 过去;或对当前函数 `finish` 跳到返回;`until` 跳出循环;`advance 地址` 一步到指定位置。单步只用于最后那几条关键指令。
**Q2**: 循环内部有你关心的某次迭代(第 N 次才出问题)?
**A2**: 条件断点锁定那次。`b 循环体 if $rcx==N` 或按处理的数据内容匹配(`if *($rdi)==目标值`)。让调试器替你数循环,直接停在关心的迭代。
**Q3**: 想统计循环跑了多少次/命中多少次而不停下?
**A3**: 用 `ignore 断点号 次数` 跳过前 N 次;或 dprintf/命令列表在命中时打印不停(`commands`+`continue`),把断点当日志用,批量观察而非逐次手动。
**Q4**: 初始化阶段有大量 malloc/加解密,拖慢整个调试?
**A4**: 跳过不关心的阶段——直接把断点下在业务入口(如 main 里读输入之后),`starti` 后一个 `continue` 直达,让初始化全速跑完。只在你真正要观察的窗口内精细调试。
**Q5**: 循环里有反调试计时,一慢就触发,快进也不行?
**A5**: 正交转向——用模拟执行跳过。Unicorn/Qiling 全速模拟这段循环拿到结果状态,再把状态搬回真机调试后续;或直接 patch 掉计时检查。用"模拟算结果"替代"真机跑循环",既快又躲计时反调试。

### 自修改代码/加壳:断点下下去代码还没解出来
**Q1**: 静态看到的代码是花指令/加密的,运行时才解密,断点下在静态地址是乱的,怎么办?
**A1**: 先让它自解密再下断。在解密循环之后、真正执行解密后代码之前设断点(通常解密完会跳到解出的区域,在那个 jmp/call 目标处断);或对将被写入的代码页下硬件写断点,写完即停,此时内存里已是真实指令。
**Q2**: 加壳程序,想在原始入口点(OEP)下断?
**A2**: 找 OEP 的经典法:ESP 定律(壳解压完会平衡栈,在入口 pushad 后对 esp 下硬件断点,pop 回来时即近 OEP)、或对代码段设不可执行,壳跳进解出的代码时触发异常停下。到 OEP 后可 dump+修复 IAT 得到脱壳样本。
**Q3**: 代码边执行边改自身(SMC),断点字节被解密覆盖?
**A3**: 软件断点(0xCC)会被自修改覆盖或干扰校验。改用硬件执行断点(不改内存),下在"代码稳定后"的地址。若整段反复自改,对写入该区域的动作下写断点,追踪它每次改成什么。
**Q4**: 解密依赖运行时密钥/环境,静态脱不了?
**A4**: 那就纯动态 dump。跑到代码解密完成的时刻,直接从内存 dump 出这一段(gdb `dump memory`),拿去静态分析。不追求完整脱壳,只要拿到你关心那段的明文指令即可。
**Q5**: 壳太强(虚拟化保护/多层),脱壳/动态都举步维艰?
**A5**: 正交转向——不脱壳,只观察 I/O 语义。VMP/Themida 类虚拟化壳逆向成本极高,改为黑盒:hook 它调用的关键 API(网络/文件/加解密)看输入输出,或 trace 它最终落地的系统调用,从"它对外做了什么"反推功能,绕开"它内部怎么做"。

### 格式化字符串:定位可控的 fmt 参数位置
**Q1**: 怀疑有格式化字符串漏洞(printf 直接吃用户输入),动态怎么确认并定位参数偏移?
**A1**: 先确认——输入 `%p %p %p` 若原样回显是普通字符串,若打印出栈上的值(地址/乱码)则确认漏洞。然后输入一串 `AAAA%p.%p.%p...` 或 `%1$p %2$p ...`,数到哪个 %p 打印出 0x41414141,那个序号就是你输入所在的参数偏移。
**Q2**: 想验证任意写(%n)能否命中目标地址?
**A2**: 在 printf 内部下断,构造好 fmt 后单步到 %n 处理时,查它要写的地址(pwndbg 会显示),确认等于你的目标地址、写入值等于已打印字符数。用 pwntools `fmtstr_payload` 生成再动态核对一遍最稳。
**Q3**: 栈上找不到你输入的偏移(输入在别的缓冲区)?
**A3**: 输入不在栈上时,%n 写目标要靠"栈上已有的指针链"——找一个栈上指向栈的指针,先用它定位,再多级 %n 间接写。或换思路:很多 fmt 利用不需要输入在栈上,改写 GOT/返回地址只要能用某个已存在的栈指针即可。
**Q4**: %n 被禁用(FORTIFY 的 %n 检查)或输出被限制长度?
**A4**: `_FORTIFY_SOURCE` 会禁止可写内存里的 %n。改用只读原语:纯 leak(%p/%s 泄露 canary/libc/栈地址)配合别的写原语;或若只是长度限制,用 `%hn`/`%hhn` 分次小额写、按字节写目标,绕过一次性大数写。
**Q5**: fmt 这条路利用不出来(检查太严/偏移不可控)?
**A5**: 正交转向——把 fmt 降格为纯信息泄露引擎,配合其它漏洞。即使不能任意写,fmt 泄露 canary/libc base/PIE base 的能力极强,拿这些泄露去喂一个栈溢出/堆漏洞完成利用。一个漏洞打不通就当情报源用,和别的原语组合。

### canary:栈溢出被 canary 挡住
**Q1**: 栈溢出能触发,但一返回就 __stack_chk_fail 报 canary 崩,怎么推进?
**A1**: 先在 gdb 里定位 canary 在栈上的位置和值(pwndbg `canary`),看你的溢出是否必须跨过它。若能不覆盖 canary 就达成目的(如只改某局部指针)最好;否则必须先泄露 canary 值,溢出时把原值填回去。
**Q2**: 怎么泄露 canary?
**A2**: 找信息泄露原语:格式化字符串 %p 打印栈(canary 特征是最低字节 00、其余随机)、越界读、或利用"逐字节写不截断"的输入函数(read 不加 00)结合逐字节爆破(每次多写一字节,不崩说明这字节对,适合无 ASLR 或 fork 保持 canary 不变的服务)。
**Q3**: fork 服务里想逐字节爆破 canary?
**A3**: fork 出的子进程继承父进程 canary(不重新随机),所以可以逐字节爆破:对每个位置 0~255 试,子进程崩了换下一个,不崩即命中,8 字节最多 8*256 次。前提是崩溃不影响父进程继续 fork。确认服务是 fork 模型再用这招。
**Q4**: 泄露了 canary 但填回去后还是崩?
**A4**: 检查是否只泄露/覆盖了部分字节,或 canary 位置算错。canary 到返回地址之间还有保存的 rbp,布局要精确。gdb 里对照实际栈帧:输入→buf→canary→rbp→retaddr,逐项核对偏移。
**Q5**: 没有任何泄露原语、又不是 fork 模型,canary 绕不过?
**A5**: 正交转向——绕开"返回地址"这条被 canary 保护的路。canary 只保护函数返回,不保护:GOT/函数指针(改这些不经过 canary 检查)、局部结构体里的指针(在 canary 之前,可覆盖)、以及堆上的目标。改用不触发栈 canary 的写目标,或换一个没开 canary 的输入点/函数。

### 环境不一致:本地能打远程打不了
**Q1**: exp 本地稳定 getshell,远程一模一样的输入却失败,从哪查起?
**A1**: 按"最可能"排查顺序:①libc 版本不同(偏移全错)②栈上初始环境不同(argv/envp/环境变量数量改变栈布局→影响栈地址/对齐)③缓冲/交互时序(远程 recv 分包,本地一次收全)。先锁定 libc 版本这个头号嫌疑。
**Q2**: 怀疑是交互时序/收发问题?
**A2**: 本地用 `p = remote` 对着自己起的服务调,复现远程行为;检查每个 `recvuntil` 是否真的收到了预期分隔符(远程可能没有你本地假设的提示串)。用 `p.recvrepeat`/精确 `recvuntil` 替代脆弱的固定长度 recv,消除分包差异。
**Q3**: 怀疑栈地址/对齐差异?
**A3**: 远程 envp/argv 与本地不同会平移栈,导致写死的栈地址失效、或 16 字节对齐状态不同(system movaps 崩)。exp 里避免写死栈地址(用泄露+相对),ROP 链里预留一个 ret gadget 兜底对齐。
**Q4**: 想在接近远程的环境本地复现?
**A4**: 用题目给的 Dockerfile/libc/ld 搭一致环境:`patchelf --set-interpreter ./ld --set-rpath . ./prog` 让本地用题目的 loader+libc 跑,或直接在同版本容器里调。环境对齐后再调,别拿本机系统 libc 假测。
**Q5**: 各种排查都对齐了远程仍失败,黔驴技穷?
**A5**: 正交转向——提升 exploit 鲁棒性而非追求精确复现。远程有你看不见的变量(ASLR 熵、并发、超时)。改用更抗抖动的技术:堆喷/大范围 nop sled 容错、多次尝试脚本(远程 ASLR 靠爆破低熵、fork 保持地址靠重连)、把"需要精确"的步骤替换成"概率命中"的策略。

### seccomp 沙箱:getshell 起不来
**Q1**: 拿到执行流了但 execve("/bin/sh") 没反应,怀疑有 seccomp,怎么确认?
**A1**: 静态/动态查过滤器:`seccomp-tools dump ./prog` 直接列出被禁的 syscall。若 execve/execveat 被 ban,起 shell 这条死路,得看放行了哪些(通常 open/read/write 还在→走 orw 读 flag)。先拿到白名单再定利用方向。
**Q2**: 确认禁了 execve,放行 open/read/write?
**A2**: 转 orw:ROP 构造 `open("flag",0)` → `read(fd,buf,n)` → `write(1,buf,n)`,直接把 flag 文件读出来打印,不需要 shell。用调试器验证每个 syscall 的寄存器参数正确、fd 返回值符合预期。
**Q3**: 连 open 都禁了,只放行 openat/其它变体?
**A3**: 看白名单里的等价 syscall——openat 替 open、readv/preadv 替 read、sendfile 直接把文件送到 fd 1(一步出 flag,免 buf)。seccomp 常只 ban 具体号,用功能等价的其它 syscall 号绕过。
**Q4**: 过滤器还限制了架构(禁 x32/禁特定寄存器)?
**A4**: 有的过滤器检查 arch 防 x32 syscall 混用。老套路是切到 x86-32 兼容模式用不同 syscall 表,但若过滤器已校验 arch==x86_64 则堵死。回到白名单内找可行组合,别硬撞被专门堵的路。
**Q5**: 白名单极窄,orw 都拼不出来?
**A5**: 正交转向——不读 flag 文件,换信息出口或提权面。若放行了网络 syscall(socket/connect/sendto),把 flag 带外发出;若这是提权链的一环,目标或许不是读文件而是改某状态。重新审题:沙箱这么严,预期解可能根本不走 execve/orw,而是逻辑漏洞或侧信道。

### catch syscall:从系统调用层锚定行为
**Q1**: 完全不懂这程序在干嘛、符号也没有,想从系统调用层快速摸清它的行为,怎么下手?
**A1**: `catch syscall` 断所有系统调用(或指定 `catch syscall open read write connect`),每次命中看寄存器里的 syscall 号和参数。这是"程序对操作系统做了什么"的最底层真相,比追任何用户态代码都可靠,反调试也很难伪造真实 syscall。
**Q2**: 想聚焦某类行为(文件/网络)?
**A2**: 只 catch 相关 syscall:文件类 open/openat/read/write/unlink,网络类 socket/connect/bind/sendto/recvfrom,进程类 execve/fork/ptrace。按怀疑的功能挑,避免被无关 syscall 淹没。ptrace 尤其要 catch——它是反调试的标志。
**Q3**: syscall 命中后想知道是哪段业务代码发起的?
**A3**: 命中时 `bt` 看栈,或 `finish` 返回到调用点,那里就是发起该操作的函数。用 syscall 作锚,`finish` 上浮到业务层,反推出关键函数地址后再精细下断。
**Q4**: 程序直接用 syscall 指令(不经 libc 封装),`b read` 断不到?
**A4**: 静态编译或手写 syscall 会绕过 libc 符号,`b read` 自然断不到,但 `catch syscall read` 照断——它拦的是内核边界,不管你怎么进内核。这正是 catch syscall 相对函数断点的核心优势。
**Q5**: syscall 层也看不出所以然(逻辑全在用户态计算,几乎不 syscall)?
**A5**: 正交转向——纯计算型程序(crackme/算法题)不 syscall,回到用户态用覆盖率/污点分析。用 Pin/Triton 做污点跟踪,追输入字节如何流经运算影响判定,或 angr 符号执行求解。syscall 锚定适合 I/O 密集程序,纯算法要换数据流分析工具。

### 动态取密钥:抓加解密函数的明文/密钥
**Q1**: 程序对数据加密后发送/存储,想拿到明文或密钥,断在哪?
**A1**: 断在加密函数的输入侧(明文进入前)和密钥装载处。若用标准库(OpenSSL EVP_*、CryptEncrypt),直接断这些 API,第一参数区往往是明文/密钥;自实现的看数据流,在"网络发送/文件写入前的最后一次变换"处下断,那之前内存里就是明文。
**Q2**: 想抓对称密钥?
**A2**: 密钥要么硬编码(静态搜高熵常量/S-box 特征识别算法)、要么运行时派生。断在加密核心函数入口,密钥通常作为参数或刚被 setup 到某结构体;对存密钥的内存下读断点,看初始化时谁写进去的。
**Q3**: 只想解密它收到的密文(不关心算法细节)?
**A3**: 复用程序自己的解密函数——用调试器控制它,把你的密文放进它的解密输入缓冲区,手动调用它的解密函数(gdb `call`),让程序自己解给你看。比自己重实现算法快得多。
**Q4**: 密钥是每次会话协商出来的(TLS/DH)?
**A4**: 抓协商后的会话密钥而非长期密钥。断在对称加密启用的那一刻(密钥已协商完),从内存 dump 会话密钥;或 hook 加密函数把明文旁路记录。别去逆密钥交换数学,直接抓落地的会话密钥。
**Q5**: 加解密在受保护/混淆区域,断点进不去?
**A5**: 正交转向——不碰算法,做端到端旁路。在数据"进加密前"和"出解密后"的干净边界打点(通常是业务层缓冲),或 LD_PRELOAD hook 掉它调用的加密库函数记录进出参数。把"逆算法"问题转成"在明文边界抓数据"。

### 断点断不下来:命中不了的排查
**Q1**: 下了断点 `continue` 却直接跑完/崩了,断点根本没命中,先查什么?
**A1**: 先确认断点是否真的设在了将执行的地址。`info breakpoints` 看是否 resolved(pending 说明模块没加载);PIE/共享库未加载时地址是错的。`starti` 停在最早处,等目标模块加载后(`catch load`)再下断,或用符号名让 gdb 延迟绑定。
**Q2**: 断点显示已设、地址也对,还是不命中?
**A2**: 可能那段代码根本没被执行(走了别的分支)——先确认控制流真的到这里:在更靠前的必经点下断验证。或者进程 fork 了、你断的是没跑这段的那个进程(见 follow-fork)。也可能被反调试提前 detach 了。
**Q3**: 断在库函数但程序用了静态链接/内联,符号名指向错地方?
**A3**: 内联/LTO 会让"函数"消失或多份拷贝。核对 `info line`/反汇编确认你断的地址确实是那段逻辑。静态链接时 `b read` 可能断到 libc 内部而非业务调用点,改断具体地址或 syscall 层。
**Q4**: 硬件断点设了不响应?
**A4**: 硬件调试寄存器可能被目标自己占用(反调试会写 DR 寄存器清掉你的断点),或超出数量上限(x86 仅 4 个)。检查 DR 寄存器状态,减少同时用的硬件断点数,或换软件断点交叉验证。
**Q5**: 各种断点都命中不了,像被系统性干扰?
**A5**: 正交转向——换观测机制。进程内断点被反调试废掉时,用进程外/内核层观测:ftrace/eBPF/uprobe 挂内核探针、Intel PT 记录全量控制流轨迹、或 QEMU 模拟执行插桩。从"在它进程里下断"转到"在它外面录轨迹"。

### 反向调试:知道结果不知道起因
**Q1**: 程序最后某变量是坏值,但导致它变坏的过程早已跑过,重跑又难复现,怎么倒查?
**A1**: 用时间旅行调试。`rr record ./prog` 录一次,`rr replay` 里跑到坏值出现处,对该内存 `watch` 后 `reverse-continue`——反向执行到"最后一次写入它"的地方,直接定位污染源。正向调试要反复重跑猜,反向调试一步到位。
**Q2**: rr 录制时程序行为和裸跑不一样(rr 下不复现)?
**A2**: rr 会串行化多线程,可能掩盖竞态。若 bug 依赖真实并发,rr 反而复现不了——这时改用非确定性录制或直接抓一次崩溃的 core dump 做事后分析。判断 bug 是否依赖并发决定用不用 rr。
**Q3**: 想反向查"这个函数指针是被谁改成非法值的"?
**A3**: replay 里对该指针 `rwatch`/`watch`,`reverse-continue` 停在最后写入点,`bt` 给出改它的调用栈。UAF/类型混淆/溢出改函数指针这类"元凶在远处"的 bug,反向 watch 是最快定位法。
**Q4**: rr 不支持目标架构(ARM/嵌入式)?
**A4**: rr 主要支持 x86。目标是 ARM/MIPS 时,退而用 QEMU 全系统模拟的 record/replay、或 gdb 自带的 `record`(process record,慢但能反向),或加密集日志(dprintf 每步打印状态)离线重建时间线。
**Q5**: 反向调试也定位不到根因(状态污染跨进程/跨模块太散)?
**A5**: 正交转向——上污点分析追数据来源。反向执行擅长"谁最后写的",但污染跨多跳时,用 Triton/Pin 污点跟踪标记"坏值从哪个输入字节流过来",从数据传播链角度找根因,而非从时间维度。

### 挑调试器:gdb 系还是别的
**Q1**: 新任务上手,该用哪套调试工具?判据是什么?
**A1**: 按平台+目标定。Linux ELF/PWN→gdb+pwndbg/gef(堆可视化、ROP、一键 leak);Windows→x64dbg(用户态)/WinDbg(内核&复杂);跨架构/嵌入式→gdb-multiarch+gdbserver/QEMU;宏观分析配 IDA/Ghidra 静态。别用一把锤子敲所有钉子。
**Q2**: gdb 原生太难用,pwndbg/gef/peda 选哪个?
**A2**: PWN 场景 pwndbg 最全(heap/bins/vis、telescope、自动 leak),gef 界面友好插件多,peda 较老。装一个够用,别都装(命令冲突)。核心是要有:堆可视化、寄存器/栈上下文自动显示、和 pattern/rop 辅助。
**Q3**: 遇到 Windows 内核驱动/蓝屏级目标?
**A3**: x64dbg 是用户态,内核要 WinDbg + 双机调试(VM+串口/网络)或本地内核调试。驱动、rootkit、内核提权漏洞必须 WinDbg 系,别指望用户态调试器。
**Q4**: 目标带强反调试,主流调试器一进就被识破?
**A4**: 换隐蔽性更强的组合:x64dbg+ScyllaHide、gdb 配 LD_PRELOAD 反反调试、或直接用模拟器(QEMU/Qiling)/DBI 框架(Frida/Pin)——它们不以传统 ptrace/调试端口附加,反调试检测面不同。
**Q5**: 所有交互式调试器都被目标环境拒之门外(无 GUI、无权限、检测严)?
**A5**: 正交转向——用 DBI/插桩替代交互调试。Frida 脚本化 hook(无需 GUI,可注入生产进程)、Pin/DynamoRIO 插桩记录、或纯静态+Unicorn 模拟。从"人在调试器前单步"转到"脚本自动化插桩采集",适应无人值守/受限环境。

### 污点/覆盖:输入太多不知道哪个字节要紧
**Q1**: 一个大输入(几百字节),只有某几个字节影响判定,怎么快速找出关键字节?
**A1**: 污点分析。用 Triton/libdft/Pin 把输入标记为污点源,跑一遍看哪些字节的污点传播到了判定分支的比较操作数——那几个就是关键字节。比逐字节 diff 试探精确得多。
**Q2**: 没有污点工具,土办法怎么找?
**A2**: 覆盖率差分:逐字节(或分块)变异输入,记录每次的基本块覆盖(用 QEMU/DynamoRIO 的 bbtrace),覆盖发生变化的字节就是影响控制流的关键字节。手动版就是"改一个字节看行为变没变"。
**Q3**: 找到关键字节后想求解它们的正确值?
**A3**: 交给约束求解。angr/Triton 对关键字节建符号变量,把"到达通过分支"设为目标,求解器解出满足值。或空间小时直接爆破那几个字节。别人肉逆变换逻辑。
**Q4**: 污点传播中断(数据过了某个不透明变换/查表)?
**A4**: 表驱动/位运算常让污点分析"变糊"(过度污染或丢污点)。在变换点前后各 dump 数据人工桥接,或对该变换单独用 Unicorn 模拟建立输入输出映射,再拼回整体分析。
**Q5**: 污点+覆盖+符号执行全都在这个目标上失效(路径爆炸/混淆)?
**A5**: 正交转向——退回黑盒 fuzzing+人工。混淆到自动化工具全跪时,用覆盖率引导 fuzz(AFL++ qemu 模式)硬碰运气找通过输入,同时人工只逆最关键的那一小段判定逻辑。放弃"完全理解",追求"找到能过的输入"。

### 附加运行中进程:attach 的时机与坑
**Q1**: 目标已经在跑(守护进程/已触发的状态),该 attach 还是重启调试?
**A1**: 状态难重建(已建立的连接、已加载的运行时数据)就 attach:`gdb -p PID`。要从头看初始化则重启调试。attach 会暂停进程,注意别 attach 错了 worker(多进程服务先 `pstree`/`ps` 找对处理你请求的那个 PID)。
**Q2**: attach 时提示 ptrace 权限不足?
**A2**: `ptrace_scope` 限制(Yama)。有 root 就 `echo 0 > /proc/sys/kernel/yama/ptrace_scope`;无 root 则只能调自己启动的子进程(父子关系豁免),改用启动调试而非 attach,或用有 CAP_SYS_PTRACE 的方式。
**Q3**: attach 上去了但进程停在无关的等待里(阻塞在 accept/read)?
**A3**: 正常——它在等输入。先下好断点再 `continue`,然后从外部触发它工作(发请求/给输入),让它跑到你的断点。别在 attach 后的阻塞点瞎单步。
**Q4**: attach 会不会被目标检测到?
**A4**: 会。attach 也是 ptrace,程序若检测 tracer(读 /proc/self/status 的 TracerPid、或已 TRACEME 占坑)会发现。需要隐蔽就用反反调试隐藏 TracerPid,或改用不基于 ptrace 的观测(eBPF/uprobe)。
**Q5**: 目标是短命进程(fork-exec 一闪而过),attach 根本来不及?
**A5**: 正交转向——不 attach,改"启动即挂起"或外部记录。用 `LD_PRELOAD` 注入在 main 前 `raise(SIGSTOP)` 等你 attach,或 gdbserver 从一开始接管;短命进程批量分析则用 strace -f/eBPF 全程记录,事后分析而非实时 attach。

### 内存搜索:知道值不知道地址
**Q1**: 知道某个值(密码明文、血量、某标志)在内存里但不知道地址,怎么定位?
**A1**: 内存搜索。gdb pwndbg `search 值`(支持字符串/字节/dword)、或 `find` 命令扫全内存;游戏修改器思路(Cheat Engine)对未知初值做"变化/未变化"渐进搜索。定位到地址后下 watch 看谁读写它。
**Q2**: 搜出来一堆匹配地址?
**A2**: 缩小:改变程序状态让该值变化,再搜新值取交集(渐进过滤);或按内存区域筛(`vmmap` 后只搜 heap/bss/stack 里的匹配,排除无关映射)。多轮过滤到唯一。
**Q3**: 值经过编码/加密存储,明文搜不到?
**A3**: 搜不到明文说明存的是变换后形式。反过来——在处理该值的函数里下断,看它加载/解码的瞬间内存里的原始形式,记下那个存储格式再搜;或直接在解码后的干净副本处定位。
**Q4**: 想定位一个指针/结构体而非标量值?
**A4**: 搜指向已知地址的指针(找谁引用了目标)——`search -p 已知地址` 找栈/堆里指向它的指针,层层上溯到根对象。这是重建对象关系图、定位结构体基址的常用手法。
**Q5**: 内存搜索完全无果(值动态计算不落地、或在寄存器/加密堆里)?
**A5**: 正交转向——从"搜数据"转"追代码"。值不稳定落内存时,在它被使用的运算点(比较/显示/网络发送)下断,从使用现场的寄存器直接抓,而不是大海捞针搜静态内存。跟着"谁用它"走。

### 条件断点表达式:复杂命中条件怎么写
**Q1**: 想只在"特定对象/特定请求"进函数时停,条件断点表达式怎么设计?
**A1**: 用参数内容做条件。`b handler if $rdi->id == N`(按结构字段)、`if strcmp((char*)$rdi, "target")==0`(按字符串,gdb 可调 strcmp)、`if $rsi==特定fd`。让条件精确匹配你关心的那一次调用,跳过成百上千次无关命中。
**Q2**: 条件里要解引用多级指针/读结构字段?
**A2**: 有符号时直接 `p->field->sub`;strip 时用偏移 `*(long*)($rdi+0x18)==value`。先在一次命中里手动 `x` 出结构布局确认偏移,再把偏移写进条件。条件断点跑得慢就说明表达式太重,简化它。
**Q3**: 条件断点让程序慢到不可用(每次命中都求值)?
**A3**: 软件条件断点每次命中都回到 gdb 求值,高频点会拖垮。改法:用硬件断点+条件、把条件下沉(在更少命中的上层函数加条件)、或用 dprintf 只记录不停+事后 grep。高频路径慎用重条件。
**Q4**: 想在"第一个满足条件后自动做一串动作"?
**A4**: 用 `commands` 给断点挂命令列表(命中即 dump 寄存器/内存、改值、然后 continue),把交互调试自动化。配合 gdb 脚本可实现"命中 N 次后才真正停"等复杂逻辑。
**Q5**: 条件逻辑复杂到 gdb 表达式写不出来?
**A5**: 正交转向——用脚本化 DBI 替代表达式。Frida/gdb-python 里用完整编程语言写命中判断(任意复杂逻辑、跨调用状态、正则匹配),比 gdb 单行条件表达式强大得多。条件复杂就升级到可编程 hook。

### 验证 exploit 原语:写没写到、读没读对
**Q1**: 我以为有个任意写原语,想在调试器里确认它真能写到目标地址,怎么验?
**A1**: 触发写的前一刻下断,单步到实际的存储指令(mov [dst], val),`p $dst地址` 确认等于目标、`p 值` 确认等于预期,执行后 `x` 目标地址核对写入成功。别假设"逻辑上能写"就真能写——对齐、越界检查、类型截断都可能让它写不到或写错。
**Q2**: 原语是"任意读",想确认读的范围和内容?
**A2**: 断在读取点,查读取的源地址和长度是否真受你控制、有没有被 clamp(长度检查会截断)。读出的内容是否包含你要泄露的目标(canary/指针)。很多"任意读"实际有隐藏边界,动态一验便知。
**Q3**: 写原语只能写受限值(不能写 0、只能写小数、字节对齐限制)?
**A3**: 摸清限制才能规划利用。动态试探:能写哪些值、几字节、地址粒度。有 00 截断就用逐字节/部分覆盖;只能加不能任意写就用相对修改。把原语的"能力边界"精确测出来,利用方案要贴着这个边界设计。
**Q4**: 原语只能用一次(触发后进程状态破坏)?
**A4**: 单次原语要一击致命——优先写"能级联出更强能力"的目标(改一个长度字段获得越界、改一个指针获得任意读写)。调试确认这一次写下去后能否接续下一步,规划好写目标的优先级。
**Q5**: 反复验证发现这个原语实在太弱(受限太多、不可控)?
**A5**: 正交转向——找更强原语或组合原语。一个弱写+一个弱读常能组合成任意读写(读泄露地址→写改指针→再读写)。或换漏洞点重找:审计其它输入面看有没有更干净的越界/UAF。别在一个残废原语上硬凑完整利用链。

### 内联/优化:源码级断点错位
**Q1**: 有源码带调试信息,但在某行下断点却停在别处或根本不停,是怎么回事?
**A1**: 编译器优化(-O2)会内联、重排、消除代码,源码行和机器指令不再一一对应。`disassemble /s` 看源码行对应的实际指令,按指令地址下断而非源码行;或用未优化(-O0)重编版本调试逻辑,拿结论回到优化版验证。
**Q2**: 变量在优化后 `p var` 显示 "optimized out"?
**A2**: 变量被放进寄存器或消除了。查它当前在哪个寄存器(`info scope`/看反汇编哪个寄存器承载它),直接看寄存器值;或在变量必然驻留内存的点(被取地址、被跨函数传递)观察。别信 "optimized out" 就以为拿不到。
**Q3**: 想在被内联的函数入口下断,但它没有独立地址了?
**A3**: 内联后该"函数"散布在调用者体内。在调用者里找到内联展开的那段指令(按源码行或特征识别)下断;若多处内联,每个调用点都有一份拷贝,要都下断或挑你关心的那个调用点。
**Q4**: 优化把你的断点位置和相邻代码合并,单步跳来跳去乱序?
**A4**: 指令重排/软件流水会让单步的源码行来回跳,这是正常的优化产物。别被行号迷惑,盯反汇编级的数据流(哪个寄存器存了什么)而非源码行顺序来理解执行。
**Q5**: 优化+LTO 让整个函数结构面目全非,源码级调试完全失效?
**A5**: 正交转向——放弃源码级,回到纯汇编级动态分析。把它当无源码二进制处理:按数据边界(输入/输出/syscall)下断、看寄存器和内存实际值,用行为驱动而非源码驱动。源码在重度优化下只是参考,以运行时真相为准。

### 抓 hook 点:改哪个函数指针最划算
**Q1**: 有了任意写,想劫持一个"程序一定会调用"的函数指针来拿控制流,选哪个?
**A1**: 判据是"可写 + 必被调用 + 调用时机可控"。经典候选:GOT 表项(RELRO 未开时可写,改后下次调该库函数即劫持)、__free_hook/__malloc_hook(老 glibc)、exit handler、_IO_FILE vtable、C++ vtable。在调试器里确认目标指针可写(vmmap 看权限)且你能触发它被调用。
**Q2**: Full RELRO 开了,GOT 只读改不了?
**A2**: GOT 不可写就换目标:堆上的函数指针(vtable、回调结构)、可写数据段的函数指针、或不经 GOT 的间接调用点。Full RELRO 只锁 GOT,程序自己的可写函数指针照样能改。
**Q3**: 高版本 glibc 移除了 malloc/free hook?
**A3**: 2.34+ 无这些 hook,转 FSOP(伪造 _IO_FILE 链,劫持 vtable,程序 exit/fflush 时触发)、__exit_funcs(需处理 pointer guard 加密,得先泄露 fs:0x30 处的 guard 或用不经加密的路径)、或找程序自身的回调机制。
**Q4**: 改了指针但调用时崩(参数不对/上下文不满足)?
**A4**: 劫持点决定了被调用时的寄存器上下文,直接跳 system 需要 rdi 指向 "/bin/sh"。若上下文里 rdi 不是你要的,改跳一个 one_gadget(找上下文匹配的)或先经一个 gadget 调整寄存器再进目标。调试里核对劫持瞬间的寄存器。
**Q5**: 所有常规 hook 点都不可写/不可达?
**A5**: 正交转向——不劫持指针,改劫持"数据决策"。改一个长度/大小/索引字段获得更强的越界能力,或改一个指向数据的指针实现任意读写(而非直接控制流),用数据面能力迂回构造控制流劫持,而不是死磕某个函数指针。

### TLS/早期反调试:main 之前就出问题
**Q1**: 程序在 main 之前(初始化阶段)就检测调试器/解密,我在 main 下断已经太晚,怎么办?
**A1**: 断更早。TLS callback(Windows,PE 的 TLS 目录里的回调在入口前执行)、.init_array/constructor(Linux,main 前的构造函数)是常见早期检测/解密点。x64dbg 设 "TLS callback" 断点、gdb 用 `starti` 从第一条指令开始,别默认停 main。
**Q2**: 怀疑 .init_array 里有反调试?
**A2**: `info functions`/看 .init_array 段里的函数指针,逐个在其入口下断。这些在 main 前跑,反调试/自解密爱藏这里。`starti` 后 `b *(init_array项)` 逐个过。
**Q3**: Windows TLS callback 里检测 PEB.BeingDebugged?
**A3**: TLS callback 在进程主线程入口前、甚至在你 attach 完成前就跑了。用"启动即挂起"调试(x64dbg 直接启动进程会停在系统断点,早于 TLS)+ ScyllaHide 预先隐藏 PEB;或在 TLS 回调地址下断确保停在它执行前。
**Q4**: 早期检测通过某种方式改变了后续解密密钥(检测到调试就解错)?
**A4**: 这是"反调试与解密耦合"——被检测后程序不崩,而是解出错误代码继续跑,很隐蔽。必须在早期检测点就绕过(让它以为没被调试),而不是等崩了才反应。在检测分支下断,强制走"未被调试"路径。
**Q5**: 早期反调试太顽固,进程一启动就被污染?
**A5**: 正交转向——静态消除或模拟执行早期代码。静态 patch 掉 TLS callback/init 里的检测(改成直接 return),或用 Qiling/Unicorn 模拟执行 init 阶段(模拟器里 PEB/ptrace 检测天然失效),拿到解密后的状态再切真机调试后续。

### GOT/PLT 观察:延迟绑定与劫持验证
**Q1**: 想理解某库函数的调用如何经过 PLT/GOT,以及能否劫持,怎么动态看?
**A1**: 在第一次调用该函数处下断,单步进 PLT stub,观察它跳 GOT:首次调用 GOT 指向 PLT+6(回到解析),经 _dl_runtime_resolve 解析后 GOT 被填成真实 libc 地址,之后直接跳。看清这个延迟绑定过程才知道改 GOT 的时机和效果。
**Q2**: 想确认某 GOT 项能否被我的写原语劫持?
**A2**: `vmmap` 看 GOT 段权限(Partial RELRO 下 .got.plt 可写,Full RELRO 只读)。可写就用写原语把该项改成目标地址,下次程序调对应函数即执行你的目标。改前 `x` 记录原值,改后核对。
**Q3**: 想利用 _dl_runtime_resolve 做 ret2dlresolve?
**A3**: 这招免 leak libc——伪造 Elf_Sym/Elf_Rel 结构骗解析器解析出 system。动态验证:在 PLT[0] 调 _dl_runtime_resolve 处下断,检查你构造的 reloc offset 和伪造结构是否被正确读取。结构布局易错,必须动态逐字段核对。
**Q4**: Full RELRO 让 ret2dlresolve/GOT 改写都失效?
**A4**: Full RELRO 下 GOT 只读且启动即全部解析,这两招基本废。转向不依赖 GOT 的路径:直接 ret2libc(需 leak)、栈上 ROP、或程序自身的函数指针/vtable。RELRO 只保护 GOT,不保护别的。
**Q5**: PLT/GOT 这条利用维度全被缓解封死?
**A5**: 正交转向——离开"链接器机制"这个维度。改走数据结构劫持(_IO_FILE/FSOP、堆里的函数指针)、或纯栈 ROP/SROP。GOT/PLT 只是控制流劫持的一种载体,缓解封死它时换别的载体,利用目标(拿控制流/读 flag)不变。
