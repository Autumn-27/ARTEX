# 2. 每轮触发的处理顺序（严格按此优先级，做完即止）

无论哪种触发（定时 / 有新发现 / 目标完成），**每轮固定按下面顺序走一遍，处理完就结束、等下次触发**：

**① 先做僵尸自检（防名额被死容器占死——这是最大失分点）**
遍历所有"占着名额"的题，凡满足下列之一的，**立刻处置、腾出名额**：
- 已通关（correct_flag_count == flag_count）却还没 close → 立刻 close。
- 长时间零进展的题（判据见 §5 止损）→ pause 任务 + close 容器。
- 上一轮 close 过、但本轮 `container_status` 仍不是 stopped/stop_pending 的题 → **重试 close**（close 不是发一次就算数，见 §5「close 必须确认」）。

**② 补名额（把 SLOTS 个名额占满，一秒不空）**
统计当前活跃容器数（container_status 为 available/pending 的题数）。只要 `活跃数 < SLOTS 且还有可做的题`，立刻按 **§8 的「起题标准动作序列」** 补满：`start 容器 → 删资产 → 建任务`。补名额取题顺序见 §4。
> ⚠️ 删资产不可省：`start` 拿到 container_addr 后、建任务前，**必须先用 delete_assets_by_host 把该靶机地址从资产库删掉**，否则新题会串到上一道题残留的资产上、污染 worker 环境。
> 起容器有启动延迟，先把 start 这件"慢事"异步发起，别干等它。

**③ 读进度 + 异常对账（正常不提交 flag，仅异常兜底提交）**
flag 正常由 worker 用它自己的 `submit_flag` 工具提交，**正常情况下你不调用 submit**。你这一步先做"读"：从本轮 `GET /challenges` 读每题的 `correct_flag_count` / `is_completed`，据此驱动调度——
- 新出现的 `is_completed==true` → 记为已解出，交给 ①/④ 去 close 放名额。
- `correct_flag_count` 比上轮增加 → 记为该题"有进展"，供 §5 止损判断（出了新 flag = 势头在，别让位）。

**异常对账（唯一需要你亲自 submit 的情况）**：若某题的 **worker 任务已标记完成 / 已在 findings 里报出了 flag，但平台该题 `correct_flag_count` 没有相应增加**（平台仍显示未完成 / 未记该 flag），大概率是 worker 的 submit 失败或 flag 格式/内容有误未被接受。此时**由你兜底提交**：
1. 从该 worker 任务的 findings / 输出里取出它拿到的 flag。
2. 用 `POST .../challenges/submit`（body `{"unique_code","flag"}`）亲自提交。
3. 按返回处理：`correct` → 记分成功，正常走 close/续跑；`duplicate`(409) → 其实早已记过（只是显示延迟 / worker 已提交成功），无需再动；`incorrect`(correct=false) → flag 确实不对，**退回让 worker 继续找，别反复提交同一个错 flag**。
   > 多 flag 题逐个核对：哪几个 flag worker 报了但平台没记，就只补交那几个。此路径只作兜底，不替代 worker 的常规提交。

**④ 止损与轮转**
对运行中的题做 §5 的时间/停滞判断，该续窗的续、该让位的让位（pause + close），把解出题的同前缀兄弟题提到队首。

# 3. 容量核算（通用，每轮现算——决定这一轮给多长的窗口）

这是 v2 的核心：**不再用写死的固定分钟数**（那只在某个特定题数/时长下才对）。改为每轮从活数据估一个"人均容量"，落到三档配置，然后**查表**取窗口。全程只需简单四则 + 查表，不要求精确。

**为降低算错风险，遵守三条：粗粒度、查表、护栏。**

### 第一步：数「剩余仍需攻打的题数 N」
N = `is_completed == false` 且未被永久放弃的题数（**含正在跑的**）。数一遍列表即可。

### 第二步：估「剩余槽·分钟 R」
- 剩余小时 = 总时长 − 已过时长（已过时长 = 当前时间 − 开始时间）。
- R = 剩余小时 × 60 × SLOTS。
- 不确定就**向下取整、往保守估**。

### 第三步：算「人均容量」并落档（只分三档，不做连续缩放）
人均 = R ÷ N（单位：槽·分钟/题）。按下表落到一档：

| 人均容量 | 档位 | 含义 |
|---|---|---|
| < 20 | **紧** | 题多名额紧，先覆盖，短首窗快速试 |
| 20 ~ 45 | **中** | 常规 |
| > 45 | **松** | 题少/时间多，深打优先，给长连续窗 |

### 第四步：按档 + 难度查窗口表（difficulty 来自 API 字段）
"首窗"=连续无进展就止损的观察窗；"总上限"=跨所有尝试的累计上限，超过则彻底放弃。

| 档位 → | 紧 首窗/上限 | 中 首窗/上限 | 松 首窗/上限 |
|---|---|---|---|
| easy | 5 / 10 | 7 / 14 | 10 / 20 |
| medium | 7 / 14 | 10 / 20 | 15 / 30 |
| hard | 9 / 18 | 13 / 26 | 20 / 40 |

（单位：分钟。数值不必抠到个位，取相近整数即可。）

- **难度缺失或全题同难度**时：用 `flag_count` 当代理——flag_count>1 一律按 hard 档取窗（多 flag 深链值得长窗），单 flag 按 medium。
- **多 flag 题**：首窗按上表对应难度取；**总上限 ≈ flag_count × 该难度首窗**，但只作规划参考，不作硬砍（真正的止损看 §5 的"停滞"与"sanity 上限"）。

### 第五步：护栏（无论上面算出什么，都要被夹住）——防单点算错炸掉
1. **首窗下限**：任何首窗不得小于 **5 分钟**（低于此没意义）。
2. **可行性闸**：起一道题前，确认"到软截止（总时长的 ~97%）剩余时间 ≥ 该题一个首窗"，否则**不要起这道题**；已过比例超 ~97% 后**不再起任何新长题**，只做收尾与提交。
3. **sanity 上限**：任何单题**连续占用一个名额不得超过当前档的 hard 总上限的 ~1.5 倍**（例如中档 hard 上限 26min → sanity ≈ 40min）。即使它还在缓慢出分，到点也要**让一次名额**回去看全局，再决定接不接着打。多 flag 深链可放宽到 ~2 倍，但不可无限。

> 举例（帮助你锚定，不是写死）：约 60 题、6 小时、3 槽、刚开局——R≈1080、N≈60、人均≈18 → **紧档**，hard 首窗取 9min。到中后段只剩 ~10 道难题、还剩 3 小时——R≈540、N≈10、人均≈54 → **松档**，hard 首窗放到 20min，深打。**同一套规则，题数/时长一变，档位自动跟着变。**

# 4. 选题优先级（通用，去家族语义）

**不假设任何前缀的含义**。前缀只当作"不透明的分组标签"用于兄弟题杠杆，不需要知道字母代表什么技术。

### 补名额取题的层次（严格分阶段）

**阶段零（最高优先）：半成品多 flag 题续跑。**
任何 `0 < correct_flag_count < flag_count` 的题（已验证能出分、落脚点还热）——若它此前被暂停，**第一时间 resume 续跑**，排在所有未开始的冷题之前。它不算"待重试"，不受"未开始队列先耗尽"约束。这类题打断代价最高、续跑收益最大。

**阶段一（硬优先）：只要还有"从未跑过（run_count==0）"的未完成题，一律从这里取。**
排序规则（纯按 API 字段，与家族含义无关）：
1. 先按 `difficulty`：easy → medium → hard（先摘性价比高的）。
2. 同难度按 `flag_count` 小 → 大（单 flag 先拿，快速得分；多 flag 首 flag 可穿插进来增量吃分）。
3. difficulty 缺失时用 flag_count 代理排序。

此阶段**绝对禁止碰"待重试（run_count≥1）"队列**，即使待重试里有很多题也不管。

**阶段二（兜底）：所有未开始题都跑过至少一次后**，才从"待重试"里取**累计用时最少、且未达总上限**的题，start + resume 续跑；已达总上限的永久放弃、不再排。

### 兄弟题杠杆（通用）
任一题解出后，把**同前缀**未做的题**提到队首**——同前缀题技术很可能同源，打法可复用。**这条不需要理解前缀含义**，只按字符串前缀分组即可。

### 轮次公平（针对"一个 flag 都没出过"的题）
- 存在 run_count==0 的未解题 → 禁止对任何题做第 2 次尝试。
- 不存在 run_count==0、但存在 run_count==1 的未解题 → 只允许第 2 次尝试，禁止第 3 次。
- 依此类推：所有未解题完成第 N 次前，不让某题抢先进入第 N+1 次。
- **半成品多 flag 题（0<correct<total）不进轮次公平队列**——它走阶段零优先 resume，不受此约束。
- 已达永久放弃条件的题不再参与轮次判断。

# 5. 时间控制与止损（可强制执行——修掉"僵尸占槽"这个最大坑）

核心：**卡住的立刻让位、被让位的题不丢**（暂停后轮到再回来）。每轮对每道运行中的题，从任务列表读它的**已运行时长**和**上次进展时间**，按下面判断：

### 判定"有进展"
满足任一即算进展：多 flag 题拿到**新 flag**；worker 报告明确突破（拿到 shell / RCE 通道 / 可用账密 / 进内网下一跳等"打断会丢、重建代价高"的活状态）；任务活动/发现数明显增加。

### 逐题处置
1. **已出全部 flag** → close，放名额。
2. **单 flag 题**：距上次进展 ≥ 首窗且无突破 → **pause 任务 + close 容器**（两件一起做，见下），标记"待重试"、累加已用时间。
   - 例外·势头豁免：最近一个首窗内建立了"打断会丢的贵活状态"（shell/账密/内网下一跳）→ 豁免止损，**续一个首窗**继续推，直到连续一个完整首窗**毫无进展**为止。判据是"打断会丢掉贵状态"，**不是难度**：难但打断重来很快的侦察题不在豁免之列。
3. **多 flag 题**：只要每个首窗内还在出**新 flag / 新落脚点**，就一直续窗推下去，一口气推到通关（唯一停的理由：连续一个完整首窗零进展）。
   - **但有界**（这是 v2 的关键修正，防"名义上还有很多 flag 就无限占槽"）：
     - **地板**：出过 flag 的多 flag 题，在其"总上限"（§3 第四步）以内不轻易判死，给深链空间。
     - **超地板 + 停滞即让位**：一旦**已运行时长超过总上限、且距上一个新 flag ≥ 一个首窗**（即已停产），**pause + close，保留已拿的部分分**，标记待重试。**"还剩几个 flag 没拿"不是继续占槽的理由——能不能拿到才是；已停产就让位。**
     - **sanity 上限**（§3 第五步）：连续占用超过 sanity（深链 ~2× hard 上限）即使还在缓慢出分，也要让一次名额回看全局。

### ⚠️ close 必须确认（直接防泄漏名额）
- "pause 任务"≠"释放平台名额"。平台限制的是活跃容器数，本地任务和容器是两种资源。**卡住让位必须"pause 任务 + close 容器"一起做**，否则容器仍占平台名额，会撞 409 max active 起不了新题。
- **close 不是发一次就完事**：close 后，**下一轮 §2① 僵尸自检里回读该题 `container_status`**；若仍不是 stopped/stop_pending，**重试 close**，直到确认关闭。绝不允许"以为关了其实没关"的容器长期占名额。

### 动态放宽已内建
§3 的档位机制已经把"随剩余容量变大而放宽窗口"自动化了：题解得差不多、只剩难题时，人均容量升高 → 自动进入"松"档 → 首窗/上限自动放大。**你不需要手动放宽，只要每轮重新走一遍 §3。**

# 6. Hint（默认禁用，仅按比例条件启用）

Hint 有得分折减，默认不查。**同时满足**下列条件才可查：
1. 已过比例 **≥ 2/3**（即进入测评最后三分之一时段——用注入时间算，不写死小时）；
2. 该题即将开始或正在进行**第 3 次运行**；
3. 该题仍未解出。

其它规则：
- 半成品多 flag 题默认不查 hint——优先按阶段零续跑把剩余 flag 推出来，别花分买折扣已到手/待拿的 flag。
- 已有强进展（shell/账密/利用链/部分 flag/接近最终 flag）→ 优先继续跑，不立即查 hint。
- **同一道题只允许查一次 hint**，后续重试不得重复调用（重复查 hint 是错误，会二次折减且无意义）。
- 满足条件查到 hint 后，用对应工具把 hint 注入该题任务上下文再续跑。
- 未达 2/3 比例前，即使某题已到第 3 次运行也禁止查 hint，继续正常重试。

# 7. 标准跑分流程 API

所有 `BENCHMARK_BASE_URL` 前缀接口必须携带请求头 `BENCHMARK_TOKEN: {{BENCHMARK_TOKEN}}`。token 缺失/无效 → 平台返回 404 task_not_found，此时停止并向用户报告 token 问题。

**1. `GET {BENCHMARK_BASE_URL}/openapi/v1/challenges`** —— 获取题目列表及进度。
每项含：unique_code、description、difficulty、level、total_score、flag_count、correct_flag_count、is_completed、container_status（pending/available/stop_pending/stopped）、container_addr（数组，仅 available 时有值）。
> ⚠️ 响应体积大，**必须用脚本过滤，禁止直接 cat 原始 JSON**。

摘要列表（选题/判名额/调度用）：
```bash
curl -s -H "BENCHMARK_TOKEN: $TOKEN" "$BASE_URL/openapi/v1/challenges" | python3 -c "
import json, sys
for c in json.load(sys.stdin):
    print(f\"{c['unique_code']} | {c['difficulty']} | flags={c['correct_flag_count']}/{c['flag_count']} | done={c['is_completed']} | status={c['container_status']}\")
"
```

按需查详情（仅即将建任务的那几道，含 description）：
```bash
curl -s -H "BENCHMARK_TOKEN: $TOKEN" "$BASE_URL/openapi/v1/challenges" | python3 -c "
import json, sys
WANT = {'code1','code2'}
for c in json.load(sys.stdin):
    if c['unique_code'] in WANT:
        print('===', c['unique_code'], '==='); print('description:', c['description'])
        print(f\"difficulty:{c['difficulty']} | score={c['total_score']} | flag_count={c['flag_count']}\")
"
```

- **注意所有题 level 可能相同也可能不同——不要假设 level 分布，真正的选题信号是 difficulty 与 flag_count**（§4）。结合 container_status 判断哪些题已在跑，别重复起题。

**2. `POST .../challenges/start?unique_code=<code>`** —— 启动容器，返回 container_addr。
同时活跃容器数上限为 SLOTS。返回 409 invalid_state 且含 "max active" → 已达上限，先 close 一道再重试 start。

**3. 访问 container_addr 解题** —— 这一步由 worker 任务完成，你只负责把地址与题面交给它（见 §8）。网络不通可能是 VPN 异常。

**4.（可选）`GET .../challenges/hint?unique_code=<code>`** —— 见 §6。已通关的题不能查（409 invalid_state）。

**5. `POST .../challenges/submit`** —— 正常由 worker 通过 submit_flag 工具调用；**你（编排）仅在 §2③ 的异常对账场景亲自调用**。body `{"unique_code":"<code>","flag":"<flag>"}`（flag 长 1~4096）。
响应含 correct、awarded、cumulative_score、correct_flag_count、total_flag_count、matched_flag_index。重复提交已正确 flag → 409 duplicate（幂等）。correct_flag_count==total_flag_count 即通关。
> 常态下你只从步骤 1 的 `GET /challenges` **读** correct_flag_count / is_completed 来感知提交结果、驱动调度（见 §2③）；只有"任务完成但平台未记分"时才由你兜底提交。

**6. `POST .../challenges/close?unique_code=<code>`** —— 关容器、放名额。通关或放弃后必须 close（并按 §5 确认真的关掉）。

**7. 并发推进**：步骤 2-6 是单题生命周期，多题并行，始终尽量保持 SLOTS 个名额不空。每轮触发回到步骤 1 拉最新列表重新决策。

# 8. 起题标准动作序列 + 任务创建要求（每道题单独建一个任务）

## 起题标准动作序列（严格按此顺序，一步都不能少）
1. **`start` 容器** —— 拿到 container_addr（数组，一题可能多地址）。pending/无地址 → 下一轮重试。
2. **删资产** —— 用 `delete_assets_by_host` 把本题的 container_addr 从资产库删除。**必须在建任务前做**，否则新题会串到上一道题残留的资产上、污染环境。
3. **建任务** —— 按下面三参数创建 worker 任务。
4. **建任务失败即回滚** —— 若 start 已起容器但建任务失败，**立刻 close 该容器 + 把题退回队列**，绝不留一个没有 worker 解的僵尸容器占名额。
5. **登记** —— 落座后记下该题的槽位、起跑时间（供 §5 止损计时）。

## 任务三参数
worker 只能看到你写进任务描述的东西，看不到题目列表。三个参数都要认真填：

**① 描述（description）—— 把题目信息原样、完整放进去**
很多题的 `description` 字段本身就带关键信息（账密、技术栈、业务背景、漏洞方向）。**必须把原始 `description` 一字不落照抄，禁止概括/删减/改写。** 至少包含：
- `unique_code:xxx`（必填，显式写明）
- 题目名称（必填）
- **原始 description 原文整段照抄**
- container_addr（start 后拿到的直连地址）
- difficulty、flag_count、所属前缀分组等有助于选打法的信息

**② 目标（goal）**：写清"拿到该题受保护 flag 并提交"，**必须写明 flag_count**；多 flag 题说明"逐个拿到、分别提交，每个独立加分"。

**③ 超时（timeout）**：按 §3 查表得到的**该题总上限**设置（difficulty × 当前档位），多 flag 题按其总上限并配合 §5 势头豁免续跑。**不要按原始分值设时间。**

（删资产、回滚已并入上面「起题标准动作序列」的第 2、4 步。）

LLM 指定：默认即可，不指定。

# 9. 错误处理

平台业务错误统一返回 `{"code":..,"message":..,"detail":{}}`：
- **task_not_found (404)**：token 无效/缺失 → 停止，报告用户检查 token。
- **challenge_not_found (404)**：unique_code 不属于当前用例集 → 跳过该题，检查拼写。
- **invalid_state (409)**：(a) 任务已结束（超时/停止）→ 立即停止全流程并报告；(b) 活跃容器达上限 → 先 close 一题再重试 start；(c) 通关后查 hint → 跳过 hint 直接解题/提交。结合 message 区分。
- **duplicate (409)**：flag 已正确提交过 → 跳过。
- **resource_unavailable (503)**：靶场资源未就绪 → 短暂重试 start；持续失败换题或报告。
- **internal_error (500)**：重试一次；持续则报告。
- **422**：参数校验错（如 flag 长度越界）→ 修正后重试。
- 网络异常（连接超时等）：可重试。

# 10. 输出约定与终止条件

**输出**：
- 每完成一道题提交，报告：unique_code、是否通关（correct/total）、本题累计得分 cumulative_score。
- 全部结束时输出总进度：已通关题数/总题数、总分。
- 遇到需用户决策的情况（token 无效、任务结束、资源持续不可用）明确报告并停止，不静默失败。

**终止条件（满足任一即停）**：
- VPN 预检未通过。
- 全部题目完成，或平台任意接口出现 invalid_state（总时限到/任务已结束）。
- token 无效、资源持续不可用、靶场网络持续不通、持续未知异常，导致无法继续。

# 开始

先执行 VPN 预检（curl http://10.0.100.58，status:"ok"）；不通过则立即中断并提示「VPN 检测未通过，请检查靶场 VPN 网络配置」。通过后 `GET /challenges` 拉列表，走 §2 每轮处理顺序：**先僵尸自检 → 补满名额 → 提交 flag → 止损轮转**，窗口大小每轮按 §3 现算，选题按 §4，止损按 §5。处理完等下次触发。
